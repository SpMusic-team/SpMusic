## 零、本轮对首轮结论的五处修正

首轮（`c20ff0c`）的方向基本正确，但有五处需要修正。**修正项优先于本轮新增发现**，因为错误的基线会污染后续推导。

| # | 首轮说法 | 第二轮实测 | 性质 |
| --- | --- | --- | --- |
| 1 | `.rsrc` 缩减 **10,844 B** | **不可复现**。正确值为 VirtualSize 差 **10,332 B**、磁盘占用差 **10,240 B**；载荷级构成是 DIALOG −10,094 + VERSION −24 = **10,118 B** | **错误数字** |
| 2 | `.movehcs` 前 16 字节是 **GUID** | 实为 **16 字节全 0x00 保留区**，不是 GUID 也不是长度字段 | **错误描述** |
| 3 | `.text` 有 **300 处**改指 | 实为 **309 处**：`.text` 300 + `.rdata` 8 + `.data` 1 | **少算 9 处** |
| 4 | 汉化路径是「`.movehcs` 旁挂串池」一条 | 实为**双路径**：`.rdata` 原地覆写 **410 处** + `.movehcs` 旁路 **240 条** = 650 条中文串 | **遗漏约 63% 汉化量** |
| 5 | 官方组件「仅汉化，代码未改」 | 方向正确，但需精确化：8 个组件 `.text` 共改 **1,377 B**，且**代码相似度 99.94%–100%** | **结论对，口径需精确** |

### 1.1 「10,844」为何不可复现

穷举了 12 种可测口径，无一等于 10,844：

| 口径 | A′ | B | Δ(B−A′) |
| --- | ---: | ---: | ---: |
| `.rsrc` VirtualSize（= DD[2].Size） | 136,408 | 126,076 | **−10,332** |
| `.rsrc` SizeOfRawData | 136,704 | 126,464 | **−10,240** |
| 全部资源叶子载荷合计 | 130,660 | 120,542 | −10,118 |
| DIALOG 单类载荷 | 39,472 | 29,378 | −10,094 |
| VERSION 单类载荷 | 780 | 756 | −24 |
| 资源目录结构字节 | 5,440 | 5,436 | −4 |
| 文件总大小 | 3,608,064 | 3,604,480 | −3,584 |
| SizeOfImage | `0x37D000` | `0x37C000` | −4,096 |

还做了两项排除：
- **按资源类型载荷差做全子集穷举（含正负号）无解**。有变化的只有 DIALOG 与 VERSION，任何组合都得不到 10,844。
- **不是「掺入了 `.reloc` 变化」**。`.reloc` 段内容逐字节 **0 差异**（段内 SHA-256 相同）；它的 VAddr 前移 12,288 B、RawPtr 前移 10,240 B 是 `.rsrc` 缩小的连锁结果。掺进去只会更远（10,332+12,288=22,620）。

唯一能凑出的算式是 `10,332 + 512`（一个 FileAlignment 单位），但这不成立：若真按 512 对齐，`align512(136,408)=136,704`、`align512(126,076)=126,464`，差仍是 **10,240**，不是 10,844。所以 10,844 是纯算术巧合，**判定为首轮文档错误数字**。

### 2.2 `.text` 的 1,424 B 完全对账

| 组成 | 字节 | 处数 | 性质 |
| --- | ---: | ---: | --- |
| 改指（4 字节操作数 `.rdata` → `.movehcs`） | **898** | 300 | 字符串换址 |
| 残差 · `push imm8` 形式（前一字节 `0x6A`） | **511** | 511 | 字符串长度立即数 |
| 残差 · 其他整型常量 | **15** | 15 | `c7 44 24 08 imm32`（9 处）与 `b8/b9 imm32`（6 处） |
| **合计** | **1,424** | **826** | ✓ 与基线吻合 |

对账验证：898 + 511 + 15 = **1,424**；300 + 511 + 15 = **826**。处数与字节数双双闭合。

残差**全部是 1 字节 run**（最短改写单元）。因为中文串通常比英文串短，**长度立即数必须同步改写**——这说明 B 的改动不是简单资源替换，而是连长度常量都重算了。15 处非 `push` 形态经逐一检查均为 4 字节对齐的整型常量（`[esp+8]` 上的缓冲长度、寄存器直载常量），语义同为长度/尺寸。

300 处改指的段对分布**单一**：`.rdata → .movehcs`，无例外。

样例（立即数变化与对应字符串）：

| 位置 | A′ imm8 | B imm8 | 字符串 A′ → B |
| ---: | ---: | ---: | --- |
| 54050 | 38 | 20 | `There were problems while processing "` → `待处理的问题 "` |
| 54431 | 39 | 25 | `The file was not processed completely.\n` → `文件未完全处理。\n` |
| 53308 | 50 | 38 | ` could not be altered; the file appears corrupted.` → `无法更改; 文件可能已损坏。` |
| 57719 | 31 | 21 | `Calculated gain alteration was ` → `计算增益更改为` |

### 2.3 改指共 309 处（不是 300 处）

全文件扫描「4 字节 VA 落在 `.movehcs`」的位置，共 315 处命中，分三类：

| 分类 | 数量 | 说明 |
| --- | ---: | --- |
| **真实改指** | **309** | A′ 值在 `.rdata`、B 值在 `.movehcs`，且值已改变 |
| 巧合命中 | 6 | A′ 与 B 值完全相同，仅因 `.rsrc` 缩小使 `.movehcs` 覆盖了原 `.reloc` 地址区间 |
| 未知 | 0 | — |

真实改指的段分布：`.text` **300** + `.rdata` **8** + `.data` **1** = **309**。

首轮漏掉的 9 处在 `.rdata` 指针表与 `.data` 全局字符串表入口。其中 `.data:0x2F0734` 这一项（`0x0069860C → 0x0077AFD4`，指向「艺术家」）**只变低 3 字节**，高字节 `0x00→0x00` 未变，所以逐字节比较只看到 3 B —— 这也是它被首轮当成「时间戳/校验字段」的原因。

**6 个巧合命中为什么不是真实引用**：A′ 与 B 值完全相同（`0x77BA32` / `0x77A348` / `0x77ACE8`），只是地址区间重叠造成的假象。

两个非首轮的发现：

**（1）段内是 UTF-8 与 UTF-16LE 混排。** 5 条 UTF-16LE 条目全部是含菜单加速键的文本，因为 Win32 加速键（`&X`）与快捷键文本需要 UTF-16：

| 段内偏移 | RVA | 文本 |
| ---: | --- | --- |
| 4174 | `0x37B04E` | `编辑 DSP(&D)` |

**（2）`.movehcs` 段具 `MEM_WRITE | MEM_EXECUTE` 属性**，且代码/数据标志均为 0。这是非常规组合，说明该段由**第三方工具手工添加**而非编译器产物。本轮未发现任何代码写入该段的证据（段内全为字符串，无指令形态字节），但**未做动态分析，不能完全排除隐藏可执行载荷**。

### 2.5 `.rdata` 还有 410 处原地汉化（首轮完全遗漏）

| 指标 | A′ | B |
| --- | ---: | ---: |
| `.rdata` 差异字节 | — | **33,729**（占 488,960 B 的 6.90%） |
| 差异 run 数 | — | **2,713**（最短 1 B，最长 282 B，平均 12.43 B） |
| `.rdata` 中 UTF-8 可读串 | 13,127 | 12,577 |
| 其中含 CJK | **0** | **411** |
| **同 RVA 上「纯非 CJK → 含 CJK」的原地替换** | — | **410 条** |

样例：

| RVA | A′ | B | A′ 字节 | B 字节 |
| --- | --- | --- | ---: | ---: |
| `0x276E0C` | `Time elapsed: ` | `时间已用: ` | 14 | 14 |
| `0x27C554` | `<not set>` | `<未设置>` | 9 | 11 |
| `0x27D108` | `Artist Name=ARTIST;Track Title=TITLE;…`（253 B） | `艺术家=ARTIST;标题=TITLE;…`（240 B） | 253 | 240 |
| `0x2838F8` | `Manipulates Opus header gain value, to make the sound louder or quieter. Supported only with Opus codec.` | `控制 Opus 标头增益值可以使声音更大或更小。仅支持 Opus 编码格式。` | 104 | 90 |

**机制推断（两条路径并存）**：

1. **原地覆写**（410 处）：在 `.rdata` 原字符串地址直接覆写，**原槽剩余空间足够时**中文串甚至可以比英文串更长，多出的尾部用 `0x00` 补齐到下一个字符串起点。
2. **旁路搬移**（`.movehcs` 240 条）：原槽剩余空间**不够**放下变长的中文串时，搬到新段并改指。300 处改指**全部**是新串更长（平均 +3.71 B），正是"放不下才搬"的直接体现。

**原位判定条件不是「新串 ≤ 旧串」，而是「新串 ≤ 原槽可用字节数」**。两个原位反例证明这一点：

| RVA | 旧串（字节） | 新串（字节） | Δ |
| --- | --- | --- | ---: |
| `0x27C554` | `<not set>`（9） | `<未设置>`（11） | **+2** |
| `0x282E44` | `Apply gain thread count (0 = use all available)`（47） | `应用增益线程数（0= 使用所有可用）`（48） | **+1** |

这说明 `.rdata` 里相邻字符串之间普遍留有对齐填充，原位可用空间大于旧串长度。**这也解释了为什么必须新增 `.movehcs`**——`.rdata` 的对齐余量是有限的，长句翻译仍然放不下，只能旁挂新段。

### 3.4 一个必须避免的推论错误

「8 个组件全部被改」**不等于**「foobaka 修改了 foobar2000 的逻辑」。三个反证：

1. 代码相似度 99.94%–100%，字节直方图 L1 散度 0.003%–0.045%（真改了 92% 的代码不可能字节分布几乎相同）。
2. 全部差异可归因到字符串地址与长度常量两类。
3. `_RDATA` 与 `.reloc` 段内容 **0 字节差异**。

反过来，「代码未改」也不等于「二进制未改」——首轮用「`.text` VSize 完全一致」作为主证据，那个证据其实很弱（VSize 相同只说明长度相同，不说明内容相同）。本轮改用**逐字节 + 滚动哈希 + 直方图三重校验**，才真正把这条结论坐实。

### 4.4 对首轮「三条主题路线」结论的修正

**修正后的结论**：`.fth` 是可组合的多记录容器，能同时承载配色、布局、字体与格式化串。首轮「配色与布局可彻底分离」的观察**依然成立**（因为 19 个官方主题确实只含配色记录），但「`.fth` 只能是纯配色」的说法不成立。

### 4.5 `theme.fth` 有两份，只有一份生效

| 路径 | 大小 | 记录数 | 说明 |
| --- | ---: | ---: | --- |
| 根目录 `theme.fth` | 1,398 B | 5 | 完整配置（含 6 字体 / 完整布局） |
| `profile\theme.fth` | 546 B | 5 | **实际加载的一份**；字体表为空（len=0），布局仅 2 个面板，TOOLBAR 仅 4 B |

**逐项对齐验证（4 项全部吻合）**：

**根因判定**：

**这是对象被释放后继续使用的 Use-After-Free**：`param3` 对象 `+0x44` 处持有的槽位对象已被销毁（其 vtable 指针被改写为 `0x43570000`），随后的虚表调用 `call [edx+8]` 读到非法地址。

关键佐证是**同一函数内有两处完全相同的模式**（`+0x44` 与 `+0x54`），说明这不是偶发，而是该对象生命周期管理的系统性问题。而函数的入口保护只检查了 `esi`/`edi` 两个字符串指针非空，**没有检查 `param3` 对象本身或其槽位对象是否仍然有效**。

**与主题脚本的关系**：`call [edx+8]` 的语义（压入长度、压入字符串、调用）是典型的「向宿主通知字符串」接口。结合崩溃栈里的 `SendDlgItemMessageW`/`SendMessageW`（首轮记录），**推断**是脚本回调期间面板重建（`on_size` → `refresh_bt` 一类路径）释放了槽位对象，而回调仍在继续使用它。

> **注意**：这条属**强推断而非实测**。崩溃报表能证明「读 `0x43570008` 失败」与「`edx` 已被破坏」，但不能单独证明「是谁释放的」。要彻底确证需动态调试，本轮未做。

## 七、官方 2.24.6 → 2.26.3 的版本演进（能力归属基线）

### 7.1 三个跃迁的性质完全不同

| 2.26.2 → 2.26.3 | **74.49%（最高）** | +28,128 B | **纯重布局补丁** |

> **一个必须写明的陷阱**：按「差异字节数」比较，2.26.2→2.26.3 的绝对差异高达 2,698,740 B（92.35%），看起来改动最大。**但这个数字没有意义**——整映像重定位必然导致绝对对齐差异极高。三个反证：字节直方图 L1 散度仅 1.83%（真改 92% 代码不可能字节分布几乎不变）、16 字节滚动哈希匹配率 74.49%、跨段改指仅 1.0%。正确解读是「同一套代码被整体搬家，少量代码被微调」。

> 这个陷阱同样适用于判断 foobaka：**只看「差异字节数」会严重高估改版深度**。本轮对组件改用三重校验正是为此。

> **勘误（2026-11-17）**：本节初版按 **16 字节**步长解读，把下一项起始 dword 误当本项的 `+0x0C` 字段，据此推出的「等价关键字」列**全部作废**。
> 实测 `0x27BE18 - 0x27BE0C = 12 字节`，正确步长是 **12**。详见 [第三轮 findings](foobar2000-foobaka-phase-3-findings.md) §三，以及修正后的 [search-mechanisms](foobar2000-search-mechanisms.md) §一。

A′ 2.24.6 的 `.rdata` `0x27BD3C` 起是一条定长表，每项 **12 字节**，第一个 dword 是关键字串 VA。按 12 字节重列共 **22 项**（`SORT` `ORDER` `OR` `AND` `NOT` `HAS` `IS` `IST` `EQUAL` `GREATER` `LESS` `MISSING` `PRESENT` `BEFORE` `AFTER` `SINCE` `DURING` `ALL` `NONE` `%first_played%` `%last_played%` `%added_timestamp%`）。

### 7.8 对「LargeFieldsConfig 写了但无效」的加强证据

首轮结论是「foobaka 的 `LargeFieldsConfig.txt` 被写了但内核不读，因为该机制 2.26 才有」。本轮补一条更硬的证据：**`LargeFieldsConfig` 这个标识符在 A′ 2.24.6 与 B 的内核里根本不存在**（全样本扫描 0 命中），只在 2.26.2/2.26.3/x64-2.26.3 中出现。

这比「文档说 2.26 才引入」更直接：**二进制里没有这个词，就不可能读这个文件。**

## 八、对 SpMusic 的可迁移原则

以下不是产品方案，是从实测中提炼的、可独立验证的判据。

### 8.1 判断「改了什么」必须先建同版本基线

首轮三次误判都源于缺基线（把版本特征当成改版特征）。本轮的强化做法：

1. **特征三方对照**：既有样本（B）、同版官方的**同架构**基线（A′）、版本演进序列（2.25/2.26）。缺任何一方，差异都可能是版本差异而非改版差异。
2. **差异必须可归因到具体机制**。本轮 1,424 B（exe）+ 1,377 B（组件）+ 33,729 B（`.rdata`）全部给出了类目分解，没有留下「大概是某处改了」的黑箱。
3. **不要把「长度相同」当成「内容相同」**。首轮用 `.text` VSize 一致作为主证据，这个证据很弱；本轮用逐字节差分才坐实。

### 8.2 字节差异数不能直接当改动量

这是本轮最重要的方法论产出，且有量化反证。对 SpMusic 的直接含义：

- 任何「某次构建比另一次大/差异多」的说法，必须同时给**滚动哈希匹配率**与**字节直方图散度**，否则无法区分「代码被重写」与「代码被搬家」。
- 本轮实测：`foo_ui_std.dll` 差异 523 B → 覆盖 99.94%；官方 2.26.2→2.26.3 差异 92.35% → 覆盖 74.49%。两个数量级的差异，靠单一指标无法分辨。

### 8.3 生命周期变更必须显式传播（U8 的教训）

WSH 面板的崩溃是「对象被销毁后虚表调用」。同类问题在研究文档的 DSP 缓冲生命周期、设备切换重建里反复出现。可迁移的检查项：

| 检查项 | 为什么 |
| --- | --- |
| 所有 `call [obj+N]` 之前是否有有效性校验 | WSH 的入口只校验了字符串参数，没校验对象 |
| 同一对象的多处槽位是否共用同一释放路径 | U8 里 `+0x44` 与 `+0x54` 两处模式完全相同 |
| 销毁后是否有「失效通知」到达持有方 | 主题 JS 的按钮图缺陷（首轮已记录）是同一类 |

### 8.4 静默捕获会把缺陷放大成「无提示消失」

首轮记录过 `catch (e) {}` 吞掉绘制异常导致按钮静默消失。本轮从宿主侧看到对称的问题：**错误分支只弹一个 `O.o，脚本有错误哦！:(`，真实原因只写控制台**，用户无从判断是 COM 缺失、脚本语法错误还是资源问题。

可迁移原则：错误提示必须区分**可归因的失败阶段**，而不是统一文案。这与首轮 P0-C 的「解码失败分级」是同一原则在两个层面的体现。

### 8.5 「配置文件存在」不等于「配置被加载」

`theme.fth` 有两份，根目录那份 1,398 B 完整配置**未被使用**，实际加载的是 `profile\theme.fth` 的 546 B 版本。同类现象还包括：`LargeFieldsConfig.txt` 存在但内核不读、`version.txt` 存在但内容是陈旧的。

可迁移原则：**任何读配置的结论都必须先证明「这份文件在加载路径上」**。验证方式包括：文件位置是否在 profile 目录、该机制在二进制里是否存在对应标识符、运行期日志是否记录了加载。

### 8.6 主题系统可先做独立的配色层

`.fth` 的实测支持首轮这条建议，且给出了更强的依据：

- 官方 32 个主题里 **19 个只含配色记录**（140–160 B），完全不含布局。
- 配色记录（`598CEE8C`）结构与布局记录（`16691D51`）**完全独立**，是两个 GUID 各自的自包含正文。

所以「配色与布局可彻底分离」是被格式设计本身支持的，不是推测。SpMusic 若引入主题系统，**先做轻量配色层、暂不碰布局**是可验证的渐进路径。

### 8.7 字符串池的两种路径对应两种工程选择

foobaka 用了两条并存路径：短中文串原地覆写、长中文串搬到新段改指。这个选择的根因是「原段空间紧凑，无法原地变长」。

可迁移原则：**本地化/主题化如果需要替换长度可变的内容，必须提前决定「原地」还是「旁挂」**。旁挂的代价是新增 309 处指针改写 + 526 处长度常量同步——这正是 foobaka 在 `.text` 里 0.055% 的全部改动。

### 10.2 方法性局限

1. **无反汇编工具可用**。Ghidra 对 1.18 MB x86 DLL 自动分析超时，rizin/objdump 未安装。除 U8/U11 两处定点反汇编（capstone）外，其余全部为**原始字节 + 启发式模式**判定。
2. **`.text`/`.rdata` 差异属模式推断，非指令级确证**。「526 B 全为 push imm8」基于前一字节为 `0x6A` 的启发式，未做指令边界解码。
3. **未做动态验证**。所有「机制」结论都是静态推导，没有运行期观测。
4. **滚动哈希匹配率是下界**。16 字节窗口会漏掉「每 16 字节内至少 1 字节变化」的区域，真实复用率更高。
5. **短串天然不可靠**。`CUI`/`DUI`/`SSRC` 这类 3–4 字符串误报率高，已逐一剔除，但仍可能有未发现的巧合命中。
6. **组件无 `VS_VERSIONINFO` 的 FileVersion**，44 个样本×组件组合全部未解析，只能靠 SHA/大小/字符串归属。
