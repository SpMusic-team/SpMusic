# 第四轮：PCM 接缝闭环、foobaka 数据层与第三轮勘误

本轮用**自建的 WASAPI 环回录制器**打通了第三轮判定为「不可完成」的 A1，
并对 B（foobaka）做了不依赖界面的**数据层对照**。

## 零、最重要的三个结论

1. **A1 闭合，且「不可能」的判定是错的**：WASAPI 环回捕获不依赖环回端点设备，
   自建录制器即可。foobar2000 的 **CUE 分轨接缝逐样本零误差**。
2. **B 用的是 `playlists-v1.4`，不是 `v2.0`**：这是版本性结构差异，
   解释了第三轮「B 有 props 记录却找不到对应 sqlite」的困惑。
3. **`52655132-…` 不是 autoplaylist client GUID**，
   而是 v1.4 `index.dat` 属性表里的**属性类型 GUID**。第三轮的一次阴性实验要重写。

## 一、A1：PCM 接缝（本轮闭合）

### 1.1 推翻第三轮的判定

| 第三轮结论 | 本轮实测 |
| --- | --- |
| 「系统无环回捕获端点 → A1 不可完成」 | **不成立**：`AUDCLNT_STREAMFLAGS_LOOPBACK` 是系统混音器能力，与设备无关 |
| 「需要换带 `--enable-wasapi` 的 ffmpeg」 | **不需要**：.NET COM 互操作直接调 WASAPI |
| 「需要启用立体声混音」 | **不需要** |

第三轮的三条**事实观察**全部属实（确无环回设备、ffmpeg 确无 wasapi、dshow 只列麦克风），
**错的是推论**——把「ffmpeg 走不通」当成了「本机做不到」。

### 1.2 判定「接缝无缝」的依据

| 用例 | 最大误差 | 失配帧 | 解释 |
| --- | ---: | ---: | --- |
| CUE 两分轨 | **0** | **0 / 480000** | 逐样本完全一致 |
| 双文件 A→B | 246 | 6 / 480000 | 单帧量化抖动，非断层 |

**能量证据**：接缝窗口 RMS 从 2992.9 → **2853.5** → 2872.7，**无塌陷、无延迟、无衰减包络**。
**零帧比例 0.25%（1 帧）**，且该帧是波形过零点。

### 1.3 证据边界（必须写清）

| 能断言 | 不能断言 |
| --- | --- |
| PCM 到达系统混音器时无丢样/重样/插静音 | **DAC 端的实际输出** |
| CUE 分轨在应用侧是连续的 | **是否 bit-perfect**：共享混音器有独立增益（α≈0.127）与 32f→16i 转换 |
| 双文件续播无静音插入 | 独占模式下更优（未测） |

## 二、B（foobaka）数据层

### 2.1 结构差异本质是「代际」而非「配置」

| 维度 | A′ 2.24.6 | B 1.7.12 |
| --- | --- | --- |
| 播放列表 | `playlists-v2.0` / `index.txt` / `.fplite` / `-props.sqlite` | `playlists-v1.4` / `index.dat` / `.fpl` |
| 属性存储 | 独立 sqlite | **内联在 index.dat** |
| 曲库目录 | `library-v2.0\folders`（相对路径） | `library\folders`（**绝对路径**） |

**为什么两者同为 2.24.6 内核却有此差异**：B 是从 **foobaka 1.6.10** 一路升级来的**已有 profile**，
沿用了旧代目录；A′ 是本轮**新建**的 profile，直接生成 v2.0。
**目录格式是 profile 代际的产物，不是内核版本的能力差异。**

> 这对对照实验是**重大方法学提醒**：
> 拿 A′ 与 B 做「格式」对照时，差异可能来自 profile 代际而非产品设计。
> **必须显式区分**「内核行为」「profile 代际」「组件配置」三者。

### 2.2 `52655132-…` 的正确定位

B 的 `index.dat`（103 B）中，该 GUID 出现在**属性表**里，前置 `u32=16` 长度：

```
[0x2B] u32 = 16                      ← 属性值长度
[0x2F] 16B = 32516552578f564c9aee17525c679a5d
           → 52655132-8F57-4C56-9AEE-17525C679A5D   ← 属性类型 GUID
```

**不是** autoplaylist 的 client GUID，**不是** v2.0 `props` 表的 key。

> **第三轮勘误**：第三轮从 B 读到该记录后，把它当作 autoplaylist 定义的一部分，
> 往 A′ 的 v2.0 `props` 表注入并观察「列表仍可编辑」。
> 现在知道**两者不在同一层**——那次阴性实验的结论「16 B 不构成完整定义」**碰巧成立**，
> 但**推理路径是错的**，不能作为「16 B blob 语义」的证据。

### 2.3 播放统计走索引表，不走主表列

B 有 1,829 条曲目、装了 `foo_playcount`，但主表五个统计列**全空**；
唯一有数据的索引表是 `C653739F`（1,829 行）。

**结论**：foobar2000 的播放统计在 **`metadb_index_<GUID>` + `_data` 独立索引表**里，
主表的 `playCount`/`rating`/`lastPlayed`/`dateAdded`/`firstPlayed` 是**结构预留、实际未启用**。

**对 SpMusic 的含义**：仿统计模型应仿「独立索引表 + 64 bit 哈希键 + filename 主键」，
**不是**「主表加五列」。且 filename 主键带**子轨前缀**（`0+`/`1+`/`2+`），
天然区分 CUE 分轨——这正是 SpMusic 统计键设计需要吸收的一点。

## 三、IS 多值语义（部分闭合：排除法）

### 3.1 存储层的关键事实

多值字段在 `metadb.info` 中是**单个分号拼接串**（44 行抽样中 ARTIST 出现 >1 次者为 0）。
这解释了为什么「逐值匹配」的直觉不成立——**存储层根本没有「值」这个概念，只有一串字符**。

### 3.2 排除了什么

穷举 50 个候选实现（整串 / 首段 / 末段 / 任段 / 子串 × 大小写两模式，以及各类 OR 组合）：

| 结论 | 强度 |
| --- | --- |
| 「任一段匹配」不成立 | **强**（会给出 14 vs 实测 11） |
| 「首段匹配」不成立 | **强**（`Guest` 会命中 05，实测 0） |
| 「末段匹配」不成立 | **强**（`Bystander` 会命中 04，实测 0） |
| 「子串包含」不成立 | **强**（`SpmQ` 会命中 15 条，实测 1） |
| 「整串相等 + 大小写不敏感」是**最优但非完美** | 7/8，仅 `spmq3` 差 1 |

### 3.3 仍然未知

**为什么 `ARTIST IS spmq3` = 12 而 `ARTIST IS SpmQ3` = 11？**

数据里只有一个全小写的 `spmq3`（第 11 首），按整串相等 + 不分大小写两查询都应是 11。
差的这一条来源未定。剩余假设是「第二个比较通道参与并集」，但**未实测验证**。

> **诚实标注**：这一节的价值在于**排除**，不在于**确立**。
> 把「不是逐值」升级为「不是任何简单分段/整串实现」，
> 候选空间从 4 种缩到「需要额外通道」这一种。

## 五、对 SpMusic 的直接含义

1. **gapless 验收可以做成硬判据**：用「预转采样率 → 环回捕获 → 逐帧对齐 → 归零失配数」
   这套流程，SpMusic 的续播实现也能被同样客观地验证。**失配帧数 = 0 是可达到的**。
2. **统计模型应仿独立索引表**，而不是主表加列；主键建议「子轨索引 + 完整路径」。
3. **对照实验必须显式声明 profile 代际**，否则会把存储格式差异误读为产品能力差异。
4. **「工具不可用」要先区分「工具不提供」与「本机不具备」**——
   第三轮 A1 停摆一整轮的代价，就是没有考虑自己写一个录制器。
