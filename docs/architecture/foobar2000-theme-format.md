# foobar2000 主题容器（.fth）格式

> 本文从 library-mechanisms 拆出，覆盖 .fth 的跨版本稳定性与 LAYOUT 内层结构。
## 一、`.fth` 主题格式的跨版本稳定性（第 16 轮新增）

### 1.1 格式零变化

对比四个版本的 32 个官方 `.fth` 主题：

| 版本 | .fth 数量 | 与 2.24.6 逐字节相同 |
| --- | ---: | ---: |
| 2.24.6 | 32 | （基准） |
| 2.25.11 | 32 | **32 / 32** |
| 2.26.2 | 32 | **32 / 32** |
| 2.26.3 | 32 | **32 / 32** |

**`.fth` 容器格式在 2.24.6 → 2.26.3 期间完全没有变化。**

这与同时期查询引擎（12→16 字节步长）和 metadb（新增 `partial` 列）的内部重构形成对比——
**foobar 在 2.26 大改内部结构时，主题容器保持稳定**。

### 1.2 容器结构（验证版）

```
[0x00] 16 B   魔数 ADA0BA98-36D4-4A16-8E14-415F73B4CB21
[0x10] u32    记录数 N
        N × 记录：GUID 类型(16) + u32 正文长度 + GUID 身份(16) + byte[长度] 正文
```

**验证**：32 个文件全部解析后**精确 EOF**，无剩余字节。

### 1.3 内容分布：配色与布局完全分离

> **这一节的样本量是充分的**：32 个官方 `.fth` × 4 个版本 = 128 份文件全量解析。
> 与 `.fcl`（只有 1 个独立样本）形成对比。

| 记录类型 | GUID | 出现次数 |
| --- | --- | ---: |
| **COLORS** | `598CEE8C-8A8D-488D-AA95-CA5BDA02622D` | **19** |
| **LAYOUT** | `16691D51-440B-4E55-A459-F1AFA3EBF343` | **13** |
| PLAYBACK_FORMAT | `3670C62D-2CC8-4762-97A0-2440ABE8518D` | 0 |
| TOOLBAR | `4F958346-B4D5-484C-AACA-2EB6FE004A49` | 0 |
| FONTS | `779E8557-2F11-4099-A04D-527D1B61742A` | 0 |

**每个官方主题恰好只有 1 条记录**——19 个纯配色主题 + 13 个纯布局主题，
**没有一个混合**。这是第 2 轮结论的独立验证（不同方法、全量样本）。

> **为什么这个分离重要**：它让「换配色不动布局」「换布局不动配色」成为可能。
> 用户改配色时不会意外破坏布局。

### 1.4 对 SpMusic 的含义

SpMusic 当前的 `appearance` 模型（颜色 / 字体 / 圆角 / 动效分开）**方向与之一致**。

若未来支持布局预设，建议保持同样的分离：

| 预设类型 | 内容 | 可独立替换 |
| --- | --- | :---: |
| 配色预设 | 颜色 token | ✓ |
| 布局预设 | 面板排布 | ✓ |

**不要做一个混合的「主题包」**——foobar 用 32 个官方样本证明了分离设计可行且被官方采纳。

### 1.5 第三方主题验证：**格式支持多记录混合**（第 33 轮）

用前两轮解出的解析方法，对 **foobaka Mixture 的 37 个 `.fth` 主题**做了全量验证：

**结果：37 / 37 精确 EOF**——解析方法完全可复用于第三方主题。

### 修正一处旧表述

第 16 轮说「每个官方主题恰好只有 1 条记录」。这是**观察事实**，
但当时没说明：**这只是官方约定，不是格式限制**。

**反例**：foobaka 的 `theme.fth` 有 **5 条记录**：

| # | 类型 | 正文 |
| ---: | --- | ---: |
| 0 | PLAYBACK_FORMAT | 98 B |
| 1 | TOOLBAR | 368 B |
| 2 | LAYOUT | 356 B |
| 3 | FONTS | 292 B |
| 4 | COLORS | 84 B |

`profile/theme.fth` 同样是 5 条（TOOLBAR 正文为 0 B）。

### 官方从未使用的三种记录类型

| 类型 | 官方 32 个中 | foobaka 中 |
| --- | ---: | :---: |
| COLORS | 19 | ✓ |
| LAYOUT | 13 | ✓ |
| **PLAYBACK_FORMAT** | **0** | ✓ |
| **TOOLBAR** | **0** | ✓ |
| **FONTS** | **0** | ✓ |

> **这个发现的价值**：`.fth` 容器能承载 5 类内容，官方只发布了其中 2 类的单类型样本。
> 若 SpMusic 参考此设计，应把容器设计成**支持任意记录组合**，
> 而不是假设「一个主题文件只装一种东西」。

### 37 个主题的分类分布

| 类型 | 数量 | 典型大小 |
| --- | ---: | --- |
| COLORS | **21** | 140–160 B |
| LAYOUT | **14** | 260–4,928 B |
| 混合（5 条） | 2 | 546 / 1,398 B |

配色主题普遍很小（140 B），布局主题大小差异大（260 B 到 4.9 KB）。

## 二、`.fth` 的 LAYOUT 正文结构（第 18 轮新增）

第 16 轮确认了 `.fth` 容器的记录格式，但 LAYOUT 记录的**正文**只写了「未解」。本轮解开了层级。

### 2.1 双层结构

```
.fth 容器
  [0x00] 16 B  魔数 ADA0BA98-...
  [0x10] u32   记录数 N（官方主题恒为 1）
         记录：GUID 类型 + u32 正文长 + GUID 身份 + byte[正文]

  LAYOUT 类型记录（GUID 16691D51-...）的正文：
    u32 count(=1) + GUID(6872CAFD-F704-4A1F-9223-B1249C4EE2F5) + u32 len + 内层正文
```

**所有 13 个官方布局主题的内层 GUID 都是 `6872CAFD-…`** ——
说明它们是同一类布局对象，只是内容不同。

### 2.2 内层正文里直接存面板名

内层是二进制几何数据，但**面板身份以 ASCII 字符串直接存放**：

| 面板名 | 出现次数 |
| --- | ---: |
| `by artist/album` | 5 |
| `Album List` | 2 |
| `Selection Properties` | 2 |
| `Spectrogram` | 2 |
| `Spectrum` | 2 |
| `VU meter` | 2 |
| `Oscilloscope` | 1 |
| `Properties` / `Playlists` / `Visualisation (1)` / `Visualisation (2)` | 各 1 |
| `Main` | 1 |

还出现了 titleformat 表达式：`[%replaygain_track_gain%]`（在 `Visualisation + Cover Art + Tabs` 里）。

### 2.3 尺寸范围

13 个布局主题的内层正文：**180 B ~ 626 B**。

最小的 `Group by Albums.fth`（180 B）没有任何可读面板名，
最大的 `Album List + Properties (tabbed) + Visualisations.fth`（626 B）
含 4 个面板名（Album List / Selection Properties / Spectrogram / Spectrum / VU meter）。

### 2.4 仍然未解的部分

| 项 | 状态 |
| --- | --- |
| 层级结构（容器 → LAYOUT → 内层） | **已解** |
| 面板名字符串 | **已解** |
| 内层的**几何字段**（尺寸/位置/分隔条比例） | **未逐字段解出** |
| 面板之间的父子关系编码 | **未解** |

> **诚实标注**：结构与面板名可读，但**几何语义未逐字段确认**。
> 继续需要对照修改前后两个 `.fth` 做差分，或反汇编 `foo_ui_std.dll` 的序列化代码。

> **对 SpMusic 的一点参考**：foobar 的布局记录里**用字符串而非 GUID 标识面板**，
> 这对可读性有一定考虑（出问题时能看出是哪个面板）。
> 但内层仍是紧凑二进制，说明作者在体积与可读性之间选了折中。

### 2.5 内层结构：**不存在统一布局**（第 25 轮修正）

> **⚠ 重要修正**：第 19 轮曾声称内层有统一的「`+0x30`/`+0x34`/`+0x38`/`+0x3C` 四字段」头部。
> **那是错的**——只对比了 2 个高度相似的样本就下了通用结论。
> 本轮扩展到全部 13 个主题后，立即暴露不一致。

**证据（三个不同类型的主题，`+0x30` 处内容完全不同）**：

| 主题 | `+0x30` 起 | 之后是什么 |
| --- | --- | --- |
| `Album List + Properties` | `17 00 00 00 / 2c 01 00 00 / 5c 0b 00 00 / 01 00 00 00` | `0f 00 00 00`(=15) + `"by artist/album"` |
| `Slim View + Tabs` | `bd 01 00 00 / c8 00 00 00 / c5 0a 00 00 / 05 00 00 00` | `04 00 00 00` + GUID + `04 00 00 00` + `"Main"` |
| `Default Playlist` | `15 00 00 00 / 60 00 00 00 / 00 00 00 00 / 29 a3 13 49` | GUID 的后半段，**不是数值字段** |

**为什么之前会错**：`Album List + Properties` 与它的 `(tabbed)` 变体恰好在此处对齐，
于是误以为该布局是全局的。**扩展样本后立刻暴露**。

**方法学教训**：差分法有效，但**样本选择决定了结论的适用范围**。
只对比 2 个相似样本得到的结构，必须再用**其他类型**的样本验证才能上升为通用结论。

### 2.6 仍然成立的部分

以下三层结构在**全部 13 个文件**上都验证通过，不受上述修正影响：

| 层 | 结构 |
| --- | --- |
| 容器 | 魔数(16) + u32 记录数 + 记录序列 |
| 记录 | GUID 类型(16) + u32 正文长 + GUID 身份(16) + 正文 |
| LAYOUT 正文 | u32 count + GUID + u32 len + 内层正文 |
| 内层 | 含 ASCII 面板名（带 u32 长度前缀），**但字段布局因主题而异** |

**仍然未知**：

| 项 | 状态 |
| --- | --- |
| 内层各字段的确切布局 | **因主题而异，未解** |
| 几何参数（尺寸/位置）在哪、如何编码 | **未解** |


第 18 轮只解到「内层是二进制几何数据 + 面板名」。本轮通过**差分两个相近的官方布局**把字段边界确定下来了。

**差分方法**：`Album List + Properties.fth`（395 B, 1 个面板）
vs `Album List + Properties (tabbed).fth`（425 B, 2 个面板）——两者只差一个 Tab。

**内层结构**：

```
+0x00 ~ 0x0F  16 B  GUID  布局类标识（所有官方主题相同：866E6C6A-…）
+0x10 ~ 0x2F  32 B  两个 GUID（各主题不同，疑似实例 id / 变体 id）
+0x30          u32  几何参数 1（A=23,   B=173 ）
+0x34          u32  几何参数 2（A=300,  B=180 ）
+0x38          u32  几何参数 3（A=2908, B=3021）
+0x3C          u32  面板数量（A=1,    B=2   ）★
+0x40          u32  填充/标志
+0x44+         面板条目序列
```

**面板条目**：

```
GUID(16) + u32 名称长度 + UTF-8 名称 + 附加字段
```

**验证**：字符串前的 u32 长度前缀**精确匹配**——
`Album List` 前置 10、`by artist/album` 前置 15。

**`+0x3C` 是面板数量的验证**：

| 主题 | `+0x3C` | 文件内匹配名称数 | 一致 |
| --- | ---: | ---: | :---: |
| `Album List + Properties (tabbed)` | 2 | 2 | ✓ |
| `Album List + Properties` | 1 | 1 | ✓ |
| `Slim View + Tabs` | 5 | 4 | 近似 |
| `Album art in playlist` | 异常值 | 0 | 该主题结构不同 |

**仍然未解**：

| 项 | 状态 |
| --- | --- |
| `+0x30`/`+0x34`/`+0x38` 三个几何参数的**确切语义** | 推断为宽度/高度/其他，未证实 |
| 面板条目内部 GUID 之后的 u32 序列 | 未解 |
| 面板**父子关系**如何编码 | 未解 |

> **方法学价值**：这次用的是**差分法**——找两个只差一个变量的官方样本对比。
> 不必反汇编序列化代码就能定出字段边界，成本低得多。
