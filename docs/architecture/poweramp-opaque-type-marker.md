# 插件系统（三十八）：type 是不透明标记

## 0. 一句话结论

第二十三篇给出过 type 的位域解读（bit0/bit1/bit2/bit3/bit4）。
本轮做**证伪检查**，结论是：

> **位域解读只是"值→场景"的归纳，Java 侧从未按位使用它。**
> `type` 是一个**不透明标记**——由调用方按场景选值，入库后仅用于分类展示。

---

## 1. 决定性证据一：`А()` 内 flag 不做位运算

`B.А(int flag, String uri)`（`:1152-1203`）是容器入库方法，`flag` 的全部使用：

| 行 | 操作 |
| ---: | --- |
| `:1181` | `int-to-long v1, p1` |
| `:1183` | `bindLong(2, v1)` → 写入 `type` 列 |

> **只有一次类型转换 + 一次绑定，没有任何 `and`/`shl`/`shr`。**

### 1.1 完整的 p1 使用轨迹

```smali
.method public final А(int flag, String uri) long
    // 查询是否已存在
    В.bindString(1, uri);
    ...
    // 不存在 → 插入
    B.bindString(1, uri);
    B.bindLong(2, (long) flag);      // ★ 唯一使用
    return B.executeInsert();
}
```

---

## 2. 决定性证据二：`type` 列全库无位运算

检索模式：`containers.type` 或 `container.*type` 同行出现 `and-int`/`and-long`/`shr`/`ushr`/`shl`。

| 结果 | 数量 |
| --- | ---: |
| 命中 | **0** |

> **`type` 从未被按位消费**。它只被：
> 1. `GROUP BY type`（第十六篇，分类统计）
> 2. 作为容器记录的标识字段返回给 UI

---

## 3. 那 6 个值的真实关系

| type | 触发场景 | 二进制 |
| ---: | --- | --- |
| `0x1` | `builtin:` | `0001` |
| `0x5` | `compiled:` | `0101` |
| `0x8` | `apk://` 自己包 | `1000` |
| `0xa` | `apk://` 外部包 | `1010` |
| `0xf` | zip 子容器 | `1111` |
| `0x14` | `dir:` | `10100` |

### 3.1 位模式的巧合 vs 意图

| 观察 | 判断 |
| --- | --- |
| `0xa = 0x8 + 0x2` | 值关系成立 |
| `0xf = 0x8 + 0x4 + 0x2 + 0x1` | 值关系成立 |
| `0x14 = 0x10 + 0x4` | 值关系成立 |
| **但代码从不按位组合/拆分** | **→ 位关系是"值选择的巧合"而非"协议"** |

> **重要**：值之间的算术关系**不代表设计意图**。
> 若作者真想表达位标志，至少会有一处 `flags & MASK` 的检查——实测 **0 处**。

### 3.2 更可能的真相

| 假说 | 支持证据 |
| --- | --- |
| 这 6 个值是**按历史顺序随意选的**（1, 5, 8, 10, 15, 20） | 无位运算消费 |
| 十进制看：1, 5, 8, 10, 15, 20 —— 像**间隔编号** | 更自然 |
| 十六进制的"规律"是**观察者的模式投射** | — |

> 我倾向第二种：**这可能是十进制编号而非位标志**。
> `0x14` = 20 在十进制序列 `1,5,8,10,15,20` 里位置合理。

## 4. 对前几篇的订正

| 篇 | 原表述 | 订正 |
| ---: | --- | --- |
| 二十三 | "位域解读"（bit0/1/2/3/4 各有含义） | ⚠️ **过度解读**。值关系成立但无代码依据 |
| 二十三 | "bit3 是 APK 类"、"bit2 是需展开" | ⚠️ 同样属归纳，非实证 |
| 二十五 | "type 扩到 6 种" | ✅ 仍成立（值确实有 6 个） |

> **本轮的教训**：看到数值间的算术关系就推"位域设计"，是**模式投射偏差**。
> 判定位域必须有**消费端证据**（`& mask` 检查）。

---

## 5. 可借鉴 / 不建议照抄

### 5.1 值得借鉴

| # | 做法 | 理由 |
| --- | --- | --- |
| A1 | **type 由调用方赋予、只用于分类** | 简单，无需中央枚举 |
| A2 | **`GROUP BY type` 做统计** | 单列即可支撑分类 UI |

### 5.2 不建议照抄

| # | 问题 | 后果 |
| --- | --- | --- |
| N1 | **type 无常量定义** | 6 个魔法数散在调用点 |
| N2 | 值语义靠约定 | 新增来源需人工避让已有值 |
| N3 | 值集看似位域实则非位域 | **误导逆向者**（本文即例） |
