# 快速拖动切歌导致转场中断、白屏或旧封面抽搐

## 问题描述

拖动播放器卡片切换歌曲时，正常、少量切换可以完成预期动效，但连续、快速或频繁反向拖动曾触发多种异常。问题在修复过程中先后表现为真实封面未及时进入转场、动效被中断后从头重播、卡片停留在拖动态、界面白屏，以及白屏消除后旧封面短暂回到中心造成的抽搐。

这些症状属于同一交互链路中的不同缺陷，但不能全部归因于单一原因：

- **像素就绪问题**：真实封面读取、解码或换入未完成，目标卡片无法及时参与拖动预览。
- **白屏问题**：高频或大量切歌期间，渲染资源及图层生命周期管理异常，画面消失但歌曲仍继续播放。
- **最终抽搐问题**：封面像素已经就绪，但旧转场会话尚未完全退休，共享动画进度被新手势重置后使旧卡片短暂重放。

本文重点记录最终已验收的拖动切歌动效中断与抽搐修复，同时保留此前失败方案和关联症状的演进，避免后续把资源供应问题与转场会话所有权问题混淆。

## 复现与症状演进

1. 以正常速度多次向下一首拖动，再连续向上一首拖动直至最初歌曲时，原本正常的切换动效会突然中断，并自动从头播放一次，形成明显卡顿。仅连续向下一首拖动十几次也可能触发；拖动越快，出现概率越高。
2. 初步修复降低了发生频率，但在多次切到下一首后首次返回上一首时，上一首卡片可能未加载出真实封面预览；松手后动效又从头播放。
3. 随后的规避处理曾使问题加重：卡片未就绪时，当前卡片会持续保持被拖动的姿态，即使鼠标已经松开。
4. 取消未就绪动画后，“松手后永久停在拖动态”消失，但只是把问题推迟到下一次封面已经就绪的手势，并未达到“无论如何拖动都使用真实封面”的要求。
5. 高频快速切歌或以中等速度切换大量歌曲时，曾出现整个播放器白屏但歌曲仍正常播放。该问题修复后，继续以极高频率拖动，仍可概率性看到旧封面短暂回到中心的抽搐。

## 最终视频逐帧证据

`抽搐现象.mp4` 为 `30 fps`，共 `370` 帧。按原始帧率逐帧检查得到以下关键序列：

| 帧 | 时间 | 画面状态 |
| --- | --- | --- |
| `f160–f163` | 约 `5.33–5.43 s` | 黄色 `MEGATON BLAST` 封面已经稳定居中。 |
| `f164–f167` | 约 `5.47–5.57 s` | 旧的 `GRAVITY ZOIE` 封面突然回到中心，但标题仍显示新曲。 |
| `f168` | 约 `5.60 s` | 画面恢复为正确的新封面转场状态。 |

异常仅持续约 `4` 帧。旧封面能够完整重新出现，而歌曲标题仍保持新曲，说明此时并非目标封面像素未完成读取或解码；更符合旧 transition pair 仍被赋予角色，并在共享 `progress` 被置为 `0` 后重新从中心姿态绘制的行为。

## 根因分析

最终抽搐由转场会话、退出图层与共享动画进度的生命周期错位共同造成：

1. 一次 settle 完成后，动画 context 会先清空，但旧 session 及其 exiting DOM 尚未同步移除。
2. 下一次 `pointerdown` 或拖动方向锁定会将共享 `progress` 重置为 `0`。
3. 此时旧 session 仍可能向旧 outgoing 图层分配角色；共享进度回到起点后，旧 outgoing 因而短暂回到中心并重新播放。
4. 会话解析逻辑曾允许历史 `transitionIntent` 抢占正在发生的 live drag，使自动切歌状态覆盖当前手势的所有权。
5. 旧图层在没有 role 时曾回落到 `transform: none`、`opacity: 1`，因此本应退出的卡片也存在重新显露的风险。
6. 旧资源清理按异步完成时机发生；若没有按 session 和 layer 身份隔离，迟到回调还可能影响新会话。

上述链路解释了视频中的“标题已切换、旧封面却短暂回到中心”：音频和当前歌曲状态已经前进，异常发生在视觉转场会话，而不是播放状态回退。

## 失败方案及不足

### 低频采帧与不足强度的复现

早期采帧频率过低，测试中的拖动次数和速度也不足。最终异常窗口仅约 `4` 帧，在 `30 fps` 视频中持续约 `0.13 s`，抽样间隔稍大就会完全漏掉；少量或低速切歌也不足以制造会话交叠。

### 未就绪时取消动画

发现目标卡片未就绪便取消当前动画，只能避免当次展示不完整内容。下一次手势在封面已就绪时仍可能正常播放，看似降低故障概率，但没有保证当前手势连续，也会导致动效被中断或稍后重新开始，属于症状规避。

### 使用占位卡

稳定占位卡可以掩盖真实封面像素未就绪，但占位内容本身就是用户不接受的可见状态，也不能证明真实封面资源已按交互时序准备完成。

### 单纯扩大缓存或更积极预取

扩大缓存、提前读取和积极换入能够改善真实封面的像素供应，应继续作为资源层策略；但最终视频中的旧封面已经具备完整像素。该策略无法修复 session 所有权、旧图层退休和共享 `progress` 重置之间的竞态。

### 只隐藏 `role = null` 的旧图层

无角色时隐藏 exiting 图层是必要安全网，可以避免 `transform: none`、`opacity: 1` 使废弃卡片直接显露；但本次抽搐发生时，旧 session 仍错误地为旧图层分配了 role，因此只处理 `role = null` 不能覆盖根因。

### 只在 commit 时清理旧 outgoing

等待新拖动成功 commit 后再移除旧 outgoing 已经太晚。旧 session 可以在新手势按下、方向锁定和 commit 之间被共享进度重置，并在数帧内重新出现。

## 最终解决方案

修复将“像素资源就绪”与“转场会话所有权”分层处理：

1. **保留真实封面预热与有界资源层**：继续提前准备相邻歌曲的真实封面，并通过有界资源池管理读取、解码、换入、复用和释放。资源层负责保证像素供应，不使用用户可见的占位卡替代真实封面。
2. **在新手势内同步退休陈旧会话**：若新 `pointerdown` 到来时不存在仍有效的 active settle，但残留旧 session 或 exiting DOM，则先同步退休旧 outgoing 并清除旧 session，随后才允许把共享 `progress` 重置为 `0`。
3. **保留有效 settle 的连续交接**：若 settle 仍处于 active 状态，新手势继承当前 handoff pose 和 progress，不把卡片跳回标准起点，确保视觉位置连续。
4. **实时手势拥有最高有效优先级**：有效 live drag 优先于历史 automatic `transitionIntent`，旧意图不能覆盖正在发生的用户手势。
5. **同一 pair 的状态转换只重键**：drag 转 automatic 且 outgoing、incoming 与方向均为同一 transition pair 时，仅 rekey 会话并保留当前进度，不重新创建从 `0` 开始的动画。
6. **收紧无角色图层可见性**：图层没有 role 时仅 active 图层可见；exiting 图层保持不可见，防止防御路径下旧封面回到默认中心姿态。
7. **隔离迟到清理**：异步清理按 session 和 layer 身份判断，只允许对应旧会话释放自身资源，避免 stale cleanup 污染当前转场。

## 验证结果

### 开发模式 WebView 动态回归

- 综合压力回归完成 `60/60` 次实际歌曲变化，采集 `3505` 个运行期动画帧样本和 `199` 次 session publish。
- 独立 Mock 封面回归完成 `80` 次歌曲变化、`82` 次拖动手势，手势间隔 `0 ms`，每 `3` 首反向一次，共采集 `2086` 帧。
- 真实封面回归完成 `50` 次歌曲变化、`55` 次拖动手势，手势间隔 `0 ms`，每 `3` 首反向一次，共采集 `2674` 帧。
- 所有压力回归中，旧卡回到中心、错误方向、无可见卡、active 图层异常、白屏、页面错误、资源池等待者残留、`staleWrites` 和 `useAfterRelease` 均为 `0`。
- 强制进入 `role = null` 防御分支并连续观察 `26` 帧，exiting 图层 `opacity` 始终为 `0`，active 图层始终为 `1`。

## 期望行为

- 无论拖动速度、次数或方向切换频率如何，转场都只展示当前会话对应的真实封面。
- 新手势中断旧 settle 时，卡片应从当前可见姿态连续接管，不回到起点、不重播旧 transition pair，也不闪现旧封面。
- 真实封面未完成准备时，资源层应通过预热和有界复用避免用户看到占位卡；不得用取消当前动画来掩盖时序问题。
- 高频切歌不应白屏，播放状态与视觉状态应保持一致，迟到的资源或清理回调不得修改当前会话。
