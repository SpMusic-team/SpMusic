# Surface Pro 10 商业版播放界面动画频繁出现封面重入

## 问题描述与证据边界

用户报告：播放界面的动画在 Intel Core i7-12700KF + NVIDIA GeForce RTX 4060 Ti 电脑上表现良好，在 Surface Pro 10 商业版上却频繁出现“封面重入”。用户进一步确认，先前版本也存在该问题，本地三个未提交文件属于新特性，不能据此将问题视为仅存在于本地未同步代码。

本条最初为候选 Bug 登记，供用户切换到 Surface 后继续复现和修复。2026-10-11 首轮接续调查时，用户明确异常入口为拖动切歌；首轮尚未取得视频、逐帧截图、运行日志或性能轨迹，当时“重入”的具体表现仍待确认。首轮代码竞争修复及浏览器验证后，用户反馈仍能复现，快速拖动更容易出现，表现为新封面到位后又从侧面重入。后续原生采样已取得实际会话与资源时间线，见下方二轮定位记录；不能以首轮浏览器回归通过判定原生缺陷已经解决。

## 2026-10-11 修复前定位记录

本节在业务修复前登记。Frontend Agent 静态检查发现了一条可导致同一次拖动被重新表现为自动切歌的时序竞争链；Architecture Agent 条件通过并补充了必要触发条件，Test Agent 正在独立核对。当前尚无 Surface 实机时间线，以下为代码层面的候选因果链，不能等同于该设备异常已实测确诊。

1. 拖动释放进入 `commitCoverDrag` 后，卡片立即向进度 `1` 收尾；较高拖动进度时，收尾的最短时间可到 `45 ms`。
2. 提交预览后，资源从 preview 转为 incoming，再到 active，需要经过 `PlayerSurface.tsx` 内 `TrackCardLayer` 的双 `requestAnimationFrame` 绘制屏障及 `markReady` 晋升。这是异步准备，完成时间不保证早于卡片收尾。
3. 若慢帧使资源晋升晚于收尾，收尾回调会先执行 `completeTrackCardExit`；此时旧资源仍是 active，而退出清理只处理 exiting，因此没有清掉这张旧封面，收尾引用却已置空。
4. **还需要收尾已完成、资源尚未晋升期间发生依赖刷新**：例如 `artworkSlots` 或 selection 变化，使失效会话 effect 再次执行。该 effect 发现 incoming/outgoing 配对尚未成立，可能清除拖动会话并把共享进度归零。资源迟到晋升后形成新的 active/exiting 配对，自动切歌路径可再次创建会话并播放入场，产生用户描述的“重入”候选表现。收尾完成本身不触发渲染；若资源直接晋升而没有这次中间刷新，现有 `completedCommittedDrag` 保护可生效，因此不能仅凭“资源晚于收尾”判定必然重入。

这条链路说明代码本身存在可检查的竞争窗口；较慢帧率可能放大该窗口。200% 缩放可能增加画布与合成负载，但尚未采集性能证据，不能认定缩放、硬件性能或显卡驱动是根因。后续修复应维护已提交拖动的会话所有权，仅保留仍被当前 selection、token、资源配对和方向接受的待晋升会话，使资源晋升和收尾完成能以任意先后顺序会合，并防止迟到资源重启同一次入场。架构约束包括保留 `800 ms` watchdog 和既有播放契约，不通过统一增加等待时间来替代生命周期修正。独立测试需覆盖资源晚于收尾并出现中间刷新、反向或连续手势等场景。

待晋升会话的保留必须有边界：除 selection/token/pair/direction 失效后的清理外，还需保留 `800 ms` watchdog 的独立超时清理路径，避免资源始终不就绪时永久占有会话。该定位记录不表示 Surface 已实测确诊或修复已通过设备验收。

### 修复前确定性时序验证

Test Agent 在 `20722d6` 基线上使用真实 `PlayerSurface` 与资源 hook，在 Edge Chromium 156 浏览器中完成动态验证。测试仅在测试环境把 incoming 绘制屏障延迟至 `180 ms`，并触发同值 intent 刷新以重跑依赖路径；DPR 为 `1`。该实验控制异步顺序，用于确认代码竞争链，不代表原生 Tauri WebView2 实测或 Surface 的自然发生频率。

| 相对拖动提交时间 | 注入依赖刷新后的观测 |
| --- | --- |
| `49.3 ms` | 收尾完成，progress 到 `1` |
| `124.8 ms` | session 被清为 null，progress 回到 `0` |
| `271.5 ms` | 资源晋升，创建 `selection:1` 自动会话，再播放约 `300 ms` 动画 |

无中间依赖刷新的对照保持 progress `1`，仅重新关联会话后立即退出，没有第二轮动画。该对照支持“延迟与中间依赖刷新共同触发”的必要条件，不能据此单独归因于 Surface 性能或 200% 缩放。修复前已记录上述定位与验证证据，随后授权 Frontend Agent 尝试修复；修复效果仍需独立验证。

补充长延迟验证：当屏障延迟为 `1000 ms` 时，即使没有主动刷新 intent，基线在 DPR `1` 与 `2` 下也都出现 progress `1 → 0` 和一次完整自动重播，说明 watchdog 路径同样需要处理已接受但未晋升的拖动。此实验仍属于确定性时序注入。

## 首轮修复后原生复现与二轮修复前定位

本节在二轮业务修复前登记。用户反馈首轮修复后问题仍然存在，快速拖动更易触发，新封面到位后又从侧面入场。Frontend Agent 与 Architecture Agent 独立核对原生采样，定位到首轮绘制屏障实验没有覆盖的资源去重缺口。

### 原生运行版本与采样边界

- 主协调通过 computer-use 在原生 `tauri.localhost` 程序导入本地歌单夹具，最大化窗口为 `1440 × 960` CSS px，DPR `2`，对应 `2880 × 1920` 像素与本机 200% 缩放。
- 原生运行资源 `sonner-CagZ_Gmo.js` 的 SHA-256 为 `8e7019fdabb82aa8585d5d743040a37607e623f8e00589a7483af082b8c1614e`，与本地 `dist` 一致。这确认了本轮原生采样加载当前本地前端构建；仍不代表另一台电脑运行同一构建。
- 共捕获 `17` 次自然手势和 `783` 帧；其中 `3` 次由自动化输入，一次捕获不完整，其余为用户自然连续输入。该混合样本用于定位，不作为完整自动化通过率或自然异常频率统计。
- 原始诊断暂存于被 Git 忽略的 `.codex/bug0018-native-live.json`。它是本地排查数据，不作为长期唯一附件；本节保留可审查的关键时间线、构建校验和与归因边界。

### 同身份 incoming 被替换导致重入

下表时间来自同一次原生采样的页面时钟，单位为毫秒。

| 时间 | 观测 |
| --- | --- |
| `275572` | progress 为 `0.710`，拖动会话 `drag:31` 的配对为图层 `29 → 30`，图层 `30` 为 incoming |
| `275605` | `detailsPending` 从 true 变 false；incoming 从图层 `30` 变为 `33`，但 track hash `6fc03860`、identity hash `e194ddda` 与 request `17` 均相同；会话清空、progress 归零 |
| `275639` | 自动会话 `selection:17` 以图层 `29 → 33` 从进度 `0` 再次入场 |

Frontend / Architecture 核对 `useArtworkVisualResource.ts`：资源 effect 在元数据就绪刷新时遗漏了对已有 incoming 的复用检查。即使 registry 命中同一 identity，仍可调用 `createLayer` 新建图层 `33` 并释放原 incoming `30`，同时丢失原 preview token。`PlayerSurface` 的拖动会话仍引用旧图层 `30`，因此配对失效，清空会话和进度；新图层随后进入自动切歌路径，产生第二次入场。这是原生时间线与静态代码对应的具体失效链，不能用首轮“仅延迟绘制屏障”的实验覆盖替代。

本次采样的 `coverTransform` 全为 `none`，没有支持共享布局 projection 重播的证据。DPR 和硬件性能可能影响触发时机，但本轮已直接观察到同 identity、同请求的图层替换；尚无证据把 Surface 性能差距或 200% 缩放认定为根因。

二轮修复目标为在当前选择与请求仍匹配时复用同身份 incoming，保持已有 layer ID 和 preview token，避免元数据完成导致会话配对失效。具体实现与边界由 Frontend / Architecture 确认；需要新增覆盖 `detailsPending` 就绪时同 identity incoming 复用的独立回归，并使用当前原生构建重复相同快速拖动场景。此处记录定位，不提前宣告二轮修复或实机验收通过。

### 二轮修复与最终浏览器回归

二轮修复在资源 hook 中复用仍属于当前请求的同 identity incoming，保留图层 ID 和 preview token；同 identity 的新请求只更新有效 intent，异 identity 和失败 fallback 继续按对应资源路径处理。
