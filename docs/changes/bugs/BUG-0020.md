# 连续拖拽停止后封面切歌被原生拖放取消

## 现象与当前结论

用户以鼠标按住播放界面封面，连续快速左右拖动切歌。二十多首后，尤其在停止连续拖动后的下一次拖动，可能出现左右均无法拖动；播放控制器仍能切歌，但不能恢复封面拖动。长按封面仍可打开“更多”，关闭后依然无法拖动。

本轮已证实并修复一处浏览器原生拖放与封面指针手势的冲突：保留的 DOM 文本选区可使封面按钮成为原生拖放源，浏览器随后发出 `pointercancel`，终止播放器拖拽。受控浏览器及真实原生程序中的对应场景均已通过修复验证。

**用户连续操作如何自然形成该选区尚未复现；用户完整原始操作仍待复测。** 本记录不将受控复现通过写成所有取消来源均已消除，也不将此前未复现故障的自动化序列视为用户验收。

## 用户日志定位

用户保存的 v1 日志为 `player-drag-1793550077828-5592-0.json`，记录约 34.6 秒；最早 2,162 条记录被容量上限覆盖，但保留了持续失效边界。

| 证据 | 结果与意义 |
| --- | --- |
| `#6972`，29,351.3ms | 最后一次成功提交切歌。 |
| `#7013`，29,525.7ms | 后续手势已启动、预览已返回，随后开始持续取消。 |
| gesture 311、312 | 均已达到 `target-ready`，仍在约 8–9ms 后取消；不能归因于未等到预览。 |
| 后续按下 | 仍能接收 `press.accepted`，随即成对出现取消及捕获丢失，没有新切歌。 |
| 最终音频与视觉状态 | logical、active、presentation、engine 曲目身份一致；几何有效，Surface 回到 idle。 |
| 最终资源与任务状态 | 画布池还有 1 个空位，等待者为 0；封面调度队列为空，元数据未阻塞，hydration 为 0。 |

成对取消符合同一个原生 `pointercancel` 先经窗口捕获处理、再经 React 处理的路径，不代表两次独立物理操作。v1 没有记录原始事件来源和 `dragstart`，因此**用户日志本身只证明了指针流持续被取消，不能直接证明原生拖放是触发源**。

这些证据排除了本次末态的画布池满、音频详情等待、曲目与活动封面不一致等解释。此前查出的重复封面解码属于独立的资源冗余问题，其缓存复用修复不能作为本次持续失效的原因或解决证据；此前试修和列表内容窗口化试验已回退。

## 已证实的冲突与复现方法

Test Agent 在真实 `PlayerSurface` 组件中，用 DOM Range 建立跨封面至歌词的选区，然后发送浏览器可信鼠标输入；没有向手势 ref 塞入状态，也没有伪造 `pointercancel`。

1. 保留选区后，第一次封面拖动可以完成切歌。
2. 停顿后的下一次拖动触发可信 `dragstart`，目标是封面内的 `BUTTON`，随后浏览器向 deck 发出可信鼠标 `pointercancel`，`buttons=0`。
3. 继续同向、反向拖动，以及长按打开“更多”、关闭后再拖，都仍被原生拖放取消，累计只完成第一次切歌。
4. 仅阻止封面区域的原生 `dragstart` 默认动作后，同一用例四次切歌全部完成，`pointercancel` 为 0；可信 `dragstart` 的 `defaultPrevented` 为 true。

空封面按钮即使自身不是显式可拖动元素，也可能受保留选区影响成为原生拖放源。自定义指针切歌与浏览器原生拖放需要明确划分输入区域所有权；取消后的清理本身不是这次修复要跳过的步骤。

普通鼠标从封面拖到歌词、再拖动的对照尚未自然形成对应选区，未复现持续取消。因此不能进一步声称“跨区域拖动一定生成选区”，也不能断言选区一定来自新增长按功能。

## 最小修复

[PlayerSurface.tsx](../../../src/features/player/components/PlayerSurface.tsx) 的 `coverDragProps.onDragStart` 增加局部屏障：

- 只有事件目标位于 `.cover-frame` 或 `.cover-input-region`，且匹配区域属于当前处理容器时，才调用 `event.preventDefault()`。
- 不调用 `stopPropagation()`，不屏蔽封面外的原生拖放。
- 不修改 `pointerdown`、焦点、DOM Selection、CSS 或转场状态；保留真正 `pointercancel` 的原有清理。
- 录制开启时输出 `cover.native-drag-blocked`，并记录 `defaultPreventedAfter=true`，用于核对用户实机是否命中该屏障。

修复位于浏览器默认动作入口，没有扩大封面池、增加重试轮询、统一重置播放器或忽略取消事件。

### 重跑入口

先在仓库根目录的单独终端运行 `npm run dev -- --host 127.0.0.1 --port 5173`。浏览器脚本使用已有 Playwright 包和本机 Edge，不要求向项目添加 Playwright 依赖：

```powershell
$env:SPMUSIC_PLAYWRIGHT = '<已有 Playwright 包的绝对路径>'
$env:SPMUSIC_TEST_ORIGIN = 'http://127.0.0.1:5173'
$env:SPMUSIC_SELECTION_EXPECT_FIXED = '1'
node src/features/player/components/nativeSelectionDrag.browser.test.mjs
node src/features/player/components/playerDragDiagnostics.browser.test.mjs
```

[选区回归脚本](../../../src/features/player/components/nativeSelectionDrag.browser.test.mjs) 默认执行诊断实验；`SPMUSIC_SELECTION_EXPECT_FIXED=1` 才启用上述正式修复断言。`SPMUSIC_SELECTION_SURFACE_PATH` 只用于可选的本机旧版 Vite 转换模块对照，普通回归不依赖该临时快照。

[原生端到端脚本](../../../src/features/player/components/nativeDragDiagnosticsExport.browser.test.mjs) 需配套以临时 CDP 端口启动、已嵌入当前前后端代码的原生程序，并配置 `SPMUSIC_NATIVE_CDP`、`SPMUSIC_PROBE_OUTPUT`；设 `SPMUSIC_NATIVE_GUARD_SMOKE=1` 可执行实际选区及双向拖动检查。不能将新前端路由到旧原生程序代替真实命令验证。原生构建入口为 `npm run tauri build -- --no-bundle`。

## 诊断 v2 与用户复测

[录制器](../../../src/features/player/diagnostics/playerDragDiagnostics.ts) 和[诊断面板](../../../src/features/player/components/PlayerDragDiagnosticsPanel.tsx) 默认关闭录制。v2 增加原始输入的来源、可信标志、焦点及选区状态，记录取消调用来源；不读取选中文字、歌词、媒体路径或封面内容，身份使用会话内加盐哈希。

记录上限为 10,000 条，低价值缓存命中与高引用计数变动聚合统计。前端导出控制在 4 MiB 内；[Rust 导出端](../../../src-tauri/src/player_drag_diagnostics.rs) 验证 JSON 对象和 `schemaVersion: 1`，硬限制为 5,000,000 UTF-8 字节，只在显式保存时向 `<AppLogDir>/drag-diagnostics/` 写入唯一文件，不接受调用方指定路径。

1. 在修复版按 `Ctrl + Shift + Alt + D`，确认面板显示“诊断版 v2”，点击“开始记录”。
2. 按用户原方式连续快速双向拖动二十多首，重点检查“停止连续拖动，松开鼠标，再次拖动”。面板隐藏后仍继续记录。
3. 若再次失效，先不要重启，点击“记录故障并保存”。保存前同步冻结故障快照，不重置手势；失败可重试同一份冻结记录。
4. 核对日志 `buildMarker` 为 `drag-diagnostics-manual-v2`，查看 `cover.native-drag-blocked`、原始 `dragstart` / `pointercancel`、取消来源及最终快照，区分原生拖放与其他系统取消。

当前待确认项是自然选区形成过程及用户原始操作的修复效果；需要用户复测结果后再更新验收状态。
