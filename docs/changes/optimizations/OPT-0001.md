# 音频线程重 I/O 与时间敏感控制混在一起

> 状态：已实现（2026-08-05）

## 问题描述

音频运行时是单一 actor 线程（`AudioRuntime`），所有请求经 mpsc 队列串行处理。`LoadFile` 在该线程内同步完成文件解析（容器探测、时长解码、标签与封面读取），期间 `Pause`、`Seek`、`SetVolume`、`GetState` 全部排队等待，时间敏感控制被重 I/O 阻塞。

## 现状依据

- `src-tauri/src/audio/controller.rs:58-79`：音频运行时线程循环内，`AudioRuntimeRequest::LoadFile` 分支（67-79 行）同步调用 `runtime.load_path(path)`，返回后才继续处理下一条消息。
- `src-tauri/src/audio/controller.rs:389-393`：`load_file_path` 发送 `LoadFile` 请求后阻塞等待回复，命令调用方同样受串行队列牵制。
- `src-tauri/src/audio/runtime.rs:158-173`：`load_path` 将阶段置为 `Loading` 后调用 `hydrate_track_ref`，进入完整解析流程。
- `src-tauri/src/audio/source.rs:196-200`：`hydrate_track_ref` 转发到 `load_track_ref_with_options`。
- `src-tauri/src/audio/source.rs:203-224`：`load_track_ref_with_options` 依次执行 `validate_existing_file`、`open_source().total_duration()`（容器探测）、`decode_duration()`（时长解码）、`read_metadata_or_default()`（标签/封面读取），重 I/O 集中在同一调用栈。
- `src/features/player/components/PlayerShell.tsx:785-803`：播放期间前端每 500ms 轮询一次 `audio_get_state`，加载期间的阻塞会直接反映为 UI 卡顿与状态滞后。

## 影响

- 加载大文件、带封面或 sidecar 歌词的文件时，解析耗时可达数百毫秒到数秒；期间暂停/快进/音量调节/状态查询全部排队，任何操作都表现为「点了没反应」。
- 前端播放期间每 500ms 轮询一次状态（见 OPT-0004），加载期间 UI 出现明显卡顿或状态滞后；`GetState` 只能返回加载前状态，无法反映真实进度。
- 排队现象随解析耗时线性放大：目录列表、连续换曲等场景可能连续触发多次 `LoadFile`，进一步加剧阻塞。

## 期望行为

- `LoadFile` 不应阻塞音频线程上的时间敏感控制；加载期间 `Pause`、`Seek`、`SetVolume`、`GetState` 应保持可用。
- 加载应有可感知的进度/阶段状态，前端能展示加载状态而非静默等待。
- 同一文件的解析结果可复用，避免并发或重复解析（与 OPT-0002 关联）。

## 验收标准（建议，待 PM / Test Agent 确认）

1. 加载大文件（≥ 100MB 或含大封面）期间，`audio_get_state`、`audio_pause`、`audio_set_volume` 响应延迟不超过 100ms（对比现状可量化）。
2. 加载期间前端能显示明确的加载状态，播放/暂停等控制不因加载被禁用或卡死。
3. 连续加载（换曲、目录列表）时音频线程不出现请求堆积导致的延迟漂移。
4. 现有 Rust 单元测试与前端行为测试保持通过；新增针对「加载期间并发控制」的测试。

## 影响范围

- 后端：`controller.rs`（请求分派）、`runtime.rs`（运行时状态机）、`source.rs`（解析调用链）。
- 前端：`PlayerShell.tsx` 轮询与加载状态展示（配合 OPT-0004）。
- 测试：Rust 单测与前端行为测试需补充加载并发场景。
- 文档：`docs/architecture/real-audio-playback.md` 需随方案更新线程模型说明。

## 优化方向（候选方案，待 Architecture Agent 决策）

### 方案 A：解析拆分到独立 worker（推荐方向）

将 `hydrate_track_ref` 的重 I/O 部分（容器探测、时长解码、元数据读取）移出音频线程，放入串行解析 worker 或带优先级队列的解析线程；解析完成后通过消息回填曲目引用，音频线程只保留控制与播放。

- 收益：彻底解除阻塞；加载与播放控制可并行；为解析缓存与预加载（OPT-0008）铺路。
- 成本：消息结构需新增「解析结果回填」通道；`AudioRuntimeRequest` 与状态机需要调整；并发解析需要去重（同一文件只解析一次）。
- 风险：跨线程状态同步复杂化，需要 Architecture Agent 输出正式消息契约。

### 方案 B：异步加载 + 阶段式处理

保留单线程模型，但将 `LoadFile` 改为阶段式异步处理（解析间隙处理控制消息），或为 `LoadFile` 提供可感知的加载进度回调。

- 收益：改动小于方案 A，可快速缓解「控制完全无响应」。
- 成本：解析总耗时不变，只是不再阻塞；大文件仍会长时间占用音频线程。
- 风险：阶段式处理侵入解析调用链，需要重构 `load_track_ref_with_options`。

### 方案 C：仅前端体验兜底

不改后端线程模型，仅在加载期间让前端展示加载态并禁用相关操作。

- 收益：改动最小。
- 成本：只是掩盖问题，控制请求仍然排队；不建议作为最终方案。

**倾向**：方案 A 作为长期方向（与 OPT-0002 的解析复用、OPT-0008 的队列收敛一致），方案 B 可作为过渡；最终取舍由 Architecture Agent 决策。

## 实现记录

### 采用方案

独立解析 worker 线程 + 代际号（generation）防串曲：

- 新增解析 worker 线程，只执行 `hydrate_track_ref`（容器探测、时长解码、元数据与封面读取），完成后经 runtime 通道回传 `TrackParsed { generation, path, result }`。
- 音频 runtime 线程收到 `LoadFile` 后不再同步解析：先失效旧轨道、置 `phase=Loading` 并立即广播状态，再把解析请求（携带自增 generation）交给 worker，随后继续处理控制类消息。
- `complete_load` 仅在 generation 与当前待加载代际一致时应用 `Ready` / `Error`，否则丢弃，防止并发加载串曲。
- 命令契约不变：`audio_load_file` / `audio_open_file` / `audio_open_source` 仍返回 `AudioTrackRef`；阻塞发生在 command 线程，音频线程保持空闲。

### 关键改动

- `src-tauri/src/audio/runtime.rs`：`start_track_parser`（解析 worker）、`TrackParseRequest`、`AudioRuntimeRequest::TrackParsed`、`start_load` / `complete_load` 状态机；加载期间 `Pause`、`Seek` 为 no-op。
- `src-tauri/src/audio/controller.rs`：runtime 循环新增 `pending_load` 簿记与 `TrackParsed` 回填分支；并发 `LoadFile` 时旧调用方收到可恢复 `INTERNAL_ERROR`（被更新请求取代），不加新错误码。
- `src/features/player/components/PlayerShell.tsx`：加载期放开音量调节（后端加载期 `set_volume` 可即时生效）。

### 验证结果

- `cargo check`：通过，0 告警。
- `cargo test --lib`：62 通过（含新增异步加载状态机、代际号防串曲、加载期 no-op、parser worker 往返测试）。
- `cargo check --tests`：通过（含 `tests/audio_compatibility.rs` 编译）。
- `npx tsc -b`：通过。

### 遗留事项

- 验收标准 1（加载期间控制响应 ≤100ms）需 Test Agent 真机大文件 smoke 测试。
- `audio_hydrate_track` 仍在 command 线程同步解析（不影响音频线程），解析复用/去重归 OPT-0002。
- `play()` 的 `rebuild_sink` 中 `open_source` 仍发生在 runtime 线程（开始播放的开销，非加载路径）。
