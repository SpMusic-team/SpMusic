# 音频线程重 I/O 与时间敏感控制混在一起

## 问题描述

`AudioRuntime` 是单一音频线程的 actor 模型，`LoadFile` 在该线程内同步完成文件解析，期间 `Pause`、`Seek`、`SetVolume`、`GetState` 全部排队等待，时间敏感操作会被重 I/O 阻塞。

## 现状依据

- `src-tauri/src/audio/controller.rs:57-79`：运行时线程的 `LoadFile` 分支同步调用 `runtime.load_path(path)`。
- `src-tauri/src/audio/runtime.rs:158,173`：`load_path` 调用 `hydrate_track_ref`，进入完整解析流程。
- `src-tauri/src/audio/source.rs:203-224`：解析流程依次执行 `open_source().total_duration()`、`decode_duration()`、`read_metadata_or_default()`，包含容器探测、时长解码和标签读取。

## 影响

- 加载大文件、带封面或 sidecar 歌词的文件时，解析耗时可达数百毫秒到数秒，期间暂停/快进/音量/状态查询全部排队。
- 前端播放期间每 500ms 轮询一次状态（见 OPT-0004），加载期间 UI 会出现明显卡顿或状态滞后。
- 加载过程中的 `GetState` 只能返回加载前状态，无法反映真实进度。

## 优化方向

将解析、扫描等重 I/O 工作拆分到独立 worker（串行或带优先级队列），音频线程只保留控制与播放；解析完成后通过消息回填曲目引用。若短期不拆分，至少为 `LoadFile` 提供可感知的异步进度，避免控制请求长时间无响应。

## 备注

- 消息结构、并发解析策略与缓存设计需要 Architecture Agent 输出正式方案后再实施。
- 应避免同一文件被并发重复解析，解析结果可复用（与 OPT-0002 关联）。
