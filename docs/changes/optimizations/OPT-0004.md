# 播放进度依赖 500ms 轮询而非推送

## 问题描述

播放期间前端每 500ms 调用一次 `audio_get_state` 获取全量播放状态，每次都是一次 IPC 往返加完整 JSON 序列化，而进度本身由后端按需计算。

## 现状依据

- `src/features/player/components/PlayerShell.tsx:785-800`：播放且使用真实音频时 `window.setInterval` 每 500ms 调用 `getAudioState()`。
- `src-tauri/src/lib.rs:147-160`：`audio_get_state` 返回完整 `AudioPlaybackState`（含 `position_ms`）。
- 前端已有 `applyAudioState` 重同步逻辑，轮询与事件通道并存（见 OPT-0003）。

## 影响

- 高频全量状态传输增加 IPC 与序列化开销，状态字段越多越明显。
- 进度条与歌词逐行高亮只能获得 500ms 粒度的位置采样。

## 优化方向

播放期间由后端以约 1Hz 推送轻量进度事件（`trackId`、`positionMs`、`phase`），前端仅在 seek、恢复、切歌等关键操作后用 `get_state` 重同步；轮询降级为兜底。

## 备注

- 事件契约与 OPT-0003 的状态通道决策耦合，建议由 Architecture Agent 统一设计。
- 歌词高亮与进度条消费同一进度源，可顺带统一。
