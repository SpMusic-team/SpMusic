# 切歌播放关键路径与展示元数据路径拆分

> 状态：已实现并完成验收，OPT-0014 关闭。

## 问题描述

当前切歌流程将“音频可以开始播放”和“完整歌曲展示数据已经读取并传到前端”绑定在同一个串行事务中。后端开始加载新歌曲时先停止并失效旧 `sink`，随后读取并返回完整 `AudioTrackRef`；前端必须等待该结果后才调用 `audio_play`。因此，歌词、封面和完整标签等非播放关键数据也会延长实际静音窗口。

这里的“等待所有数据”不是把整首音频文件读入内存。音频正文仍由解码器按流读取；阻塞播放启动的是完整曲目引用的准备与跨 IPC 返回，包括格式探测、时长、基础标签、歌词、内嵌封面、封面 Base64 编码和序列化。

## 运行证据

使用用户提供的真实本地 MP3 / FLAC 样本，通过生产 Tauri IPC、当前 Windows 默认音频输出设备和约 15 ms 间隔的端点峰值采样复现：

| 切换样本 | 旧声最后峰到新声首峰 | 点击到新声首峰 | 目标文件前导静音 |
| --- | ---: | ---: | ---: |
| 河北墨麒麟 → wrd.maker | 914 ms | 1113 ms | 约 550 ms |
| wrd.maker → 十万嬉皮 | 421 ms | 589 ms | 约 73 ms |
| 十万嬉皮 → 大石碎胸口 | 400 ms | 526 ms | 未检测到不少于 50 ms 的前导静音 |

上述结果反证了“`audio_load_file` 约 100 ms，因此声音切换也约 100 ms”。排除目标文件自身前导静音后，当前应用路径仍可产生约 400 ms 的实际无声区间。

另一次 `大石碎胸口.flac → 早.mp3` 的结构化日志与 IPC 计时为：

- 旧 `sink` 停止到新轨道进入 `Playing`：约 585.5 ms。
- parser 完成完整曲目引用：54 ms。
- `rebuild_sink` 与重新 `open_source`：11 ms。
- `audio_load_file` 后端完成到 `audio_play` 到达后端：约 517 ms。
- JavaScript 侧 `audio_load_file → audio_play` Promise 全链路：约 716 ms。

该 MP3 的内嵌 JPEG 封面为 2,545,707 bytes；编码为 Base64 后负载约增加到 3.4 MB。即使绕过 React 状态更新、直接串行调用 Tauri IPC，仍能复现主要延迟，因此 React 渲染不是该样本的必要根因。

## 当前因果链

1. 用户点击上一首、下一首或队列歌曲，或自然结束触发自动切歌。
2. Rust `AudioRuntime::start_load` 立即失效旧音频资源并停止旧 `sink`。
3. parser 执行音频探测、时长解析和完整元数据读取，包括歌词与封面。
4. 后端将包含完整元数据和封面 `dataUrl` 的 `AudioTrackRef` 序列化并跨 Tauri IPC 返回。
5. 前端 `await loadAudioFile(...)` 完成后更新曲目详情，再调用 `playAudio({ restart: true })`。
6. Rust `play()` 重新打开音源、构建 `sink` 并进入 `Playing`。
7. 从第 2 步停止旧 `sink` 到第 6 步新 `sink` 播放之间形成用户可听见的中断。

## 优化目标

将切歌拆成互不阻塞的两条路径：

### 播放关键路径

只执行开始输出新音频所必需的工作：

- 确认目标请求、曲目 ID 与规范化文件路径。
- 验证存在可用音频流和受支持解码器。
- 准备播放 source / sink 和必要的输出状态。
- 开始播放并提交轻量 `AudioPlaybackState` 或等价确认。
- 时长若能在播放准备阶段低成本获得则返回；否则允许后续补齐。

### 展示元数据路径

在不阻塞播放启动的情况下异步读取并提交：

- 标题、艺术家、专辑及其他标签。
- 歌词。
- 封面缓存路径或必要的后备数据。
- 非播放必需的详情字段。

元数据尚未返回时，前端可用文件名和稳定曲目 ID 作为占位信息；详情返回后原子更新当前歌曲展示。

## 已实施契约

Architecture 评审后采用新增事务、保留旧命令兼容性的方案：

1. 新增 `audio_load_and_play({ path, requestId })`，由后端完成一次打开音源、构建 `sink` 和进入 `Playing` 的播放事务；既有 `audio_load_file`、`audio_play` 与 `audio_hydrate_track` 语义保持兼容。
2. 播放结果仅返回 `requestId`、`generation`、`trackId`、`fileName` 和轻量 `AudioPlaybackState`，不携带歌词、封面或完整标签。
3. 完整 `AudioTrackRef` 在播放启动后异步水合，并通过 `audio_track_details_changed` 的 `ready` / `error` 事件提交。
4. 后端以 `generation + trackId` 抑制过期详情；前端以 `requestId + generation + trackId` 联合校验 command、状态事件和详情事件。
5. 新播放关键路径使用跳过标签读取的 `open_source_fast`，不读取 ReplayGain 或完整标签；legacy 音源路径继续保留 ReplayGain 行为。
6. 封面缓存成功时只返回 `filePath`，缓存不可用时才使用 `dataUrl`，两者满足 XOR。
7. 元数据未完成时前端提交仅含文件名的占位曲目，并清空旧歌词和封面；详情失败只反馈展示错误，不中断已经开始的播放。
8. 上一首、下一首、队列选择和自然结束在需要自动播放时使用新事务；暂停态切歌与初次打开播放列表继续走 legacy 路径，以保持既有产品语义和 M3U8 跳过行为。

## 实施与验证结果

已完成的代码级验证：

- `npm run lint` 通过。
- `npm run build` 通过；仅保留既有的大于 500 kB chunk 警告。
- `cargo check` 通过。
- `cargo test --lib` 通过，86 项测试全部成功。
- `git diff --check` 通过，仅有工作区既有的 LF / CRLF 提示。
- 单测覆盖播放快速路径不读取标签、legacy 路径保留 ReplayGain、过期详情抑制、详情失败不停音和封面 XOR。

独立静态验收确认：详情监听在发起新事务前就绪；未绑定 generation 的旧 `error/null` 状态不能污染新选择；A → B → C 的迟到 command、事件、错误、toast 和 finally 不能结算 C；切歌期间可继续选择上一首、下一首或队列歌曲，其余互斥控制在界面和 handler 上保持一致。

真实文件已验证可完成 legacy load、进入 `Playing` 并呈现歌词和封面；用户已完成最终真实切歌验收。此前一次隔离实例采样因物理坐标未实际触发切歌，相关六轮数据已判无效，不作为本次关闭依据。

## 范围

本候选优化包括：

- Rust/Tauri 音频加载、播放和详情水合的职责拆分。
- 轻量播放结果与异步详情结果的跨层契约。
- 前端先显示稳定占位信息、再提交完整元数据的状态处理。
- 封面负载从播放关键路径移除。
- 对快速连续切歌、失败和迟到结果的 generation / request 防护。
- 使用真实输出端点和无明显前导静音样本进行前后性能对比。

## 非目标

- 不要求无缝切歌、gapless playback、交叉淡化或双 `sink` 混音。
- 不要求在新音源准备完成前持续播放旧歌曲。
- 不预读整首音频文件，也不增加全量音频内存缓存。
- 不建立媒体库、持久化元数据索引或网络元数据服务。
- 不改变队列、循环、随机播放和自然结束的产品语义。
- 不以固定延时、隐藏 loading、吞错或减少日志掩盖声音中断。

## 验收标准与当前状态

第 1 至 6、9 项已通过代码、静态分析和自动化检查；第 7、8 项仍需有效的真实切歌与输出端点采样后才能关闭：

1. 切歌播放启动不等待歌词、封面或完整标签完成读取、Base64 编码、IPC 返回和前端渲染。
2. 新音频进入 `Playing` 后允许元数据继续加载；详情成功返回时，当前歌曲的标题、艺术家、专辑、歌词和封面正确更新。
3. 元数据未完成时显示文件名等稳定占位内容，不短暂显示真正的空播放器，也不残留上一首的歌词或封面。
4. 快速连续选择 A → B → C 时，B 的迟到详情、错误或取消结果不得覆盖 C；只有当前 generation 可以提交详情。
5. 详情读取失败不应中断已经成功开始的音频播放；界面显示可理解的后备信息和详情错误反馈。播放准备失败则不得提交成功播放状态。
6. 有封面缓存文件时，生产 DTO 不同时携带同一封面的 `filePath` 和 Base64 `dataUrl`。
7. 在输出设备已初始化、目标文件无不少于 50 ms 前导静音的条件下，至少选取 5 个真实支持格式样本、每个方向重复切换 3 次；应用产生的旧声最后峰到新声首峰中位数相对本文基线降低至少 50%，且不得出现由完整元数据 IPC 导致的 300 ms 以上串行空档。
8. 记录同一时钟下的点击、旧 `sink` 停止、播放准备、详情读取、播放 command / transaction 完成、`Playing`、元数据提交和输出端点首峰；不得继续用单独的 parser 耗时替代完整声音切换耗时。
9. `npm run lint`、`npm run build`、`cargo check`、相关 Rust 测试以及真实 Tauri 上一首、下一首、队列选择、自然结束和错误输入回归通过。

## 依赖与建议分工

- Requirements Agent：确认性能目标、占位展示和失败时播放 / 详情关系的正式验收标准。
- Architecture Agent：定义播放事务、详情 hydrate、command / event、generation 和错误语义。
- Rust/Tauri Agent：拆分播放准备与元数据读取，保持状态机和资源所有权安全，补充结构化时序日志。
- Frontend Agent：消费轻量播放状态和异步详情，处理占位、迟到结果与失败状态。
- Test Agent：使用无明显前导静音的确定性样本和真实输出端点独立测量，并执行乱序与回归验证。
- Documentation Agent：在需求获批和实现验证后更新本记录及相关能力说明。

## 与现有事项的关系

- `OPT-0005` 解决封面同时返回 `filePath` 与 `dataUrl` 的负载膨胀，是本优化减少详情 IPC 成本的直接依赖，但单独完成 OPT-0005 不能消除播放必须等待完整详情的串行结构。
- `BUG-0011` 解决切歌 loading 期间误挂载空播放器的界面状态问题；本优化解决真实声音中断和播放关键路径耗时，两者症状相关但根因与验收口径不同。
- `OPT-0001` 已将重解析移出音频 runtime actor，改善控制请求阻塞；其保留的完整 `AudioTrackRef` command 契约正是本优化需要进一步拆分的边界。
