# 播放状态轮询与封面解码内存治理

> 状态：P0 / P1 前端方案已实施，dev 长稳门槛已通过；production 三轮长稳及 3000 × 3000 封面连续 10 分钟等关闭条件尚未完成，OPT-0015 未关闭。

## 问题描述

修复前，播放器稳定播放同一首歌曲时，前端每 500 ms 获取一次轻量播放状态。状态应用路径会在曲目没有变化时仍重建展示曲目和封面对象，使封面加载逻辑把相同内容误判为新资源并反复创建、解码图片。大尺寸封面和环境背景滤镜进一步放大 WebView2 renderer 的原生图像内存峰值。

本问题不是“每 500 ms 从后端重新读取全部元数据”。`getAudioState` 返回的播放状态 DTO 不包含封面、歌词或完整标签；问题发生在前端将轻量实时状态投影到展示详情时破坏了对象身份稳定性。

## 已验证证据

### 用户现场

用户提供的任务管理器截图显示：

- WebView2 `spmusic` renderer 内存为 6,945.9 MB。
- WebView2 进程组总计为 7,066.8 MB。
- 系统内存占用为 95%。
- 现场为 `tauri dev` / Vite 开发会话，从 01:37 起已持续约 11 小时。

截图只作为现场现象来源；本文不记录截图在用户临时目录中的绝对路径。

### 后续采样

同一现场的后续空闲采样显示：

- renderer 约为 415.7 MB Private、101.2 MB Working Set，连续 30 秒空闲采样保持稳定。
- `app.exe` 约为 20.6 MB。

这些数据说明异常主要集中在 WebView2 renderer，并包含播放期间产生、随后可回收的内存峰值。现有证据不能把截图中的约 7 GB 归因于 Rust 音频进程，也不能仅凭峰值判断存在同等规模的永久泄漏。长时间开发会话及 Vite 热更新可能增加残留和测量噪声，因此生产构建与开发构建必须分别验收。

### 封面与详情负载边界

- 正常封面详情满足 `filePath` / `dataUrl` 二选一，不会同时携带同一份封面。
- 本机检查的 4 张封面缓存文件合计约 4.6 MB，其中最大封面为 3000 × 3000 像素。
- 因此，“后端每 500 ms 重复传输全部详情或同一封面的双份负载”不符合当前 DTO 和现场文件证据。
- 3000 × 3000 图片仅一份未压缩 RGBA 像素缓冲就约为 34.3 MiB；解码中间表面、主封面、环境背景和模糊滤镜可继续放大 renderer 内存，但它们是放大因素，不是重复触发的首要原因。

## 证据边界

当前证据足以支持“相同封面被重复提交和解码”这一修复前因果链，以及前端 renderer 为主要治理对象。P0 / P1 已实施，dev 构建已有一轮完整 600 秒数据并满足 dev 门槛；但尚未形成 production 构建三轮长稳数据，也未完成 3000 × 3000 封面连续 10 分钟验证。本文的 production 阈值和未覆盖场景仍是后续验收标准，不得写成当前实现已经全部达到。

开发会话中的 HMR、浏览器缓存、垃圾回收时点和系统内存压力会影响单点读数。验收必须采用规定的预热、采样频率、持续时间和增量口径，不能用任务管理器某一瞬间的下降代替长稳验证。

## 根因链

修复前确定的因果链如下：

1. 播放器每 500 ms 调用 `getAudioState`，获得 phase、position、duration、volume、generation、track ID 和错误状态等轻量实时状态。
2. `applyAudioState` 在 track ID 未变化时仍可能调用 `upsertTrack` 和 `commitPresentationTrack`。
3. `audioTrackToTrack` 由同一 `AudioTrackRef` 创建新的 `Track`，同时形成新的 `TrackArtwork` 对象引用。
4. `useLoadedArtwork` 依赖封面对象身份，因引用变化而把内容相同的封面视为新资源。
5. 相同封面反复执行 `new Image()` 与 `image.decode()`。
6. effect cleanup 只能解除回调或阻止部分迟到提交，不能终止已经开始的图片解码工作。
7. 大图像素解码、环境背景和模糊滤镜放大单次重复工作的内存成本，最终形成 renderer 的高峰值和回收压力。

修复前另有两个独立的长期累积风险：

- `hydratedAudioTrackCacheRef` 无容量上限，详情对象会随访问曲目增加。
- `tracks` 会保留旧播放列表 scope 中的曲目及其歌词、封面引用，切换来源后仍可能继续占用内存。

## 优化目标

1. 分离高频实时播放状态与低频展示详情，稳定播放同一首歌曲时不重建曲目或封面资源身份。
2. 相同封面内容在同一会话中只触发一次成功解码，不因 position、phase、volume 或相同 duration 更新重复解码。
3. 将水合详情缓存限制为可预测的固定容量，并在播放列表来源切换时清理旧 scope 数据和抑制迟到结果。
4. 保持现有 500 ms 轮询、Tauri DTO、播放语义、歌词与封面后备行为不变。
5. 用生产与开发环境分开的客观长稳指标验证 renderer 内存，而不是只验证功能或观察单点内存。

## 非目标

- 本项不改变 500 ms 轮询间隔，也不取消 `getAudioState`。
- 本项不修改 Tauri command / event DTO，不改 Rust 音频运行时。
- 本项不建立全局 decoded bitmap 缓存，不跨曲目长期保存浏览器解码位图。
- 本项不在前端对 Base64、完整封面 JSON 或完整资源内容做长字符串拼接、哈希或深比较。
- 本项不实现超大封面缩略图生成、磁盘缩略图缓存或 Rust 图像处理。
- 本项不以重启开发实例、强制垃圾回收、降低图片显示质量或关闭环境背景作为正式修复。

## 已实施方案

以下 P0 / P1 方案已经完成前端实施，保持既有 500 ms 轮询和 Tauri 契约不变。

### P0：停止相同详情重复提交与解码

P0 为纯前端修改，不改变轮询和后端契约。

1. 将 realtime state 与 presentation details 分离：
   - position、phase、volume 等实时字段只更新对应标量状态。
   - 同一 track ID 的这些更新不得调用 `audioTrackToTrack`、`upsertTrack` 或 `commitPresentationTrack`。
   - duration 只有值确实变化时才执行标量 patch，不通过完整曲目重建来更新时间。
2. 使展示详情提交幂等：当 track ID、详情内容和封面内容未变化时返回旧 `Track` / `TrackArtwork` 引用，不产生等价新对象。
3. 为 `TrackArtwork` 增加会话内紧凑 `resourceKey`：
   - 仅当 `trackId + coverTone + primary + fallback` 的内容发生变化时递增或生成新 key。
   - key 只表达当前会话中的资源版本，不拼接完整 `dataUrl`、完整 JSON 或其他大字符串。
4. `useLoadedArtwork` 以 `resourceKey` 和必要的原始资源字段为依赖：
   - 同一 key 最多启动一次 primary 解码；只有 primary 失败时才尝试一次 fallback。
   - cleanup 必须解除 `onload` / `onerror` 等 handler，将 `src` 置空，并通过 token 阻止过期任务提交结果。
   - cleanup 的设计不得声称能够取消已经进入浏览器内部的 `decode()`；避免重复启动才是主要治理手段。
   - 不建立全局 decoded bitmap 缓存。

### P1：限制详情缓存并隔离播放列表 scope

1. 将 hydrated 详情缓存改为最多 8 项的会话内 LRU：
   - 采用 Architecture Agent 建议的容量 8，不使用 32。
   - 命中时提升为 MRU；插入第 9 项时淘汰 LRU。
   - 水合失败不得写入缓存。
   - `inflight` 只用于请求去重，并在 Promise settle 后清理。
2. 定义播放列表 scope 为 `sourceKind + normalized sourcePath`。
3. 新 scope 生效后必须：
   - 清空 hydrated LRU。
   - 递增或切换 epoch，使旧 scope 的迟到 hydrate 结果失效。
   - 让 `tracks` 只保留新 scope 的曲目，不继续持有旧 scope 的歌词与封面。
4. 当前播放曲目由 `audioTrackRef` 单独持有，不受 LRU 淘汰影响；淘汰缓存不得中断当前播放或清空当前展示。

### P2：超大封面缩略图后续治理

缩略图生成、像素上限与环境背景专用尺寸另建后续 OPT，并在实施前由 Architecture Agent 与 Rust/Tauri Agent 评审。P2 不属于 OPT-0015 的关闭条件，本项不得顺带修改 Rust 或引入图像处理依赖。

### 实施补充

- 同 ID 轮询已实现幂等：高频 position、phase、volume 更新不再重建相同展示详情；duration 通过标量 patch 更新，内容不变时保留原引用。
- 封面使用会话内 `art-N` 资源版本；加载层按 `resourceKey` 复用相同尝试并去重 `decode()`，token 与 handler / `src` cleanup 阻止迟到结果提交。
- hydrated 详情采用 8 项 LRU；播放列表以 `sourceKind + normalized sourcePath` 建立 scope，scope epoch 使旧 hydrate 结果失效，当前播放仍由独立引用持有。
- 环境封面和静态曲目展示使用 `memo` 隔离，播放进度变化不再持续重渲染静态封面、歌词外壳和曲目信息区域。
- 视觉时间轴时钟移出 React state：`requestAnimationFrame` 只更新外部 visual clock，进度条和歌词按订阅更新必要 DOM / 局部状态。
- `ProgressControl` 保留局部 500 ms 语义位置采样，用于控件值和可访问语义；视觉进度通过 CSS 属性更新，不把每帧进度提升为播放器根级 React 渲染。

## 方案不变量

- 高频播放状态 DTO 始终保持轻量，不新增封面、歌词或完整标签。
- 同一内容的状态输入不得改变 `Track`、`TrackArtwork` 或 `resourceKey` 引用/值。
- 封面内容发生真实变化时必须获得新 `resourceKey`，旧解码结果不得覆盖新封面。
- primary 失败时仍可使用 fallback；无图曲目不得启动图片解码。
- 当前播放引用独立于详情 LRU，缓存淘汰和 scope 清理不得改变音频状态机。
- 失败请求不进入 LRU，迟到请求不跨 epoch 提交，settled 请求不残留在 `inflight`。

## 独立验证结果

Test Agent 已在无 HMR 的 `tauri dev` 会话中完成独立采样。以下斜率均为普通最小二乘法（OLS）趋势，增量相对各轮预热后的基线：

### 3000 × 3000 封面短时样本

使用 `wrd` 的 3000 × 3000 封面进行 55 秒采样：

- renderer Private OLS 斜率为 2.338 MiB/min，Working Set OLS 斜率为 2.808 MiB/min。
- 该轮记录的结束增量为 4.481 MiB，峰值增量为 5.008 MiB。
- DOM Nodes、Layout Objects 和 event listeners 数量不变。
- primary `decode()` 总计 1 次，后续轮询没有增加。

该曲目总时长为 337 秒；受测试起点和播放结束限制，本轮最长有效连续播放约 3 分 56 秒，55 秒结构化窗口和该次连续播放均不能替代“3000 × 3000 封面连续 10 分钟”验收。本文不将其伪报为 10 分钟通过。

### 1280 × 1280 封面完整 dev 长稳样本

使用 `河北墨麒麟` 的 1280 × 1280 封面完成 600 秒连续采样：

- Private OLS 斜率为 2.239 MiB/min，用于结束值判定的 `last60` 增量为 18.899 MiB，峰值增量为 20.563 MiB。
- Working Set OLS 斜率为 2.163 MiB/min，用于结束值判定的 `last60` 增量为 18.371 MiB，峰值增量为 20.047 MiB。
- DOM Nodes、Layout Objects、event listeners 和 JavaScript heap 均进入平台期，没有随轮询持续增长。
- primary `decode()` 总计 1 次。

该完整 600 秒样本满足 dev 环境的结束增量、斜率和峰值门槛，证明 dev 门槛已通过；它不等价于 production 构建三轮验收，也不覆盖 3000 × 3000 连续 10 分钟。

### 诊断收敛记录

实施迭代前两阶段曾观察到约 422 → 329 → 25 MiB/min 的失败基线收敛过程。这些数据用于定位 React 根级视觉时间轴更新和静态展示重渲染，不作为最终验收结果；最终结论以本节独立结构化采样为准。

## 验收标准

### 解码与引用稳定性

1. 使用带 3000 × 3000 封面的曲目稳定播放 10 分钟，覆盖约 1200 次 500 ms 轮询：
   - primary 在选择开始后的解码启动总计不超过 1 次；首次成功后增量为 0。
   - primary 失败场景中，每个实际 fallback 的解码启动总计不超过 1 次。
   - 无图曲目的图片解码启动次数为 0。
2. 对 `applyAudioState` 或拆分后的等价入口连续输入 1200 次内容相同、仅轮询重复的状态，`Track`、`TrackArtwork` 和 `resourceKey` 均保持同一引用/值；position、phase 或 volume 真实变化只能改变对应标量，不得改变上述引用。
3. 封面 primary、fallback、tone 或 track ID 真实变化时产生新 `resourceKey`，旧 token 的迟到成功或失败结果不得提交。

### renderer 内存

所有内存指标均针对 WebView2 `spmusic` renderer，分别记录 Private Bytes 与 Working Set；以预热结束时为基线，每 5 秒采样一次，报告结束增量、线性趋势斜率和峰值增量。

4. production 构建执行 3 轮独立测试；每轮均新启动应用，预热 60 秒后稳定播放 10 分钟：
   - Private Bytes 与 Working Set 的结束增量各不超过 64 MiB。
   - 两者趋势斜率各不超过 2 MiB/min。
   - 两者峰值增量各不超过 192 MiB。
5. 新启动 `tauri dev` 会话，在测试期间不发生 HMR，按相同方式预热和采样（当前已由 600 秒独立样本通过）：
   - Private Bytes 与 Working Set 的结束增量各不超过 128 MiB。
   - 两者趋势斜率各不超过 4 MiB/min。
   - 两者峰值增量各不超过 256 MiB。
6. production 三轮数据均须单独满足阈值；不得用平均值掩盖单轮持续增长，也不得将 `app.exe` 数值替代 renderer 指标。

### 缓存与 scope

7. hydrated LRU 的已完成缓存项始终不超过 8；连续 hydrate 100 条不同曲目后仍不超过 8，命中项目已提升为 MRU，淘汰顺序可验证。
8. 失败 hydrate 不进入缓存；所有 hydrate Promise settle 后 `inflight` 项数为 0。
9. 从 scope A 切换至 scope B 后，LRU 和 `tracks` 容器不再持有 A 的详情引用；A 的迟到成功、失败或 finally 不得提交到 B，也不得删除 B 的 `inflight` 状态。
10. 当前播放曲目即使不在 LRU 中仍可继续播放、显示详情并响应控制。

### 功能与工程回归

11. A → B → C 快速切歌、无图、primary 失败转 fallback、歌词加载、暂停、seek、音量修改和自然结束均通过回归；迟到详情或图片结果不得覆盖当前曲目。
12. 上一首、下一首、队列选择、播放列表来源切换和详情失败语义保持现状。
13. `npm run lint` 与 `npm run build` 通过。
14. Test Agent 完成独立验证并给出上述计数、竞态、功能和三轮内存采样证据后，OPT-0015 才可进入关闭评估。

当前仍待完成的关闭证据为：production 构建 3 × 10 分钟独立采样、3000 × 3000 封面连续 10 分钟、fallback / no-cover 动态解码场景、LRU hydrate 100 条，以及 A → B → C / scope epoch 自动化竞态验证。上述任一项未完成时均不得关闭 OPT-0015。

## 禁止方案

- 不通过调大或取消 500 ms 轮询掩盖对象身份问题。
- 不在状态 DTO 中加入封面或歌词，也不让每次轮询触发 hydrate。
- 不用 `JSON.stringify`、完整 `dataUrl`、完整图片字节或大字符串作为 `resourceKey`。
- 不建立无界 Map、数组或全局已解码图片缓存。
- 不把 effect cleanup 描述为能够可靠取消浏览器已经开始的 `decode()`。
- 不用强制刷新 WebView2、定时清缓存、重启应用或手动 GC 作为验收方案。
- 不在本项中修改 Rust、引入缩略图依赖或顺带实现 P2。

## 风险与回滚

- 详情幂等比较遗漏字段可能导致真实封面变化不刷新；应以 `trackId + tone + primary + fallback` 为明确边界，并用字段变化测试覆盖。
- cleanup 将 `src` 置空在不同 WebView2 版本上的行为可能存在差异；token 才是防止迟到提交的最终保护，不能依赖单一清理动作。
- scope 规范化不一致可能造成误清理或跨来源复用；实现必须复用项目现有路径规范化语义，并测试 Windows 路径分隔符和 M3U8 / folder 来源。
- LRU 容量 8 会增加回访旧曲目时的 hydrate 次数，但当前播放不受淘汰；若后续需要调整容量，应以独立采样为依据，不得直接改为无界或 32 项。
- 若 P0 产生功能回归，可回滚 `resourceKey` 与解码去重提交，但应保留诊断与测试；不得通过恢复无界重复解码来关闭问题。
- 若 P1 产生 scope 竞态，可单独回滚 LRU / epoch 改动并保留 P0；P0 与 P1 应采用可独立回退的提交边界。

## 与 OPT-0014 的关系

`OPT-0014` 已将播放关键路径与展示元数据路径拆分，并确认轻量播放状态不携带歌词、封面或完整标签。OPT-0015 不修改该跨层契约，而是治理拆分后前端消费轻量状态时的对象身份和资源生命周期问题。

两项优化的边界不同：OPT-0014 解决切歌启动被完整详情阻塞；OPT-0015 解决稳定播放期间相同详情被重复投影、封面被重复解码以及详情引用长期累积。OPT-0015 的 P0 / P1 已实施，但 OPT-0014 已完成和当前 dev 门槛通过均不能替代 OPT-0015 剩余的 production 与大图长稳验收。
