# 歌曲列表封面缩略图持久化与播放列表加载反馈

> 当前结论：代码改动及漏载回归修复已经实施；用户确认“所有歌曲”滚动封面加载明显变快，但播放列表首轮与滚动加载仍明显慢于“所有歌曲”。播放列表性能目标未达成，尚无可证明两者已接近的真实场景耗时对比，本记录不作关闭处理。

## 原始目标

用户希望首次扫描歌曲后，在本地文件夹保存最长边 256px 的封面缩略图。再次展示列表时直接读取缩略图，减少每次从歌曲文件提取原图并缩小的等待。范围包括“所有歌曲”和播放列表中的歌曲封面，并希望改善拖动滚动时的加载速度。

## 实现位置

- `src-tauri/src/audio/cover_pixels.rs`：缩略图生成、磁盘缓存、读取及缓存校验；缓存目录为应用缓存目录下的 `audio/thumbnails`。
- `src-tauri/src/library_cover_warmup.rs`：首次扫描后的批量缩略图预热。
- `src/features/player/services/audioCommands.ts`、`playlistCoverScheduler.ts`：缩略图命令封装与前端请求调度。
- `src/features/player/hooks/useAllSongsWindow.ts`：“所有歌曲”可见窗口请求 256px 缩略图。
- `src/features/player/hooks/useAudioPlayer.ts`、`useLibraryArtwork.ts`：当前播放源和非当前播放源的播放列表封面需求、可见范围、侧栏预览与首曲升级。

## 用户实际反馈与效果

1. 首次实施后，用户明确反馈“所有歌曲”界面拖动加载速度“变快了非常多”；同时认为播放列表提升没那么明显，要求借鉴“所有歌曲”的方式。
2. 播放列表按可见范围加载调整后，用户反馈首轮加载慢、滑动时大部分封面不加载、播放列表侧栏封面也不加载，并提供了界面截图。该反馈表明这轮调整产生了用户可见回归，不能以自动化通过覆盖。
3. 漏载修复后，用户反馈“感知不明显，所有歌曲的加载速度还是远高于播放列表界面”。因此，当前实现虽然保留了缩略图缓存并修复所见漏载，播放列表的体验目标仍未达到。

上述均为用户实际体验陈述；目前没有同一设备、同一曲库、同一缓存状态下“所有歌曲”与播放列表的首轮成屏时间和滚动封面呈现时间数据，不能量化两者差距，也不能据此断定单一瓶颈。

- `edd62ea` 当轮报告构建、Lint、缩略图调度器测试及播放列表滚动、预热、来源切换浏览器回归通过；另有一个界面切换动画测试在返回概览页时超时，未通过。
- `e87e22a` 当轮报告构建、Lint，以及覆盖 240 首歌曲、超过 40 张同时可见封面、延迟读取、连续快速滚动和侧栏加载的相关浏览器回归通过；一个界面动画测试在进入封面检查前超时，未计为通过。
- 相关测试路径包括 `src/features/player/services/playlistCoverScheduler.test.mjs`、`src/features/player/components/allSongsCoverCache.browser.test.mjs`、`playlistContentWindowLoading.browser.test.mjs`、`playlistCoverPreload.browser.test.mjs`、`importedPlaylistArtwork.browser.test.mjs` 和 `playlistSourceSwitchArtwork.browser.test.mjs`。

自动化结果说明所覆盖的功能路径和回归条件；它们没有证明播放列表在用户真实曲库中的首轮与连续滚动速度达到“所有歌曲”的水平。用户反馈是当前体验结论的主要依据。

## 后续分析范围

需要在相同曲库和缓存状态下，分别记录两界面的首轮可见封面完成时间、滚动后新可见封面完成时间，以及封面请求排队、磁盘缓存命中、解码和前端渲染耗时。还需分别覆盖当前播放源与非当前播放源播放列表、侧栏预览、快速连续滚动及高 DPI。依据测量结果再定位播放列表独有的等待环节并提出后续改动；在完成真实场景复测前，本项保持“播放列表性能目标未达成，待分析”。
