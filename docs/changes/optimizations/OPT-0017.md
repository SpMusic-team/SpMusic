# 播放界面快速拖动切歌的封面解码内存峰值治理

> 当前结论：**尚未实施任何代码改动**。本文记录排查证据、根因判断与两套候选方案的取舍，供后续决策。
> 核心判断：500MB 峰值**不是**"加载了 800 张封面"造成的，而是**单次解码原图时的瞬时分配放大**造成的（用户本机封面普遍 4000px 级，单次解码峰值约 190–260MB，两次重叠即接近 500MB）。

## 问题描述

用户在播放界面**高速拖动切歌**（快速连续切换歌曲）时观察到进程内存暴涨至约 500MB，之后回落。与"仅播放不操作"时的缓慢爬升（已由 OPT-0015 及其后续处理覆盖）是**两条不同路径**。

用户初始假设：内存 500MB 意味着加载了 800 张以上封面，或者加载了过多高清封面。

**该假设经排查不成立**（见下文证据 3）。

## 实测证据

### 证据 1：增长发生在 WebView2 renderer，不在 Rust 后端

8 分钟 1 Hz 采样（`app.exe` + 全部 WebView2 子进程）：

| 进程 | Private Bytes | CPU |
| --- | --- | --- |
| `app.exe`（Rust/Tauri） | 15.3 – 16.4 MB，全程平直 | 1.3% |
| WebView2 renderer | 152.8 → 332.1 MB | 2–3% |
| WebView2 GPU | 231 – 274 MB | 0.4% |

锯齿形态实测样例：

```text
t=310s  168.2
t=330s  172.2 -> 193.4   (+21)
t=331s  193.4 -> 226.6   (+33)
t=333s  227.6 -> 251.8   (+24)
t=335s  270.0 -> 323.4   (+53)
t=347s  332.1 -> 206.9   (-125)   ← 一次性大回收
```

上升段线性拟合 **+7.3 MiB/min（全程）**，陡峭段 **+24～29 MiB/min**。

注：该组采样对应"仅播放"稳态，不是拖动场景；拖动场景的 500MB 由用户现场观察给出，尚无同等精度的采样数据。

### 证据 2：用户本机封面原图尺寸（决定性证据）

实测应用缓存 `%LOCALAPPDATA%\SpMusic\SpMusic\cache\audio\covers`：

- 共 **1674 张**，合计 **677.3 MB**
- 最大尺寸抽样：

| 尺寸 | 大小 |
| --- | --- |
| 4096×4096 | 1984 KB |
| 4188×4188 | 1961 KB |
| 4000×4000 | 1922 KB |
| 3543×3543 | 1977 KB |
| 2100×2100 | 1915 KB |
| 1440×1440 | 1976 KB |

即：**用户的封面以 4000px 级为主**。

### 证据 3：前端 hero 路径驻留数量极少

`useArtworkVisualResource.ts` 的 hero 资源上限：

- `createArtworkCanvasPool()` 固定 8 个 canvas（`:232`）
- registry 上限 7（`:934` `while (registry.size > 7)`）
- 预热候选 `slice(0, 6)`（`:1561`）
- standby 最多 2 个（`:1563-1566`）
- 活跃层最多 3 个 slot（`:1596-1598`）

**合计最多约 9 张**，远不可能是 800 张。用户假设被否证。

### 证据 4：后端 hero 解码严格串行，不存在并发堆积

`cover_pixels.rs`：

- `CoverRequestCoordinator` 的 `decode_gate` 是 `Mutex<()>`（`:492`），`run_registered` 先取锁再检查过期（`:537-539`）
- `load_cover_pixels` 使用 `run_latest`（`:1091`），注释明确：「Rapid track changes therefore keep at most the current decode plus the newest waiting decode; superseded futures return STALE_REQUEST without entering the blocking pool.」

因此后端不会同时跑多个 hero 解码，排除"并发解码堆积"假说。

## 根因：单次解码的瞬时分配放大

### 关键差异：hero 路径跳过了预降采样

`cover_pixels.rs` 有两条解码路径，策略不同：

**列表缩略图路径（有预降采样）** — `:2373-2385`
```rust
if playlist {
    if let Some((pre_width, pre_height)) = playlist_pre_dimensions(...) {
        image = image.thumbnail_exact(pre_width, pre_height);   // 先廉价缩小
    }
}
image = image.resize_exact(width, height, FilterType::Lanczos3);
```

**hero 大图路径（无预降采样）** — `:2311-2316`
```rust
fn decode_and_pack(bytes: &[u8], max_edge: u32) -> Result<Vec<u8>, CoverPixelsError> {
    decode_and_pack_with_strategy(bytes, max_edge, false)   // ← false：不预降采样
}
```

`load_cover_pixels_blocking`（`:2092-2103`）直接调 `decode_and_pack`，即恒为 `playlist = false`。

### 单次解码内存核算（针对用户 4000px 级封面，目标 1536）

| 阶段 | 估算占用 |
| --- | --- |
| 原图解码为全尺寸 RGBA（4000×4000） | 64 MB |
| `resize_exact` Lanczos3 f32 工作缓冲 | 约 190 MB |
| `into_rgba8().into_raw()` 输出 1536×1536 | 9 MB |
| `pack_rgba` 再复制一份输出（含 header） | 9 MB |
| **单次解码峰值合计** | **约 190 – 260 MB** |

对 3000×3000 封面，单次峰值约 114 MB。

结合证据 4，后端串行意味着**同一时刻只有一次 hero 解码**；因此 500MB 量级需要「正在解码的这次」+「上一次尚未被分配器归还给 OS 的保留页」叠加，或本轮解码与前端 canvas/registry 驻留（约 75MB）叠加。

**结论：这是 `image` crate 全尺寸解码 + Lanczos3 重采样的瞬时峰值问题，不是缓存无界问题。**

### 附带发现：预降采样阈值对 hero 路径几乎不生效

`playlist_pre_dimensions`（`:2323-2326`）的触发条件是 `factor >= 2`：

```rust
let factor = (source.0 / target.0.checked_mul(4)?).min(source.1 / target.1.checked_mul(4)?);
(factor >= 2).then(|| (source.0.div_ceil(factor), source.1.div_ceil(factor)))
```

即 `source / (target * 4) >= 2`，等价于**原图 ≥ 目标尺寸的 8 倍**。

对 hero 目标 1536，需要源图 ≥ 12288 才触发。用户 4000px 封面**一张都不会触发**。

这意味着：**即便把 `decode_and_pack` 的 `false` 改成 `true`，对用户当前曲库也零收益**。此点已在方案评估中修正前期判断。

## 候选方案与取舍

### 方案 A：拖动期间降低解码档位（已否决）

做法：拖动中先按 1024 出图，落定后补 1536。

**否决理由（用户提出的风险，经代码核实成立）**：

`useArtworkVisualResource.ts:839-846` 把 `coverMaxEdge` 纳入解码身份：
```ts
const identity = [
  artworkSchedulerScopeRef.current,
  artwork.resourceKey,
  artwork.coverFilePath ?? '',
  artwork.coverImage ?? '',
  artwork.coverImageFallback ?? '',
  coverMaxEdge,          // ← 档位在身份内
].join('\u0000')
```

档位变化会引发：

1. **资源身份变化** → 同一封面被判为新资源，触发重新解码
2. **registry 准入竞争** → 可能挤掉正在显示的旧资源（`registrySet` `:918`），导致**占位图闪现**
3. **canvas 池不退档** → `makeLease` 的 `if (entry.backingEdge >= requestedEdge) return`（`:256`）只增不减，1024/1536 来回切会让 canvas 长期撑在 1536，**收益被抵消**

结论：会引入用户可察觉的封面重入与占位图现象，与"改善体验"目标冲突。

### 方案 B：取消在途解码（推荐，待可行性验证）

做法：**不改动任何画质档位**，仅让后端对已过期的解码请求提前退出。

```rust
// 解码循环中定期检查，过期即提前返回
if cancelled.load(Relaxed) { return Err(stale) }
```

**优势**：

- 前端 `coverMaxEdge`、`resourceKey`、registry、canvas 生命周期逻辑**一行都不用动**
- **无封面重入、无占位图**：取消只发生在已被丢弃的请求上，正在显示的封面永不受影响
- **零画质影响**

**待验证的前提**：`image` crate 的 `resize_exact`/Lanczos3 重采样能否在中间被打断。

- 若可插入检查点 → 收益最大化
- 若不可 → 退化为"解码前检查 + 解码后检查"，收益减小但仍能避免部分无用解码

**风险**：需改动 Rust，需重新编译（`cargo build` 数分钟）。未验证前不应动手。

### 方案 C：真正降低单次解码峰值（更根本，成本更高）

调整 hero 路径的重采样策略，例如：

- 对 hero 路径也启用预降采样，但把阈值从 8 倍放宽到合理比例（如目标尺寸 2 倍）
- 或先 `thumbnail_exact` 到目标 2 倍再 `resize_exact`

**收益**：直接作用于 4000px 封面的 190MB 工作缓冲。

**代价**：改变画质路径，需实测确认 1536 最终输出无明显劣化；且需要重新验证现有 `cover_pixels` 相关测试。

## 方案对比

| | A 拖动降档 | B 取消在途解码 | C 降低解码峰值 |
| --- | --- | --- | --- |
| 封面重入风险 | 有（已核实） | 无 | 无 |
| 占位图闪现 | 可能 | 无 | 无 |
| 画质影响 | 拖动时降级 | 无 | 需实测 |
| 改动范围 | 前端多处 | 后端为主 | 后端为主 |
| 峰值收益 | 高 | 中高 | 高 |
| 前提验证 | 不需要 | **需要** | 需画质实测 |

## 当前倾向

1. **优先验证方案 B 的可行性**：确认 `image` crate 重采样能否插入取消检查点。这是唯一同时满足"无前端风险 + 零画质影响"的路径。
2. 若 B 不可行，再评估方案 C，并配合真实画质对比。
3. **不采用方案 A**。

## 证据边界

- 500MB 为**用户现场观察值**，本仓库尚无该场景的同等精度采样（现有采样覆盖的是"仅播放"稳态）。
- 单次解码峰值（190–260MB）为**基于 `image` crate 行为的静态推算**，不是本机实测。要获得准确数值，应在 `decode_and_pack_with_strategy` 的 `resize_exact` 前后插入 `GetProcessMemoryInfo` 采样并跑一次连续拖动。
- 封面尺寸矩阵（1674 张 / 最大 4096×4096）为**本机实测**，可直接采信。
- 后端串行语义、预降采样阈值、前端资源上限（7/8/6/2/3）均为**代码核实**。

## 与现有事项的关系

- OPT-0016 的缩略图持久化改善了列表加载速度，同样不影响 hero 路径。
