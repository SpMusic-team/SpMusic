# OPT-0018 列表封面路径方案集成记录

根据用户确认，将通过正式往返对照的路径版 `3847bcc806665d8fd958f6b945dc22ff3577b038` 合入 develop，并与远端 `3550c3c` 的媒体库队列功能集成。后续诊断埋点和局部并发实验保留在各自的历史记录中。以下性能数据来自合入前固定版本的测试。

## 已改善的行为

- 列表封面通过受管 JPEG 和 asset 路径交给 WebView，减少常规加载时跨 IPC 传递裸像素及前端转码的工作。播放器大封面及失败恢复保留像素通道。
- 同一会话内来回拖动列表，回程的封面更早显示。全屏小卡片的 20 对正式对照中，整段视口存在未显示封面的时间配对中位减少 **225.5 ms**，18/20 对改善。回程各站松手后的补齐时间合计中位从 **387.5 ms 降到 25 ms**，20/20 对改善。去程没有明确差异。见[往返正式对照](../../test/opt-0018-ab-multistop-formal-2026-11-09.md)。
- 缩略图写盘后可在重启时复用。重启后捕获的 23 条目标请求全部命中已有 JPEG，未观察到源图解码、缩放或编码。其余目标缺少对应后端记录。见[磁盘持久化验证](../../test/opt-0018-disk-cache-persistence-2026-11-09.md)。
- 修复了歌单头图和菜单遗漏展示身份，以及 512 档故障恢复误走路径的问题。三个反例均通过，普通卡片、头图和菜单的 12 次原生故障注入均观察到恢复。见[P1 修复报告](../../test/opt-0018-p1-fix-verification-2026-11-08.md)。

## 集成所接受的不足

- 直接拖到本次会话尚未到达的位置时，另一组全屏高密度测试中，两个视图档位的全部补齐时间配对中位分别多 **256.5 ms** 和 **129.5 ms**，松手时未显示的封面也更多。这与多站往返路线的去程是不同操作，分别保留。见[全屏专项结果](../../test/opt-0018-fullscreen-drag-2026-11-09.md)。
- 预热后打开列表没有达到预设提速门槛。首次打开来源测试观察到新版慢约 **17.5 ms**，幅度低于预设退化门槛。见[首次打开来源结果](../../test/opt-0018-first-open-result-2026-11-08.md)。

## 后续待解决

- 继续验证首次到达与真回访在不同设备、列表入口及长期滚动下的表现。早期小歌单上的固定并发 2→4 实验未改善，已撤回。长歌单的后续自适应方案见下节。
- 核对侧栏 `LibraryCover` 的展示身份和坏图恢复，补齐实际恢复作业与原生请求的对应证据，以确认去重次数。
- 目前速度收益适用于本机、该曲库及全屏小卡片往返路线。大曲库、慢盘、高 DPI 和同条件 CPU/内存收益仍需专项验证。

## 合并后验证

- 合并冲突集中在卡片和全部歌曲视图。合并结果同时传递媒体库队列状态和封面展示身份。封面恢复测试夹具补齐了同步队列依赖，原有断言保留。
- 前端生产构建和 lint 通过。封面目标测试 126/126、独立 P1 反例 3/3、队列模型 3/3 通过。640 px 与 1280 px 下的队列浏览器交互测试均通过，浏览器测试使用模拟原生命令。
- Rust `cargo check --lib --locked` 通过，`cargo test --lib --locked` 为 398 通过、0 失败、10 跳过。合并结果中的 `src-tauri` 与 `3847bcc` 一致。
- 原生 WebView2 故障注入和 20 对拖动实测对应合入前的 `3847bcc` 产物。合并后的验证覆盖构建、自动化回归及浏览器交互，原生性能数据沿用固定版本的历史证据。

## 首次到达的自适应并发

播放列表封面起步时最多同时处理两项。独立的只读查询确认后端至少有三个解码名额时，该列表提升为三项，并立即检查待处理队列。名额不足、查询未返回或失败时，列表继续按两项处理。

基于 `735168a` 的 R1 候选在 400 首歌单、全屏 112 张落点的正式对照中，已落盘缩略图的整屏补齐时间配对中位缩短 **185 ms（10.9%）**，现场生成时缩短 **1195 ms（27.0%）**。两个场景各 20 对，候选均更快。真回访 10 对的配对中位缩短 32 ms，仍无法排除小幅退化。

低名额保持两项的证据来自隔离模拟。真实低核机器、原生切歌单和长时间滚动的资源占用仍待验证。上述性能数据来自合入前的 R1 候选。
