# 专辑库列表封面由像素 IPC 改为 asset 协议路径下发

> **状态更新（2026-11-08）**：本文记录第一轮实施。该轮已于 `71adeed` 回退，真实根因是前端取消谓词传反（详见 [OPT-0018-v2-result.md](./OPT-0018-v2-result.md) §2）。
> 重做版在 `feature/opt-0018-path-lane-v2` 完成并做了真机验证，完整实测数据、独立复核发现的缺陷、以及保留/回滚判定依据见 **[OPT-0018-v2-result.md](./OPT-0018-v2-result.md)**。
> 阅读本文时请注意：§5.2「预期收益」的倍数只是**单张载荷比**的估计，**不是端到端时延保证**；重做版实测显示端到端可见时延差异落在噪声带内。

> 核心判断：SpMusic 列表封面慢，**不是缺缓存，也不是缺并发**，而是**每张封面把 256 KiB 未压缩 RGBA 经 IPC 搬进 JS，再在主线程逐像素转成 BMP**。
> LyciaMusic 稳态下只传约 100 字节的**路径字符串**，由 WebView 走 asset 协议自己解码一张十几 KB 的 JPEG。
> 两者单张传输量相差约 2600 倍，且 SpMusic 额外多两次解码与一次主线程转码。

## 1. 问题描述

用户在实际使用中感知：LyciaMusic 的专辑页面封面加载速度明显快于 SpMusic。要求定位 LyciaMusic 的实现方式，并评估 SpMusic 的可优化空间。

本调查为**跨仓库静态代码对照**，未运行 benchmark。所有耗时数字为按代码结构推算的量级估计，非实测值。

## 2. 现状链路（SpMusic，改造前）

### 2.1 完整通路

```
AlbumLibraryPanel.tsx
  AlbumCard → collectionCover()  构造 kind='track-candidates' 的候选封面项
  AlbumCover → useCollectionCoverUrl(store, item)
        ↓
useAllSongsWindow.ts
  pump() 按优先级取出 desired 中的 key
  scheduleTrackThumbnail({ maxEdge: 256, windowGeneration })
        ↓
playlistCoverScheduler.ts
  MAX_CONCURRENT = 4 的优先级队列（priority 0/1/2）
  去重键：JSON.stringify([kind, clientId, windowGeneration, source, maxEdge])
        ↓
audioCommands.ts
  invoke<ArrayBuffer | Uint8Array>('audio_load_track_thumbnail')
        ↓  ← 二进制 IPC，返回裸像素
  parseCoverPixels() 零拷贝视图指向 ArrayBuffer 偏移 40
        ↓
playlistCoverPixels.ts
  playlistCoverImageFromPixels()  逐像素 RGBA→BGR、丢 alpha、上下翻转
  URL.createObjectURL(new Blob([encoded], { type: 'image/bmp' }))
        ↓
<img src="blob:...">
```

### 2.2 载荷量化

| 项目 | 数值 | 出处 |
| --- | --- | --- |
| SPXR 头 | 40 B | `cover_pixels.rs` `HEADER_LEN` |
| 单张 RGBA 像素 | 256 × 256 × 4 = 262,144 B | `pack_rgba`，`stride = width * 4` |
| 单张 IPC 总载荷 | **262,184 B ≈ 256 KiB** | 40 + 262,144 |
| 列表 maxEdge | 固定 256 | `useAllSongsWindow.ts:278/287/288` |
| 磁盘缩略图 | `{blake3}-256-t2-d1.spxr` = 44 + 262,184 B | `thumbnail_filename` |
| 磁盘缓存预算 | 8 GiB / 32768 文件 | `THUMBNAIL_CACHE_BYTES`、`THUMBNAIL_CACHE_FILES` |

> 预算校验：`8 GiB ÷ 262,228 ≈ 32,758`，与 `THUMBNAIL_CACHE_FILES = 32768` 吻合，说明整套预算就是按裸 RGBA 尺寸设定的。

### 2.3 关键：磁盘缩略图不是浏览器可解码格式

这是本次调查中**推翻了初始假设**的发现：

- 缩略图落盘格式是**自定义 `.spxr`**：44 字节 SPTC 头（`THUMBNAIL_DISK_MAGIC`、`THUMBNAIL_DISK_HEADER_LEN`）+ 内嵌 40 字节 SPXR 头 + **裸 RGBA 数据**。
- `cover_pixels.rs` 中所有 `ImageFormat::Jpeg` / `ImageFormat::Png` 写入**全部位于 `mod tests`（自第 2561 行起）**，是测试夹具，**不是生产代码**。
- 因此单张磁盘缩略图是 256 KiB 而非十几 KB，**`convertFileSrc` 指向 `.spxr` 时 WebView 无法渲染**。

**结论：不能简单地「把现有缩略图路径返回给前端」。必须新增一种 WebView 可解码的格式。**

### 2.4 其它耗时点

| 编号 | 问题 | 位置 | 量级 |
| --- | --- | --- | --- |
| P1 | 裸 RGBA 走 IPC | `audioCommands.ts` invoke 二进制通道 | 每张 256 KiB |
| P2 | JS 主线程逐像素转 BMP | `playlistCoverPixels.ts:32-42` | 65,536 次迭代 ≈ 1–3 ms/张，且同步阻塞 rAF |
| P3 | WebView 再解码一次 BMP | `<img src="blob:...">` | BMP 仍未压缩 |
| P4 | 前端并发 4 vs 后端许可 | `playlistCoverScheduler.ts:53` vs `cover_pixels.rs` `playlist_decode_permits` | 8 核实为 2 个许可，前端队列优先级在后端失效 |
| P5 | 缓存查找前需读完整原封面 | `load_playlist_cover_pixels_blocking_with_cache_path` | 冷启动隐藏成本（读原图 + blake3） |

> P4 说明：`playlist_decode_permits()` 为 `available_parallelism() / 4` clamp 到 `1..=4`。8 核 → 2，4 核 → 1，仅 ≥16 核才达到 4。

## 3. 对照组：LyciaMusic 的做法

### 3.1 数据通路

```
SongTable/Albums 可见性判定（IntersectionObserver / 虚拟切片）
  → preloadPriorityCovers(paths)
  → loadCoverInternal(path, 'thumbnail')
  → invoke('get_song_cover_thumbnail', { path })      ← 只回传字符串
  → Rust get_or_create_thumbnail → 返回磁盘绝对路径，并回写 DB
  → convertFileSrc(diskPath)
  → <img src="asset://localhost/...">                 ← WebView 原生解码 150px JPEG
```

### 3.2 决定性做法

| 编号 | 做法 | 出处 |
| --- | --- | --- |
| L1 | **缩略图路径持久化进 DB**，命中后完全不 invoke | `covers.rs:425-433`；前端 `primeCoverPath`，单测锁定「uses a primed thumbnail path without invoking the backend」 |
| L2 | **按封面字节 SHA-256 命名**，同专辑 N 首曲目共享一份缩略图与一次解码 | `covers.rs:127-131`、`.ref` alias `:267-271` |
| L3 | asset protocol 直接读文件 | `useCoverCache.ts:296`；`tauri.conf.json` CSP `img-src asset:` |
| L4 | 缩略图 150px **JPEG**（压缩，约十几 KB） | `covers.rs:311`，`FilterType::Triangle` |
| L5 | 前台并发 4 / 后台并发 1（`requestIdleCallback`），Rust `Semaphore(2)` | `useCoverCache.ts:13-14`、`music/types.rs:6` |
| L6 | 视口快照（72 项）+ 滚动位置记忆，消除返回白闪 | `SongTable.vue:248-289`、`useListScrollMemory.ts` |

> 注意：LyciaMusic **同样不预生成缩略图**，扫描入库时 `cover_thumb_path` 置 `None`（`scanner/parser.rs:564`），扫描期还显式关闭封面读取（`tags.rs:41-43`）。**所以「预热」不是它更快的原因。**

### 3.3 对照表

| 环节 | LyciaMusic | SpMusic（改造前） |
| --- | --- | --- |
| Rust → JS | 路径字符串 ~100 B | 裸像素 262,184 B |
| 磁盘缩略图 | 150px JPEG，约十几 KB | 256px 裸 RGBA `.spxr`，256 KiB |
| 解码方 | WebView 原生 | Rust + JS 转码 + WebView |
| JS 侧处理 | 无 | 逐像素转 BMP |
| DOM | `<img loading="lazy" decoding="async">` | `<img src="blob:...">` |

## 4. 优点澄清（为什么像素通道不能整体删除）

| 判断 | 结论 |
| --- | --- |
| 传像素更清晰？ | **否**。清晰度取决于像素尺寸，与传输形式无关。SpMusic 256px 确实比 Lycia 150px 更清晰，但那是**尺寸选择**带来的。 |
| 像素通道只为网络流服务？ | **否**。`isStreamSource` 在 `useAllSongsWindow.ts:276` 是**跳过**网络流的，主体仍服务本地文件。 |
| 有没有做封面取色？ | **没有**。Rust 端搜 `dominant_color`/`palette` 零结果；JS 端 `getImageData` 仅 `useLibraryArtwork.ts:72` 用于缩略图转换。界面上的「封面氛围」`cover-ambient` 是用封面图本身做 CSS 模糊铺底（`shell.css:68`），**不提取主色**。 |
| 像素通道真正的不可替代价值 | ① 播放器大封面 1024/1536px 需裸像素 `putImageData` 写 canvas；② EXIF 方向归一（`cover_pixels.rs:2363-2366`）与格式兼容，WebView 处理不可靠；③ 隐私边界：scope 仅 `$CACHE/**`，不必像 Lycia 那样开到 `"**"`；④ 为无本地路径的源保留统一抽象。 |

**因此结论是「按尺寸分层」而非「整体替换」。**

## 5. 方案

### 5.1 分层规则

```
maxEdge ≤ 512   →  生成 JPEG，返回磁盘路径，前端 convertFileSrc   （列表 / 侧边栏 / 歌单卡）
maxEdge ≥ 1024  →  保持 SPXR 裸像素 + 二进制 IPC                  （播放器 / 背景 / 拖拽投影）
```

依据：`ALLOWED_PLAYLIST_MAX_EDGES = [128, 256, 512]`（列表用）与 `ALLOWED_MAX_EDGES` 的 1024/1536（播放器用，`useArtworkVisualResource.ts:519-520`）天然分离。

### 5.2 预期收益

| 指标 | 改造前 | 改造后 |
| --- | --- | --- |
| 单张 IPC | 256 KiB 像素 | 约 100 B 路径 |
| 磁盘单张 | 256 KiB | 约 15 KiB JPEG |
| 磁盘总量 | 8 GiB 预算 | 约 0.5 GB（省约 16 倍） |
| JS 主线程 | 逐像素转码 1–3 ms/张 | 无 |
| 解码次数 | 3（Rust + JS + WebView） | 1（仅 WebView） |

### 5.3 功能影响评估

**不受影响：**

- EXIF 方向归一、格式兼容：仍在 Rust 解码阶段完成，且在编码 JPEG **之前**，结果一致。
- 隐私：asset URL 指向 `$CACHE` 下的缩略图，**不需要**把 scope 放宽到 `"**"`。
- 网络流：本就被 `isStreamSource` 跳过。
- 回退能力：像素通道完整保留。

**需要留意：**

- 首次生成多一次 JPEG 编码（约 1–2 ms），之后永久命中。
- 需提升缓存格式版本号，使旧 `.spxr` 失效重建。
- asset 方式绕过后端 `Semaphore(2)`，解码改由 WebView 承担（Lycia 即如此，实践中可行，但属行为变化）。
- `useAllSongsWindow.ts` 的 `sweep()` 依赖扫描 `<img>` 回收 object URL，切到 asset URL 后逻辑需相应调整，且不可误伤播放器仍在使用的 blob URL。

## 6. 回滚方案

本次改动置于独立分支 `feature/album-cover-asset-pipeline`，不触碰 `develop`。

- **构建级回滚**：直接切回 `develop` 重新打包即可，`main` 与 `develop` 全程未被修改。
- **运行级回退开关**：前端优先使用新的路径命令；若返回空或报错，**自动回落到现有像素通道**，保证最坏情况不劣于改造前。
- **缓存级回滚**：新格式使用独立文件后缀与独立版本号，旧 `.spxr` 缓存不受破坏；删除旧分支后可直接按原逻辑继续使用。

## 7. 验证计划（真机实测）

由用户在 Windows 上打包 release 实测，重点观察：

1. 专辑库首屏打开耗时（快/慢两态对比）。
2. 快速滚动时的掉帧与卡顿感。
3. 二次打开同一专辑（应命中磁盘缓存，几乎瞬时）。
4. 播放器大封面、背景氛围、拖拽投影是否正常（应完全不受影响）。
5. 内存占用（WebView renderer 与 app.exe 分别观察）。
6. 无封面 / 损坏封面 / 网络流曲目的占位与回退表现。

**判定标准**：体感明显改善且功能无回退则保留；若有任一功能异常或无明显改善，直接回滚分支。
