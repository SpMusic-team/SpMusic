# 第四轮：PCM 接缝闭环、foobaka 数据层与第三轮勘误

本轮用**自建的 WASAPI 环回录制器**打通了第三轮判定为「不可完成」的 A1，
并对 B（foobaka）做了不依赖界面的**数据层对照**。

## 零、最重要的三个结论

1. **A1 闭合，且「不可能」的判定是错的**：WASAPI 环回捕获不依赖环回端点设备，
   自建录制器即可。foobar2000 的 **CUE 分轨接缝逐样本零误差**。
2. **B 用的是 `playlists-v1.4`，不是 `v2.0`**：这是版本性结构差异，
   解释了第三轮「B 有 props 记录却找不到对应 sqlite」的困惑。
3. **`52655132-…` 不是 autoplaylist client GUID**，
   而是 v1.4 `index.dat` 属性表里的**属性类型 GUID**。第三轮的一次阴性实验要重写。

## 一、A1：PCM 接缝（本轮闭合）

### 1.1 推翻第三轮的判定

| 第三轮结论 | 本轮实测 |
| --- | --- |
| 「系统无环回捕获端点 → A1 不可完成」 | **不成立**：`AUDCLNT_STREAMFLAGS_LOOPBACK` 是系统混音器能力，与设备无关 |
| 「需要换带 `--enable-wasapi` 的 ffmpeg」 | **不需要**：.NET COM 互操作直接调 WASAPI |
| 「需要启用立体声混音」 | **不需要** |

第三轮的三条**事实观察**全部属实（确无环回设备、ffmpeg 确无 wasapi、dshow 只列麦克风），
**错的是推论**——把「ffmpeg 走不通」当成了「本机做不到」。

### 1.2 判定「接缝无缝」的依据

| 用例 | 最大误差 | 失配帧 | 解释 |
| --- | ---: | ---: | --- |
| CUE 两分轨 | **0** | **0 / 480000** | 逐样本完全一致 |
| 双文件 A→B | 246 | 6 / 480000 | 单帧量化抖动，非断层 |

**能量证据**：接缝窗口 RMS 从 2992.9 → **2853.5** → 2872.7，**无塌陷、无延迟、无衰减包络**。
**零帧比例 0.25%（1 帧）**，且该帧是波形过零点。

### 1.3 证据边界（必须写清）

| 能断言 | 不能断言 |
| --- | --- |
| PCM 到达系统混音器时无丢样/重样/插静音 | **DAC 端的实际输出** |
| CUE 分轨在应用侧是连续的 | **是否 bit-perfect**：共享混音器有独立增益（α≈0.127）与 32f→16i 转换 |
| 双文件续播无静音插入 | 独占模式下更优（未测） |

## 二、B（foobaka）数据层

### 2.1 结构差异本质是「代际」而非「配置」

| 维度 | A′ 2.24.6 | B 1.7.12 |
| --- | --- | --- |
| 播放列表 | `playlists-v2.0` / `index.txt` / `.fplite` / `-props.sqlite` | `playlists-v1.4` / `index.dat` / `.fpl` |
| 属性存储 | 独立 sqlite | **内联在 index.dat** |
| 曲库目录 | `library-v2.0\folders`（相对路径） | `library\folders`（**绝对路径**） |

**为什么两者同为 2.24.6 内核却有此差异**：B 是从 **foobaka 1.6.10** 一路升级来的**已有 profile**，
沿用了旧代目录；A′ 是本轮**新建**的 profile，直接生成 v2.0。
**目录格式是 profile 代际的产物，不是内核版本的能力差异。**

> 这对对照实验是**重大方法学提醒**：
> 拿 A′ 与 B 做「格式」对照时，差异可能来自 profile 代际而非产品设计。
> **必须显式区分**「内核行为」「profile 代际」「组件配置」三者。

### 2.1b B 渲染失败的根因：一个不可解析的面板类型

`三页面.fcl` 声明 11 个面板类型，扫描 B 的全部 67 个 DLL 后：

| 结果 | 数量 |
| --- | ---: |
| 能解析到具体组件 | **10** |
| **无法解析** | **1** |

无法解析的是 `4532EC89-C567-4267-B33A-0C154B6F0105`（**面板栈分离器**）。
值得注意的是 `foo_uie_panel_splitter.dll` **确实装着**（128 KB），
但**它不提供这个 GUID**（三种字节排列均未命中）。

**机制**：Columns UI 与 DUI 的关键差异是**没有回退布局**——
遇到不可解析的面板类型就中止整个渲染，于是窗口停在初始化尺寸、内容空白，进程仍存活。
这解释了第三轮「进程 133 线程、Responding=True，但 1248×162 全白」的现象。

> **对 SpMusic 的直接含义**：布局/配置加载必须有一个显式的
> **「依赖不可解析」状态**，让外壳保持可用并提示缺什么，
> 而不是整块渲染失败退化成白屏。这是本轮最可落地的一条产品教训。

### 2.1c B 界面不稳定的真因：脚本宿主与 COM 自动化

B 的安装目录自带 **35 份崩溃报告**（2024-12 ~ 2025-07，原作者环境）。
崩溃模块分布是决定性的：

| 模块 | 次数 |
| --- | ---: |
| `OLEAUT32`（COM 自动化） | **13** |
| `foo_uie_wsh_panel_mod_plus`（脚本面板宿主） | **12** |
| `USER32` | 5 |
| `foo_uie_eslyric` | 1（`entry=>app_mainloop`，启动即崩） |

**`OLEAUT32` + `foo_uie_wsh_panel_mod_plus` 合计 25/35**，
占绝对多数。异常码 `C0000005h`（Access violation）33/35。
**全部 35 份都提到 `dynwrap`**，与 `dynwrapx.dll` 的注册强相关。

**这改变了归因**：

| 第三轮 | 第四轮 |
| --- | --- |
| 「Columns UI 布局渲染失败」 | **脚本面板宿主 + COM 自动化持续崩溃**，布局只是表象 |
| 「注册脚本已成功，排除注册问题」 | 实测 `dynwrapx.dll` 的 COM **未注册**（`AutoItX3` 已注册） |

> **对 SpMusic 的可落地教训**：B 的脆弱性集中在**进程内脚本宿主**。
> 若 SpMusic 未来支持用户脚本，必须做成**隔离进程 + 超时 + 崩溃不拖垮外壳**，
> 而不是像 WSH 面板这样把脚本引擎跑在主进程里。

### 2.1d `.fcl` 不是二进制布局，是扁平配置节点序列

第二轮把 `.fcl` 的 42,899 B 记为「未解」。本轮解开：**它不是布局几何**，
而是 **636 个「长度前缀 + UTF-8 文本」节点**。

| 组成 | 数量 |
| --- | ---: |
| 面板类型表 | 11 |
| 配置节点 | **636** |
| 配色条目（`Color.<角色>` + `RGB(...)`） | **64** |
| 内嵌 WSH 脚本块 | **15** |
| 配置节 | 12（`Layout`/`Colours`/`Columns`/`Titles`/`Groups`/…） |

**这改变了对「主题」的理解**：foobaka 的主题 = **面板类型表 + 键值配置 + 内嵌脚本**。
配色不是编译进二进制的常量，而是 `Color.Selected.panel = RGB(245,245,245)`
这种**显式可寻的键值对**。

> **对 SpMusic 的直接含义**：主题/布局的配置层应当是**显式键值模型**，
> 每个颜色、每个列定义都是独立可寻、可差分的条目。
> 这为候选卡 P2-D（配色先行层）提供了**格式层面的可行性依据**——
> 不需要复刻二进制容器，只需要复刻「键 → 值」这层语义。

### 2.1e 为什么缺一个面板类型就整树崩塌

上一轮定位到 B 的 `.fcl` 引用了 1 个无法解析的面板类型 `4532EC89-…`。
本轮解出面板树拓扑，**填补了「缺类型 → 白屏」之间的机制空白**。

**实例记录格式**（实测）：

```
u32 parent_index | GUID type | u32 nchild | （可选）u32 len + UTF-8 实例名
```

**`4532EC89` 是布局骨架，不是叶子面板**：

| 指标 | 值 |
| --- | ---: |
| 在 `.fcl` 中出现次数 | **21** |
| 其中作为容器（`nchild > 0`） | **18** |
| 作为叶子 | 3 |
| 承载的实例名 | `左` / `右` / `播放` / `列表歌词` / `PL` / `ES` |

对比其它类型：`WSH 面板加强版` 16 次、`Horizontal splitter` 4 次、其余 7 种各 2 次。

**完整因果链**：

```
组件缺失 → 该面板类型无法解析
        → 18 个容器节点全部无法实例化
        → 整棵树没有骨架
        → 进程存活但无任何可渲染层级 → 白屏
```

> **对 SpMusic 的关键教训**：**容器类型与叶子类型必须有不同级别的失败策略**。
> 叶子面板失败可以降级成占位符；**容器失败必须能回退到「扁平布局」**，
> 否则整个界面直接不可用。这是本轮最具体、最可落地的一条工程结论。

### 2.1f `.fcl` 记录语义完全解出（本轮）

上一轮解出「636 个长度前缀节点」，但节点之间怎么组织还不清楚。本轮解出**记录的完整格式与种类枚举**。

**单条记录格式**：

```
u32 type | u32 size | GUID(16) | u32 namelen | UTF-8 name | [payload]
```

**type 是记录种类枚举**（47 条实记录的统计）：

> **样本量限定**：这 47 条统计自 **B（foobaka）的单个 `.fcl` 文件**
> （`三页面.fcl`，仓库里另有 1 份是它的副本，**不是独立样本**）。
> `type` 枚举的**取值集合**在此文件内完整，但**各类别的典型占比不可外推**到其他布局。

| type | 含义 | 条数 | 样例 |
| ---: | --- | ---: | --- |
| **0** | 面板实例声明 | 14 | `4532EC89` + `'左'`；`3C2C4BDC` + `'1play'` |
| **1** | 该实例的属性块 | 13 | `3C2C4BDC` + `'WSH 面板加强版'` / `'ctl'` |
| 2 | 全局配置节 | 1 | `'Misc fonts'` |
| **4** | 全局配置 | 6 | `'Columns'` / `'Layout'` / `'Colours'` / `'Titles'` / `'Fonts (unified)'` |
| **5** | 尺寸/数值记录 | 13 | GUID 恒为 `00000005-…`，name 恒为 `'0'` |

**嵌套关系实拍**（每个页面内部都重复这个模式）：

```
type=0  4532EC89  "左"        ← 声明 splitter 实例
type=0  3C2C4BDC  "1play"     ← 声明 WSH 实例（splitter 的子）
type=1  3C2C4BDC  "WSH 面板加强版"  ← 该实例的属性块
type=1  3C2C4BDC  "ctl"       ← 该实例的控件配置
type=5  00000005  "0"         ← 尺寸记录
```

**这补上了「缺失类型为何整树崩塌」的最后一环**：

| 证据 | 值 |
| --- | --- |
| `4532EC89` 作为 **type=0（实例声明）** 出现 | **6 次** |
| `4532EC89` 作为 **type=1（属性块）** 出现 | **3 次** |
| 合计 | **9 条记录** |

它是这份布局里**最活跃的容器类型**。缺少它时，9 条记录全部无法解析，
而 `3C2C4BDC`（WSH）等子面板都挂在它下面 —— 于是整棵树失去根，白屏。

> **三个页面的结构完全同构**：`半屏歌词页` / `三页面` 等各自都有一套
> `左` / `1play` / `右` / `播放` / `PL` 的组合，因此缺失 `4532EC89` 会导致**全部页面**一起失效，
> 不只是某一个页面。这解释了第三轮观察到「整窗全白」而非「部分面板空白」。
### 2.1g DUI 有「部分加载」回退，Columns UI 没有（本轮决定性证据）

第 4 轮说「Columns UI 不像 DUI 那样有回退布局」——本轮从两个组件的字符串表**直接证实**了。

**DUI（`foo_ui_std.dll`, 1,734,656 B）** 有一条文案：

```
The layout was loaded partially because the following required components could not be found: 
```

这明确说明 DUI 实现了**部分加载**：缺组件时保留能加载的那部分，
并把缺失清单列给用户看。

**Columns UI（`foo_ui_columns.dll`, 3,923,456 B）** 则有专门的异常类：

```
exception_missing_panel@fcl@cui
exception_fcl_dependentpanelmissing
```

配套的用户可见文案聚成一组，呈现**严重度递增**的多档报错：

| 文案 | 含义 |
| --- | --- |
| `Unrecognised file header` | 不是 .fcl 文件 |
| `Missing dependent panel(s)` | 布局引用的面板类型缺失 |
| `Bug check: panels missing` | 内部一致性检查失败 |
| `Need a newer version of Columns UI` | 版本太旧 |

**但没有「部分加载」这一条。**

### 2.1h 两者对比

| 维度 | DUI | Columns UI |
| --- | --- | --- |
| 缺组件时的行为 | **部分加载 + 列出缺失项** | **抛异常，无恢复路径** |
| 异常类 | — | `exception_missing_panel` 等 2 个 |
| 结果 | 界面仍可用，只是少了某块 | **整树无法实例化 → 白屏** |

**这补齐了 B 白屏的完整因果链**：

```
B 用 Columns UI
  → .fcl 引用了 1 个本机缺失的面板类型（4532EC89）
  → 触发 exception_missing_panel
  → 该 UI 无「部分加载」路径
  → 整树无法实例化
  → 窗口白屏，但进程存活（无崩溃）
```

> **对 SpMusic 最具体的一条工程结论**：
> **「部分加载 + 列出缺失项」比「整块失败」明显更好**，DUI 的实现可直接借鉴。
> 具体做法：布局加载时逐项尝试实例化，失败项记为占位并累积缺失清单，
> 最后一次性提示用户（DUI 用了 `the following required components could not be found:` 这样的引导语）。
### 2.1i `.fcl` 头部结构修正与面板实例精确清点（第 27 轮）

> **⚠ 修正两处旧记录**：
> 1. 第 6 轮把头部 `[0x1C]` 误读为「类型数」——实际 **`[0x18]` 是类型数，`[0x1C]` 是 16 字节 GUID**
> 2. 旧记录的面板实例数（21 / 9）**不是最终答案**——正确值是 **22**

**修正后的头部结构**：

```
[0x00] 16 B  magic F3DFAA9F1AE58B4AB4A3D209A36AB301
[0x10] u32   2
[0x14] u32   0
[0x18] u32   11        面板类型数
[0x1C] 16 B  GUID 8FA0BC24-882A-4FFF-8A3B-215EA7FBD07F
[0x2C] 记录流起点
```

**记录流格式**：`u32 长度 + UTF-8 文本`

**验证**：解析出 **634 条记录**，结束于 `0xA912` = **43,282**，与文件长度**精确相等**（精确 EOF）。
这比旧记录的「636 个节点」更可信——因为它是**从正确头部起步、无跳字节、精确收尾**的解析。

**11 种面板类型与实例数**：

| 面板类型 | 实例数 |
| --- | ---: |
| **WSH 面板加强版** | **7** |
| **ESLyric** | **4** |
| **面板栈分离器** | **3** |
| Horizontal splitter / Menu / DSP preset / Filter search / Playback order / Seekbar / Spectrum analyser / Buttons | 各 1 |
| **合计** | **22** |

> **`面板栈分离器`（`4532EC89`）只有 3 个实例，不是 9 个也不是 21 个。**
> 之前的数字混淆了「类型名出现次数」与「配置记录数」。
> 但**它仍是容器**：3 个实例撑起整个多页面布局，缺失时仍是骨架性失败——
> 结论方向不变，只是实例计数被纠正。
### 2.1j **重大修正：GUID 与面板名的对应关系整体错位了一格**（第 28 轮）

> **这是本研究最需要知道的一处修正。**
> 此前多轮反复讨论的「`4532EC89` 是面板栈分离器」——**这个对应是错的**。

**正确的方法**：`.fcl` 头部 `[0x2C]` 起是类型表，每条是

```
u32 名称长度 + UTF-8 名称 + 16 字节 GUID
```

**逐条配对得到的权威映射**：

| 面板名 | GUID |
| --- | --- |
| **Horizontal splitter**（水平分隔器） | **`4532EC89-C567-4267-B33A-0C154B6F0105`** |
| **面板栈分离器** | **`3C2C4BDC-D387-44E9-A2A8-EAAEADCA14CE`** |
| **WSH 面板加强版** | `547ABB10-D8AC-4C39-9F8B-9C7AF989443D` |
| ESLyric | `76E6DB50-0DE3-4F30-A7E4-93FD628B1401` |
| Menu | `9BD325A4-B2E6-47AD-9B54-8DA35F427849` |
| DSP preset | `6E3B8B17-AEBD-40D2-A10F-9D3ACF74F091` |
| Filter search | `ABA09E7E-9C95-443E-BDFC-049D66B324A0` |
| Playback order | `678FE380-ABBB-4C72-A0B3-72E769671125` |
| Seekbar | `D947777C-94C7-409A-B02C-9B0EB9E374FA` |
| Spectrum analyser | `D8E65660-64ED-42E7-850B-31D828C25294` |

### 之前错在哪

| 之前认为 | 实际是 |
| --- | --- |
| `4532EC89` = 面板栈分离器 | **`4532EC89` = Horizontal splitter** |
| `3C2C4BDC` = WSH 面板加强版 | **`3C2C4BDC` = 面板栈分离器** |
| （未识别） | `547ABB10` = WSH 面板加强版 |

**结论方向不变，但名字全错位**：

- 缺失的那个类型**确实是布局骨架**（它是容器，有 3 个实例撑起多页面）
- 但它的**名字是 `Horizontal splitter`（水平分隔器）**，不是「面板栈分离器」
- 而真正的「面板栈分离器」是 `3C2C4BDC`

> **为什么之前会错**：早期只看到 GUID 出现在特定偏移附近，
> 没有做「名字紧跟 GUID」的逐条配对，靠上下文就近猜测，于是整体错位。
> **本轮的方法**（严格按 `u32 len + name + 16B GUID` 逐条走）才有权威性。
### 2.1k **「面板数量」有三个层级，必须分清**（第 29 轮）

此前多轮出现过 21 / 22 / 9 / 3 等互相矛盾的数字。**根因是混用了三个不同层级。**

| 层级 | 位置 | 数量 | 含义 |
| --- | --- | ---: | --- |
| **1. 类型定义表** | `0x2C` – `0x18F` | **10** | 类型声明（**不是实例**） |
| **2. 实例声明** | `≥ 0x18F` 记录流 | **11** | 真正的面板实例 |
| **3. GUID 引用** | 配置块内 | **45** | 类型引用（一实例可多次引用） |

**权威答案（针对 `三页面.fcl`）**：

```
面板实例数：11
```

另外 7 种类型**定义但未使用**（Menu / DSP preset / Filter search /

### 层级 1：类型定义表（10 条）

格式：`u32 名称长度 + UTF-8 名称 + 16 字节 GUID`

### 层级 3：GUID 引用分布（45 次）

### 2.1l **面板父子关系已解出：完整树结构**（第 30 轮）

**编码方式**：每个面板实例的结构是

```
GUID(16 B, 父容器类型) + u32 名称长度 + UTF-8 类型名 + 配置块
```

**决定性证据**：11 个实例中，**每一个**声明前恰好 16 字节处都是**一个 GUID 引用**，
**距离恒为 16**，无一例外。这个前置 GUID 就是**该实例所属的父容器类型**。

### 还原出的完整树

```
Horizontal splitter  (根, 4532EC89)
  ├─ 面板栈分离器 #1  (0x034A5, 3C2C4BDC)
  └─ 面板栈分离器 #2  (0x05EDE, 3C2C4BDC)
       │
       └─ WSH 面板加强版 ×6  (547ABB10)
            │
            └─ ESLyric ×3   (76E6DB50)
```

| 类型 | 实例数 | 层级 |
| --- | ---: | --- |
| Horizontal splitter | **1** | **根** |
| 面板栈分离器 | 2 | 第二层（容器） |
| WSH 面板加强版 | 6 | 第三层（容器） |
| ESLyric | 3 | 叶子 |
| **合计** | **11** | — |

### 这解释了「缺一个类型就整树崩塌」的**精确机制**

| 缺失类型 | 后果 | 原因 |
| --- | --- | --- |
| **Horizontal splitter** | **整树全毁** | 唯一根，其余 10 个实例**全部间接依赖**它 |
| 面板栈分离器 | 两个分支全毁 | 6 个 WSH + 3 个 ESLyric 在其下 |
| WSH 面板加强版 | 部分毁 | 只影响其下的 ESLyric |
| ESLyric | **局部** | 叶子，不影响兄弟或上层 |

> **这比之前「它是骨架」的说法精确得多**：
> 之前只知道 `4532EC89` 缺失会白屏，现在知道**为什么**——
> 它是树的唯一根，删掉后没有入口，其余实例全部成为孤儿。
### 2.1m **三个 Tab 页的真实名称，与「整窗白屏」的最终解释**（第 31 轮）

文件名 `三页面.fcl` 里的「三页面」到底是哪三个？**本轮找到了**。

| 序 | 文件偏移 | 页面名 |
| ---: | --- | --- |
| 1 | `0x02251` | **半屏歌词页** |
| 2 | `0x04A43` | **全屏歌词页** |
| 3 | `0x07271` | **嵌入歌词页** |

**结构**：每个 Tab 页 = `u32 长度 + UTF-8 页面名` + 该页的根实例（`4532EC89` 类型的 GUID）。

### 这补上了「整窗白屏」的最后一环

第 30 轮我说「H-Split 是唯一根」——**这个说法不够精确**。
实际情况是：**每个 Tab 页各有一个 H-Split 根**，三个页面就有三个根，
但它们**都是 `4532EC89` 这同一个类型**。

所以缺失该类型时：

```
半屏歌词页 -> 无根 -> 无法渲染
全屏歌词页 -> 无根 -> 无法渲染
嵌入歌词页 -> 无根 -> 无法渲染
                => 整个窗口没有任何可显示内容 = 白屏
```

**这彻底解释了为什么是「整窗白屏」而不是「部分空白」**——
三个 Tab 页同时失效，窗口里一个可渲染的页面都没有了。

> **第 30 轮 vs 第 31 轮的差异**：
> - 第 30 轮：「H-Split 是唯一的根」（暗示只有一个根实例）
> - 第 31 轮：「每个 Tab 页各有一个 H-Split 根」（精确）
>
> 结论方向一致，但机制描述被修正得更准确了。

### 2.2 `52655132-…` 的正确定位

```
           → 52655132-8F57-4C56-9AEE-17525C679A5D   ← 属性类型 GUID
```

**不是** autoplaylist 的 client GUID，**不是** v2.0 `props` 表的 key。

### 2.3 播放统计走索引表，不走主表列

B 有 1,829 条曲目、装了 `foo_playcount`，但主表五个统计列**全空**；
唯一有数据的索引表是 `C653739F`（1,829 行）。

**结论**：foobar2000 的播放统计在 **`metadb_index_<GUID>` + `_data` 独立索引表**里，
主表的 `playCount`/`rating`/`lastPlayed`/`dateAdded`/`firstPlayed` 是**结构预留、实际未启用**。

**对 SpMusic 的含义**：仿统计模型应仿「独立索引表 + 64 bit 哈希键 + filename 主键」，
**不是**「主表加五列」。且 filename 主键带**子轨前缀**（`0+`/`1+`/`2+`），
天然区分 CUE 分轨——这正是 SpMusic 统计键设计需要吸收的一点。

## 四、ReplayGain 四值字段：确认是哨兵值，不是数据

`metadb.info` 的 `[8:24]` 是 4 个 float。第三轮记为「占位 `-1000`/`-1`」，
本轮在 **400 个真实样本**上验证：

| 位置 | 唯一取值 | 出现 |
| --- | ---: | ---: |
| `[0]` | **-1000.000000** | 400/400 |
| `[1]` | **-1000.000000** | 400/400 |
| `[2]` | **-1.000000** | 400/400 |
| `[3]` | **-1.000000** | 400/400 |

**零例外**。所以这四个 float 是**「未扫描」的哨兵**，不是增益数据：

- `[0]`/`[1]` 应为 Track/Album **增益**（单位 dB），未扫描时 `-1000`
- `[2]`/`[3]` 应为 Track/Album **峰值**（线性），未扫描时 `-1`

> **对 SpMusic 的含义**：这个字段布局可以照抄——「4 个 float + 明确的未设置哨兵」
> 比「可空列 + 额外状态位」更紧凑，且天然区分「未扫描」与「扫描结果为 0 dB」。
> 注意哨兵值要选**不可能合法出现的值**（-1000 dB 与 -1 线性峰值都满足）。

## 五、回到 SpMusic：两项只读代码核查

### 5.1 主题/布局加载：SpMusic 已经是逐字段降级，风险低

核查 `src/features/appearance/model/appearanceThemeCodec.ts`（37,798 B）：

| 指标 | 值 |
| --- | ---: |
| `fallback` 出现 | **126** |
| `warnings.push` | **19** |
| `try/catch` | 2 |
| **`throw` 语句** | **0** |

解码入口 `deserializeAppearanceTheme()` 的**每一个失败分支**都是：

```ts
return { ok: false, appearance: safeFallback, error: '…' }
```

即：**任何输入都返回一份可用的默认外观 + 明确的错误原因**，从不抛异常、从不返回空壳。
未知键通过 `reportUnknownKeys()` 收集进 `warnings`，不拒绝整份文档。

**与 foobaka 的对照**：

| 维度 | SpMusic | foobaka |
| --- | --- | --- |
| 配置格式 | 扁平 `AppearancePreset` | 可嵌套面板树 |
| 失败策略 | **逐字段降级 + 累积 warning** | **全有或全无** |
| 单个组件缺失的后果 | 该字段用默认值 | **整树失效 → 白屏** |
| 存在 `throw` | 0 | — |

**结论**：SpMusic 当前**不存在**「容器失败即整树崩塌」这个风险，因为它的主题模型里
根本没有可嵌套的容器层级。这既是安全性的来源，也说明 SpMusic 目前**不支持**等价的自定义布局树。

> **若未来引入可嵌套布局**，必须复用现有 codec 的 per-field fallback 范式：
> 容器不可解析时降级为**扁平布局**，而不是拒绝渲染。

### 5.2 查询能力：SpMusic 只有 `HAS` 语义，没有 `IS`

核查 `src/features/player/model/librarySearch.ts`（47 行）：

```ts
const needle = query.trim().toLocaleLowerCase()
const matches = (...text) => text.some(v => String(v ?? '').toLocaleLowerCase().includes(needle))
```

**这是大小写不敏感的子串匹配**，正好等价于 foobar 的 `HAS`：

| 语义 | foobar | SpMusic 现状 |
| --- | --- | --- |
| 子串包含、不分大小写 | `HAS` | **✓ 已是此语义** |
| 整值相等、不分大小写 | `IS` | **✗ 不存在** |
| 通配符 `*` `?` | `IS` 支持 | ✗ |
| 布尔组合 `AND`/`OR`/`NOT` | ✓ | ✗（仅单一关键词） |
| 字段限定（`ARTIST IS …`） | ✓ | ✗（跨字段模糊匹配） |

**这意味着**：SpMusic 若要实现类 foobar 查询语法，`HAS` 那一半**已经就绪**；
需要新增的是**字段限定 + 整值比较（`IS`）+ 通配符 + 布尔组合**。

> 第三轮实测出的反直觉点在这里变得更有意义：**`IS` 不是 `HAS` 的子集**——
> 它在多值字段上的行为与 `HAS` 完全不同（`HAS Bystander` 命中、`IS Bystander` 不命中）。
> 所以「先有子串、再补整值」不是简单的开关，而是**两套并行语义**，必须分别设计。

## 八、两条方法学教训

### 8.1 对照物必须是有效的

我曾判断「136 B 定义不足以决定 autoplaylist 成员」，并把一个**已被清空的**
`All Music`（0 行）当作参照。事实相反：新建的合成列表成功求值出全部 20 条。

**教训**：做否定性判断前，先确认参照物本身处于预期状态。

### 8.2 判据必须落在可分辨的量级上

最初想在 24-bit 最低位埋标记来判断链路精度。±1（24-bit 刻度）
只相当于 0.0039 个 16-bit LSB——**低于可分辨能力，任何链路都会丢弃它**，
这个实验设计**证明不了任何事**。

**教训**：设计判据时先算清楚它在目标分辨率下等价于多少 LSB。

## 九、对 SpMusic 的直接含义

1. **gapless 验收可以做成硬判据**：用「预转采样率 → 环回捕获 → 逐帧对齐 → 归零失配数」
   这套流程，SpMusic 的续播实现也能被同样客观地验证。**失配帧数 = 0 是可达到的**。
2. **统计模型应仿独立索引表**，而不是主表加列；主键建议「子轨索引 + 完整路径」。
