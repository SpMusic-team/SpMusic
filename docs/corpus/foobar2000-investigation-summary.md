# foobar2000 / foobaka 逆向研究总结

> 本文汇总 36 轮的工作，给出**结论清单、证据索引、以及明确的能力边界**。
> 目标读者：接手的人。
>
> **⚠ 引用任何结论前，先看** [证据强度分级](foobar2000-evidence-index.md#零之二证据强度分级先看这个)：
> 本研究的结论可信度**差异很大**——只有 `.fth` 那套经过 69–128 个真实样本验证，
> 其余大多建立在 1–4 个样本上。

## 零、全局结论

| 问题 | 答案 | 强度 |
| --- | --- | --- |
| foobaka 的界面为什么打不开？ | **进程内脚本宿主（WSH）+ COM 自动化持续崩溃**，不是布局问题 | **强**（35 份崩溃报告） |
| 缺一个面板类型为何整树崩塌？ | 缺失的是**布局骨架**（21 个实例中 18 个是容器），不是叶子 | **中**（仅 1 个 `.fcl` 样本） |
| `IS` 和 `HAS` 有什么不同？ | **并行语义**，不是包含关系；`IS` 实现比 `HAS` 重一倍 | **强**（反汇编 + 实测） |
| 动态列表的过滤条件存哪？ | **不持久化**在 profile 任何 SQLite 里 | **强**（全表 dump） |
| 曲库增量判据是什么？ | `size` + `mtime`，单曲是最小重读单位 | **强**（三场景 + ETW） |
| 接缝是否无缝？ | CUE 分轨**逐样本零误差**；双文件仅 6 个量化帧 | **强** |
| 内层布局的字段结构？ | **不存在统一布局**（第 25 轮修正了第 19 轮的错误推断） | **强**（13 样本全验证） |

## 一、按主题的结论清单

### 1.1 查询引擎

| 项 | 值 |
| --- | --- |
| 运算符分派表 | file `0x27BD40`，**19 项**，12 字节步长 |
| 紧邻的时间戳别名表 | file `0x27BE24`，**8 字节对**，5 对 |
| `IS`/`IST` handler | `0x0058CD20`（共用，409 字节，17 个调用） |
| `IS` 比较函数 | `0x0058BCF0` |
| `IS` 主匹配器 | `0x0063B3B0`（带通配符，7/8 探针吻合） |
| `HAS` 比较函数 | `0x0058C180`（子串，**无**多值遍历） |
| 大小写折叠表 | `0x00680798`（标准 tolower） |
| 通配符 `?` 推进方式 | 按 **UTF-8 字符**，非字节 |

**五条硬约束**（实现查询语法必须遵守）：

1. 字段名含 `#$%` → titleformat 通道；否则 metadata 通道
2. `IS` 与 `HAS` 是多值字段上**行为不同**的两套语义
3. `SORT BY` 必须在查询末尾
4. 关键字全大写、值不区分大小写
5. `* HAS` 复用简单搜索语义

### 1.2 数据存储

| 项 | 值 |
| --- | --- |
| `metadb` 主表 | 15 字段，`name`（路径）即主键 |
| `info` BLOB | `[0:8]` 时长 + `[8:24]` 4×float ReplayGain + `[24:]` 键值串 |
| ReplayGain 四值 | **全是哨兵**：`-1000`（增益未扫）/ `-1`（峰值未扫），400 样本零例外 |
| 多值字段 | 存成**单个分号串**，不是多条记录 |
| 播放统计 | 走 `metadb_index_<GUID>` 独立表，**主表五列实际未启用** |
| 索引主键 | `filename` 带**子轨前缀**（`0+`/`1+`/`2+`） |
| 动态列表定义 | 136 B blob：`flags + clientGUID + limit + sort_pattern + u64` |
| 过滤条件 | **不持久化**（穷举确认） |

### 1.3 布局与主题

| 项 | 值 |
| --- | --- |
| `.fcl` 结构 | `16B 魔数 + u32 version + u32 reserved + 11 类型表 + 记录流` |
| 记录格式 | `u32 type + u32 size + GUID + u32 namelen + UTF-8 name` |
| type 枚举 | 0=面板实例 / 1=属性块 / 2=全局节 / 4=全局配置 / 5=尺寸 |
| 真记录数 | 47 条（严格筛选后） |
| 配色 | 64 个 `Color.<角色>` + `RGB(...)` 键值对 |
| 内嵌脚本 | 15 个 WSH 的 `// ==PREPROCESSOR==` 块 |

### 1.4 音频

| 项 | 值 |
| --- | --- |
| 环回捕获 | **可自建**，不依赖环回端点设备 |
| 共享混音链路 | 实测工作在 **16-bit**（±0.5 LSB 抖动被量化掉） |
| CUE 分轨接缝 | 最大误差 **0**，失配 **0/480000** |
| 双文件接缝 | 最大误差 246，失配 6（单帧量化抖动） |
| 接缝能量 | RMS 2992.9 → 2853.5 → 2872.7，无塌陷 |

## 二之二、证据强度的样本量说明

本研究的结论**证据强度不均**，关键差别在样本量：

| 结论类别 | 样本量 | 强度 |
| --- | --- | --- |
| `.fth` 容器格式 | **128 份**（32 × 4 版本） | 强 |
| 运算符分派表 | **4 个版本** | 强 |
| ReplayGain 哨兵值 | **400 条记录** | 强 |
| 接缝无缝 | 480,000 样本 | 强 |
| **`.fcl` 记录 type 枚举** | **1 个独立样本** | **中** |
| **`.fcl` 21 实例 / 18 容器** | **1 个独立样本** | **中** |
| **`.fpl` 字段序列** | **1 个独立样本** | **中** |
| `IS` 算法重建 | 8 条探针（7/8） | 中 |

> **第 25 轮的教训**：第 19 轮只用 2 个相似样本就断言 `.fth` 内层有统一布局，
> 扩展到 13 个样本后立即被推翻。**样本量决定了结论的适用范围**，
> 上表标注「中」的结论都只有 1 个独立样本，不应外推到其他布局/主题。

## 二之三、全量 EOF 审计：确认解析完整性（第 35 轮）

第 34 轮发现 `.fpl` 有 468 字节尾部被遗漏后，本轮做了**全量核查**，
确认这不是系统性方法缺陷。

**方法**：对每个二进制结构核对「已解析长度 == 文件长度」，不一致即报告差值。

| 结构 | 文件数 | 精确 EOF | 结论 |
| --- | ---: | ---: | --- |
| 官方 `.fth` | 32 | **32** | 无遗漏 |
| foobaka `.fth` | 37 | **37** | 无遗漏 |
| `.fcl` | 1 独立 | **精确** | 类型表 `0x18F` → 记录流 → `0xA912` = 文件长 |
| `.fpl` | 1 独立 | **有 468 B 尾部** | 已在第 34 轮记录并分析 |

**审计结论**：

| 项 | 判定 |
| --- | --- |
| `.fth` | **69/69 精确 EOF**，最可靠 |
| `.fcl` | 记录流精确 EOF（623 条记录 + 31,288 B 二进制配置） |
| `.fpl` | 唯一存在尾部区，已记录 |
| **整体** | **`.fpl` 的遗漏是孤立事件，不是系统性缺陷** |

> 这个结论有价值：它说明前 34 轮的解析方法总体是严谨的，
> 只有 `.fpl` 一处因为没做 EOF 核对而遗漏。
> 而 `.fth` 的 69/69 通过，是整套研究里**验证最充分**的部分。

## 五、对 SpMusic 的可落地结论

| # | 结论 | 依据 |
| ---: | --- | --- |
| 1 | 容器类型与叶子类型要有**不同级失败策略** | foobaka 整树崩塌 |
| 2 | 主题配置用**显式键值模型**，不用二进制大块 | `.fcl` 的 `Color.*` 设计 |
| 3 | 统计仿**独立索引表**，主键含子轨前缀 | `metadb_index` 结构 |
| 4 | ReplayGain 用**哨兵值**表未设置 | 400 样本零例外 |
| 5 | `IS` 与 `HAS` 必须**分别实现** | 反汇编证实并行语义 |
| 6 | 动态列表**自行设计持久化**，不能照抄 | foobar 不落盘 |
| 7 | **不要**在主进程跑脚本宿主 | 崩溃报告 25/35 来自 WSH/OLEAUT32 |
| 8 | 通配符按**码点**推进，非字节 | UTF-8 解码器实测 |

### 6.1 「逆向不出结果」的具体依据

| 未解项 | 为什么静态做不到 |
| --- | --- |
| `ARTIST IS spmq3`=12 vs `SpmQ3`=11 的差 1 | 需在标志位 `[edi+0x20]/[edi+0x21]` 处下断点读值 |
| `metadb_index` 的 64-bit 哈希算法 | 两条独立路径（数据反推 + 反汇编）均失败；需在 `get_key` 返回处读 `eax:edx` |
| `.fth` 内层几何字段语义 | 结构因主题而异，无统一定位；需反汇编 `foo_ui_std` 序列化代码 |
| `.fpl` 尾部区 `+0`–`+80` 字段语义 | 单样本，无法交叉验证 |
| `.fcl` 头部 `[0x18]`=11 vs 实际 10 条类型 | 单样本，无法交叉验证 |
| 同任务找歌 / 批量迁移实测 | 自动化两轮均失败，需人工操作界面 |

**这 6 项里没有一项能靠纯静态分析补齐。**

### 6.2 「需要实机运行 SpMusic」的依据

SpMusic 侧的全部产出都是**静态代码核查**与**设计文档**：

| 产出 | 性质 | 是否验证过 |
| --- | --- | :---: |
| appearance codec 逐字段降级 | 读代码核查 | ✓（代码本身即证据） |
| 查询能力只有 `HAS` 语义 | 读代码核查 | ✓ |
| 差距分析（需补哪些能力） | **设计文档** | ✗ |
| 动态列表格式设计 | **设计文档** | ✗ |

> **两个设计文档从未经运行时检验**。要验证它们是否正确，
> 必须实现并运行 SpMusic——这正是第二个终止条件。

**建议**：逆向部分可以收尾。若要继续，应转向 SpMusic 侧的实际实现与验证。
