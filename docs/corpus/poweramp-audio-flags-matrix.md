# 插件系统（二十八）：音频输出 flags 位矩阵

## 0. 一句话结论

第十九篇列了 `c1` 的 7 个"开关"，本轮发现**每个开关都携带一个位掩码**，
与第二十四篇的 `flags` 合成表**互相印证**——

**UI 侧的掩码 = 运行时 flags 的位定义**。两处独立代码给出同一张位表。

---

## 1. UI 侧掩码（`c1.z()` 的 `w()` 调用）

`w(String key, long time, ..., int mask, ...)` 是统一的"加一行开关"方法。
实测 9 个调用：

| 行 | key | **掩码** | 位 |
| ---: | --- | ---: | ---: |
| `:2304` | **`oem_variant`** | **0x40000** | bit18 |
| `:2345` | `no_dvc` | **0x10** | bit4 |
| `:2415` | `no_headroom` | **0x20** | bit5 |
| `:2435` | `no_equ` | **0x40** | bit6 |
| `:2453` | `float` | **0x80** | bit7 |
| `:2542` | `no_duck` | **0x2000** | bit13 |
| `:2558` | `no_af` | **0x100000** | bit20 |
| `:2601` | `cc_force_aa` | （未取到） | — |
| `:2639` | `cc_show_meta` | （未取到） | — |

### 1.1 与第二十四篇合成表的交叉验证

| 掩码 | UI 侧（本篇） | 合成侧（二十四） | 一致 |
| ---: | --- | --- | :---: |
| `0x10` | `no_dvc` | （不在合成表） | ⚠️ |
| `0x20` | `no_headroom` | `or 0x20`（`i.smali:392`） | ✅ |
| `0x40` | `no_equ` | `or 0x40`（`:397`） | ✅ |
| `0x80` | `float` | `or 0x80`（`:387`） | ✅ |
| `0x2000` | `no_duck` | `or 0x2000`（`:418`） | ✅ |
| `0x1000` | — | `or 0x1000`（`:406`） | — |
| `0x100000` | `no_af` | （不在合成表） | ⚠️ |
| `0x40000` | `oem_variant` | （不在合成表） | ⚠️ |

> **5 个掩码严格对应**，3 个只在一侧出现。
> 差异原因：合成表（`i.А`）只合成**9 个布尔**，而 UI 有 9 个开关；
> 两处列表**不完全重合**，说明存在不同的传递路径。

## 2. ★ `oem_variant` 的作用（第十九篇遗留）

`:2304-2332` 的完整逻辑：

```smali
pref = w("oem_variant", ..., mask=0x40000, ...);
if (pref != null && (flags & 0x500000000000000L) != 0) {
    pref.setTitle(0x7f08007d);              // ★ 改标题
}
```

### 2.1 两个常量

| 常量 | 十六进制 | 位宽 |
| --- | --- | --- |
| 掩码 | `0x40000` | 32 位内（bit18） |
| 检查 | `0x500000000000000L` | **64 位**（bit52 + bit56） |

> **注意是 `L` 后缀的长整数**——`c1` 的某些判断用了 64 位 flags，
> 而 `i.А()` 合成的是 32 位 int。**这是两套不同宽度的 flags**。

### 2.2 `oem_variant` 的语义

`0x7f08007d` 的字符串名可确定标题含义。据命名与行为推断：

| 项 | 推断 |
| --- | --- |
| 含义 | **OEM 变体**——某些厂商 ROM 需要特殊的音频输出处理 |
| 行为 | 当 flags 含 bit52/bit56 时，**标题改成另一资源串**（提示该变体已生效） |
| 掩码 bit18 | 该开关在 32 位 flags 中的位置 |

## 3. 三套 flags 的宽度对照

| 来源 | 宽度 | 用途 |
| --- | --- | --- |
| `preference/i.А()` | **32 位 int** | 合成音频输出选项 |
| `c1` 的 `w()` 掩码 | **32 位** | UI 开关与位对应 |
| `c1` 的 `0x500000000000000L` | **64 位 long** | OEM/设备能力标志（另一维度） |
| `NativePluginInfo.flags` | 32 位 | 插件角色位域（第一篇，另一体系） |

> **注意不要混淆**：`NativePluginInfo.flags`（插件类型）与本文的音频 flags **完全无关**。
> 这也印证了第二十四篇 §5.2 N4 的提醒。

---

## 4. 可借鉴 / 不建议照抄

### 4.1 值得借鉴

| # | 做法 | 理由 |
| --- | --- | --- |
| A1 | **UI 掩码与运行时位一一对应** | 一个开关改一位，语义清晰 |
| A2 | **`w()` 统一加行** | 掩码作为参数，无需重复代码 |
| A3 | **flags 变化时改标题** | 直观提示"某变体已生效" |
| A4 | **能力标志单独用 64 位** | 与 32 位选项 flags 分离，避免位耗尽 |

### 4.2 不建议照抄

| # | 问题 | 后果 |
| --- | --- | --- |
| N1 | **同名 `flags` 三种含义**（插件/选项/能力） | 极易误读 |
| N2 | 64 位能力标志无常量名 | `0x500000000000000L` 含义不明 |
| N3 | UI 与合成侧列表不完全重合 | 需双表对照才能理解 |
| N4 | `oem_variant` 的标题资源硬编码 | 换文案要改代码 |
