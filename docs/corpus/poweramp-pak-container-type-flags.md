# 插件系统（二十三）：容器 type 位域与四种取值

## 0. 一句话结论

第十五篇只知道 `milk_preset_containers.type` 来自 flag，
本轮**枚举出 4 种取值**，并给出位域解释（后经第二十五篇补全至 **6 种**：新增 `0x1`/`0x5`）。

| flag | 二进制 | 含义（推断） | 触发场景 |
| ---: | --- | --- | --- |
| **0x8** | `0b1000` | 本包 / APK 内置 | `apk://` 自己包 |
| **0xa** | `0b1010` | 外部 APK | `apk://` 外部包 |
| **0xf** | `0b1111` | **zip 子容器** | 嵌套 zip 展开 |
| **0x14** | `0b10100` | **目录容器** | `dir:` 路径 |

---

## 1. 全部 flag 常量与调用点

实测 `milk/scanner/B.smali` 中只有 6 处 flag 常量，对应 4 个不同值：

| 行 | flag | 目标方法 | 场景 |
| ---: | ---: | --- | --- |
| `:284` | 0x8 | `Х(...)` | 内置 pak（`B.smali` 起点） |
| `:328` | 0xa | `Х(...)` | 外部 pak |
| `:665` | 0x8 | `Х(...)` | **自己包**（`apk://` 分支 ①） |
| `:710` | 0xa | `Х(...)` | **外部包**（`apk://` 分支 ②） |
| **`:876`** | **0x14** | **`А(...)`** | **`dir:` 目录容器** |
| **`:963`** | **0xf** | **`у(...)`** | **zip 子容器** |

### 1.1 `Х()` 与 `А()`/`у()` 的分工

| 方法 | 参数 | 用途 |
| --- | --- | --- |
| `Х(path, pkg, flag, set)` | 4 参 | **外层入口**（apk:// 两种） |
| `А(flag, uri) J` | 2 参 | **仅建容器记录**，返回 id |
| `у(flag, path, pkg, extra, mode)` | 5 参 | **完整扫描**（建容器 + 遍历 + 回填） |

> `dir:` 与 `zip:` 走 `А()`/`у()` 直接路径，**不经 `Х()` 的去重包装**。

---

## 2. 位域解读（⚠️ 已被第三十八篇证伪）

> **⚠️ 重要订正**：以下位域解读是`值→场景`的**归纳**，
> 但实测 `А()` 内 flag **只做 `int-to-long` 后入库**，全库 **0 处**对 `type` 做位运算。
> 因此这些`bit 含义`**没有代码依据**，属模式投射。
> 详见 `poweramp-opaque-type-marker.md`（三十八）。


把四个值排开：

```
0x8  = 0000 1000
0xa  = 0000 1010
0xf  = 0000 1111
0x14 = 0001 0100
```

| 位 | 0x8 | 0xa | 0xf | 0x14 | 可能含义 |
| --- | :---: | :---: | :---: | :---: | --- |
| bit3 (0x8) | ✅ | ✅ | ✅ | ❌ | **基础位：APK 类容器** |
| bit1 (0x2) | ❌ | ✅ | ✅ | ❌ | **外部**（非自己的包） |
| bit2 (0x4) | ❌ | ❌ | ✅ | ✅ | **子容器 / 需要展开** |
| bit0 (0x1) | ❌ | ❌ | ✅ | ❌ | zip 特有 |
| bit4 (0x10) | ❌ | ❌ | ❌ | ✅ | **目录类容器** |

### 2.1 观察到的规律

| 规律 | 证据 |
| --- | --- |
| **bit3 是"APK 类"** | 0x8/0xa/0xf 都含 bit3，只有 0x14（目录）不含 |
| **bit1 是"外部"** | 0xa = 0x8 + 0x2 |
| **bit2 是"需展开"** | 0xf 与 0x14 都含 bit2，二者都是嵌套/递归场景 |
| **bit4 是"目录"** | 0x14 = 0x10 + 0x4，且仅目录用 |

> **注意 0xf 与 0x14 的对比**：
> 0xf = `8+4+2+1`（APK + 展开 + 外部 + zip）
> 0x14 = `16+4`（目录 + 展开）
> 两者都含 bit2，正是"需要递归展开"的共同特征。

## 3. 第 5 种 URI scheme：`zip://`（本轮新发现）

第五篇列了 4 种 scheme（builtin/compiled/dir/apk），
本轮发现**第 5 种 `zip://`**（`B.smali:945`）：

```smali
Uri.Builder()
    .scheme("zip")
    .authority(...)      // 容器 id 或包名
    .path(...)           // zip 内路径
    .build();
у(0xf, path, pkg, extra, false);
```

> **但 `X(String)` 的分派里没有 `zip:` 分支**——它只在**内部构造**时产生，
> 作为容器记录的 `uri` 字段值，不参与外部输入分派。
> 这是第五篇"四种 scheme"的补充：**对外 4 种，对内还有 zip://**。

## 4. `type` 列的最终语义

结合 `MilkRestProvider` 的 `GROUP BY type` 查询（第十六篇），设置页显示的分类应为：

| type | 显示（推断） |
| ---: | --- |
| 8 | Built-in |
| 0xa | Installed packages |
| 0xf | Nested archives |
| 0x14 | Folders |

> **推断依据**：4 个值与 4 类来源一一对应，且 `GROUP BY type` 的用途正是分类计数。

## 5. 可借鉴 / 不建议照抄

### 5.1 值得借鉴

| # | 做法 | 理由 |
| --- | --- | --- |
| A1 | **type 用位域而非枚举** | 一个 int 表达"来源 + 属性"两维 |
| A2 | **bit3 统一标识 APK 类** | 便于 `& 0x8` 快速筛选 |
| A3 | **bit2 标识"需展开"** | 递归场景统一处理 |
| A4 | **zip:// 仅内部使用** | 不与外部 scheme 混淆 |

### 5.2 不建议照抄

| # | 问题 | 后果 |
| --- | --- | --- |
| N1 | 位含义**无文档** | 只能靠 4 个样本反推 |
| N2 | flag 直接存进数据库 `type` 列 | 表结构耦合实现细节 |
| N3 | 0xf 与 0x14 的位组合不对称 | 规律不整齐，易误判 |
| N4 | `Х()` 与 `А()`/`у()` 两套入口 | 去重逻辑只覆盖一半 |
