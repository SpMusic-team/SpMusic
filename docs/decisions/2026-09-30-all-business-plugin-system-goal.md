# 全业务插件化长期目标

## 决策状态与目标

2026-09-30，依据用户连续确认的方向，接受 SpMusic 的长期目标：建立较完善的插件宿主框架，使所有业务能力以插件形式交付、通过宿主装配，并遵守统一的服务、依赖、生命周期、配置、权限和兼容规则。

本次确认长期目标与设计方向，固化需求、架构方向和路线图。当前代码尚不是该插件系统；本次没有批准业务实现、依赖安装或版本排期，也不代表下述阶段已经完成。

## 业务范围与产品交付

- 现有播放控制、队列、解码、音频输出、歌词、元数据、封面、主题、播放器 UI 和业务设置 UI，最终均通过插件组织。
- 以后单独批准的媒体库、播放列表、网络存储、搜索、收藏、播放历史等业务能力，也遵守相同插件规则。此决策不等于批准这些功能立即建设。
- 官方基础插件随产品交付，默认配置装配完整播放器；用户无需另外寻找或安装第三方插件才能使用产品基础能力。
- 官方插件与第三方插件均遵守宿主规则。官方基础能力不得通过隐藏的直连入口长期绕过服务容器、生命周期或权限检查。
- 基础业务可以依赖官方插件。关闭可选插件时，默认基础能力仍应可用；官方必要插件的停用、替换和故障恢复必须有明确规则，不能用“任意插件都可随时停用且播放永不中断”作为承诺。
- 业务插件化不要求所有插件采用同一执行环境，也不要求所有插件都是动态库、可运行时安装或可无条件热替换。编译随产品交付的 Rust 官方插件同样必须参与统一装配和生命周期管理。

## 完整宿主能力边界

宿主框架围绕以下十一类基础设施设计。具体契约由 Architecture Agent 维护，需求验收由 Requirements Agent 维护；此表用于确认长期覆盖范围。

| 能力 | 目标覆盖 |
| --- | --- |
| 插件描述与兼容 | 身份、版本、宿主 API 版本、入口、服务与依赖声明、能力声明、配置声明和加载前检查 |
| 服务容器 | 类型化服务、作用域、多个提供器选择、唯一服务约束与业务状态权威 |
| 依赖与装配 | 依赖图、缺失与循环检查、确定的启动顺序、官方默认组合和配置覆盖 |
| 生命周期与资源 | 异步启动停止、失败回收、逆序退出、取消任务和资源统一清理 |
| 配置与持久化 | 校验、版本迁移、插件独立存储和更新失败恢复 |
| 事件与任务 | 类型化事件、作用域订阅、取消、超时、并发限制和过期结果处理 |
| 权限与执行环境 | 受控文件、网络和播放等能力入口，可信官方插件与第三方代码的执行和隔离规则 |
| 安装与更新 | 包校验、安装取消、启停卸载、更新恢复和重启要求 |
| 跨端服务桥接 | TypeScript/Rust 服务与事件映射、消息校验、错误语义、连接和退出处理 |
| 诊断与开发 | 插件状态、依赖关系、日志、耗时、资源统计和开发重载 |
| 测试与 SDK | 插件开发接口与示例、宿主测试工具、服务替身、兼容、生命周期及故障验证 |

宿主负责基础设施，不持有播放策略、曲目处理、歌词解析、队列策略或界面等业务实现。TypeScript、Rust 与 Tauri 的具体职责及实时音频边界见[架构方向](../architecture/all-business-plugin-system.md)。

## 参考项目的使用方式

参考 `D:/OpenProject/deepseek-harness` 与其使用的 Cordis，借鉴插件装配、服务依赖、生命周期、资源归属和管理机制。参考项目用于提供设计证据，不直接证明 SpMusic 当前具备相同能力。

本次未决定采用 Cordis 库、复制 dsh 实现或使用特定沙箱技术。是否复用库、如何连接 Rust、如何执行第三方代码、如何保障实时音频路径，必须在后续技术评估与契约审查中确定；同进程加载或 `node:vm` 不能当作第三方安全隔离的完成证据。

## 分阶段目标与验收方向

三个阶段覆盖最终目标，不以歌词 PoC 或可选增强系统替代全业务迁移。阶段是独立长期工作流，未绑定发布日期或版本号；进入实施前应再拆分经审查的任务与验证方案。

| 阶段 | 交付目标 | 阶段完成所需证据 |
| --- | --- | --- |
| 一：宿主框架与官方业务迁移 | 建立宿主基础和统一规则，迁移全部现有业务为官方插件，由默认组合启动完整播放器；为后续治理与音频扩展确定边界 | 业务清单逐项有插件归属；默认制品无需用户另装插件；服务调用与状态权威清晰；依赖缺失、启动失败、退出清理及现有播放回归有证据；没有永久双轨入口 |
| 二：插件治理与第三方接入 | 完成兼容、权限、安装更新、配置迁移与独立存储、受限执行及插件管理开发闭环 | 第三方插件安装、启停、更新失败恢复与卸载可验证；权限在入口执行；越权、故障、资源残留和不兼容分支有独立验证；SDK 与诊断可支撑开发和定位 |
| 三：深层音频扩展 | 开放解码、音频输出、DSP 等实现的替换与组合，完成会话切换、性能和故障恢复规则 | 当前会话权威唯一；替换前置条件、停止或迁移流程和失败恢复明确；实时路径的执行预算与资源边界有测量；兼容、可听播放与回归覆盖相应组合 |

十一类宿主能力在最终验收中逐项核对，不能用某一个演示插件或一次成功启动推断整个目标完成。具体可检查条件以[单项需求](../requirements/all-business-plugin-system.md)为准。

## 覆盖旧约束与保留边界

本决策覆盖路线图、总需求和总体架构中“插件只能增强”“基础业务不得依赖插件”“核心必须直接内置”的长期限制。替代规则是：基础业务由随产品交付的官方插件实现，用户基础体验由默认插件组合保障。

历史 v0.1 文档和当前 Sprint 中“插件系统不在版本范围内”等版本限制继续有效。本次不重排 v0.1～v0.6 路线、不调整既有 Sprint、不生成实施任务或激活扩展 Agent。`REQ-PLUGIN-001` 的长期目标已确认，实施未排期；当前索引的 P3 是相对现行 v0.1 版本的优先级，不表示插件化最终仅是可选增强。

## 尚未决定的事项

- 实施版本、日期、预算、迁移任务顺序和发布门槛。
- Cordis 或其他库的复用、自研比例、具体插件包格式与加载实现。
- TypeScript/Rust 跨端协议细节、第三方执行隔离技术和权限模型的实现。
- 解码器、输出与 DSP 替换的兼容矩阵及实时性能预算。

## 下一步：架构选型与契约设计

在创建代码实施任务前，先完成架构选型与契约设计。设计阶段的可审查产出必须覆盖：

- Cordis 复用、自研及必要适配方案的比较，说明适配 SpMusic 的依据、约束和成本，再形成选型结论。
- TypeScript、Rust、Tauri 桥接层的职责、服务调用和事件契约，以及跨端状态权威和错误语义。
- 第三方代码的执行与隔离备选、能力入口和授权撤销规则，区分声明权限与实际执行检查。
- 音频服务的依赖、启动停止、资源清理、会话替换前置条件，以及实时路径约束。
- 十一类宿主能力的覆盖映射与全部现有业务的迁移清单，明确尚未解决的事项。

完成依据是这些设计项具有明确方案、可验证契约和待决事项清单，并经 Architecture Agent 审查；仅有方向文档不代表技术方案已定。本次不生成代码任务卡。

插件市场、云分发服务、账号系统和新的媒体业务功能不因这次基础设施目标自动进入范围。后续进入实施时，由 PM 依据需求与架构输出排期，匹配 Frontend、Rust/Tauri 等实施 Agent，并由 Test Agent 独立验证。
