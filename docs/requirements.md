# SpMusic v0.1 MVP 需求说明

## Summary

SpMusic v0.1 是项目地基阶段，目标是把当前 Tauri + React + TypeScript 模板项目收敛为一个边界清晰、可运行、可验证的本地优先桌面音乐播放器雏形。

本版本不提供真实音频播放能力。v0.1 的重点是验证产品方向、播放器主界面、最小播放状态模型、前后端通信链路和基础工程验收流程。

## User Problem

当前项目仍是通用模板，无法表达 SpMusic 作为本地优先音乐播放器的产品形态。团队需要先建立一个范围受控的 MVP 地基，在不引入真实音频、媒体库、数据库、插件系统或在线服务复杂度的前提下，验证应用外壳、核心状态和后续开发边界。

## Target Users

- 希望使用本地优先桌面音乐播放器的用户。
- 需要在实现真实播放和媒体库之前确认 v0.1 范围的 SpMusic 贡献者。
- 需要客观验收标准来制定计划、实现功能和进行评审的产品与工程 Agent。

## MVP Scope

- 将模板项目身份替换为 SpMusic 项目身份。
- 提供一个静态播放器主界面。
- 使用假歌曲数据展示播放队列或歌曲列表，至少包含 5 条歌曲。
- 展示当前歌曲信息，例如歌曲名、艺术家、专辑、时长等。
- 支持播放、暂停、上一首、下一首的 UI 状态切换。
- 定义最小前端 `PlayerState` 或等价结构，表达当前歌曲、播放状态和队列。
- 为队列为空的情况提供可渲染的 Empty State 分支。
- 增加一个最小 Tauri command，用于验证 React 到 Rust 的通信链路。
- 记录 v0.1 的本地验证命令与验收标准。

## Out of Scope

- 真实音频解码、播放、暂停、拖动进度和音量控制。
- 使用 `HTMLAudioElement` 或其他真实音频播放 API 播放文件。
- 文件系统扫描、文件夹导入、媒体库管理、元数据解析、封面提取和歌词。
- 数据库存储、缓存层、迁移系统和持久化媒体索引。
- 插件系统、插件市场、扩展运行时和复杂模块架构。
- 在线音乐搜索、流媒体服务、账号系统、云同步、Last.fm 或其他在线服务。
- 高级音频 DSP、均衡器、可视化效果、波形渲染或音频分析。
- 完整接入 shadcn/ui、主题编辑器或高级设计系统。

## User Scenarios

### 场景 1：启动应用

用户在本地开发环境中启动桌面应用。

- 首屏能够识别应用为 SpMusic。
- 页面不再显示 Vite、React 或模板 starter 内容。
- 不需要选择音乐文件夹、登录账号、初始化数据库或连接网络，即可看到播放器外壳。

### 场景 2：查看假歌曲列表

用户打开应用后查看当前展示的歌曲列表。

- 应用展示至少 5 条假歌曲。
- 每条可见歌曲包含可区分的信息，例如歌曲名、艺术家、专辑或时长。
- 当队列不为空时，有一首歌曲被表示为当前歌曲。

### 场景 3：切换播放 UI 状态

用户点击播放控制按钮以验证前端状态模型。

- 点击播放 / 暂停按钮后，界面中的播放状态发生切换。
- 点击下一首后，当前歌曲切换到假队列中的另一首歌曲。
- 点击上一首后，当前歌曲按同一队列规则切换。
- 当前歌曲在列表中有可识别的视觉状态。
- 不加载也不播放任何真实音频文件。

### 场景 4：验证前后端通信

用户启动应用后确认前端可以通过 Tauri 调用 Rust 侧能力。

- 前端调用一个最小 Tauri command。
- 界面展示该 command 的返回结果或明确的连接状态。
- 该 command 不扫描文件、不访问媒体库、不播放音频。

## Functional Requirements

- FR-001：应用首屏必须体现 SpMusic 产品身份。
- FR-002：应用必须渲染静态播放器主界面，包含当前歌曲信息、播放控制区和歌曲列表。
- FR-003：假歌曲队列必须至少包含 5 条歌曲数据。
- FR-004：当前歌曲信息必须至少展示歌曲名、艺术家、专辑、时长中的 3 类信息。
- FR-005：界面必须提供可点击的播放 / 暂停、上一首、下一首控制。
- FR-006：播放 / 暂停控制必须在 UI 层切换播放状态。
- FR-007：上一首 / 下一首控制必须更新 UI 中的当前歌曲。
- FR-008：歌曲列表必须展示哪一首是当前歌曲。
- FR-009：前端必须存在最小播放器状态结构，包含当前歌曲标识、播放状态和队列。
- FR-010：队列为空时，界面必须有可渲染的 Empty State 分支。
- FR-011：Rust 侧必须暴露一个最小 Tauri command 用于通信验证。
- FR-012：前端必须展示 Tauri command 的返回结果或连接状态。

## Non-functional Requirements

- NFR-001：v0.1 必须保持本地优先，核心验证不依赖网络访问。
- NFR-002：v0.1 不得引入真实音频播放依赖或媒体库持久化能力。
- NFR-003：v0.1 范围必须足够小，能够通过构建、Lint、`cargo check` 和人工 UI 检查进行客观验收。
- NFR-004：在真实播放和媒体库需求确认之前，不应提前引入复杂架构抽象。
- NFR-005：文档必须清晰区分 v0.1 范围与后续真实播放、媒体库、插件和在线能力。

## Key Rules

- 假歌曲队列只是验证用数据，不是真实媒体库。
- 播放控制在 v0.1 中只改变 UI 状态。
- 当队列不为空时，当前歌曲必须来自当前队列。
- 队列为空时，界面必须能渲染 Empty State，不能崩溃。
- Tauri command 只用于验证前后端通信链路。
- 任何真实播放、媒体扫描、数据库持久化、插件支持或在线服务需求都必须延期到 v0.1 之后。

## Edge Cases

- 空队列：界面展示 Empty State，而不是当前歌曲详情。
- 单曲队列：点击上一首 / 下一首后，当前歌曲状态仍然有效。
- Tauri command 调用失败：界面展示明确的未连接或不可用状态。
- 连续点击播放 / 暂停：UI 状态可预测地切换，且不尝试播放音频。
- 连续点击上一首 / 下一首：当前歌曲始终保持有效，并能在队列中被识别。

## Acceptance Criteria

- `docs/requirements.md` 存在。
- 文档包含 Functional Requirements、Non-functional Requirements、MVP Scope、Out of Scope、User Scenarios 五个章节。
- Out of Scope 明确排除真实音频播放、媒体库、数据库、插件系统和在线服务。
- 至少定义 3 个可验证用户场景：启动应用、查看假歌曲列表、切换播放 UI 状态。
- 需求明确说明播放行为仅改变 UI 状态，不要求真实音频引擎。
- 需求明确说明最小 Tauri command 仅用于前后端通信验证。
- 文档可交付给 PM、前端、Rust/Tauri、文档和测试 Agent 使用，且不会扩大 v0.1 范围。

## Open Questions

- v0.1 播放控制应使用纯文本按钮、图标按钮，还是图标加文本？
- 假歌曲数据应直接放在播放器组件中，还是拆到独立 fixture 文件？
- 最小 Tauri command 应返回简单字符串，还是返回结构化状态对象？

## Risks

- 模板残留可能导致无法清晰判断项目是否已经脱离 starter 状态。
- 音乐播放器天然容易发生范围膨胀，滑向真实播放、媒体库、歌词、封面或插件能力。
- 过早引入持久化或文件扫描会增加 v0.1 的验证和维护成本。
- 如果不尽早验证 Tauri command，前后端通信风险会延后暴露。

## Recommendation

SP-001 在本文档完成后可交由 PM Agent 对照 sprint 计划进行验收。后续应进入 SP-002 和 SP-003，但不得把 v0.1 扩展到本文档之外的真实播放、媒体库、数据库、插件系统或在线服务能力。
