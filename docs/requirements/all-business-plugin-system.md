# 需求分析：全部业务能力插件化

## 摘要

SpMusic 的长期目标是建立较完善的插件宿主框架，全部音乐业务和产品界面由插件提供；官方基础业务插件随应用交付，用户安装应用即可获得完整的默认播放器。内置插件与第三方插件服从统一的服务、依赖和生命周期规则，差异通过明确的信任与能力策略表达。

用户已确认这一产品方向。本次固化目标和最终验收要求，不实施代码、不排定版本，不改变当前 v0.1 发布范围或宣称现有代码已完成插件化。完整目标不以歌词插件试验或仅开放外围扩展点替代。

目标决策见[全部业务能力插件化目标](../decisions/2026-09-30-all-business-plugin-system-goal.md)，架构评估见[全部业务能力插件化架构](../architecture/all-business-plugin-system.md)。

## 用户问题

仅允许主题、歌词源等外围增强，不能满足替换播放、队列、解码、输出和界面的长期需求。各业务模块如果直接依赖内部状态和具体实现，替换能力需要持续修改核心；插件各自处理退出、配置和错误，又容易产生资源残留与不兼容组合。

需要一个可装配、可替换、可诊断的业务体系，让官方默认播放器和用户自定义组合使用同一套机制；普通用户仍能直接安装、离线播放，不承担寻找或安装基础插件的负担。

## 目标用户

- 安装应用后直接使用默认播放器的本地音乐用户。
- 需要替换界面、音频能力、来源或工作流的高级用户。
- 开发与维护官方插件、第三方插件和宿主的开发者。

## 用户场景

- 用户离线安装应用，官方插件组合自动装配，完成本地播放及当前版本已交付的基础功能。
- 用户添加歌词、元数据或面板插件，能查看依赖、版本、权限和实际启用状态。
- 用户选择其他已兼容的业务服务实现，宿主检查依赖，并按该服务允许的条件切换。
- 用户关闭第三方增强插件，官方基础业务插件组合仍可运行。
- 插件加载失败、请求超时或升级失败时，用户能看到受影响能力、错误原因和恢复入口。

## 优先级建议

长期架构方向已由用户确认；相对当前 v0.1，实施优先级建议 P3，不表示最终目标是可选增强。目标版本与执行优先级由 PM Agent 决定。现有 v0.1 插件系统排除项仍有效，不能因方向确认推导为已进入当前发布版本。

## 版本建议

以长期目标维护，实施尚未排期。PM Agent 根据架构评估确定迁移范围和版本，不能把目标批准等同于代码完成、第三方生态已可用或发布承诺。

## 范围

- 完整宿主能力：插件描述与兼容、服务容器、依赖与装配、生命周期与资源、配置与持久化、事件与任务、权限与执行环境、安装与更新、跨端桥接、诊断与开发工具、测试基础设施。
- 当前已有业务迁入统一插件体系，后续批准的业务也采用同一插件实现方式。
- 官方基础插件随应用交付，提供可验证的默认播放器组合。
- 不同执行环境共享明确的身份、依赖、生命周期、错误和能力规则；具体加载和运行机制可不同。
- 第三方扩展具有可检查的兼容、授权、启停、升级和卸载闭环。

## 不在范围内

- 不因本目标新增在线音乐平台、在线曲库搜索、推荐、版权内容服务、强制账号或强制联网。
- 不自动批准插件市场、商业分发平台、账号、云服务或新的媒体库产品功能。
- 不要求所有插件都运行时动态安装或都能无中断热替换；重启生效与受控替换也是明确的能力模式。
- 不指定复用 Cordis、全量自研、Rust 动态库、WASM、独立进程或特定隔离技术。
- 不在本文制定 Sprint、任务卡、具体任务分配或修改业务实现。

### 假设与依赖

- 本地优先及[总需求分析](总需求分析.md)的产品能力边界继续有效。
- “全部业务能力”约束实现方式；尚未建设的未来功能仍按各自需求、批准范围和验收标准建设。
- 宿主负责通用基础设施；播放策略、曲目业务规则、歌词、主题和业务 UI 不因改名为宿主模块而豁免插件化。
- PM Agent 维护版本与范围决策；Architecture Agent 定义跨 TS/Rust/Tauri、实时音频和第三方执行边界；实施后的 Test Agent 独立验证插件组合和原有业务回归。

## 功能需求

### 业务覆盖

以下为覆盖清单，不是新功能排期。现有目录只作为迁移输入，不代表其已采用插件宿主。

| 业务能力 | 目标实现方式 | 范围说明 |
| --- | --- | --- |
| 播放控制、会话和播放状态 | 官方播放插件提供服务，状态权威与会话归属明确 | 迁移现有业务，不要求重写现有控制器 |
| 解码、音频输出、设备选择 | 官方原生业务插件提供服务，可按契约替换 | 原生插件可随应用编译；实时替换条件单独明确 |
| 队列、随机/循环、临时来源和 m3u8 | 队列及来源业务插件，通过服务协作 | 保持队列与产品级播放列表的范围区分 |
| 标签、歌词、封面、缓存与编辑 | 提供器及业务插件，统一任务和结果归属 | 已有能力迁移，未来编辑/在线来源仍按独立批准范围 |
| 播放器、歌词/封面/队列面板、设置 | 官方 UI 插件消费服务与界面贡献机制 | 产品界面业务不能以固定宿主 UI 绕过插件规则 |
| 主题、外观配置、动效与布局 | 官方外观插件提供默认实现，并支持受控扩展 | 保留既有主题配置兼容性要求 |
| 音乐库、扫描、索引、搜索、收藏、历史、播放列表 | 后续官方业务插件 | 未交付功能不因本目标提前进入版本 |
| FTP/SMB/WebDAV、用户自有流媒体资源 | 后续官方来源插件 | 基础产品支持随对应功能交付，无需用户另找第三方插件 |
| 快捷键、国际化、桌面控制与字幕 | 官方业务插件使用受控桌面能力 | 平台支持和桌面字幕范围仍独立确认 |
| 智能播放列表、独占输出、统计、同步、Scrobbler、自定义功能区 | 后续官方或扩展业务插件，遵守各自支持责任 | 原有高级产品支持不转嫁给第三方生态 |
| 新增业务能力 | 一律通过插件及正式服务/贡献接口接入 | 新功能需独立批准，不得绕过宿主注入私有状态 |

### 宿主能力

| ID | 能力 | 必须满足的要求 |
| --- | --- | --- |
| PH-01 | 插件描述与兼容 | 插件有稳定身份、版本、宿主 API 范围、服务/能力/配置声明；冲突或不兼容在执行前拒绝并定位原因 |
| PH-02 | 服务容器 | 类型明确，约束作用域、唯一权威与多个提供器选择；业务插件通过服务接口协作，不直接修改其他插件内部状态 |
| PH-03 | 依赖与装配 | 校验依赖缺失、循环和重复提供；按依赖顺序装配，支持官方默认组合和受校验的用户覆盖 |
| PH-04 | 生命周期与资源管理 | 管理异步启动/停止、失败回收、逆序退出；订阅、任务、定时器及临时资源有插件归属，可验证清理 |
| PH-05 | 配置与持久化 | 配置有校验和迁移规则，插件独立存储；无效更新拒绝，迁移失败可恢复且不破坏其他插件数据 |
| PH-06 | 事件与任务系统 | 事件有明确类型及订阅作用域；任务支持取消、超时、并发控制和过期结果拦截，避免切歌或禁用后回写 |
| PH-07 | 权限与执行环境 | 区分官方可信实现与第三方执行策略，文件、网络、播放控制等通过宿主检查；未授权访问可验证地拒绝 |
| PH-08 | 安装与更新管理 | 校验包身份和兼容，管理安装/更新/取消/卸载及失败恢复；区分已安装、已启用、实际运行和等待重启 |
| PH-09 | 跨端服务桥接 | TS/Rust/Tauri 两侧使用明确的服务、事件和错误契约；消息校验、请求归属、取消与断连处理可追踪 |
| PH-10 | 诊断与开发工具 | 可查询插件实际状态、依赖图、错误、日志、耗时及资源；开发重载遵循清理和兼容规则 |
| PH-11 | 测试基础设施与 SDK | 提供公开插件开发接口、SDK/示例、宿主测试环境、服务替身、契约/兼容测试和生命周期故障注入，验证默认组合与替换组合；开发者无需引用内部实现即可构建合规插件 |

这些能力都属于最终目标；交付可以分段，但不得以只完成 PH-01 至 PH-04 或歌词插件闭环宣称整个目标完成。

## 非功能需求

- 官方默认组合在无网络、无登录、无第三方插件条件下提供当前版本承诺的本地基础能力。
- 现有播放、队列、歌词、封面、主题和已承诺格式兼容行为有迁移前基线及迁移后回归证据。
- 实时音频路径不得依赖无界第三方任务、管理操作或不受控跨端往返；性能预算和检测方法在架构/验证设计中明确。
- 插件扩展 API、配置和持久数据的版本兼容策略有文档和可重复测试。
- 插件与业务数据默认本地保存；权限覆盖实际访问路径，生命周期捕获异常不被宣称为安全隔离。
- 启动时间、稳态资源、音频稳定性等量化门槛实施前根据现有基线确定；最终验收必须提供实际测量和通过结论，不能只使用“轻量”“稳定”等描述。

## 关键规则

- 全部业务遵守插件服务、依赖和生命周期，无内置业务的隐蔽直连通道。
- 必要的进程启动、运行环境、通用资源访问与服务治理是宿主基础设施；具体音乐、队列和产品呈现逻辑属于插件。
- 官方基础插件随应用交付并默认启用；用户无需另装。关闭第三方增强插件不影响默认基础能力。
- 必需服务缺失或用户停用基础提供器时，拒绝不安全操作或进入可诊断恢复状态，不能声称所有插件都关闭后仍能播放。
- 替换服务必须检查依赖及运行中的资源/会话，明确立即生效、停止后生效或重启生效，失败有恢复路径。
- 基础服务故障与增强服务故障区分处理；后者不能错误地把正常播放标记为失败，前者须安全终止受影响操作并报告。
- 播放状态和核心曲目字段有明确唯一所有者；异步补充数据按规则合并，不允许旧结果或其他插件覆盖当前会话。

## 输入、输出与状态

- 输入：插件包/内置声明、官方组合、用户覆盖配置、授权决定、启停/更新操作、业务服务请求与事件。
- 输出：装配后的服务和 UI 贡献、实际运行状态、操作结果、错误原因、受影响依赖、是否要求重启及恢复建议。
- 状态至少区分可用、被禁用、等待依赖、启动中、运行中、停止中、失败、等待重启；安装状态独立于运行状态。具体枚举由 Architecture Agent 确定。
- 拒绝或失败不得产生成功状态；只有服务和资源完成实际启动/退出后才能报告相应完成结果。

## 边界情况

- 默认基础插件丢失、损坏、版本不兼容或依赖成环。
- 多个插件同时声明唯一播放服务；一个提供器替换时仍存在依赖者或播放会话。
- 启动执行到一半失败，停止超时，连续启停或开发重载。
- 切歌、退出或禁用后，旧歌词/元数据任务继续完成。
- 配置更新无效、数据迁移失败、更新中断或卸载涉及用户数据。
- 第三方插件越权调用文件/网络服务、发送无效消息或尝试直接访问原生能力。
- TS/Rust 连接中断，消息重复或迟到，音频设备丢失或服务异常。

## 验收标准

以下为最终目标的完成定义，须由实现、运行证据和独立验证共同证明；本文写完只代表目标已固化。

| ID | 可验证结果 | 所需证据 |
| --- | --- | --- |
| AC-01 | 当前业务覆盖清单逐项映射到官方插件，未来业务有统一接入约束；宿主无音乐业务和固定业务 UI 实现 | 模块归属清单、代码依赖检查及架构审查 |
| AC-02 | 新安装离线启动官方组合，完成当前发布版本要求的播放控制、队列和展示；不要求另装插件 | 制品安装与离线操作记录 |
| AC-03 | 官方与第三方业务均经过相同服务/依赖/生命周期机制，差异均有明确策略声明 | 官方及第三方样例的注册、启停、授权证据 |
| AC-04 | PH-01 至 PH-11 每项有实现和测试/操作证据，缺少任一项不得报告完整目标完成 | 宿主能力验收矩阵 |
| AC-05 | 缺失/循环依赖、唯一服务冲突与版本不兼容在执行前拒绝，诊断指出具体插件和原因 | 故障注入测试 |
| AC-06 | 服务调用、提供器选择和合法替换可验证；非法运行中替换被拒绝或受控退出，无状态双写 | 替换组合测试、状态所有权检查 |
| AC-07 | 启动失败回收、逆序停止及连续至少 10 次启停后，无该插件残留订阅、任务或资源记录 | 生命周期测试及资源统计 |
| AC-08 | 切歌、禁用、卸载后旧任务结果不回写；超时和取消有结束状态 | 异步乱序、取消和超时测试 |
| AC-09 | 配置校验、配置/数据迁移、插件间存储隔离及迁移失败恢复可重复验证 | 有效/无效/旧版本配置和迁移故障测试 |
| AC-10 | 未授权文件、网络或播放控制请求被实际拒绝；选定执行环境符合声明的信任边界 | 权限与执行环境验证，包含跨端入口 |
| AC-11 | 包安装、更新、取消、卸载、失败恢复及重启生效状态可从真实操作结果确认；用户数据处置明确 | 管理操作和故障恢复记录 |
| AC-12 | 跨端无效消息、断连、迟到响应和错误转换不会产生虚假成功或更新失效会话 | TS/Rust/Tauri 契约及异常测试 |
| AC-13 | 日志/状态能定位失败插件、依赖、阶段和原因；开发重载结束后旧实例资源清理完毕 | 诊断查询、依赖图和开发重载记录 |
| AC-14 | 默认组合和至少一个合规替换组合通过原有业务回归；关闭第三方增强后官方基础能力继续可用 | Test Agent 独立报告、格式基线及操作证据 |
| AC-15 | 实施前确定的性能门槛有测量并通过；构建、静态检查、宿主/契约/回归检查全部通过 | 对应平台测量及检查输出，包括 `npm run build`、`npm run lint` 和 Rust 检查 |
| AC-16 | 开发者仅使用公开 SDK 和示例即可构建、装配及退出合规插件；配套测试能检出依赖/权限拒绝和退出资源残留 | 示例构建运行记录、SDK 接口检查及故障测试 |

## 开放问题

- 复用 Cordis、借鉴其机制自研，还是分别实现 TS/Rust 宿主适配？需基于源码、维护成本、依赖和运行环境评估。
- 第三方插件支持哪些语言、包格式和运行环境？哪些能力需要隔离，原生解码/DSP 能否开放以及以何种模式开放？
- 哪些服务允许多个提供器、运行时切换或开发重载？实时音频会话的替换和故障恢复条件是什么？
- API 版本兼容、插件更新、用户数据迁移与分发信任如何定义？离线安装包校验和可信来源范围是什么？
- 宿主中需要保留哪些启动/恢复界面，其基础设施边界如何防止固定业务 UI 回流？
- 量化性能预算、支持平台、迁移顺序、目标版本及历史配置兼容期限是什么？

## 风险

- 全业务迁移涉及 React、Tauri、Rust、音频及持久化，边界不清会形成另一套业务绕过通道。
- 管理生命周期、权限控制和执行隔离是不同能力，不能因参考项目具有前者而推断具备后两者。
- 参考项目的 Node/Agent 运行负载与实时音频不同，不能直接复用其热更新或同进程执行假设。
- 拆分过细会增加音频路径开销；拆分过粗或仅给模块贴上插件名称又无法验证替换能力。
- 目标完整但实现未排期，若与当前版本交付混淆，会形成没有证据的发布承诺。

## 建议

由 PM Agent 保持目标与当前发布范围区分，并在架构评估后决定实施版本。Architecture Agent 应先明确宿主/业务边界、统一服务与生命周期、跨端契约、信任模型和实时音频约束，再进入迁移实现。最终按完整业务覆盖和 PH-01 至 PH-11 验收，允许分段交付，但不能以较小试验替换完整目标。
