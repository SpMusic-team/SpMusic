# 需求分析：内置播放队列

## 摘要

SpMusic 需要存在一个内置播放队列，用于决定当前播放上下文和下一首播放内容。该队列不要求提供独立的“播放队列页面”，用户从歌单列表播放歌曲时，默认以该歌单作为当前播放队列；用户也可以手动将歌曲设置为“下一首播放”，将歌曲插入当前队列的下一播放位置。

## 用户问题

用户在本地播放器中通常希望“从哪里开始播放，就继续按那个列表播放”，同时又希望临时插入一首想听的歌，而不破坏原本的歌单播放上下文。如果没有明确的内置播放队列规则，歌单播放、下一首播放、上一首 / 下一首、随机 / 循环等行为会变得不可预测。

## 目标用户

- 通过歌单、专辑、文件夹或搜索结果连续播放歌曲的普通用户。
- 希望临时插入歌曲但不手动重建歌单的用户。
- 需要为播放状态、播放列表和音频引擎定义边界的后续实现 Agent。

## 用户场景

- 用户在某个歌单中点击一首歌曲，SpMusic 从该歌曲开始播放，并将该歌单作为当前播放队列。
- 用户在播放歌单 A 时，从其他列表中选择一首歌曲并执行“下一首播放”，该歌曲插入到当前播放歌曲之后。
- 用户插入下一首歌曲后，当前歌曲播放结束或用户点击下一首时，优先播放被插入的歌曲。
- 用户不需要进入专门的播放队列页面，也能通过播放行为感知队列存在。

## 优先级建议

P1。

播放队列是播放器核心行为之一，但不进入 v0.1 播放界面。建议在虚构播放列表管理 UI、真实音频播放、基础播放列表或歌曲来源模型进入目标版本时同步纳入分析和计划。

## 版本建议

不建议进入 v0.1。建议作为真实播放能力和基础播放列表能力之后的核心需求进入后续目标版本。若 PM Agent 批准真实音频播放或基础播放列表工作，本需求应作为前置或并行需求参与边界定义。

## 范围

- 应用存在一个内部播放队列。
- 播放队列不需要独立页面展示。
- 从歌单列表播放歌曲时，默认以该歌单的歌曲列表作为当前播放队列。
- 当前播放歌曲应在队列中有明确位置。
- 用户可以对歌曲执行“下一首播放”。
- “下一首播放”会将歌曲插入当前播放歌曲之后，优先于队列中原本的下一首。
- 播放队列应支持上一首 / 下一首行为读取当前队列状态。
- 播放队列应能记录队列来源，例如来自某个歌单。

## 不在范围内

- 独立播放队列页面。
- 可视化拖拽排序队列。
- 批量编辑播放队列。
- 保存播放队列为歌单。
- 跨设备同步播放队列。
- 云端播放队列。
- 智能推荐插队。
- 插件修改播放队列规则。
- 复杂随机播放算法和高级循环策略。

## 假设

- “歌单”在后续版本中会作为可播放歌曲列表存在。
- “下一首播放”可以从歌单、歌曲列表、搜索结果、专辑或文件夹列表等歌曲入口触发。
- v0.1 中的假播放列表和假歌曲数据只用于 UI 状态验证，不代表本需求已经实现。
- 播放队列是播放器内部状态，不等同于用户创建的播放列表。

## 依赖

- 真实音频播放能力。
- 歌曲实体或最小曲目信息模型。
- 播放列表或可播放歌曲列表的来源模型。
- Architecture Agent 对播放状态、队列状态和音频引擎边界的定义。
- UI/UX Agent 对“下一首播放”入口和反馈方式的定义。

## 功能需求

- FR-001：系统必须维护一个内部播放队列。
- FR-002：内部播放队列默认不要求通过独立页面展示。
- FR-003：用户从歌单列表播放某首歌曲时，系统必须将该歌单内歌曲作为当前播放队列。
- FR-004：用户从歌单列表中间歌曲开始播放时，当前歌曲必须设置为被点击歌曲。
- FR-005：用户点击下一首时，系统必须按当前播放队列决定下一首歌曲。
- FR-006：用户点击上一首时，系统必须能按当前播放队列和播放历史规则返回上一首歌曲。
- FR-007：用户对某首歌曲执行“下一首播放”时，系统必须将该歌曲插入当前播放歌曲之后。
- FR-008：如果已有手动插入的下一首歌曲，后续“下一首播放”的插入顺序必须有明确规则。
- FR-009：手动插入的歌曲播放后，系统应继续回到原播放队列中尚未播放的后续歌曲。
- FR-010：播放队列必须能区分队列来源，例如歌单、专辑、文件夹或搜索结果。
- FR-011：当前播放歌曲不应因为插入“下一首播放”而立即中断。
- FR-012：如果用户直接从另一个歌单播放歌曲，系统应将当前播放队列替换为新的歌单队列。

## 非功能需求

- NFR-001：播放队列规则必须稳定、可预测，并能被验收用例覆盖。
- NFR-002：播放队列不应依赖网络或账号系统。
- NFR-003：播放队列状态应与歌单数据解耦，避免临时插入操作修改原歌单内容。
- NFR-004：播放队列应与播放列表、媒体库和音频引擎保持清晰边界。
- NFR-005：在未提供独立队列页面时，用户操作后仍应获得可识别反馈。

## 输入与输出

- 输入：从歌单播放歌曲、点击上一首、点击下一首、执行“下一首播放”、从新的可播放列表直接播放歌曲。
- 输出：当前播放歌曲、内部播放队列、队列来源、下一首歌曲、播放状态反馈。

## 关键规则

- 播放队列是内部播放上下文，不等同于歌单。
- 从歌单播放歌曲会创建或替换当前播放队列。
- “下一首播放”只影响当前播放队列，不修改原歌单。
- “下一首播放”插入的歌曲应优先于原队列中的自然下一首。
- 当前歌曲正在播放时，插入下一首不得打断当前播放。
- 不设置专门队列页面不代表系统不存在队列状态。

## 边界情况

- 用户在空歌单中尝试播放。
- 用户在只有一首歌的歌单中播放。
- 用户连续多次执行“下一首播放”。
- 用户对当前正在播放的歌曲执行“下一首播放”。
- 用户对已在当前队列中的歌曲执行“下一首播放”。
- 用户在已有手动插入歌曲时切换到另一个歌单播放。
- 原歌单被修改、删除或其中歌曲被移除。

## 异常情况

- 被插入的歌曲不可播放时，系统应跳过该歌曲或展示错误状态，具体策略需后续定义。
- 当前播放队列为空时，点击下一首不得导致应用崩溃。
- 歌单来源不存在时，播放队列仍应保留足够的曲目信息用于当前播放，或进入明确的不可播放状态。

## 数据或权限约束

- 播放队列不得要求用户登录账号。
- 播放队列不得默认依赖云端同步。
- 手动插入队列不得写回原歌单。
- 如后续需要持久化播放队列，应单独分析存储范围和隐私边界。

## 验收标准

- 文档明确播放队列是内部状态，不要求提供独立页面展示。
- 从歌单列表播放某首歌曲后，当前播放队列来源为该歌单。
- 从歌单列表播放某首歌曲后，当前歌曲为用户点击的歌曲。
- 点击下一首时，系统根据当前播放队列切换歌曲。
- 执行“下一首播放”后，被选择歌曲位于当前歌曲之后。
- 执行“下一首播放”不会修改原歌单歌曲顺序。
- 有手动插入歌曲时，点击下一首优先播放手动插入歌曲。
- 手动插入歌曲播放完成后，系统继续播放原队列后续歌曲。
- 从另一个歌单直接播放歌曲后，当前播放队列被替换为新的歌单队列。
- 空队列、单曲队列和连续插入下一首均有明确处理规则。

## 开放问题

- 连续多次“下一首播放”时，后插入的歌曲应排在已插入歌曲之后，还是始终插到当前歌曲之后？
- 对当前正在播放的歌曲执行“下一首播放”时，应忽略、提示，还是允许形成重复队列项？
- 对已在当前队列中的歌曲执行“下一首播放”时，应移动原队列项，还是新增一个重复队列项？
- 上一首行为应基于队列顺序、真实播放历史，还是两者结合？
- 播放队列是否需要在应用重启后恢复？
- 随机播放和循环播放进入范围后，应如何影响手动插入的“下一首播放”优先级？

## 风险

- 如果播放队列和歌单概念混淆，临时插入操作可能误修改用户歌单。
- 如果不定义连续插入规则，下一首播放行为会在实现和用户预期之间产生分歧。
- 如果不提供专门队列页面，用户可能缺少对插入结果的可见反馈，需要 UI/UX Agent 设计轻量反馈。
- 如果过早引入持久化队列，会扩大数据层和恢复逻辑范围。

## 建议

建议 PM Agent 将本需求标记为 v0.1 之后的 P1 核心播放行为需求。进入实现前，建议 Architecture Agent 先定义播放队列、播放历史、播放列表和音频引擎之间的状态边界；UI/UX Agent 需要定义“下一首播放”的入口、反馈和无专门队列页面时的可感知状态。
