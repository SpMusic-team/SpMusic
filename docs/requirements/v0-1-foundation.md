# v0.1 项目地基版本需求分析

## 摘要

v0.1 的目标是建立 SpMusic 的项目地基，而不是实现完整播放器。该版本从 `docs/requirements/总需求分析.md` 中切出最小可验证范围，用于验证项目身份、播放器外壳、前端状态、前后端通信和基础验收流程。

## 用户问题

当前项目仍保留模板应用形态，无法表达 SpMusic 的产品方向，也缺少后续开发所需的基础边界。团队需要先建立一个足够小、可运行、可验证的版本，避免直接从最终愿景跳到真实播放、媒体库、网络存储或插件系统。

## 目标用户

- 需要确认 SpMusic 产品方向的项目维护者。
- 需要基于明确验收标准开展实现工作的开发 Agent。
- 需要在真实播放和媒体库前验证 Tauri + React 工程链路的协作者。

## 用户场景

- 用户启动桌面应用，首屏能识别为 SpMusic，而不是模板项目。
- 用户看到静态播放器外壳、当前歌曲信息和歌曲列表。
- 用户点击播放 / 暂停 / 上一首 / 下一首，界面状态发生可预测变化。
- 用户看到前端与 Rust/Tauri 后端通信成功或失败的状态。

## 优先级建议

P0 / P1。

v0.1 是后续所有真实播放、媒体库、播放列表和扩展能力的工程地基，必须先完成。

## 版本建议

建议进入 v0.1。该版本只承接最终需求中的“项目地基”和“播放器外壳验证”部分，不承接真实音频播放、媒体库、网络存储或插件能力。

## 范围

- SpMusic 项目身份。
- 静态播放器主界面。
- 假歌曲队列，至少 5 条。
- 当前歌曲展示。
- 播放 / 暂停 / 上一首 / 下一首的 UI 状态切换。
- 最小前端播放器状态结构。
- 空队列 Empty State。
- 最小 Tauri command 通信验证。
- 基础验证命令和人工检查项。
- README 与版本范围说明。

## 不在范围内

- 真实音频播放、音频解码、音量、进度拖动。
- 本地文件夹扫描、媒体库索引、元数据解析。
- 数据库、缓存、迁移系统。
- 播放列表真实创建、编辑、导入、导出。
- FTP、SMB、WebDAV 网络存储播放。
- 歌词、封面、元数据编辑器。
- 插件系统、插件市场、扩展运行时。
- Last.fm、Pano Scrobbler、云同步、自定义功能区。

## 功能需求

- FR-001：应用首屏必须体现 SpMusic 产品身份。
- FR-002：应用必须展示静态播放器主界面。
- FR-003：假歌曲队列必须至少包含 5 条歌曲。
- FR-004：当前歌曲必须展示歌曲名、艺术家、专辑、时长中的至少 3 类信息。
- FR-005：界面必须提供播放 / 暂停、上一首、下一首控制。
- FR-006：播放 / 暂停控制必须只改变 UI 状态。
- FR-007：上一首 / 下一首必须切换当前假歌曲。
- FR-008：歌曲列表必须能标识当前歌曲。
- FR-009：前端必须存在最小播放器状态结构，表达当前歌曲、播放状态和队列。
- FR-010：空队列时必须有可渲染 Empty State。
- FR-011：Rust 侧必须提供一个最小 Tauri command。
- FR-012：前端必须展示 Tauri command 返回结果或连接状态。

## 非功能需求

- NFR-001：核心验证不依赖网络。
- NFR-002：不得引入真实音频播放依赖。
- NFR-003：不得引入媒体库持久化能力。
- NFR-004：不得为了 v0.1 引入复杂架构抽象。
- NFR-005：验收必须能通过构建、Lint、`cargo check` 和人工 UI 检查完成。

## 关键规则

- 假歌曲数据仅用于 UI 和状态验证。
- 播放控制仅改变 UI 状态，不播放真实音频。
- Tauri command 仅用于验证通信链路。
- 队列为空时应用不能崩溃。
- 任何超出 v0.1 范围的能力必须进入后续版本规划。

## 边界情况

- 空队列。
- 单曲队列。
- 连续点击播放 / 暂停。
- 连续点击上一首 / 下一首。
- Tauri command 调用失败。

## 验收标准

- 应用首屏显示 SpMusic，而不是 Vite / React 模板内容。
- 页面展示静态播放器主界面。
- 页面展示至少 5 条假歌曲。
- 当前歌曲展示至少 3 类信息。
- 播放 / 暂停能切换 UI 状态。
- 上一首 / 下一首能切换当前歌曲。
- 当前歌曲在列表中可识别。
- 空队列分支存在并可渲染。
- 前端能调用一个 Tauri command。
- Tauri command 不访问文件系统、不扫描媒体、不播放音频。
- `npm run lint` 通过。
- `npm run build` 通过。
- `cargo check` 在 `src-tauri/` 下通过。

## 开放问题

- 假歌曲数据应放在组件内还是单独 fixture 文件中？
- 最小 Tauri command 返回字符串还是结构化对象？
- 播放控制按钮使用文字、图标还是图标加文字？

## 风险

- 模板残留会影响项目身份判断。
- 总需求很大，容易把后续能力提前塞进 v0.1。
- 如果 Tauri command 不尽早验证，前后端通信风险会后移。

## 建议

建议 PM Agent 基于本文档维护 Sprint 计划和任务卡。Architecture Agent 应先定义播放器状态与命令契约，UI/UX Agent 应先定义播放器外壳规格，然后再进入前端与 Rust/Tauri 实现。
