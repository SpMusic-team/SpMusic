# 总需求分析

## 摘要

SpMusic 的最终产品定位是：美观、高性能、有强大扩展能力的本地音乐桌面播放器。

SpMusic 坚持本地优先，不做在线音乐平台，不提供在线曲库、音乐搜索、内容推荐或版权音乐服务。产品核心价值是通过现代、流畅、触控友好的 UI 与动画体验，配合强大的本地与网络存储音乐管理能力，为拥有大量本地音频、同人音声或复杂文件夹收藏的用户提供可扩展的桌面播放器。

## 用户问题

现有本地音乐播放器通常存在以下问题：

- UI 设计陈旧，缺少现代桌面应用的视觉、动画和交互体验。
- 触控交互不足，难以适配现代桌面与触屏设备。
- 本地音乐管理能力不够适配大量文件、多文件夹、同人音声或非标准元数据场景。
- 一些播放器功能强但系统开销较高，轻量播放器又缺少管理能力和扩展能力。
- 外观自定义和功能扩展能力有限，难以满足不同用户的使用偏好。

SpMusic 要解决的核心问题不是单纯提供播放能力，而是让用户能够以美观、流畅、低开销、可扩展的方式管理和播放大量本地或用户自有网络存储中的音频内容。

## 目标用户

- 拥有大量本地音乐、同人音声或音频文件收藏的用户。
- 对本地播放器外观、动画、触控交互和性能开销有明确要求的用户。
- 不希望被在线音乐、广告、账号体系或内容推荐干扰的用户。
- 希望播放器长期具备外观自定义、功能扩展和高级管理能力的高级用户。

## 用户场景

- 用户以窗口模式打开 SpMusic，浏览音乐库并播放本地音乐。
- 用户将 SpMusic 放在后台播放音乐，并通过主窗口、快捷键或后续高级控制界面操作播放。
- 用户导入多个本地文件夹，并按全部文件夹或指定文件夹范围浏览歌曲、艺术家和专辑。
- 用户分别浏览不同范围的音乐库，例如“艺术家（所有文件夹）”“艺术家（音乐文件夹）”“艺术家（同人音声文件夹）”。
- 用户创建、编辑、重命名、删除、导入和导出播放列表。
- 用户导入或导出标准 `m3u8` 播放列表，并在 SpMusic 中维护播放列表内容。
- 用户查看本地播放历史列表。
- 用户根据设备性能选择不同外观和动画预设。
- 用户在关闭网络的情况下继续播放本地音乐、浏览本地音乐库和使用基础播放列表。
- 用户通过后续高级能力同步应用配置、使用 Last.fm / Pano Scrobbler、拆分自定义功能区或启用更完整的外观自定义。

## 非功能需求

- NFR-001: 应用必须坚持本地优先，核心播放、音乐库、历史和播放列表默认不依赖网络。
- NFR-002: 用户音乐库、播放历史、偏好数据和配置默认应保存在本机。
- NFR-003: 应用不应要求用户登录账号才能使用核心播放器能力。
- NFR-004: 应用在关闭网络时仍应支持本地播放、本地音乐库浏览和基础播放列表。
- NFR-005: UI、动画和触控交互是产品核心差异化能力，不能作为纯装饰功能处理。
- NFR-006: 应用必须支持视觉效果和动画按设备性能降级。
- NFR-007: 应用应在美观和流畅的前提下尽可能降低系统开销。
- NFR-008: 基础能力必须内置，插件只能作为可选增强。
- NFR-009: 音频播放、音乐库、播放列表、网络存储、UI 外观、插件、同步等模块应保持清晰边界。
- NFR-010: 产品应适配大量文件、多文件夹、同人音声、长音频和非标准元数据场景。
- NFR-011: 如继续使用 Tauri 技术路线，应尽量保持 Windows、macOS、Linux 行为一致。
- NFR-012: 界面文案、时间、数字和状态文本应支持国际化扩展，避免把单一语言硬编码到核心界面逻辑中。

## 关键规则

- SpMusic 不做在线音乐服务，但支持用户自有音乐资源的本地与网络存储播放。
- 网络存储播放属于基础内置能力，不应依赖插件。
- 播放、音乐库、播放列表、基础搜索、收藏、播放历史列表和基础主题不应依赖插件。
- 插件系统是长期核心方向，但插件应提供增强能力，而不是基础使用前提。
- Last.fm、Pano Scrobbler、云同步适配和自定义功能区属于高级内置支持，不应只作为第三方插件能力处理。
- 播放历史的基础要求是可查看列表，不要求同时支持搜索、收藏、统计分析或高级筛选。
- 明暗模式属于基础外观能力，应与主题切换兼容。
- 多语言适配属于基础产品能力，应在界面和文案设计中预留。
- 独占音频输出属于高级音频能力，需要在基础播放链路稳定后单独评估。
- 性能档位是产品需求，不只是实现优化；用户应能选择更轻量或更完整的视觉和动画体验。
- 扩展 `m3u8` 信息时必须避免破坏标准播放列表兼容性。

## 边界情况

- 用户导入多个文件夹，其中部分文件夹属于音乐收藏，部分属于同人音声收藏。
- 用户只选择某个文件夹范围浏览时，艺术家、专辑、歌曲分类结果必须只来自该范围。
- 用户关闭网络后，应仍可播放本地音乐并浏览本地音乐库。
- 用户关闭插件后，基础播放、音乐库、播放列表和网络存储播放能力仍应可用。
- 用户使用低性能设备时，应能选择较低动画和视觉效果档位。
- 用户导入标准 `m3u8` 文件时，即使文件不包含 SpMusic 扩展信息，也必须能正常读取基础播放列表内容。
- 用户导出 `m3u8` 文件时，应能被标准播放器识别基础列表内容。
- 音频文件元数据缺失或不标准时，应用仍应能在音乐库中展示可理解的后备信息。

- 文档明确 SpMusic 支持用户自有本地与网络存储音乐资源。
- 文档明确核心能力本地优先，关闭网络时仍可完成本地播放和本地音乐库浏览。
- 文档明确最终需要真实本地音频播放，并优先支持 `flac`、`wav`、`aac`、`mp3`。
- 文档明确最终需要音乐库、文件夹扫描、歌曲索引和按文件夹范围浏览。
- 文档明确最终需要播放列表创建、编辑、删除、导入、导出和 `m3u8` 支持。
- 文档明确播放历史基础要求是可查看列表。
- 文档明确网络存储播放属于基础内置能力。
- 文档明确明暗模式和不同语言界面适配属于基础产品能力。
- 文档明确独占音频输出属于高级音频能力。

## 开放问题

- 真实音频播放应采用哪个底层音频方案，以及各平台格式支持边界是什么？
- 独占音频输出应支持哪些平台和后端能力，例如 WASAPI Exclusive、Core Audio 或 ALSA/PulseAudio/PipeWire 相关能力？
- 首批多语言适配应支持哪些语言，以及是否需要跟随系统语言自动切换？
- 网络存储播放是否需要与本地音乐库使用统一来源抽象？
- `m3u8` 扩展信息应保存在播放列表文件内，还是保存在 SpMusic 自有配置 / 数据文件中，以避免兼容性风险？
- 同人音声场景是否需要额外支持长音频章节、分轨、作品维度或社团维度？
- 云同步应同步哪些数据：应用设置、外观配置、插件配置、播放列表、播放历史或收藏？
- 自定义功能区是否需要作为窗口系统能力、布局系统能力，还是插件 / 主题系统的一部分？
- 插件系统应开放哪些 API，哪些能力必须禁止插件访问？

## 风险

- “美观、动画、触控、高性能”之间存在天然张力，需要尽早定义性能档位和降级规则。
- 插件系统如果过早进入，会拖慢基础播放器能力建设并污染核心边界。
- 网络存储播放和云同步容易被误解为在线音乐服务，需要在产品文档中持续强调边界。
- 同人音声场景可能带来长文件、分轨、文件夹结构、封面、元数据不标准等特殊复杂度。
- 播放列表扩展字段可能影响标准 `m3u8` 兼容性。
- 可拆分、可置顶功能区会影响窗口管理、状态同步、布局系统和插件 API，需要后续单独分析。
- 音频格式支持范围会受底层音频库、系统解码能力和跨平台差异影响。

## 建议

建议将本文档作为 SpMusic 的最终产品总需求分析草案，交由 PM Agent 和 Architecture Agent 评审。

PM Agent 应基于本文档维护路线图、排期和实施边界。Architecture Agent 应优先评估真实音频播放、音乐库索引、网络存储播放、插件系统、自定义功能区和云同步对架构边界的影响。
