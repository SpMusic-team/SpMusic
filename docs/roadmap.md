# SpMusic 路线图

## 摘要

SpMusic 是本地优先的桌面音乐播放器。既有版本路线保持先建立可运行的真实本地播放闭环，再扩展播放列表、媒体库、网络存储和外观自定义。2026-09-30 确认长期架构目标：建立较完善的插件宿主框架，使所有业务能力通过插件装配，官方基础插件随产品交付。

长期目标已确认，当前实现尚未具备该插件系统，实施版本和日期未排期。本次不调整既有 v0.1～v0.6 候选路线和当前 Sprint；插件化作为独立长期工作流，后续由 PM 依据需求与架构拆分实施计划。参见[目标决策](decisions/2026-09-30-all-business-plugin-system-goal.md)。

2026-10-01 架构设计基线形成，产品实现与运行验证未完成。设计采用 Rust 全局治理、选择性 Cordis 核心适配与多执行环境；设计审查不等于依赖采用、第三方隔离或实际音频验证通过。参见[宿主设计](architecture/plugin-host-design.md)、[架构决策](decisions/2026-09-30-plugin-host-architecture.md)和[独立设计审查](test/plugin-host-design-review.md)。

## 版本规划

### v0.1 真实本地播放可发布闭环

目标：在当前播放器界面基础上，实现一个可验证的真实本地音频播放链路。

范围：

- SpMusic 项目身份、README 和基础工程检查。
- 播放器界面、当前歌曲展示和基础播放控制。
- 最小 Tauri command 契约。
- Rust/Tauri 真实音频播放后端。
- 本地音频资源的播放、暂停、继续、停止、seek 和进度状态。
- 前端接入真实播放 command。
- 用户选中文件后，对同目录音频执行非递归、只读枚举，并形成当前会话临时队列。
- 用户直接选择 `.m3u8` 文件时，可生成本地、只读、当前会话临时队列；本地绝对路径允许指向其他目录。
- 临时队列的上一首、下一首、直接选择和自然结束切换。
- 基础标签及嵌入式歌词 / 封面的读取展示与缺失后备。
- 以确定性合成语料验证的当前解码兼容性基线；只声明当次有证据的组合。
- 真实播放综合验证、Tauri 制品构建、版本一致性和制品 smoke。

不包含：

- 递归扫描、媒体库、文件监控、数据库和持久化索引。
- 产品级播放列表、临时队列持久化、跨目录队列、播放历史、收藏、网络 HLS 和完整 `m3u8` 导入导出。
- 网络 / sidecar 歌词、逐字歌词、歌词 / 封面 / 标签编辑。
- CUE / M4B 公共交互、FFmpeg 运行时 fallback、跨曲目 gapless。
- 网络存储播放。
- 真实频谱分析、高级 DSP、独占输出。
- 插件系统。

### v0.2 队列与播放列表体验收敛

目标：在真实播放最小闭环稳定后，补齐播放列表 UI 的可用体验。

候选范围：

- 把 v0.1 的只读同目录临时队列收敛为有明确需求的队列体验。
- 队列展示、排序 / 移除候选、上一首 / 下一首联动和空状态。
- 虚构或轻量播放列表管理 UI；是否持久化由 Requirements Agent 另行批准。
- 播放错误、后端不可用和无音频资源时的 UI 状态。
- 根据 v0.1 后端反馈调整播放控制细节。

不包含：

- 完整媒体库扫描。
- 数据库持久化播放列表。
- 网络存储播放。

### v0.3 本地音乐库地基

目标：建立本地音乐库最小闭环。

候选范围：

- 选择本地文件夹。
- 扫描音频文件。
- 基础歌曲索引。
- 按歌曲浏览。
- 缺失元数据后备展示。
- 本地数据存储方案决策。

### v0.4 本地音乐库浏览与真实播放列表

目标：让本地音乐管理进入可日常使用的基础形态。

候选范围：

- 按艺术家、专辑浏览。
- 按文件夹范围过滤。
- 基础搜索。
- 收藏 / 喜欢。
- 播放历史列表。
- 基础播放列表。
- `m3u8` 导入导出策略。

### v0.5 网络存储播放

目标：支持用户自有网络存储中的音频资源。

候选范围：

- FTP / SMB / WebDAV 来源抽象。
- 网络文件浏览或引用。
- 流式播放能力评估。
- 离线与错误状态处理。

### v0.6 UI、性能与多语言

目标：强化 SpMusic 的核心体验差异化。

候选范围：

- 明暗模式。
- 基础主题切换。
- CSS token 白名单式视觉自定义。
- 多语言适配基础。
- 动画、动效 token 和视觉性能档位。
- 触控友好的关键交互。

### 后续高级能力

- 网络 / sidecar / 逐字歌词、歌词编辑和歌词来源管理。
- 专辑封面搜索、替换、编辑和缓存策略。
- 元数据编辑器。
- 智能播放列表。
- 独占音频输出。
- 收听记录可视化。
- Last.fm / Pano Scrobbler。
- 云同步适配。
- 自定义功能区。
- 可拆分、可置顶功能区。
- 全业务插件体系，按下述独立长期工作流推进。

## 独立长期工作流：全业务插件化

目标：参考 dsh/Cordis 的成熟机制，设计较完善的宿主基础设施，将现有播放控制、队列、解码、音频输出、歌词、元数据、封面、主题、播放器 UI 和业务设置 UI 迁移为官方插件。以后单独批准的媒体库、网络存储等业务能力也遵守同一套规则。

完整宿主覆盖插件描述与兼容、服务容器、依赖装配、生命周期与资源、配置持久化、事件任务、权限与执行环境、安装更新、跨端桥接、诊断开发以及测试与 SDK 十一类能力。具体范围和验收见[单项需求](requirements/all-business-plugin-system.md)，运行边界见[架构方向](architecture/all-business-plugin-system.md)。

| 阶段 | 目标 | 进入下一阶段的依据 |
| --- | --- | --- |
| 一：宿主框架与官方业务迁移 | 通过统一宿主规则装配完整默认播放器，迁移全部现有业务并确定后续治理与扩展边界 | 全部现有业务有插件归属；默认制品无需额外安装；依赖、启动失败、清理、状态权威和当前播放回归有验证证据 |
| 二：插件治理与第三方接入 | 完成兼容、权限、安装更新、存储迁移、受限执行和 SDK/诊断管理闭环 | 不兼容、越权、故障、更新恢复和卸载清理可验证；权限与执行边界经过审查 |
| 三：深层音频扩展 | 开放解码、输出、DSP 的替换与组合，完成会话迁移、性能和恢复规则 | 唯一会话权威、替换前置条件、实时预算、音频兼容与实际播放回归有相应证据 |

阶段用于完整覆盖最终目标，未承诺版本和日期，也不等于批准立即实施。歌词演示或只开放增强点不能作为全业务插件化完成依据。最终按十一类基础设施、全部业务归属及音频扩展规则逐项验收。

架构设计基线已选择 Rust 作为全局装配、权限与生命周期权威，Cordis 仅在可替换适配层辅助可信官方 TS 插件；官方 Rust 插件随应用静态编译交付，第三方通过受限独立 runner 接入。公开 SDK 不绑定 Cordis，具体依赖制品、引擎与平台配额、包签名方案和量化性能预算仍须在相应验证闸门冻结。插件市场、云分发服务和新业务功能不自动进入该工作流范围。

下一步是**G1～G5 选型验证原型与实现任务拆分**。五个闸门目前全部未取得运行验证证据，按[宿主设计的验证条件](architecture/plugin-host-design.md)推进：

- G1：验证 Cordis 精确制品、许可、浏览器构建与受控生命周期；失败则采用自研 TS 作用域适配。
- G2：验证第三方 JS/WASM runner 的实际能力隔离、平台配额、身份绑定与终止边界。
- G3：验证依赖与跨 part 装配、配置迁移、安装更新事务、中断恢复和回滚。
- G4：建立现有可听播放与性能基线，验证有界 PCM、预读、资源退出及音频替换协议。
- G5：验证全部现有业务归属、默认离线装配、旧入口退出、用户数据兼容和完整业务回归。

PM 根据这些证据要求拆分后续原型与实现任务，明确责任 Agent、文件所有权及验收；本次仅完成设计阶段索引，不生成任务卡、不调整 Sprint，也不将设计通过写成产品完成或发布通过。

## 范围护栏

- 所有业务能力最终通过统一插件规则组织；基础播放等能力由随产品交付的官方插件和经过验证的默认组合保障，不要求用户额外安装第三方插件。
- 官方插件和第三方插件遵守统一规则。可选插件关闭不得破坏默认基础能力；必要插件的停用、替换和故障恢复遵循已审查的依赖与会话规则。
- “全业务插件化”不要求所有插件动态安装或无条件热替换；随产品编译交付的插件仍须参与统一服务、依赖和生命周期管理。
- 新长期目标覆盖旧“仅增强”限制，历史版本的排除范围继续有效；v0.1 不纳入插件系统建设。
- SpMusic 不做在线音乐平台、在线曲库搜索、内容推荐或版权音乐服务。
- 每个版本必须有可验证的完成定义。
- v0.1 的临时队列只允许用户选中音频文件后的同目录非递归枚举，或用户直接选择本地 `.m3u8` 文件；不得把它扩张为选择文件夹扫描、媒体库、网络 HLS 或产品级播放列表。
- 格式能力只按容器、codec、检查维度和平台证据声明；不得由扩展名或编译 feature 外推。
