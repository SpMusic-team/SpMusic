# foobar2000 与 foobaka mixture 双样本研究目标

## 直接交给 DS

> 请用我提供的 foobar2000 原版和 foobaka mixture 实物研究两者的产品设计与实现。先确认每份文件究竟是安装器、便携包、主程序还是完整安装目录，记录实际版本与可观察范围。用相同语料亲自完成可复现的操作对照，优先追踪长列表首次可用、封面首次到达/回访及头图清晰度，再研究播放管理、音频链路和组件边界。每项写出用户动作、结果、实现证据、替代解释、如何证伪、可供 SpMusic 独立实现的原则。按下面的最低交付先形成闭环，再扩展有条件的项目。原件、测试设置、原始观测及未知项都保留可追溯记录。

优先级 P2，属于研究任务。负责人 DS 协调实物盘点和实验。按项目规则由 UI/UX 核对用户路径、Architecture 核对实现归因、Test 核验操作与测量，音频兼容问题由对应角色复核。可用角色与签名据实记录。当任务不能并行时，按阶段串行保存证据，将待独立复核项交接。本轮交付为研究报告和可复跑实验；SpMusic 产品改动另立任务。公开资料研究给出了 L1–L5、M1–M5、P1–P4、O1–O7 的假设与仓库落点，执行时按条核对覆盖状态。[前置研究](../architecture/foobar2000-research.md)

## 1　先确定比较对象

1. 逐一登记原件别名 A（原版）、B（用户提供的 mixture）、到手形态、来源说明、文件名/大小、SHA-256、可读取的签名和版本字段。名称中的“原版”“mixture”先作为样本标签。保留原件，用副本在独立测试目录或虚拟环境操作，各有独立 profile、测试库、输出记录。原件缺失时写明缺哪一份和最低所需输入，继续已具备部分。
2. 先用标准包清单工具读包内容，或在隔离环境按正常流程安装生成目录清单。记录安装前/后、首次启动前/后出现的文件、相对目录、组件名/版本、皮肤/布局、脚本、默认配置、字体/图标等。记录程序“关于”“组件”“输出”“布局/面板”中可见信息，保留关键画面。包内随附、安装时可选和当前启用分别标记。PE 仅采集公开版本资源、普通导入及架构作为静态线索。示例只读命令，实际路径赋给变量后执行。

```powershell
Get-FileHash -Algorithm SHA256 -LiteralPath $samplePath
(Get-Item -LiteralPath $samplePath).VersionInfo | Select-Object ProductName,ProductVersion,FileVersion,OriginalFilename
Get-AuthenticodeSignature -LiteralPath $samplePath | Select-Object Status,SignerCertificate
Get-ChildItem -LiteralPath $isolatedInstallRoot -File -Recurse | Select-Object FullName,Length
```

3. 若只有单个 exe，先判断是否安装器/可列清单的归档，尝试其正常安装或启动流程。独立主程序可能缺 DLL、组件、主题、脚本、配置或 profile；记录实际错误和能够验证的基础事实。可以正常运行时记录实际创建/加载的环境。最小补件列出同版本完整便携/安装目录、默认配置或合法安装包。无法取得时将“B 交付时的默认界面/组件/内部算法”标为未知；社区截图、同名下载或另一个发行版只能作为单独标记的参考。
4. 比较 A/B 核心版本、位数、系统、语言、DPI、主要组件与默认配置。不同核心版本时，能取得与 B 同版同架构的官方包则增加 A' 作控制；否则披露版本混杂。首先保留两套实际默认体验；随后用测试 profile 副本控制一项设置/面板/组件并复跑。通过正常首选项、布局切换、组件管理和公开文本配置做归因。对二进制核心可采用公开 SDK 接口、官方说明和正常行为交叉验证。范围限于产品结构与正常运行观测。
5. 运行时区分“原版也可配置出来”“mixture 默认提供捷径”“随附外部组件实现”“皮肤/脚本改变布局与行为”“核心版本带来能力”“证据尚不足”。同名 DLL、导入符号、菜单名、相同 SHA、SDK 存在接口均不能独立证明某段代码参与了这次动作。记录反例和未识别的提供方。

### 对普通功能做定点静态逆向

每次选择一个明确问题，例如“当前布局先取嵌入封面还是目录图”“切换缓存选项后哪个组件负责读取配置并访问派生图”。在所给二进制副本与随包可读配置中，通过可用符号、菜单/选项名称、配置键、资源标识、字符串交叉引用和普通文件读取调用，定位可能的功能模块与调用关系。保存样本 SHA、模块/版本、函数符号或模块相对位置、引用关系、可观察输入/输出和未知分支，写成简短的模块调用说明。再用只含嵌图、只含目录图、二者冲突及改一项设置的输入，观察来源、文件活动和最终画面；列出能推翻当前解释的结果。缺符号、缺组件或仅发现字符串时如实降低归因置信度。报告交付功能级契约、证据定位和独立行为测试，不附第三方实现代码。

## 2　研究问题与可证伪实验

每项问题都先记录 A/B 原始默认状态，再做单变量干预。记录“可见产物事实 / 正常运行观察 / 公开接口契约 / 推断 / 未知”证据类别。提供 screen、manifest、run 等证据编号与路径。每个机制推断附带至少一个不同的解释及可区分两者的观测。

| 问题 | 操作、证据与判定 | 对应 SpMusic 设计问题 |
| --- | --- | --- |
| 第一屏是否先给文字与可用操作，封面稍后出现？大库重启是否少做工作？ | 同盘同曲库试首次入库、重启、改一首、目录暂时不可达。分别计输入至首行、可实际搜索/播放、首屏封面就绪、扫描结束；记录公开状态/控制台和可得文件 I/O。重启变快也可能是 OS 缓存；保留对照，只有逐项证据才判断增量。 | 标签/时长快照、索引及失效、离线语义，见 L1–L3。 |
| 大幅拖到本次启动未到达区域时，mixture 是更早显示文字、先低清后升级，还是加载了更少图片？ | 两端使用相同本地歌单、排序、显示尺寸和带可识别封面的测试图。保存开场/拖动/松手/目标完全显示录像及帧号、可见条目数、封面面积与身份。默认布局差异单独测，再调到接近的同密度布局复测。已落盘新进程 H、新隔离 profile 从未生成 G、同会话真回访 R 分开。落点位于原可见/加载范围之外；允许未知缓存态，缓存文件变化或回访变快仅作线索。 | 普通行、头图的独立需求，预取、缓存和收益的观察边界。 |
| 详情头图的“清楚”来自更多源图细节还是更小显示区域？ | 同一含小字/细线原图，记录源尺寸、物理显示尺寸、DPI、布局和裁剪。保存原生截图与 1:1 同区域局部；普通卡/详情/正在播放分别测。更换原图、删除嵌图或同目录封面、同名专辑及无图用例，比较选择顺序和失效。请求尺寸或缓存编码不可见时仅报告输出可辨细节；单凭截图无法确定具体缩放核。 | 高档选择条件、来源优先级、坏图恢复和视觉预算。 |
| 找歌、组织与控制播放哪个版本更省步骤？ | 录制从首页找合作曲、流派→艺人联动筛选、多值标签、保存动态规则、改评分后进出列表；区分选中条目、下首、追加队列、永久列表和当前曲。比较默认入口、操作数、反馈、键盘可达、撤销及重启恢复。切换相同布局或组件验证差异归属。 | 联动筛选、自动列表和键盘效率，见 L4–L5、M4。 |
| 哪些整理操作可预测、可恢复？ | 在可丢弃音频副本做批量标签预览、冲突/部分失败、按标签改名移动、换盘重定位、重复引用与统计恢复。记录预览和实际差异，检查歌单引用/评分/次数字段、同标签异版是否误合并。有意重复、缺标签与坏音频单列。 | 整理、迁移、只读体检，见 M1–M3、M5。 |
| 同一 PCM 信号跨曲是否有空隙？ReplayGain、子曲目由谁提供？ | 同源连续信号切成两段 FLAC，自然续播/手切/seek 分开，固定设备与音量；数字捕获可用时比对接缝静音/丢样/重样。使用 Track/Album/缺半组标签，各入口比增益；用 CUE、多章节与重复条目追踪身份、定位及重启恢复。格式覆盖用可分发正常与截断对照语料，标明容器、解码或输出阶段。 | 区分单曲裁剪与跨曲拼接，策略与扫描分离，见 P1–P4。 |
| 两端输出差别来自默认 DSP/设备配置还是核心？ | 记录输出模式、实际设备、源位深/采样率、音量、ReplayGain、DSP、共享混音格式；默认后做等设置对照。按能力测 44.1→48、96→48、48→48，24-bit 低位、声道顺序、暂停/seek/切设备、共享/独占回退。注明测量边界：软件端信号、共享 loopback、数字设备回录、DAC 指示各自支持的结论。可闻差异另需等响度盲测。 | 活跃信号链、PCM 精度、重采样、设备策略与爆音，见 O1–O7。 |
| mixture 的体验可拆成哪些扩展？ | 选一项可切换面板、一项输入/DSP/输出能力，建立“入口→启用项→配置/脚本→公开 SDK 服务契约→观察结果”。在克隆配置禁用/恢复该项，做 A/B/A 验证；记录服务版本和适用范围。主题声明某命令而运行缺组件时记录依赖。 | 对照既有插件路线中的能力声明、版本协商、DSP 边界、缓冲生命周期、出错恢复与卸载。 |

## 3　普通路径的实验规程

- 首批小语料应包含可识别封面/无图/同专辑共享图、不同艺人同专辑名、多值标签及至少一首可播放 PCM 已知的音频。使用匿名夹具、统一排序和冻结清单。长列表用足以令起点/落点目标不相交的数百首开始，记录独立音频/图像数。条件足够再按公开研究扩为 1 万/5 万/10 万首，重复引用另标。两个样本共用只读输入，用户配置、缓存和音频输出分开。
- 一台机器独占测量时段，固定系统显示缩放、播放器版本、窗口、布局、滚动起终点和输入时间，记录测量时是否播放、是否后台扫描。先每种状态做一次 pilot 检查身份和终点，然后同一动作至少 3 对交错重复；按轮报告中位、范围、失败、缺项和原始文件。样本少只作描述，强性能结论需要预登记样本数、设备范围和重复。不同密度的默认布局结果须同时给目标张数和面积。
- 封面计时以输入前开始录制，松手时冻结屏内固定有图集合，到全部正确图稳定出现为终点。报告松手空白数、半屏/90%/全齐及拖动中空白暴露。用两帧稳定画面、录像帧率和人工/脚本复核交代误差。缺图保留在分母并注明超时。黑盒应用无法证明纯 H/G 时标“新会话已有/无准备产物，真实命中未知”。回访须先在本会话实际全齐再离开返回。
- 只在专属测试 profile 修改配置或使用组件的正常管理入口，保留改前快照、改后证据并恢复一次。文件 I/O、CPU、私有字节等采样记下工具、时间窗、进程族和采样率。资源数值无法替代主观路径或用户可见计时。公开 SDK/更新日志按版本及具体文件/接口定位；外部作者组件单列来源和许可证。
- DS 能力以实际可运行工具为准。只有文件访问则先交清单、版本、资源、公开契约与可由另一台 Windows 机器运行的实验卡。只能人工操作则保存手工操作/录屏证据。无 PCM 捕获则保留设备设置、输出状态和主观现象，写明接缝样本、位深保留、bit-perfect 仍待核实。遇到工具无法使用（含绕过或后来恢复）即填写[本次能力报告](../test/foobar2000-foobaka-ds-capabilities.md)，若不可写交付可复制的完整 Markdown。每阶段留 SHA、证据编号、已完成项目和下一步操作。

## 4　最低交付、完整交付及独立设计

1. 在本机研究目录按 A/B/profile/run 分目录保存 manifest、匿名语料、版本与配置快照、观测明细和实验脚本；在仓库报告中给证据索引与摘要。避免将安装包、第三方 DLL、私有配置、受许可限制的皮肤/脚本和音频一并提交。
2. 首批最低闭环为两份实物清单与版本、同一用户任务的一条 A/B 操作路径、一次长列表/封面首次到达和真回访、至少一个可逆干预后复现的归因实例、一个音频或组件契约案例，以及三项有证据的 SpMusic 候选。若样本本身不含所需能力或输入不全，提交已完成的部分、实际阻塞、精确补件和复跑步骤；完整交付状态保留待测。可先交最低闭环再分批扩展上表方向。
3. 最终研究报告建议路径 `docs/architecture/foobar2000-foobaka-comparative-research.md`，由 Architecture 归纳。原生实验协议、逐轮数字/失败与复核建议汇入 `docs/test/foobar2000-foobaka-comparison.md`。每个 L/M/P/O 条目和插件领域标注“实测/公开契约/仅假设/未覆盖及原因”。能力日志另存，不混入观察结果。
4. 每条核心结论以“样本和版本 / 操作 / 证据编号 / 观察 / 归因与可信度 / 替代解释 / 可证伪测试 / 对用户的影响”呈现。并列展示默认体验和受控实验。若仍有核心与组件版本混杂、实验容量不足或观察不到内部调度，直接报告未知。
5. 给 SpMusic 的建议按价值、实现与维护成本、风险和证据强弱排序。每项写明现有模块与行为、欲解决的用户问题、可独立编写的最小实现思路、替代设计、可量化验收与回滚条件。例如先以公开契约和自建语料测“改一首是否只重读一首”“回访是否保持已知封面”“自然续播接缝是否连续”。现成组件、脚本和皮肤保留原作者与分发边界；借鉴应落实为独立的数据契约、界面操作和验证标准。
