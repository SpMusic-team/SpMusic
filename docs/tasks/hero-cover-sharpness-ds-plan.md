# 列表详情头图清晰度与两会话并行执行方案

## 给第二个 DS 会话的指令

> 执行本文件，目标是让播放列表、专辑及文件夹等分类详情头图在大窗口和高 DPI 下显示更多源图细节。先在独立工作树完成阶段 0 的现况、证据和决策单。按已确认的产品选择与架构契约分批实现，检查低清占位到高清替换、资源预算、错误恢复以及普通列表首次到达速度。与正在执行列表提速的会话共用一个基线，分别留存补丁，协调者依本文件安排交叉验证。每阶段写 checkpoint。任何工具不可用，立即填本任务的独立能力报告，给出能继续执行的下一步。

P2 体验增强。正式技术输入为[头图架构方案](../architecture/hero-cover-sharpness-plan.md)，列表 H/G/R 的测试口径见[首次到达任务](./opt-0018-post-r1-first-visit-ds-plan.md)。架构方案中的历史行号、预算和选档推导需针对所冻结 SHA 核对。这里的数字均为验收设计或历史推导。

## 阶段 0　隔离工作与准备决策

1. 双方记录同一 develop 完整 SHA（须含 R1）、git status、环境和可用空间。各自建具名分支及不同绝对路径的 worktree，一方只写自己的树。分配独立的 node 构建输出、Cargo target、exe、LOCALAPPDATA 隔离根、WebView profile、CDP 端口、进程及证据目录。资源清单注明 PID、启动时间和路径。只读语料可共用；索引、缩略图及测试结果独立。把写集和时段贴给协调者，两个 DS 聊天能否互通以实际工具为准。没有通信工具时将协调单交项目负责人转达。
新工作树不会继承协调目录尚未提交的方案和模板。DS 可从 D:/spmusic/docs/tasks 和 D:/spmusic/docs/test 读取本文件与本会话模板，将模板复制到本任务工作树对应位置并记录来源摘要。两个聊天的能力报告各自独立填写。
2. 另一会话可同时做源码阅读、报告整理或不干扰测量的准备。**同一测试机的原生计时、内存采样独占时间段**，在书面排期中写起止、执行者、机名、活动进程，确认另一会话暂停构建、基准及其他重负载后开跑。长跑受打扰标记原因，按预登记规则重做整对。共用工作树时仅可分别读代码，先建隔离环境再分头写入。
3. 热点文件逐个登记，特别是 useAudioPlayer.ts、useLibraryArtwork.ts、useAllSongsWindow.ts、audioCommands.ts、playlistCoverPathLane.ts、cover_pixels.rs、共享测试及 benchmark。每个相交文件只指派一个写入人，另一方交付符号级需求，由协调者串行纳入。避免双边同时修改同一协议。分配不清时先做各自独立部分。最终集成由协调者在第三棵工作树处理，保留两组可单独构建的补丁。
4. 记录当前各入口实际 owner、两条请求通道/允许 edge、前后端响应校验、DOM 错误回调、资源持有者、回收时机、当前预算、失败计数。用高分辨率且允许测试的图（小字/斜线/纹理、照片各一组）和小原图、透明/EXIF/坏图作对照。记录源尺寸、散列、方向、显示裁剪、DPR、当前请求档及响应真实宽高。可离线准备截图裁剪脚本、计算各档成本、编写失败注入与测试草案。所有这些工作可在产品选择前进行。
5. 每次工具缺失、调用失败、无权限、原生窗口不可控、代理不可用，均追加到[本会话工具能力报告](../test/hero-cover-sharpness-ds-capabilities.md)。附平台/版本、调用、原始错误、时间和证据、重试/替代及局限、计划影响和恢复状态，已绕过者也保留。无法写文件时在回复中给完整可复制的报告及路径。仅有浏览器 mock 时可验证路由、尺寸变化与失败逻辑，真机清晰度与常驻开销留待原生执行者。每次恢复对齐 SHA、决策版本和已完成样本对。

### D1–D3 决策单

执行者将下表连同阶段 0 证据交产品负责人填写。记录每项选择、人、时间、适用入口和版本。架构建议供选择，未选项目维持待定。依赖 D1–D3 的产品实现从选择齐全后开始。若既有会话已明确选择，引用原决定即可。[正式决策依据 §12](../architecture/hero-cover-sharpness-plan.md)

| 事项 | 可选项与代价 | 当前状态 |
| --- | --- | --- |
| D1 播放态受管常驻预算 | 保持 48 MiB，1536 时推算 warm 约 64 张；或 64 MiB，以增加 16 MiB 预算换取约 100 张预取容量。架构建议后者。实际驻留需测主进程、WebView 和 GPU。 | 待选 |
| D2 头图清晰度上限 | 1536 默认时 2560@1x 预计残余放大 1.43×；2048 默认可降至约 1.07×，成本更大。架构建议先默认 1024/1536，另列 2048 是否仅加入协议白名单供实验。两项分别记录。 | 待选 |
| D3 单张 JPEG 字节上限 | 保持 1 MiB，或采用按实际请求档派生的 min(16 MiB, max(1 MiB, edge²/2))，或选更宽的 edge²×1.5 方案并明确上下限。架构推荐中项，前后端及读盘/发布要一致。用实际 Rust 编码的扫描件/噪点校验边界。 | 待选 |

决策单再附一张各命令的“允许请求档 / 默认可选档 / 失败回落档”矩阵。正式方案 §5 与 §12 对 1024、2048 的表述有差异，实施以产品选择和架构签核后的矩阵为准，覆盖每个默认桶都能被 Rust 接受、2048 仅实验时不被默认选中的反例。

## 阶段 1　按依赖拆分实现

先请 Architecture 根据当前源码审查跨端契约、真实恢复路径、缓存身份、所有权、文件写集及交叉影响。按项目规则派给 Rust/Tauri、Frontend、Test，各阶段每文件一个写入人。缺少对应代理时可以继续准备独立基线、复现和任务卡，记录待接手角色。按架构 §5、§10 的符号清单逐步核对，任何行号漂移以实际生产调用链为准。

| 批次与责任 | 实施和本批验证 |
| --- | --- |
| 1. 后端与前端协议串行联调 | Rust/Tauri 明确 playlist、track、folder 路径允许的离散档，按 D3 校验实际档的 JPEG 大小、尺寸、格式、受管路径及原子发布。Frontend 同步 TS 请求联合类型、响应上限及参数检查。测低档历史文件、新档缓存键、非法边缘、中间未授权档、上限边界和损坏文件。缓存复用按源身份、版本和 edge 核验。 |
| 2. 前端量取与两种播放列表 owner | 对稳定的 .playlist-hero-artwork 量布局宽，乘 WebView 实际 DPR 向上取允许桶并封顶。测量不可用时按同一 CSS 断点估算，布局稳定后复测。覆盖 1024→1025、resize、跨屏 DPR、共享元素过渡完成和离场。不能仅用共享投影存在推断动画正在进行，核实完成信号。先显示已有低档，升级失败保留可用图，对实际目标 edge 记失败，限制重复升级。检验浏览和播放态切换都更新当前身份。 |
| 3. 分类详情与预算 | 优先复核架构 B2。高档需求有稳定且与普通卡片区分的 hero 身份、可变档位和留存边界；同页普通卡片继续低档，进出详情/跳转/返回/离场动效后释放旧 hero 或降档。实测稳态最多一份高档 hero、过渡最多两份并能回收，计入旧作业迟到和租约。播放态普通列表在途预算按 4×512²×4 = 4 MiB，高清活动作业按实际档计费。依 D1 对最坏 pixel 路径核算 required、warm 和在途，验无负数、预算挤空或超额长期驻留。 |
| 4. 失败恢复及终态 | 分类 track/folder 高档走 path，失败时明确降至其 pixel 命令支持的 256。路径预解码失败、共享图片发布后 DOM error、取消/stale、连续错误/熔断、低档也失败分别走真实入口。播放列表 pixel 是否允许高档按冻结后的命令和预算分别验证。核对路径错误计数、熔断阈值、一次性补救、旧代次隔离、多消费者去重和资源释放，正确区分无图与失败。 |

当前 R1 名额查询只覆盖 useAudioPlayer；useLibraryArtwork 和 useAllSongsWindow 各自限 2，全局调度上限为 4。分别记录三条入口的实际请求宽度、可见卡等待及预算。检查 useLibraryArtwork 中升级失败按 512 记 failedEdge 的旧逻辑在新增档位时能正确记实际失败档。强制测试高清头图仍在途时立即拖进新区域、换详情并返回，将 H/G/R 可见等待、旧 hero 租约与迟到发布一并写入明细。

## 阶段 2　清晰度、性能与资源的可复验验收

- 对同一源图、同一布局/DPR 和同一裁剪区域，保存原生 WebView2 release 的 A、候选两张无损截图、同坐标 1:1 局部裁剪及源图参考，提供可盲看的对照。每例附 CSS 布局、自然宽高、请求/实际命中 edge、稳定时间、是否达到上限。按架构 §0.1 六场景核算实际物理需求，重点真测 2560@1x 和 2880@200%，确认 WebView 上报 DPR。观察细字、斜边和纹理，记录是否比基线可辨认及是否带来锯齿/错误裁剪。只提高请求数字、原图分辨率不足或模拟 DPR 时单列。验收要求高清样例真实获得新增细节、按选定档位补齐、小原图不承诺新增源细节、普通卡片请求的档位正确。
- 对每个 owner 记录打开至首张可用图、高档完全显示的分布，已有低档在升级期间应连续可见。检查至少十次连续详情切换、动画期间反向返回、快速换歌和二十页磁盘增长。测试命中和现场生成、损坏 JPEG、删除派生图、回退失败，观察恢复次数与后续正常图。正常浏览不能因非法档位引发 path 熔断。独立 Test 复核截图是否来自正确 exe、资源是否释放、失败数据是否保留。
- 记录主进程、renderer、GPU 的峰值/稳定区私有字节、工作集、CPU 和停滚后收敛，保留相同脚本与真实经过时间。途中同时记录高档驻留条数、租约、在途、预取获准/拒绝数及对应预算。理论 JPEG 体积和 JS 准入估算均与进程实测分开。达到上限、出现持续增长、正常图永久丢失、错图或将高清请求传播到普通行时中止候选，记录最小复现。
- 构建、lint、Rust 库检查及测试、受影响的封面 owner/预算/回退测试、真实浏览器交互按架构 §8、§10.3 运行，逐条确认脚本存在、参数和环境适用。附日志和 skipped。耗时、内存和可用清晰度由实际 release 产物验收。

## 阶段 3　四个版本交叉复核

| 产物 | 冻结组成 | 关键比较 |
| --- | --- | --- |
| A | 共同基线，含 R1 | 两个任务共用对照 |
| H | A + 头图补丁 | H 对 A 量清晰度、头图延迟和列表 H/G/R 代价 |
| S | A + 列表提速补丁 | S 对 A 验单独提速、普通头图基线 |
| HS | A + 两个最终补丁及明确的整合差异 | HS 对 S 验高清在提速版上的收益及代价，HS 对 H 验提速在高清版上的收益；对 A 给用户最终表现 |

上表的 H 是版本标签，数据列另以 cache_state 区分磁盘命中 H、现场生成 G、真回访 R。正式结果存两个独立字段。记录每个版本的 commit、补丁/驱动/fixture/exe 摘要和决策值；编译与运行路径要能追溯。冻结脚本、测量指标和门槛后，把四版按配对区组在同机交错执行，每版独立等价缓存。先每版同配置短跑筛错，再对受影响比较正式复验，H/G/R 遵循列表方案中的样本数、空白曝光、配对区间及回访上界。比较 H−A 与 HS−S、S−A 与 HS−H 的方向与幅度，以辨认交互；报告每对明细与区间。头图模块资源或首张可用图延迟若另设门槛，在看候选前由负责人冻结。尚缺 S 时可先完成 A/H，自行优化组的结果从该组执行者取得，等 HS 就绪再补测，不以两组收益相加替代联合验证。

整合时若 HS 与单项结论矛盾，用相同输入在重叠 owner/预算/调度处定位，保留四版和失败记录。决定只采纳一个补丁时回到该独立产物验证。只有快照和修复后的精确产物完成相应验收，才能更新交付状态。

每阶段 checkpoint 保存决策来源、工作树与 SHA、允许写入文件、候选摘要、执行/排期人、证据目录、已完成场景、失败和下一条操作。最终交付补丁、可复跑的命令和环境、四版结果表、独立能力报告、清晰度截图与预算/恢复报告。标明已测入口和设备，并记录下一位执行者需要补齐的证据。
