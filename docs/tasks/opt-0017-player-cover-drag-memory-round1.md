# 播放页拖动切歌内存优化实施与测试方案

DS 负责原版复现、单变量实现、打包和对照测试，提交候选补丁及实测证据。Codex 复算数据、独立复跑、淘汰得不偿失的候选，选定方式后在目标分支重新实施并验收。每个候选以基线为父提交单独实现，筛查阶段仅在隔离工作树运行。正式方案在最终结果评审后落地。

## 1. 目标与基线

- 主场景为 Windows 桌面 Release 中播放本地音乐，连续横向拖动当前封面完成多次切歌。验收同时看切歌峰值、停止后恢复、实际提交速率、最后封面呈现、音频、动画与画质。
- **同口径绝对峰值低于 300,000,000 bytes**（约 286.1 MiB）为目标。首轮请复现用户速度、窗口和设置，记录任务管理器列名、行、组内进程及实际 PID，然后同时采集该口径和进程树 Private Bytes。绝对峰、静置值、增量都列出。若原截图口径无法确认，300 MB 达成状态记为待验证，仍可按同口径 A/B 判定收益。若基线尚未交互便高于 300 MB，量化静置成本并单列，保留绝对目标。OPT-0018 的列表滚动增量阈值用于它自己的工作负载。
- 固定 A 源码为 `0a5e5f241ab59af650fa9482c30c38ef924f4cfa`。本地已提交 HEAD 与本地记录的 `origin/develop` 在此处仅有 foobar2000 研究文档差异。现有工作树有其他在制修改，A 和各候选只从该 SHA 派生。如需换集成基线，重建并复跑 A 及参选臂。
- 标准包沿用生产应用数据路径，在专用 Windows 账号或快照 VM 中安装或运行。使用同账号的自动化时给全部参测臂应用同一隔离补丁，验证配置、库、封面缓存和 WebView2 profile 的实际路径均在每次测试专用根。设置 `WEBVIEW2_USER_DATA_FOLDER` 只隔离 WebView2。全程只读使用真实音乐文件。保存 Windows、WebView2、GPU/驱动、DPR、窗口大小、缩放、供电、主题背景、歌词、可视化、队列和播放设置。

## 2. 先定位当前峰值

1. 快速拖动首轮用用户常用设置做人工原生复现，再冻结能重现的轨迹和曲序。旧诊断仍用于提出假设。2026-11-10 报告的稳态采样和 OPT-0018 的列表滚动采样均须另建记录。旧文档对 4K 图解码峰值的估算，须用当前包和实际拖动验证。
2. 路径从 `PlayerSurface.tsx` 的手势、目标选曲和预取输入进入 `useArtworkVisualResource.ts`。同模块前景与预取执行器串行，1024/1536 由当前布局与 DPR 决定。8 个源 canvas 对应当前、前后各三首与一份周转余量。正方形 RGBA backing 单张约 4/9 MiB，8 张理论 32/72 MiB，空闲约 2.5 秒可清零。展示层 `ArtworkCanvas.tsx` 的封面、背景、过渡与就绪 canvas 另有分配。以上面积是像素量估算，外部进程采样负责量化实际成本。
3. `audio_load_cover_pixels` 走 SPXR 裸 RGBA 二进制 IPC。Rust 的 `CoverRequestCoordinator` 在 worker 启动前检查最新请求，阻塞 worker 当前执行全图解码、方向处理、Lanczos3、打包。前端退出消费者不会自动停止 worker。现有前端执行器串行，新 invoke 也可能在旧工作之后才到 Rust。分别跟踪运行中的孤儿工作、真实共享消费者以及过期完成后仍发生的 canvas 写入。A 已对后续冷选曲做 110 ms 尾部合并，首张冷图会立即触发 I/O。对照保留该策略，记录实际发起时间，避免把现有合并误算为候选收益。
4. 优先做三组单变量对照。4K 与同内容 1536 源图可隔离原始解码成本。暖缓存往返与未见过的图可隔离驻留和重复加载。真实拖动与按键同速切换可定位手势/过渡负载。记录同一时刻 app、renderer、GPU 进程 Private Bytes，结合实际 decode/resize/pack、响应字节、源/展示 backing 总面积、几类 fallback、活动 lease 和延迟，决定下列哪一臂值得实现。若诊断只指向其他 UI，先做单开关定位并恢复设置复核。

## 3. 候选实现

| 实验 | 实现步骤 | 支持或淘汰所需证据 |
| --- | --- | --- |
| B 播放页源像素驻留窗口 | 保留当前元数据候选发现和两个方向的即时预览，限制主动解码驻留为当前与前后各一首。从 A 单独改 `useArtworkVisualResource.ts` 对邻近预取与 registry 保留的决策。优先回收离窗、零消费者、非已发布/排队/预备/提升的源资源。仍持有过渡 lease 的层等现有完成协议释放。保留原 pool 上限与尺寸策略，让实际 backing 计数说明改变是否生效。 | 暖态 renderer 或 GPU 峰与源图驻留同变才优先做 B。测解码次数、重复往返与反向拖动预览命中、已释放 backing 面积及静置成本。若少驻留造成持续重解码、切歌延迟或更高峰，淘汰。 |
| B2 源 backing 尺寸或释放时机 | 若追踪看到池的实际像素面积维持在高位，单独比较复用更小 backing 与零租约时提早清零，两者各从 A 开始。仅调整源池，先用零租约 backing 清零验证 2.5 秒保留的影响。尺寸候选以解码真实宽高为准，后台换尺寸只在取得新 lease 且提交前进行，验证宽高比、内容矩形和 fallback；缺少可行的无额外拷贝路径时，先保留尺寸方案。 | 比较峰值面积、重分配数、复用优势以及展示延迟。若峰值由活动展示层主导，按实际 cover/ambient/ready 的额外 backing 证据提出单独候选，保护离场动画持有的最后一帧。 |
| C 前端取消孤儿作业的提交 | 把 `AbortController` 放到 scheduler job，由入队、消费者引用计数和 job finalizer 管理。前景提升复用共享作业。末个有效消费者离开且资源未交给 owner 时取消其可取消等待，等待 IPC 返回后、写 canvas 前再检查；执行中的 `image.decode()` 完成后按信号丢弃并清理 URL。取消、过期走统一清理，真实读取错误仍按现有 fallback。再次请求同一 key 时允许新作业，旧 finalizer 只删除登记仍指向自己的项。 | Trace 说明实际无人消费仍写 canvas、等待资源或走 fallback，且 C 降低对应次数/字节。仍然需要等待真实 Rust worker 完成的任务继续占执行槽。验证同 key 重入、取消前景与共享预取、卸载及最终落点。 |
| D Rust 阶段取消 | C 后仍存在显著孤儿 worker 浪费时，以 C 为父再增加独立增量。由前端 job 对已经发出的 requestId 显式失效，通过同一请求生命周期传达，设计登记/取消乱序和完成后清理。Rust 在读后、解码后 resize 前、resize 后打包前及交付前检查过期，使用现有 `STALE_REQUEST` 语义。仍持有其他消费者时保持有效。保留真实阻塞任务的互斥门至 join，维护有界取消登记。 | 对照 C 与 C+D。当 trace 证明动作中已及时到达 Rust，且跳过阶段并降低实测峰/等待才保留。现有解码、Lanczos 调用内部的取消粒度仍是阶段边界。 |
| E 降低 Rust 单次解码或缩放峰值 | 若单次大图冷加载复现 app 峰，按诊断定位阶段做最小候选。若峰在 resize，优先评估有界预缩小后最终 Lanczos3、及时 drop 已完成的中间缓冲。若峰在原图解码，验证 JPEG 解码缩放能力后单列 JPEG 候选，PNG/其他格式各走已支持的安全路径，并分别报告峰值。保持目标尺寸、EXIF 方向、透明通道和现有图像分配限制。 | 比较同尺寸合成和真实图像的实际峰值、解码时间、最终画质以及失败处理。当前列表预缩小阈值需双轴约 8 倍，直接开旧开关无法覆盖典型 4K→1536。 |

优先筛 B 与 C 中有证据的一到两臂。不同层同时获益时先保存单独对照，之后才测组合。若 renderer 峰与 IPC 字节相关且 B/C 收益不足，可另做受限派生图路径实验，复用本地资产协议、验证受信缓存范围与源身份，保存透明、方向和动画交接语义，并分别测磁盘冷/热。当前列表 JPEG 路径的编码与缓存策略需要针对播放页单独验证。若 fallback 启动时才复现，优先测限制 fallback 源的真实解码尺寸和同步资源释放。以原分辨率、原背景和原动画的相同设置作为候选验收条件。

## 4. 可重放测试

- **夹具。** 使用实际问题曲序的脱敏只读清单，加 36 首独立身份的可再分发合成曲目。嵌入 4000×4000 JPEG 和同内容的 1536 JPEG 组成 A/B 输入对照，再加 PNG 透明/半透明、EXIF 旋转、方图/宽图、共用实际资源身份与同像素不同身份各一组，以及有效、缺图、损坏、备用源可用和主备失败样本。保留 SHA-256、图像像素尺寸、压缩体积、时长、曲序和生成命令。用足够长的曲目避免压力段自然结束。
- **原生输入。** 优先用 Windows SendInput 或现有原生输入方式执行真实封面区域的 down/move/up。先确认窗口坐标、DPR、拖动阈值和正反方向。筛查可用 `nativeMouseSequence.browser.test.mjs` 和配套 `nativeInteractionProbe.browser.test.mjs` 核实可重复手势。其 CDP、IPC 和 React 探针用于定位轮。正式内存轮只保留等量轻量输入与边界记录，同轮观察实际提交次数，保持窗口前台并避免任务管理器抢焦点引发 WebView 内存策略变化。
- **采样。** 从可识别启动开始，用 PID、创建时间、父子拓扑和独立 WebView2 profile 归属进程。可改造 `tools/thumbnail-benchmark/coverlane-memory.ps1`，其现有实现一次性枚举进程，正式轮需低频刷新拓扑，并用单调时钟及每批 sample ID 目标 50 ms 采样 Private Bytes、Working Set、CPU，记真实间隔与扫描跨度。以 p95 间隔 ≤100 ms、最大 ≤250 ms 为首轮有效线，临界峰另跑更密采样。丢失 renderer、长采样断点或无法解释进程重启的轮留档补跑。GPU 进程 Private Bytes 单列，与显存指标分列。同步总峰用同批次相加。
- **窗口。** 首曲播放 60 秒，取最后 30 秒为 B0。热态按相同输入预热并确认命中，再静置 30 秒取末 20 秒为 B1。冷态核实专用缓存未命中并省略预热。按轨迹操作，松手后继续播放 120 秒。分别报告启动、预热、拖动和恢复峰，恢复的 30/60/120 秒前各 10 秒中位数，以及回到 B1 + max(20 MiB, 10%×B1) 并维持 10 秒的时间。未在窗口内恢复则记 >120 秒。自然恢复采样全程使用相同窗口焦点，无强制 GC。

| 场景 | 操作 | 检查 |
| --- | --- | --- |
| T0 空载对照 | 首曲不操作播放 8 分钟 | 静置成本及自然波动 |
| T1 单图 | 冷态选一首 4K JPEG、1536 JPEG、4K PNG 后各静置 | 识别单次解码、尺寸与格式成本 |
| T2 正常切歌 | 20 次约 500 ms 间隔的完整拖动 | 首滑与一般节奏，音频、标题、封面、背景一致 |
| T3 高速主场景 | 30 次单向拖动，按 150/80 ms 目标预试，取用户机器能稳定提交且复现问题的轨迹。必要时补测 50 ms 和用户手势 | 保存每次输入及实际提交。基线和候选使用同轨迹、同落点，合成 4K 在冷/热各测，1536 和真实曲序各跑对照 |
| T4 反向与回访 | 两首往返 20 次，另测 A→B→C 中途反向、邻近热命中与窗口外冷加载 | 确认共享作业、旧响应、预览提升及首滑是否正确 |
| T5 长稳 | 同一进程 10 轮复现轨迹，每轮后继续播放 120 秒，末轮继续 5 分钟 | 逐轮峰、残留与平台趋势；确保优化没有把工作推到停止段 |
| T6 回归 | 缺图、坏图、备用源、透明图、暂停恢复、seek、自然切歌、退出播放页再进入、关闭窗口、缩放与窗口档位变化、重新扫描 | 错误后能恢复，最后呈现正确，动画无白屏/残影、音频无额外中断，资源可释放 |

筛查每个支持假设的重点场景 A 与候选各至少 3 次。晋级后对 T3 冷、热及真实复现中的代表条件分别执行至少 5 对 AB/BA 交错独立启动，保存顺序、逐对差值、中位数与范围。T5 在 A 与晋级候选各整跑至少两次。实际提交速率不同时保留结果并核查输入或产品退化。有效输入因候选掉提交属于回归。最终落点一致只是判定条件之一。

每轮完成后先核对同一采样批的进程归属与时间轴，再核对最后一笔播放动作及最后封面呈现。缺口用原始记录标明。出现进程归属不明、崩溃或系统内存压力时停该轮，保留当时的证据。可沿用 OPT-0017 旧测试方案的测试保护线 `min(2 GiB, 物理内存的 25%)`，它用于终止压测。

## 5. 回收结果与定案标准

1. 正确性先决。自动验证实际已接受的手势、正确曲目/音频、最终封面及背景、新旧图交接和退出资源释放。候选以相同曲序、相同最终分辨率进行截图对照。若候选改变缩放算法，另留无损样本，按原尺寸和实际 DPR 检查细字、斜线、纹理、方向和透明边缘。
2. 性能判定。以已复现实测增长最大的进程以及同步总树为判定指标。筛查要求主指标活动增量峰中位至少降低 15%，并超过 A 的跨轮波动。基线波动尚未分辨时补测。至少 4/5 对改善且候选静置、从启动到恢复的绝对峰和 T5 残留均无明确恶化才晋级。绝对峰目标按第 1 节单独判定。临界值报告观测范围，不用四舍五入掩盖超限。
3. 体验门槛。比较首次拖动、正常切歌、已停留到能呈现的样本和 burst 最后一次提交。计时从手势/提交到正确封面真实呈现，另列音频切换。优先同仪器收集 ≥20 次终点呈现，比较 p50/p95。p95 恶化超过 10% 且超过 16.7 ms，或新增白屏、旧图闪回、音频中断、可见画质差异，进入回归复查。辅助报 >33 ms 帧间隔比例，录像与重诊断从正式内存轮分开。
4. 交付每臂 SHA/补丁和 SHA-256、Release 包与构建日志、环境及缓存定义、夹具 manifest 与生成命令、手势轨迹、逐轮 CSV/JSONL、诊断时间线、画质样本和可复算报告。按 `runId, arm, scene, profile, sampleId, monoMs, pid, role, privateBytes, workingSetBytes` 保存内存原始行，记录按键/拖动、选曲、作业、资源、取消和真实呈现事件的相关 ID。报告原始失败、未复现、无效轮和执行不足。每项优化附一个反证实验。命令与脚本版本一并交回。
5. Codex 按相同输入复跑，复算峰值、分项和延迟，淘汰体验回退、把开销挪到预热/停止或将峰挪到另一进程的方案。多臂通过时，优先选满足相同指标的最小实现。若结果指向组合，先验证每项都提供独立收益及组合回归，然后在当时的目标分支重新实现并安排 Test Agent 独立验证。以生产 Release 和固定的真实复现路线收尾。

## 6. 构建命令

交接包中的 `SpMusic-A-0a5e5f2-x64-setup.exe` 是从干净基线构建的标准 Windows x64 NSIS Release。配套 `baseline-manifest.json` 记录源码 SHA、构建命令及产物 SHA-256。已验证构建和打包，原生安装、拖动复现和内存采样由 DS 在隔离测试环境执行。

重建时在干净的 A 或候选工作树内执行。候选的实验开关、隔离补丁和诊断补丁均记录提交或 SHA-256。将每臂包复制到独立的产物目录并验证哈希。

```powershell
npm ci --no-audit --no-fund
npm run lint
npm run tauri -- build --bundles nsis
cargo test --manifest-path src-tauri/Cargo.toml --lib cover_pixels
```

前端自动化先跑 `node --test src/features/player/hooks/playerArtworkRecovery.test.mjs`。浏览器组另启 `npm run dev -- --host 127.0.0.1`，按脚本支持的 `SPMUSIC_TEST_ORIGIN` 与 `SPMUSIC_PLAYWRIGHT` 指向测试服务及隔离的 Playwright 安装。逐个以 `node` 运行 `src/features/player/components/` 下的 `artworkPoolCleanup.browser.test.mjs`、`coverTransition.browser.test.mjs`、`coverRapidLongPress.browser.test.mjs`、`previewReadiness.browser.test.mjs` 和 `dragReturnContinuity.browser.test.mjs`。新增测试仅覆盖所选候选的具体漏洞，例如共享取消、过期响应乱序、挂起期间重新接入、仍在过渡的 canvas lease 或大图缩放/透明边界。对影响共享代码的候选补测媒体库与其封面加载。
