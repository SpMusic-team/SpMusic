# OPT-0018 拖动内存第二轮 DS 执行方案

后续探索与实现由 Codex 接手。二级大列表的实际卡片窗口化已接入 develop 工作树，并保留 256 px 封面。首次挂载、回访、真实滚动条松手时延和原始峰值的复测见 `D:/SpMusic-opt0018-r2-diag/codex-runs.md`。窗口化稳定降低 renderer 峰值，300,000,000 bytes 整组拖动目标仍待完成。下文保留此前 DS 复核方案。

本轮以活动播放列表的 256 px 行图做主对照，保持头图档位、Lanczos3、t2 资产和像素回退。内存验收按第 0 节执行，同时检查松手补图速度、画质和回访体验。512 px 行图作为独立的高清压力对照，详见第 5 节。

## 0. 11 月 18 日诊断后的执行顺序

按 [DS 第二轮诊断报告](../test/opt-0018-drag-memory-r2-diag-2026-11-18.md) §0.7–§0.11 接续。本节的采样与验收口径适用于后续各实验臂。

1. **先取得可配对的基线。** 最大化、四列、同一 1821 首夹具、每站停留 2 秒。两臂核验播放状态、布局、视口、曲序和磁盘缓存准备。按被测应用根 PID 归属采样，逐个时刻汇总进程组 `WorkingSetPrivate`。保留原始字节值和采样覆盖，缺少根进程或必要角色读数的采样标为不完整。分报启动、初始静置、首访、回访和恢复峰值。首访与回访活动期各验收整组绝对峰值 ≤ 300,000,000 bytes。旧工作集、私有提交量和 H/G 增量继续用于诊断。
2. **首访与同站回访各测。** 用更新后的 `D:/SpMusic-opt0018-r2-diag/tools/drag-rounds.mjs` 记录实际落点、视口范围和阶段时间。覆盖检查包括初始首屏、互不重叠的首扫视口，以及实际命中原视口的回访。首访指本次运行首次落地该视口。缓存命中、实际生成、封面身份分别取证。跳转诊断完成后，用原生滚动条拖动复测沿途加载和松手补图，保留 `fixed` 作为两点回访对照。
3. **优先配对验证切断离屏 `<img>` 引用。** DS 的运行时实验观察到 renderer 在 8 秒内由 491 降至 297 MiB。先用同一 runner 做 A/A，再按 AB、BA 对比基线与实时切断离屏引用。285 MiB 的报告来自单次未播放实验，仓外 `pool-total-peak.mjs` 同步采样全机匹配进程名，还缺少采样与实际滚动的时间对齐。按第 1 条重测，逐对记录离屏释放量和峰值。750 MiB 场景也用同一 runner 校验播放与真实落点。
4. **配对复现后，做隔离的 React 原型。** 比较严格可见窗口与额外保留一行缓冲两种 `src` 生命周期。保持 256 px 资产和现有预取策略。记录正确封面出现时延、停留 2 秒的补图率、占位闪烁、串图、换源和坏图恢复。分别报告首屏、慢拖和松手回访。提交隔离实验结果，产品实现另行排期。
5. **静止播放单列。** DS 验证真播放、最大化且无输入后测得稳态 187 MiB，同期视口外已解码封面为 0。若追查 150 MB，固定播放曲目和采样窗口，分别对照列表与头图绘制成本，记录仍未归因的内存。拖动候选继续按第 1–4 条验收。

仓外 runner 用法为 `node drag-rounds.mjs <exe> <独立运行目录> [port] [rounds] [dwell-ms] [any|playing|not-playing]`。`playing` 检查传输栏状态。播放对照需先接入 `measure-verified.mjs` 的启动播放步骤，在初始静置前完成，再由 runner 校验。正式记录保留 `tm.csv`、`window.json` 和 `drag-rounds.json`，并检查启动早段的实际采样覆盖。

本机旧 CSV 复算：`%LOCALAPPDATA%/spmusic-full-88f76daa/tm.csv` 的同刻进程组峰值为 786,436,096 bytes（750.00 MiB）。`%LOCALAPPDATA%/spmusic-poolpeak-b0905722/tm.csv` 的峰值为 299,032,576 bytes（285.18 MiB），该文件有 434 个全机汇总采样，报告引用 421 个样本且未附切片边界。保留此读数作为复测线索。两次轨迹的活动条件、进程归属和时间窗需要按上述规则统一。

## 1. 第一轮证据与假设

- R1 多站暖扫中，跳过临时预解码的探针 L 在两对等路线里都把活动期 renderer 私有内存中位降低约 85 MB，GPU 进程活动期中位的变化方向在两对间相反。首轮的进程轨迹支持验证浏览器图片成本，GPU 进程分配来源仍待归因。
- R1 缩短驻留、降低名义预算和关闭离屏预取的试验缺少稳定收益。代码仍有独立的呈现入口，已就绪封面会在离屏保留实际图片节点。把挂载范围作为单独变量，可测已有图片资源在浏览器呈现路径上的增量。
- 路径命令返回后，原生调度名额已经释放，才会创建临时 `Image`。列表 owner 的整条工作链仍有并发上限。在这两个约束之间可以独立测量临时预解码的重叠，以及不同请求返回同一图片的重复校验。
- 复算 R1 的固定往返与关闭整库预热探针后，发现约 230–265 MB 的静置骤降主要发生在 renderer，关闭预热的运行也出现同类阶跃。R1 从文件打开的路径是否实际排了整库预热仍待调用计数核实。暖扫先观察浏览器链路，只有冷扫复现原生分配与整树峰重合时才重新排原生解码实验。

## 2. 冻结基线并修正采样

1. 从实际目标集成源码冻结完整 SHA。若依赖工作树修改，保存可重建快照和补丁摘要。A 和各实验臂使用相同 release 配置和隔离补丁，保留可核验的二进制哈希。R1 对照工件仅用于复查历史数据。
2. 将活动前和首次静置的稳定检查覆盖分母实际使用的末 10 秒。两个窗口都至少静置 15 秒，使用连续 10 秒有效样本，沿用 R1 修订工具的 20 MiB 波动上限和最长 60 秒等待。采集脚本在同一组用于评分的样本上复核收敛，记录实际等待和跨度。未收敛、缺 renderer 或拓扑漏样风险未解决的运行保留原始记录，重做整对。若稳定条件持续不能满足，回报轨迹与后台任务状态。
3. 校验恢复采满 60 秒。保留 Quiet、Idle 中位、活动/恢复/全程峰、两项增量、峰值同刻角色分项和各角色活动期水位。记录 PID 加启动时间。R1 的 E 对照两侧都曾出现短命的第二个 GPU PID。用进程启动与退出事件补足低频拓扑刷新，核对 GPU 短命实例有无漏采。保留原采样门槛、轨迹质量检查和进程树归属。独立记录主机干扰。资源诊断与正式内存、松手时延采样分开跑。
4. A/A 使用与候选相同的首访和回访路线，检查实际滚动距离、静置基线和绝对峰的波动。R1 的 12 个循环落点可用于历史暖扫复查。报告同时保留 bytes 和十进制 MB。

## 3. 三条独立实验链路

### B　约束离屏图片节点的挂载

- [PlaylistPanel.tsx](../../src/features/player/components/PlaylistPanel.tsx) 给卡片保留完整内容，[PlaylistCard.tsx](../../src/features/player/components/PlaylistCard.tsx) 的已就绪封面与显式 URL 分支在离屏仍可能挂载 `<img>`。先在 A 上记录视口内外实际挂载的封面数、唯一 URL、源像素面积、与视口距离和周转速度。离屏量明显时继续出 B 包。
- 基于活动列表的现有几何采样，独立计算图片挂载范围。按第 0 节先测严格视口，再加一行缓冲，另测导航和拖排需要持有的行。首次几何就绪前沿用现有呈现行为，避免暖图先空一帧。完整卡片、布局和交互、封面读取需求、预取带、owner 驻留预算及动效都沿用 A。卡片按实际挂载取得和释放自己的呈现引用。保持资源 owner 的 lease、旧图交接和真实 `load`/`error` 回调。
- 配对诊断核对读取次数、挂载数和源像素面积变化，并与 GPU、renderer 轨迹对齐。回访查看已有图是否及时出现、是否重复渐入。覆盖首次打开、恢复滚动位置、反向和慢拖、选择拖排、窗口外松手、共享 fallback lease、换源和坏图的一次恢复。卸载本身不能确认替换，记录挂起替换的数量、字节、等待时间及真实加载或撤销需求后的收敛。

### C　限制临时预解码同时运行数

- [playlistCoverScheduler.ts](../../src/features/player/services/playlistCoverScheduler.ts) 在路径命令完成后释放调度名额，[playlistCoverPathLane.ts](../../src/features/player/services/playlistCoverPathLane.ts) 随后创建临时 `Image`。先统计在途峰值、持续时间与分位数、尺寸、等待和过期数，量化与 DOM 图片发布以及资源峰重合的程度。若在途很少或寿命极短，优先跳到 D 的诊断。
- 在活动播放列表普通行的临时预解码入口分别验证 8 与 4，先试能形成有效约束的较宽档。按现有当前曲、可见、预取优先级派发，同优先级按队列顺序。许可在创建 `Image` 前取得，清理 `src` 和监听后释放。原有解码超时从开始实际解码计，排队单独计时。保持 Rust 许可和其他 owner 的宽度。
- 普通行目前主要靠 `isCurrent` 判断。入队、获许可、发布前均检查当前性，并在 owner 窗口失效时清掉已过期的等待者。等待取消按 dropped 退出。真实解码失败继续走一次像素回退，保留原图片对象的 readiness、身份校验和熔断语义。核对慢拖可见队列、松手后的排队时延、换页/换源、低宽度、坏图以及名额回收。降峰后若恢复期出现补发峰，按同一内存口径计入。

### D　合并同一派生图片的在途预解码

- [cover_pixels.rs](../../src-tauri/src/audio/cover_pixels.rs) 的歌曲缩略图以图片内容哈希和档位生成资产身份。不同歌曲共享同一封面时可能得到同一 URL，而 [playlistCoverPathLane.ts](../../src/features/player/services/playlistCoverPathLane.ts) 逐次创建临时 `Image`。先在真实曲库统计同 URL、同派生尺寸的重叠请求。另用共用封面的相册夹具验证机制，按真实曲库结果决定是否入围。
- 仅合并身份一致且当前仍在进行的预解码。共享的是这次浏览器校验的结果。各消费者仍独立检查当前性，并给各自的图片对象标记 readiness、发布身份和一次恢复权限。前景加入时保留其优先级。一个消费者退出时，其余消费者继续，最后一个离开后清理 `Image`。作业结束后立即清理记录。若无法确定同 URL 仍代表同一代资产，按各自请求校验。覆盖损坏文件修复、同 URL 重建、重扫版本变化和重入竞态。
- 保持路径命令、入队宽度与 DOM 呈现不变。核对峰值在途、实际启动减少量及共享命中，核对真缺图、失败熔断计数和单次恢复。收益若仅出现在高度共图的合成夹具，记录该适用范围和真实曲库结果。

## 4. 按结果继续

1. **先按第 0 节复测 B。** C 的在途峰值实测为 16，D 的同 URL 在途重叠约 4%。若配对发现预解码与内存峰同步，再测 C 的并发限制。D 等真实重叠率上升的证据。移除临时预解码的原型已有契约测试失败，重开时先核对坏图、取消与发布顺序。
2. **内存方向稳定后补冷盘、固定往返和松手计时。** 内存按第 0 节验收。[R1 的 H/G/R 门槛](opt-0018-drag-memory-r1-plan.md#4-入围与最终验收) 继续用于补图和交互时延。各臂独立过筛后才测试组合。
3. **交回 Codex。** 附冻结 SHA、隔离补丁、各臂补丁、可重放命令、原始 CSV/phase/gesture、时延、画质截图与失败样本。逐对注明是否过 300 MB。若有明显改善但仍超标，报告剩余差距及同期角色分项。10 分钟长跑、正式 H/G 矩阵和向媒体库推广按入围结果再排。

## 5. 512 px 高清压力对照

256 px 筛出稳定收益后，再用隔离包比较 A-512 与候选-512。先确认活动列表的曲目路径和像素回退都能真实通过各自 512 档，启用正确的资产身份和预热准备，再记录暖扫峰值和恢复。当前活动列表普通歌曲行分支、歌曲像素命令和整库预热存在 256 限制，需显式核对每条链路和旧缓存兼容。512 压力对照单列结果；涉及档位接入的实现和验收由后续高清任务安排。
