# 任务：播放列表滑动与封面加载性能优化计划

## 背景

用户观察到其他播放器滑动列表时封面几乎没有可见加载，希望优化 SpMusic。现有实现已移除固定 40 首资格截断，并具备实际可见区域调度、128/256/512px 列表档位、96 MiB 前端受管资源预算、有限并发与列表独立请求会话；这些是当前代码事实，不代表真实 WebView 的延迟、帧率或内存已经达标。Rust 列表封面仍可能读取、完整解码原图并缩放；前端仍将 RGBA 转为 BMP Object URL，网格仍挂载全部卡片。level 0 当前有近屏几何索引实验，其他布局及其回退路径仍按全量几何读取；该实验尚未验收。它们是待测的成本来源，不预先判定主因。

`docs/architecture/playlist-artwork-loading.md` 是此前正确性修复的草案，保留了“40 首截断”“仅 256/512 档位”“尚未实施”等过时现状叙述。实施性能优化前由 Architecture Agent 校准它或另立当前契约，不能以这些旧叙述制定目标。用户已要求启动本计划；具体性能目标、缓存容量、缩略图格式、虚拟化方案和版本排期仍须由阶段 0 证据确定。

## 目标

- 在可复现的 Release 环境下拆分封面可见延迟、滚动主线程负载、重复解码和内存成本，找出主要瓶颈。
- 依据测量证据，分别决定是否实施有界磁盘缩略图缓存、列表虚拟化或图片传输格式优化；每项独立评审和验收。
- 保持有效可见封面的完整性、列表与播放器封面隔离、资源上限和 Object URL 所有权正确。

## 非目标

- 阶段 0 不以未测量的方案修改播放列表行为；如需最小观测代码，由对应实现 Agent 明确写入归属与撤除条件，不把观测点当作性能优化成果。
- 不一次性捆绑缓存、虚拟化和传输协议改造；不为了主观“更快”增加无限并发、整库预解码或常驻原图。
- 不新增媒体库数据库、网络封面、标签编辑、音频引擎能力或权限。
- 不把旧架构草案中已修复的问题重新作为本轮实现任务。

## 优先级与状态

**P2，阶段 0 执行中；有条件的后端缓存与 level 0 前端几何实验仍在评估，前端分段计时已撤除，Rust 命令内分段计时已撤除，Stage 0E 外层探针未通过事件顺序闸门，Stage 0F 的队列数值条件通过但完整分支闸门未通过，未纳入版本排期。** 这是已有列表体验的高价值性能增强，当前证据尚不足以将它定为阻塞 v0.1 交付的 P0/P1 缺陷。用户“开干”“继续”授权执行证据驱动的可回退实验；缓存、虚拟化和传输协议均未被选定为最终性能方案。若基线发现可见封面永久缺失、无界增长或稳定卡顿，PM Agent 按证据另立缺陷任务并重新定级。

## 阶段与依赖闸门

### 阶段 0：Release 基线与问题分流

Test Agent 与对应实现 Agent 先确定可采集方法，在**同一 Release 构建、同一曲库、同一操作脚本**下至少各重复 5 次冷首次、热往返、快速跨越并反向停下。覆盖 100、1,000、10,000 曲规模，最密封面布局、最大支持窗口与高 DPR；已获授权的真实曲库约 1,816 个音频文件，可用于 100、1,000 规模的只读抽样，10,000 规模若无合适素材须标记未覆盖，不能据 1,816 曲外推。冷态必须明确是应用内缓存冷、磁盘缓存冷还是 OS 文件缓存冷；热态记录已预热的层级。

逐项记录以下原始数据与汇总，不只记录主观视频：

- “进入真实可见区域 → `<img>` `load`”的 p50/p95/p99、有效可见封面最终完成率；无封面、坏图、取消与超限单列，不混入有效封面分母。
- 元数据等待、前端排队、Rust 排队/读取/解码/缩放、RGBA 传输、主线程 BMP 转换、图片元素解码各段耗时，以及同一内容同一档位的重复原图解码次数。
- 按实际刷新周期归一化的滚动帧间隔、超预算帧占比、长任务数量与耗时；挂载卡片数、布局/几何计算次数及耗时。
- Rust、Renderer、GPU 的峰值与长时间往返后的稳定平台，受管 Object URL、在途像素和磁盘占用；记录平台工具无法测得的部分。

**阶段 0 完成门槛**：原始记录可关联构建、样本、脚本和运行轮次；上述指标均有值或明确的测量限制；能将主要等待归入解码/重复读取、DOM/布局、传输/BMP 转换或其他已证实类别。若现象无法稳定重现，继续补观测，不直接选技术方案或宣称优化完成。PM Agent 根据基线与 Requirements Agent 的用户体验分析批准具体 p95/p99、帧与内存目标及版本范围；本卡当前不预设这些数值。

**阶段 0 当前证据（非完成判定）**：本地曲库枚举约 1,816 首，约 1,808 首初步检出封面。Test Agent 对固定 83 首 FLAC 做了 5 轮 Pillow 代理测量：每轮重复完整解码合计约 1.86–2.33 秒；热读取 p50 小于 0.4 毫秒，解码 p50 约 15–17 毫秒。真实 Release WebView 的 1,816 卡片列表上，900px/帧往返 5 轮的滚动 rAF 间隔 p50 为 18.8 毫秒、p95 为 28–31 毫秒；空闲 p50 为 3.1 毫秒。固定视口的 5 个新位置共记录 208 张有效封面，起始均未显示，4 秒时均显示；各组 p95 为 2.15–3.38 秒。逆序热重访 4 处的 p95 仍约 1.13–1.84 秒，但同进程各层缓存状态未严格固定，不能视为独立冷/热 A/B。这些数据能稳定观察到滚动和补图耗时，尚未完成严格的首次可见至 `load` 端到端分段归因与长期资源测量，阶段 0 门槛仍未达成。

同一 WebView 中直接对 120 首运行的代理请求显示：元数据 hydration p50 约 9 毫秒，首次像素 p50 约 12–16 毫秒，BMP 转换约 1 毫秒，重复像素 p50 约 4.5–6 毫秒。这绕过真实 UI 的调度、排队及部分生命周期，不能把其分布外推为 208 张实际卡片的等待主因；也没有证据支持启动 TS/Rust 传输协议改造。

2026-10-02 的实际列表 UI/IPC 补测中，Test Agent 独立复算三份脱敏原始汇总。五个固定视口共 184/184 张有效可见图在 4 秒内完成；另一个单视口的 40 张可见图中，hydrate 请求从脚本滚动到发起的 p50/p95 为 934/1,924 毫秒，成功关联的 38 张 pixel 请求发起为 1,006/2,058 毫秒，pixel POST 自身耗时为 40.8/194.9 毫秒。五视口的 BMP URL 创建至图片 `load` p50 约 21–22 毫秒、p95 约 24–34 毫秒。这些样本不是同一次采集，不能合并分位数；脚本滚动时刻也不等于真正进入可见区域时刻。已观察到请求启动前的等待及 pixel POST 尾部，但仍无法从网络记录区分前端元数据/视觉队列、共享 hydration、会话等待与 Rust 内部阶段，不能把解码、BMP 或某个队列定为独占根因。

### 阶段 0A：有条件的 Rust 缓存探索实验

PM 决定先允许 Rust/Tauri Agent 在现有 `cover_pixels` 响应契约内部做**可回退、有界的缩略图缓存探索**，只验证重复解码能否被消除及其代价，不把它称为已验收的用户体验优化。实施前须用现行 Rust `cover_pixels` 路径的 Release 构建，对固定的同一原图哈希与档位重复请求至少 5 轮，记录完整解码耗时、冷请求耗时和资源占用；实施后以相同输入记录热命中、冷生成、磁盘占用及轮次波动。热命中改善须大于基线轮次波动，冷请求不能出现明显退化，否则停止该分支并回退实验改动。

Architecture Agent 的实现门槛：键包含可信原图内容哈希、档位和变换/编码版本；仅使用专属应用缓存子目录；同时限制总字节与文件数；同目录临时独占写入后原子发布；损坏条目按 miss 回源，源内容变化失效；淘汰只作用于衍生缩略图，不碰现有 `audio/covers` 原图。现有 TS/Rust 命令与 SPXR v1 响应、受限路径和解码限额保持一致。原图缓存本身仍无容量上限，须列为残余风险，不得将衍生缓存上限宣称为总封面缓存上限。

这项实验不关闭阶段 0：真实 WebView 的封面可见延迟、帧率、前后端排队和内存峰值仍待测。前端虚拟化与图片传输协议不随本次实验启动；是否保留缓存并进入正式实现分支，须根据 Rust 对照实验、真实 WebView 基线与独立回归结果再决定。

**迭代 1 观测与闸门判定（同步写入版）**：固定 83 张、5 轮 Rust Release 测量中，旧版每轮约 4,045–4,146 毫秒；同步缓存版冷路径约 4,287–4,360 毫秒。随后同进程交错 A/B 的 5 对运行确认冷路径每 83 张增加 196–258 毫秒，约 5–6%，为可重复退化，判定**未通过“冷路径不能明显退化”门槛**。热路径每轮约 59–70 毫秒、83/83 命中，缓存占用约 21.75 MB/83 文件，证明复用收益，但不能抵消冷路径闸门或证明 WebView 体验改善。同步写入版不得标记完成或作为最终实现直接保留。

**后续范围决策**：允许在 Architecture Agent 先审查生命周期、背压、容量、取消、退出和写入失败语义后，仅进行一次有界后台写入探索迭代；该授权不包含无界队列、增加解码并发、改动 TS/Rust 命令或扩大磁盘预算。实施后由 Test Agent 独立复测同素材交错 A/B 至少 5 对、热命中、写入中断/损坏回源、资源收敛与退出行为。若冷退化仍可重复、热命中依赖未完成写入、资源不收敛或契约回归，回退缓存实验代码并保留测量报告。Architecture Agent 若不认可有界异步契约，也直接停止并回退，不以热路径收益跳过闸门。

**后台写入实验进度**：Architecture Agent 已确认单写者、128 项/32 MiB 双限及退出边界。协调 Agent 完成代码接入，并在固定 83 张素材上做两组各 5 对的 Rust Release 交错 A/B。Test Agent 随后在不停止用户 Release 应用的情况下，对同一 lib 的 ignored benchmark 独立完成 5 对交错复测：冷响应配对差异均值约 +79 毫秒（+1.86%），5 对均为正；热轮 83/83 命中，约 59–69 毫秒。原版后台 writer 将“队列项处理完”计为 `completed`，无法区分落盘失败。Rust/Tauri Agent 已将写入结果分为 `Written`、`AlreadyPresent`、`Skipped`、`Failed` 并分别计数；Test Agent 独立验证 23 项 Release 测试通过、1 项忽略，包括目录不可用时失败不计成功且列表像素仍可回源。修复后固定 83 张的 5 对交错 A/B 冷响应均值约 +66 毫秒（+1.58%），逐对差异正负皆有；热轮 83/83 命中，约 57–69 毫秒。同步写盘版约 5–6% 的稳定退化未重现，但不能宣称无冷退化或正式验收。内存平台、真实退出中断、系统级写盘失败与真实 WebView 各段等待仍待验证。详见 `docs/test/sp-022-playlist-performance-baseline.md`。

### 阶段 0B：仅限 level 0 的前端几何优化实验

**实施前范围决策：批准可回退实验，不批准正式方案或网格虚拟化。** 旧版真实 1,816 卡片列表中，每次滚动发布读取 1,816 次 `getBoundingClientRect`，回调约 4.4–6.4 毫秒；新实验在 level 0 几何有效时只读近屏候选，其他布局和几何失效回退时仍走全量路径。实施前只读同一 WebView、level 0 布局、首组 80 个滚动位置的代理比较，旧版全量几何排序与“二分边界 + 近屏扫描”输出 80/80 一致；旧路径耗时 p50/p95 为 1.7/3.1 毫秒，候选路径为 0.2/0.3 毫秒。首组始终先跑旧路径，可能影响缓存与布局热度。追加另一组 80 个位置并交替先执行两种路径，各 40 个位置先执行，输出仍 80/80 一致；旧路径先执行时 p50/p95 为 1.9/2.6 毫秒、后执行时为 1.6/2.6 毫秒，候选先或后执行均为 0.2/0.3 毫秒。该 Release 窗口为 2560×1439，`data-layout-columns="2"` 是布局描述值；CSS `repeat(auto-fill, 270px)` 实际排出 **8 个物理列**。上述代理只验证了这一窗口的 level 0 实际八列几何，不证明 level 0 始终两列或八列。顺序公平性证据增强，但仍只是实施前的 CDP 同步脚本代理，不能代替下述实现后的真实滚动和状态更新 A/B。证据当时足以批准受限于已验证前提的单项实验，不足以扩展到其他布局或宣称滚动、封面最终体验已改善。

- **允许采集**：JS `invoke` 前、Promise resolve/reject 后及可安全区分的响应解析前后时间；CDP 同一请求的 POST start、response、finish、bytes 和可用 timing 字段；同一 renderer 的时钟锚点用于校准。事件以匿名调用序号关联，导出只含时间、档位、字节数、状态及匿名号，不保存原始请求/响应 body、文件路径、封面内容、trackId、Object URL 或曲目名。缺少 CDP response/timing 字段时标为缺项，不能把 `response` 或 `finish` 擅称首字节/纯传输时间。
- **运行边界**：调用保持串行，不构造或撤销图片 URL，不触碰播放器封面，不推进真实列表 `clientId`/session，不改动前端任务队列、Rust 解码门、命令/SPXR、权限或缓存规则；探针结束时清理自身 CDP 监听，并仅按现有接口释放独立会话，不新增清理命令。采集结果只表示热缓存封面的一次直接 IPC 外层成本，**不能代替真实列表队列、首次进入可见区域至图片 `load` 的端到端分布或冷解码成本**。
- **可证伪验收**：每档五轮的 JS 调用与 CDP POST 一对一关联率至少 95%，时钟校准后所有已关联事件顺序有效、字节与状态可复核，三档分别报告 `invoke→resolve`、POST start→response/finish 及可观测前后间隔的 p50/p95 和轮次范围；任何阶段缺事件、重复匹配或时钟偏移应计入分母。若关联/时钟/扰动不达标，只报告未分段残差并停止外推。若在至少 4/5 轮同档位中，已可靠观测的 POST 内部间隔占 `invoke→resolve` 的逐请求比例中位数超过 50%，再请 Architecture Agent 单独审查 `src-tauri/src/lib.rs` 命令包装计时；若主耗时在 POST 之外或无法稳定重现，转回真实列表的前端准入/可见时序观测。无论结果如何，本阶段**不批准**新命令、Rust/TS 协议改造、增加并发、预计算或缓存语义变更。

**独立复核与闸门判定（2026-10-03）**：Test Agent 对匿名原始记录独立复算，20 个预热样本 × 三档 × 五轮共 300 次 JS 调用与 300 个 CDP POST 为 300/300 双向唯一关联；状态、返回字节与 CDP 数据字节一致。128、256、512 各档的 `requestWillBeSent→loadingFinished` 占 `invoke→resolve` 逐请求比例中位数均在五轮超过 50%（约 72%–74%）。然而 300/300 次 `responseReceived` 均晚于 `loadingFinished`，不满足本阶段“所有已关联事件顺序有效”的硬闸门；探针也没有独立证明磁盘缓存命中、运行进程哈希和采样扰动。**Stage 0E 不通过完整可解释性验收，不据数值条件批准 `lib.rs` 包装计时或任何传输、序列化、协议优化。** 这段 `start→finish` 只是自定义 IPC 的粗粒度观测区间，不能命名为首字节、纯传输或 Rust wrapper 耗时；串行直接调用亦不能解释真实列表的排队和卡片显示。详见 `docs/test/sp-022-playlist-performance-baseline.md`。Architecture Agent 复审建议先补真实列表同一卡片的可见、队列、占槽、调用、BMP、图片加载时序；若未来仍需 Rust wrapper 诊断，须另有证据和单独范围决定。

## 不随基线放宽的验收门槛

- 稳定视口中**有效封面最终显示率为 100%**；无封面、坏图、受安全限制拒绝单独统计。可见优先级不能被屏外预取长期挤占。
- 热缓存命中时，同一内容、档位和变换版本的请求不再完整解码原图；若该缓存方案获批，此项以重复解码计数 `0` 验证。
- 若虚拟化获批，挂载卡片数随视口和明确的预取行数增长，而不是随曲目总数增长；定位、选择、搜索、多布局与转场回归通过。
- 资源用量和未完成任务数在重复往返后收敛，不随累计浏览曲目数持续增长；不会撤销仍被使用的 Object URL，过期结果不串入新列表。
- 保留现有前端有限任务数、Rust 列表串行解码、路径/尺寸/字节安全限制及播放器大图独立会话，除非新的架构评审和测量明确批准改变。
- 若采用磁盘缓存，容量/文件数均有上限，写入中断或缓存损坏可回源重建，源内容变化不会命中旧图；磁盘占用在淘汰后回到配置上限内。

上述为正确性与有界性门槛；“加载几乎不可见”的 p95/p99、掉帧率和峰值内存数值目标，须由阶段 0 的数据和目标设备确定后写入独立实现任务。本卡不把 96 MiB、128/256/512 档位、并发 2 或任何未来缓存容量视为已验证的最佳参数，也不擅自调整它们。

## 风险与回退

- 磁盘缓存可能降低热浏览耗时，却增加容量、失效与损坏恢复责任。若命中率或收益不足、清理不能保持上限，停用新缓存读取/写入路径并保留原有受限解码路径，记录磁盘清理与迁移处理。
- 虚拟化可能破坏搜索定位、焦点/选择或转场中的卡片引用。出现错位、跳动或引用提前释放时回退该独立改动，保留当前完整可见调度，不以遮挡或延时隐藏故障。
- 新传输格式可能产生前后端版本不一致或解码失败。先以可对照的 A/B 路径验证，再整体回退协议两端；不得单边更改响应格式。
- Release 与开发模式、Windows 与其他目标平台的 WebView/GPU 内存表现可能不同；报告只对实际测得的平台和设备成立，新增平台需复测。
- 如果任一方案让有效可见封面不完整、资源无界、过期图串列表、当前播放图消失或 BUG-0016/BUG-0017 相关问题复发，该方案不得进入完成状态；回退后仍保留观测证据和后续 Owner。
