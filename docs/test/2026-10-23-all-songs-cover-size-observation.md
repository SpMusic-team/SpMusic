# 测试记录：所有歌曲封面请求尺寸与加载速度

## 观察与范围

2026-10-23，用户在自己的实际使用环境中比较了“所有歌曲”界面的封面加载体验，反馈：封面请求尺寸变化对加载速度影响“非常非常巨大”，并要求回退本次实验改动。本记录保存这项用户实测观察，供后续封面性能工作参考；它不是独立完成的定量性能验收。

本次实验将“所有歌曲”的封面请求改为：首曲固定 `512px`，其他详情歌曲按布局尺寸与屏幕像素倍率请求 `128/256/512px`。播放列表管理卡预览原已请求 `256px`，本次没有修改。实验前，“所有歌曲”独立窗口封面请求使用固定 `maxEdge: 128`；这不代表播放器等其他封面通道都只请求 `128px`。

## 回退状态

根据本次回退后的工作树检查，`src/features/player/hooks/useAllSongsWindow.ts` 的独立窗口封面请求为 `maxEdge: 128`。对上次实验涉及的 `useAllSongsWindow.ts`、`PlaylistLibraryPanel.tsx`、`allSongs.browser.test.mjs` 执行 `git diff`，结果为空；这三个路径没有留下本次实验的未提交差异。工作树中其他未提交文件不属于本记录的回退范围。

## 证据边界与结论

- **用户实测观察**：提高“所有歌曲”详情封面请求尺寸后，用户感到加载速度受到很大影响；用户据此认为封面大小是这次速度差异的主要原因。
- **独立证据**：本次未取得同设备、同曲库、同缓存状态下的成对计时或资源采样，也未记录屏幕倍率、布局、实际请求尺寸分布、封面数量、文件内容或加载阶段耗时。因此无法从现有证据给出耗时、倍数、显著性或每个通道的因果占比。
- **可执行结论**：后续若再次调整“所有歌曲”的封面尺寸，应把真实场景加载延迟和最终显示质量一起列为验收条件；不能仅凭图片更清晰或单项请求完成就认定改动值得保留。本次尺寸升级已按用户反馈撤回。

## 后续性能实验建议

若重新评估尺寸策略，先冻结同一设备、窗口布局、屏幕倍率、曲库与测试曲目，并分别记录空派生缓存和磁盘缓存重用场景。对 `128px` 基线与候选策略交错运行多次，记录每张实际请求尺寸、首张封面出现时间、可见区域达到目标覆盖率的时间、最终清晰图完成时间、失败数与资源峰值。区分“所有歌曲”独立窗口封面、播放器首曲封面和播放列表管理卡预览，避免把不同通道的请求归入同一结果。只有同口径结果齐备时，再判断耗时变化和图片质量取舍。
