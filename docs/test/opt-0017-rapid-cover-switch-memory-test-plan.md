# 快速拖动切歌的封面内存诊断与优化验证方案

本文是交给执行者的测试方案，**所有测试均未执行，没有修复或性能通过结论**。本轮只新增方案文档；下述探针与优化分支是后续执行要求，不代表已有实现。

## 1. 目标与执行顺序

先回答快速拖动时哪个进程增长、增长与哪些事件相连、停止操作后能否回落，再决定优化位置。不得先实施 OPT-0017 的 B/C，再用下降的总内存倒推原根因成立。

1. 阶段一：固定构建与输入，以原版 Release 做低干扰复现，取得 app.exe、renderer、GPU 的同场景时间序列。
2. 阶段二：只对阶段一未能区分的假设增加诊断，关联选择、调度、Rust 阶段、像素交付与 canvas 生命周期。
3. 阶段三：依据证据选择候选方案，单变量配对比较内存、响应、画质和回归。允许结论为“不建议优化”或“证据不足”。

执行者先完成阶段一并输出中间报告。缺少取消传播或中途取消接口时，不得把“方案 B 不可直接实现”写成已验证 B 无收益。

以下是 2026-10-30 只读审查的代码事实，执行前必须按实际工作树重新核对，记录变化：

## 3. 环境冻结、隔离与材料

### 3.1 构建与环境记录

- 保存 git HEAD、`git status --short`、相关 tracked diff 和未跟踪输入副本；有未提交改动时，HEAD 不能代表测试源码。记录执行时间及 Asia/Shanghai 时区。
- 保存 package/lockfile、Cargo.lock、构建命令、日志、feature、相关环境变量、诊断补丁、exe 与前端 index/assets 哈希。不得只写“最新 Release”。
- 记录 Windows、WebView2 runtime、GPU/驱动、CPU/RAM、显示器、分辨率、缩放、窗口尺寸与 DPR，电源模式、是否远程桌面。
- 固定主题、背景效果、歌词、队列长度、排序、播放模式、音量和窗口可见状态；关闭其他高负载任务。正式计时期间不构建、不安装依赖。
- 使用 Release。DevTools、CDP、录屏、堆快照会扰动内存，低干扰组默认关闭；诊断组另记工具及参数。
- 记录实际构建/检查结果；相关命令可用 `npm run build`、`npm run lint`，Rust 在 src-tauri 下执行 `cargo check --release --lib`。这些不能替代运行时验证。

### 3.2 数据隔离

先检查项目当前是否有可用的独立 config/data/cache/WebView profile 方案，并验证实际解析路径；不得假设存在某个环境变量或复用旧诊断开关。没有隔离能力时先用独立操作系统测试账号，或由对应实现 Owner 准备隔离入口。

所有造图、损坏文件、删缓存和错误注入只针对专用临时夹具与已核实的测试根。不得清空用户缓存、改写原音乐或覆盖现用 exe。真实用户场景可读取原曲目，但使用隔离状态或记录其不可隔离限制。每轮记录退出后缓存清理行为，避免把退出自动清理误作“热缓存”。

### 3.3 夹具与缓存定义

准备两套输入：真实复现曲序的只读清单；可再分发的合成短音频与封面。合成音频应足够长，防止压力操作期间自然结束；另设自然结束用例。

| 集合 | 建议内容 | 目的 |
| --- | --- | --- |
| F1 | 20–40 首不同歌曲/不同 4000×4000 JPEG RGB8 封面 | 大图、持续不同资源 |
| F2 | 与 F1 同图案和曲序的 1536×1536 JPEG | 控制源尺寸，目标尺寸保持一致 |
| F3 | 4000px PNG RGB8、RGBA8，带透明/半透明边缘；至少各 4 张 | 通道与格式差异，不把它与尺寸效应混为一谈 |
| F4 | 多首歌曲共用同一实际封面身份，以及相同像素但不同资源身份两组 | 分离资源去重与重复解码；记录实际 key，不能只看图片相同 |
| F5 | 无封面、损坏封面、主源失败但 fallback 可用、主备均失败 | 错误与浏览器 fallback；通过专用副本或诊断注入构造 |
| F6 | 高对比文字、细线、棋盘格、斜线、渐变及有代表性的真实封面 | 后续画质评估 |

保存 manifest：fixtureId、音频/封面路径及 SHA-256、尺寸、格式、通道、压缩字节数、资源来源、固定曲序；真实路径可以脱敏，保留本地映射。

“新进程”仅代表应用内存重新开始；“应用冷缓存”指核实的测试缓存未命中；“应用热缓存”指同一路径预热且有命中证据。三者均不等于 OS 文件缓存冷。不要为基础测试强制清 OS 缓存；必要时单列重启后组，并记录磁盘状态。

## 4. 观测方法与数据格式

### 4.1 进程采样：阶段一必需

以 exe 路径、PID、创建时间、父子关系确认本次 app.exe 及其 WebView2 后代，按命令行角色区分 browser、renderer、GPU、utility；不要按进程名汇总机器上所有 WebView2。保存进程树，持续发现新增/退出/PID变化；多个 renderer 分别记录并另给汇总。

用 PowerShell/.NET 进程 API、性能计数器或等价工具采集下列数据，不要求先安装 profiler。建议目标 20Hz；短峰诊断可升至 50Hz。若工具只能稳定 5–10Hz，保留实际时间戳、漏采和开销，明确结果是采样下界。原有 1Hz 只适合趋势，不能否证亚秒峰值。

- 每进程 Private Bytes（提交内存）、Working Set（驻留）、CPU 累计时间、线程数；采样器自身 CPU、实际采样间隔。
- app、renderer、GPU 各自峰值与增量；全组 Private Bytes 可另列，但不能混入 Working Set，也不能把各进程不同时间的最大值相加当同步总峰值。
- GPU进程 Private Bytes 不等于显存；可选采集可归属到该 PID 的专用/共享 GPU 内存。工具无可靠归属时记未测，不能用系统全局显存当本应用数据。

统一 MiB=字节/1048576，保留原始字节。任务管理器截图只作旁证，记录其指标口径，不能代替序列。

### 4.2 时序、交互与呈现

动作、采样与日志使用统一 runId，优先共同的单调时钟。跨 Rust/JS/外部工具记录各自时钟原点和同步事件，测量映射误差；不能直接比较不同进程 performance.now 的绝对值。

记录输入开始/释放、实际选择提交、trackId、resourceKey、请求入队/开始/完成/过期、最终封面稳定显示、音频切换。只有请求完成而无呈现证据时，不得称“封面已显示”。可用诊断呈现标记结合低帧率录像校验；录像单列诊断组。

基础组至少记录动作起止及实际完成选择次数。自动化输入的计划频率和真实选择提交频率分别统计；未达到速率时保留该轮并标明偏差，不能当作计划速率通过。

### 4.3 证据目录与最低字段

每轮专用目录：`environment.json`、`fixture-manifest.json`、`process-tree.json`、`process-memory.csv`、`actions.jsonl`、`events.jsonl`（诊断组）、`summary.json`、构建/采样日志、可选录屏/轨迹。建议收集脚本也随报告保存版本与哈希；本方案未提供或执行脚本。

```text
process-memory.csv:
run_id,mono_ms,utc,pid,process_start,role,private_bytes,working_set_bytes,cpu_total_ms,sample_gap_ms
actions.jsonl / events.jsonl:
runId,monoMs,clockDomain,event,actionId,trackId,resourceKey,jobId,requestId,purpose,status
诊断可选扩展:
sourceWidth,sourceHeight,targetWidth,targetHeight,format,channels,responseBytes,
canvasId,width,height,owners,queueDepth,consumerCount,stage,durationMs,errorCode
```

空值或缺失值写明，不填 0 假装已测。保留逐次记录再计算分位数，不能只留摘要。

## 5. 阶段一：原版 Release 基线

### 5.1 每轮统一流程

1. 确认上一轮测试进程已退出；按本轮缓存条件准备专用根，启动唯一测试实例并保存进程树。
2. 加载固定曲序，播放首曲，等待 60秒稳定；取最后 30秒 Private Bytes 中位数为各进程基线 B。稳定期间若仍有加载，延长并记录原因，不随意挑低点。
3. 记录动作时间，执行下表场景。停止输入后继续播放，记录最后选曲及 0/5/15/30/60/120秒内存。
4. 每轮结束保存数据、异常及实际选择次数。基础场景每种至少 3 次独立启动；重复轮不得混用冷/热缓存口径。
5. 对能够复现问题的组合追加阶段二；无复现时保留全部阴性数据，扩展用户原始操作速度/曲序，不能直接宣布不存在问题。

### 5.2 必做场景矩阵

| ID | 操作与输入 | 对照/目的 |
| --- | --- | --- |
| S0 | 首曲仅播放 8分钟，不操作 | 分离稳态增长与拖动；歌词/背景保持真实设置 |
| S1 | F1、F2、F3 各选一张，单次冷加载，停留 120秒 | 单图峰值和格式差异，避免多次切换混杂 |
| S2 | 正常完整封面拖动，20次，每次释放约间隔 500ms | 正常交互与最终显示 |
| S3 | F1 固定曲序完整拖动，20次，目标间隔 150/80/50ms，分别成组 | 逐级压力；不能实现 50ms 完整手势则标未达成并报告真实速率 |
| S4 | 同 S3 的可复现节奏，用下一首按钮或命令触发 | 诊断旁路对照；不能替代完整 pointer down/move/up 拖动路径 |
| S5 | A/B 往返20次、A→B→C快速反向，F4同身份/不同身份各组 | 去重、过期作业、旧图污染和方向竞争 |
| S6 | 同一曲序立即重复，核实热命中；另做专用空缓存组 | 缓存效果与预热窗口内/外：±3邻近选择和远距离选择分开 |
| S7 | 选已复现节奏，连续10轮 burst，每轮20次后正常播放120秒；最后再观察5分钟 | 峰值有界与恢复基线趋势；这一用例同一进程，不每轮重启 |
| S8 | 快速切换时关闭/重开播放界面，停止拖动后静置，再正常切歌 | 退出层、卸载与资源恢复；关闭界面与退出应用分开记 |
| S9 | F5逐项正常选择及快速切换，故障后切回有效封面 | fallback、错误传播、重试、最终封面/占位图正确性 |

完整拖动记录起止坐标、位移、方向、速度、跨阈值及释放；固定窗口位置，优先可重放 pointer 事件或原生输入。若只能人工执行，给节拍、录像及实际选择时序，不声称输入精确到 50ms。

S3与S7至少使用 F1/F2 的尺寸对照；F3/F4/F5先做诊断子集，不必把全部变量组合穷举。真实曲库复现至少做 S0、可达成的 S3 和 S7；若不宜长压，明确覆盖限制。

如增长主体在 renderer，用同一可复现用例分别关闭歌词、背景或队列面板，每次只改一个设置，再恢复验证；属于定位组，不能把关闭效果当最终修复。固定曲长，单列自然结束、暂停/恢复、seek 与正常切歌回归。

## 6. 阶段二：有针对性的诊断

先报告阶段一结果，再由对应 Owner 在隔离诊断构建中准备最小探针。探针只记录，不改变调度、延时、画质、回收或错误语义；不逐像素打印，不在每帧做大对象序列化，不在计时中拍 heap snapshot。

| 层 | 记录内容 | 能回答的问题 |
| --- | --- | --- |
| 前端调度 | selection/job/request关联、入队、开始、消费者加入/abort、active消费者数、作业交付/丢弃、预取purpose | 用户已离开但旧作业是否继续；新选择何时到达Rust |
| Rust | 登记代次、等门/入门/出门、worker起止、读图、原图解码、方向变换、resize、RGBA转换、pack、响应；各阶段输入输出尺寸/通道/字节 | 大缓冲在哪个阶段；排队旧作业是否被拒绝；串行是否真实成立 |
| IPC/像素 | 响应字节数、同时在途数、到达至写canvas耗时、过期响应数 | 传输/转换是否贡献renderer短峰；TypedArray view不是额外复制证据，原生传输复制需另查 |
| 源资源 | canvas唯一ID、尺寸变化、lease获取/释放、registry/layer/queued/prepared/promoted引用、空闲清零时刻 | 8个源canvas及共享引用是否有界；2500ms回收是否实际发生 |
| 展示与fallback | 展示canvas挂载/退场/卸载、backing尺寸、图片对象/URL创建释放、fallback原因/次数/源尺寸 | 额外展示资源和浏览器原图解码；源池有界不能代表所有资源 |
| 浏览器 | JS heap、DOM/detached节点、rAF逐帧间隔、必要时内存/渲染轨迹 | native增长还是JS增长；掉帧是否与解码/交付关联 |

阶段前后读一次内存可能漏掉 resize 内部峰值；必须同时连续外部采样，必要时用分配跟踪或可证明的最大活跃缓冲记录。函数返回后没有增长不能证明函数内部没有分配。

诊断构建与未加探针 Release 在同一场景至少各3次，交错顺序比较开销；若探针明显改变节奏/峰值，降低日志密度或另用低干扰观测。GC/heap snapshot/内存整理只可在独立定位轮做，并记录触发时刻，不混入自然恢复指标。整理后下降只说明有可回收资源，不能证明无泄漏。

## 7. 指标、反证与阶段门槛

### 7.1 必算指标

- 每个进程：基线 B、动作期绝对峰 P、增量 P−B、同步进程组总量峰；停止后30/60/120秒中位数与基线差。
- 自然恢复：恢复到 `B + max(20MiB, 10%×B)` 并保持10秒的时间；未恢复记右删失，如“>120秒”，不能填120秒当成功。
- S7：每轮停止后最后30秒中位数 R1…R10、残留 Rn−B、随轮数与随时间的斜率；保留原始点和稳态对照S0。
- 实际选择数、解码启动/完成/过期/失败数、预取数、fallback数、响应字节数、峰值源/展示canvas数量与像素总面积。
- 有呈现探针时计算选择→正确封面稳定显示的中位/p95及最终选择延迟；被新选择取代的任务单列，不能当成功显示样本。少于20个有效样本时展示逐项数据，p95不作强结论。
- 有逐帧采样时报告 rAF间隔p95、>33.3ms及>50ms比例；rAF只是代理，非真实GPU呈现帧率。另统计长任务、音频中断、白屏、重入、占位闪现、最终图错误。

上述恢复区间为诊断比较规则，**不是已批准产品SLO**。S7若后五轮残留持续增长且斜率>2MiB/轮，或最终5分钟仍显著高于初始恢复区间，触发继续调查；未触发不能证明没有缓慢泄漏。500MB绝对值、单轮峰值或一次回落均不能单独判成败。

### 7.2 假设反证表

| 假设 | 支持所需证据 | 反证/替代解释检查 |
| --- | --- | --- |
| H1 Rust瞬时峰值主导 | app峰与decode/resize时间重合，F1相对F2显著增大 | 若只renderer涨，不能归因Rust缓冲；排查fallback/前端面积 |
| H2 renderer短期资源 | renderer峰与响应、canvas创建/退场相关，源/展示面积可解释部分增量 | 排除JS其他模块；面积估算不等于实测native内存 |
| H3 fallback | fallback计数和原图尺寸与峰同步，正常像素路径对照消失 | 无fallback也复现则不能以其作唯一根因 |
| H4无效作业 | 消费者已归零但仍decode/pack/交付，量化浪费时间/字节 | 仍有共享消费者的作业不能算应取消；不保证取消降低单次峰 |
| H5其他UI | 单变量关闭/恢复某模块可重现改变，相关事件吻合 | 关闭导致输入速率/布局变化时须纠正混杂 |
| H6高水位保留 | 多轮最终形成平台、自然回落或可复用，资源所有权无增长 | 强制整理下降不是充分证据；继续看长期趋势 |
| H7持续滞留 | 重复轮残留单调增长，存活对象/引用或分配可追溯 | 对比S0、预热和OS缓存；不能仅凭不归还OS称泄漏 |

可以多因素共同成立；证据不足的环节标“待验证”，不要强行选择唯一根因。

## 8. 阶段三：条件式优化对照

仅在阶段一/二证据指向对应路径时进入；架构/实现 Owner 先确认边界。固定基线与候选构建、夹具、配置、实际选择速率、缓存状态和初始等待，每次只改一个因素。正式比较至少5对独立启动，AB/BA交替，报告每对差值、中位数与范围，异常轮保留并说明；性能差异小于跨轮波动时判证据不足。

| 候选 | 前提与必须核验 | 限制 |
| --- | --- | --- |
| B阶段间过期检查 | 先具备及时到达Rust的过期信号；读后/解码后resize前/resize后pack前检查；统计跳过阶段 | 不宣称中断resize，不承诺降低已发生的峰值；仅完成后检查不能避免已完成解码 |
| B真正中途取消 | 明确替换/维护算法成本与取消粒度，再实现；验证共享消费者、取消后清理、最终曲交付 | 取消外层future不等于停止spawn_blocking；worker未停不得提前释放串行门造成并发 |
| C预缩小/重采样 | app峰值确实受resize影响；记录中间尺寸、实际峰值、总耗时和全部像素分配 | 直接false→true对4K→1536可能不触发现有8倍阈值；2倍预缩小有高频混叠风险 |
| 前端资源生命周期 | renderer峰由对象/展示资源证据定位 | 不能靠禁用背景/动画、吞错、增加延时或频繁强制GC冒充根因修复 |
| A拖动降档 | 只有单独批准评估时才测；记录任务key、展示identity、升档次数和池实际面积 | 不能先验认定必闪图；热canvas不降尺寸但IPC字节仍可能下降 |

C使用F6做1536最终输出A/B，保留无损产物与哈希；100%显示及实际DPR/窗口下看文字、细线、斜线、纹理、透明边缘。数值可补PSNR/SSIM，但不可替代观察；记录模糊、振铃、混叠、alpha边缘。保持色彩/方向处理一致，不能仅凭缩略预览认定无画质影响。

每个候选都回归：连续同向/反向拖动、共享封面、预取命中/未命中、错误fallback、关闭重开、窗口/DPR切换、歌词/背景、暂停恢复/seek/自然结束，确认最后选曲、音频和封面一致，无白屏、旧图污染、死锁、饥饿、无限重试或资源不归还。取消测试必须在worker运行中发生，并在最后一次选择后验证其最终完成，不能只看STALE计数。

探索性优化收益门槛：目标进程增量峰值或残留至少改善10%，并超过基线跨轮波动；最后封面延迟、p95帧间隔若恶化>10%则复查；任何正确性回归均不通过。这些是本次筛选规则，不能自动成为产品承诺，不能掩盖绝对延迟或视觉回归。

## 9. 停止条件与交付

遇到持续白屏/崩溃、用户数据路径误用、操作系统明显内存压力、采样器造成负载、测试进程身份不明时停止该轮，保留数据并标失败/无效。建议启动前设置测试进程组Private Bytes总和的停止线为 `min(2GiB, 物理内存的25%)`，另以系统可用内存<10%为停止条件；记录实际阈值，不为追峰耗尽机器。停止线只是测试保护，不是产品内存预算。

执行者提交一个报告并链接全部原始证据，最低包含：

| runId/场景 | 构建/缓存/夹具 | 实际选择数/速率 | app B/P/Δ | renderer B/P/Δ | GPU进程 B/P/Δ | 30/120秒残留 | 显示延迟/帧指标 | 异常/证据 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 待执行 | 待执行 | 待执行 | 待执行 | 待执行 | 待执行 | 待执行 | 未测 | 待执行 |

另附S7十轮恢复表、假设逐项支持/反证/未定表、正式A/B逐对差值和画质产物。说明哪些是亲自执行，哪些只复核其他人的结果；列出缺失场景、采样漏峰、时钟误差、工具扰动和未隔离条件。

结论分开写：问题是否复现、增长主体、已证实因果、仍待验证因素、是否需要优化、建议方案与收益/代价、回归是否通过。未跑的项保持“未执行”，缺少关键证据写“证据不足”；不得仅凭构建/单测通过或总内存下降宣布解决。

执行交接清单：先完成环境/夹具清单与S0–S9可达成部分，保存原始数据并给阶段一报告；按观测缺口选择最小诊断；得到因果证据后再实施与比较候选。不要同时改调度、画质、缓存预算和回收策略。
