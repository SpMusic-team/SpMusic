# 磁盘缓存跨重启验证：命中、复用与重新生成

> 验证目标：确认 256 档 JPEG 与索引真的写盘；退出应用后保留缓存再启动，拖到同一位置时这些目标是否**命中索引、读取已有 JPEG、还是重新缩放编码**。
> **会话内回访**与**重启后**分开记录。

## 1. 方法与三个阶段

用**正常入库流程**导入曲库（`audio_open_source` → 列表），选定拖动落点会显示的曲目，然后：

| 阶段 | 做法 |
| --- | --- |
| **A** | 首次拖到落点，等 cohort 补齐；随后直接在磁盘上核对 JPEG 与 `.idx` 已写入 |
| **B** | **同一会话内**回到顶部，再拖到同一位置（会话内回访） |
| **C** | 关闭应用、**保留缓存根**，用**同一个缓存根**重新启动，再拖到同一位置 |

三个阶段的缓存根路径完全相同，这是本测试的关键。

记录项：是否命中索引、是否读取已有 JPEG（`prepareCacheHit`）、是否重新解码/缩放/编码（对应微秒计时）。

## 3. 三个阶段对比

| 阶段 | cohort | 松手时已就绪 | 命中 | 未命中 | 解码 | 缩放 | 编码 | 写盘 | probe |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| A 首次 | 78 | 52 | 1 | 40 | 6.7 ms | 26.4 ms | 1.5 ms | 7.1 ms | 8.2 ms |
| B 会话内回访 | 78 | **78** | 22 | 0 | 0 | 0 | 0 | 0 | 0 |
| C 重启后 | 78 | 58 | 23 | 0 | 0 | 0 | 0 | 0 | 0 |

### 会话内回访 vs 重启后的差异

| 项 | B（会话内） | C（重启后） |
| --- | --- | --- |
| 松手时已就绪 | **78 / 78** | 58 / 78 |
| 命中 | 22 | 23 |
| 是否有重新生成 | 否 | 否 |

**两者都不重新生成**，但**松手时已就绪的比例不同**（78/78 对 58/78）。

这是本轮最值得注意的发现：**重启后 IPC 往返与进程内内存状态都要重建**，虽然磁盘缓存全部命中，但松手瞬间仍有 20 张未就绪。也就是说：

- **磁盘缓存确实消除了生成成本（这是确定结论）**；
- 但**"松手即就绪"依赖的不只是磁盘缓存**，还有进程内的内存驻留。

所以「回访松手即就绪」这个能力**跨重启会退化**，这不是缓存没生效，而是内存层没有预热。

## 4. 本轮修掉的两个测量错误（否则结论会错）

必须记录，两次都是**我的工具错，不是产品问题**：

1. **索引目录名查错**：我用 `thumbnail-index`，实际是 `thumbnail-index-v1`，导致第一次测出"索引文件数 = 0"，一度误以为索引从未写入。
2. **外层缓存命中未标记**：索引命中走的是 `read_track_thumbnail_path_cache` 直接返回，**根本不经过 prepare 阶段**，所以 `prepareCacheHit` 保持默认 `false`。第一次测出"重启后命中 0 次、但各段全为 0"这种自相矛盾的数据，正是这个原因。已在该返回点显式标记为命中。

**修正后数据完全自洽**：命中 23 次、未命中 0、生成工作全 0。

## 5. 对下一步的意义

| 问题 | 答案 | 依据 |
| --- | --- | --- |
| 256 档 JPEG 和索引是否真的写盘 | **是** | 117 个 JPEG + 120 个 `.idx`，重启后仍在 |
| 重启后是否命中索引 | **是** | 23/23 |
| 是否读取已有 JPEG 而非重新生成 | **是** | 生成工作严格为 0 |
| 是否存在重复生成 | **否** | 命中目标中非零工作数 = 0 |
| 会话内回访是否命中 | **是** | 22/22 |
| "松手即就绪"是否跨重启保持 | **否** | 会话内 78/78，重启后 58/78 |

因此：

1. **磁盘层没有浪费**——写入、索引、复用全部正常，之前测到的"每张都要缩放编码"只发生在**首次生成**，不是重复劳动；
2. **要进一步降低首次到达**，仍然只能动首次生成的 `scaleUs`（26.4 ms，占后端约 45%）；
3. **但"回访即就绪"的退化指向另一个方向**：重启后需要预热内存驻留才能恢复该能力，这与磁盘缓存是两个独立问题。
