# OPT-0018 连续拖动内存对照

当前 develop 在相同拖动负载下已经能超过 1 GiB。最终候选在这组对照中进一步增大了占用。应用和专属 WebView2 进程合计的私有内存峰值从 1277.8 MiB 增至 1431.6 MiB，增加 153.8 MiB，约 12.0%。内存为本轮观察项，性能达标仍按真实松手后封面补齐判断。后续单独处理内存归因和优化。

## 运行方法

- A 为 develop 4d4477c5211e228c2e0de5e7c4c6bbd2b89a36c0；B 为保留原 Lanczos3 和 t2 的最终候选。两臂二进制 SHA-256 分别为 B50A392D7350BB8EA3EB6FB74F6828E107BC6173877C26F73A1927510FCFCF15、7F4593B2BF9B0DAC2449615F688129EE10BF9139788D3E49079CB8A166A0F572。
- 台式机本地 Windows/WebView2、同一 1799 首曲库、相同 2544×1431 视口和 level 2 布局。两臂使用分别新建的应用数据与 WebView2 profile。先跑 B 再跑 A，两臂连续执行预热拖动 30 秒、静置 15 秒、活动拖动约 120 秒、停止后观察 30 秒。
- CDP 在真实滑块注入按下、移动和松手。脚本以相同目标比例循环。两臂各 142 次手势均移动滚动位置，A 有 137 次、B 有 141 次最终位置落在计划比例的 4 个百分点内。候选实际滚动总距离多 2.7%。记录每次实际坐标与结果。
- 约每秒从各次启动的应用 PID 重新解析专属进程树，采集各子进程的 private bytes 和 working set。活动期分别取得 118 和 119 个采样。各角色的峰值拆分取自同一个总私有内存峰值时刻。工作集相加可能重复计算共享页。JS 堆通过 CDP 定期抽样，覆盖范围小于 renderer 的原生内存。

两臂停止后均低于各自活动前静置中位。观察确认高占用可在基线重现，也确认该次运行中候选在活动和恢复窗口占用更高。单对、先 B 后 A、两分钟活动，以及实际落点略有不同，限制了增量的归因范围。单秒采样还可能漏掉较短的峰值。该记录未识别用户手里的具体 DSH exe，也未建立长期泄漏结论。

此前 2026-11-08 的独立验证已经观察到 renderer 在拖动期间增长并在静置时回落。更早的 SP-022 记录中，GPU 私有内存峰值的五轮中位约 804–829 MiB，renderer 约 342–358 MiB。各角色的历史峰值可能出现在不同时刻，无法用它们复算同期总占用。[早期拖动记录](opt-0018-independent-verification-2026-11-08.md) · [SP-022 子进程峰值](sp-022-thumbnail-optimization-comparison.md)

## 后续优化方向

1. **先复现增量并拆分内存所在的进程。** 用同一台机器补反顺序和长跑。冻结一组目标，反复来回而不引入新封面，再停止和切出列表，跨过 5 秒的封面保留期持续采样。同步记录已解码资源、活动作业、可见图片和 GPU、renderer 占用，检查固定集合是否仍持续增长。
2. **把常驻预算和并发分别做单变量对照。** 在相同宽度下比较 48/96 MiB，再在同一常驻预算下比较并发档位。对照 H 和 G。若暖态增量主要随常驻预算变化，优先缩小离屏资源保留、释放不再使用的资源引用，并检查 WebView2 解码缓存和 GPU 资源的回落。若冷态增量主要出现在主进程，优先按实际解码字节限制并发，在大封面和低内存设备上保持前台优先。
3. **用松手收益约束后续内存优化。** 同时记录固定落点补齐、同会话回访、拖动期峰值和停止后的平台。应用层的 96 MiB 是封面调度的常驻预算，WebView2 解码与 GPU 分配也会进入进程树占用。16 个 permit 对应的解码限制乘积是理论额度，实测值以进程采样为准。
