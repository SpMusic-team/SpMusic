## 0. 判定口径

### 0.1 指标必须用专用工作集

任务管理器「内存」列 = **`WorkingSetPrivate`**（`Win32_PerfRawData_PerfProc_Process.WorkingSetPrivate`）。

同一时刻三种口径实测差异：

| 口径 | 值 |
| --- | ---: |
| `WorkingSet64` | 736 MB |
| `PrivateMemorySize64` | 865 MB |
| **`WorkingSetPrivate`（任务管理器）** | **110 MB** |

早期工作用了后两者，导致报告 850 MB 而用户看到 ~110 MB。**本报告全部数据均为 `WorkingSetPrivate`，按被测应用根 PID 归属汇总整个进程组。**

### 0.2 测量条件（每次必须验证）

1. 窗口最大化（2560×1439），用 Win32 `ShowWindow(SW_MAXIMIZE)` + 回读 `GetWindowRect` 断言
2. 四列封面布局（`level=2`）
3. 1821 首夹具，实际打开列表
4. 每落点停留 2 秒，6 个互不重叠落点，多轮首访/回访
5. 播放状态需确认（若要测播放场景）
6. **记录 C: 磁盘空闲空间**

### 0.3 噪声门

三次同配置重复：773 / 791 / 809 MiB，**极差 36 MiB**。

**小于约 36 MiB 的差异不可信。**

## 1. 结论摘要

| 阶段 | 整组峰值 | 是否达标（≤300 MiB） |
| --- | ---: | --- |

## 2. 有效手段

### 2.1 `--enable-low-end-device-mode`（最大单项收益）

Chromium 源码依据 `cc/tiles/image_decode_cache_utils.cc` 的 `GetWorkingSetBytesForImageDecode(for_renderer)`：

```cpp
if (use_desktop_limits && for_renderer) {
  if (base::SysInfo::IsLowEndDevice()) {
    decoded_image_working_set_budget = base::MiB(32);
  } else if (AmountOfTotalPhysicalMemory() >= 4 GiB) {
    decoded_image_working_set_budget = base::MiB(256);
  }
}
```

`base/system/sys_info.cc` 的 `DetectLowEndDevice()` 第一件事就是检查该开关。

实测：

| 角色 | 基线 | lowend | 差 |
| --- | ---: | ---: | ---: |
| **renderer** | **511** | **183** | **−328** |
| gpu | 86 | 210 | +124 |
| app | 138 | 126 | −12 |
| 整组峰值 | 664 | **488** | −176 |

三次重复：488 / 504 / 476 MiB（中位 488，极差 28）。

### 2.2 拖动期强制 LOW 档位

`webview_memory.rs` 的 LOW 原本只在**窗口失焦**时生效，而拖动时窗口必然聚焦，所以这段代码在真正需要的场景下从未执行过。

新增 `test_hooks.rs`（仅实验 worktree）暴露 `test_set_memory_target(level)`，通过 `ICoreWebView2_19::SetMemoryUsageTargetLevel` 在拖动开始/结束切换。

实测稳态：中位 226–241 MiB，p95 237–249 MiB。

### 2.3 `MAX_PLAYLIST_DECODE_PERMITS` 16 → 4

真实曲库封面普查（893 张，解析 JPEG SOF / PNG IHDR）：

| 指标 | 值 |
| --- | --- |
| 宽度 p10 / p50 / p90 | 640 / 1500 / 3000 px |
| **每张完整解码 RGBA** | **15.72 MiB（均值）** |
| 文件本身 | 416 KiB |

16 并发 × 15.7 MiB ≈ 250 MiB，与 app 进程峰值吻合。降到 4 后：

| 配置 | 全程峰 | app 峰 |
| --- | ---: | ---: |
| permits 16 | 548 | 319 |
| **permits 4** | **398** | **168** |

**代价**：并发低 → 解码慢 → 缓冲驻留久 → 稳态从 248 升到 346–370。但目标是峰值，故取 4。

## 5. 启动峰的构成

t=1.6 s 的 398 MiB：

| 角色 | MiB | 性质 |
| --- | ---: | --- |
| renderer | 126 | 页面加载 + 首屏渲染（WebView2 必然成本） |
| app | 168 | 歌单解析 1821 首 + 元数据 + 首批封面解码 |
| gpu | 63 | GPU 进程初始化 |
| 其他 | 41 | browser + utility |

**renderer + gpu = 189 难压；app 的 168 是唯一可动部分。** 若压到 40–70，峰值约 300–330。

## 6. 磁盘空间的干扰调查

用户观察到实验期间 C: 一度只剩 2.5 GB，要求调查。四档对照（同 exe 同配置）：

| C: 空闲 | 能否启动 | 峰值 |
| ---: | --- | ---: |
| 17.8 GB | 正常 | 421 MiB |
| 4.9 GB | 正常 | 394 MiB |
| 2.5 GB | **失败** | localStorage SecurityError |
| 768 MB | **失败** | 同上 |

**结论一**：磁盘严重不足时应用直接失效（不是省内存），所以低值不可能是磁盘压力造成的假象。
**结论二**：17.8 → 4.9 GB 峰值降 27 MiB，小于 36 MiB 噪声门。**
**结论三**：稳态复测 249/250 vs 254/242（差 5 MiB），磁盘对稳态无影响。

## 10. 启动峰的性质：一过性 1 秒（第 5 轮高分辨率采样）

### 10.4 这意味着什么

1. **启动峰是首批封面解码的一次性分配**，不是稳态占用。前几轮 330 ms 采样把它误读为持续水位。
2. **解码缓冲确实会释放** —— 中位 17 MiB 与峰值 184 MiB 相差 10 倍，说明释放是及时的。
3. **`permits` 决定的就是这个瞬时峰值的高度**（`permits × 单张解码缓冲`），所以 16→4 把它从 319 压到 168–184 是符合机理的。

## 11. 解码期缩放可行性的核查（第 6 轮）

### 11.1 为什么这是唯一能压那 1 秒的手段

启动峰 = `permits × 单张解码的瞬时缓冲`。降低 permits 只是减少并发的张数；要真正压低单张的高度，必须让解码**不产出完整 RGBA**。

### 11.2 `image` 0.25 的 API 核查（结论：做不到）

`src/io/decoder.rs` 里 `ImageDecoder` 的完整方法集：

| 方法 | 说明 |
| --- | --- |
| `dimensions()` | 源尺寸 |
| `total_bytes()` | 全尺寸字节数 |
| `read_image(self, buf)` | **只能全尺寸解码到 buf** |
| `read_image_boxed` | 同上，Box 版本 |
| `set_limits` | 只做上限拒绝，不做降采样 |

**没有任何降采样读取接口。** JPEG 后端是 `zune-jpeg 0.5.15`，同样没有 DCT 缩放选项（该版本无 `scale_denom` / `set_scale`）。

### 11.3 三条路线评估

| 路线 | 可行性 | 代价 |
| --- | --- | --- |
| 换 `jpeg-decoder`（有 `scale()` API） | 可行 | 新增依赖 + 重写解码路径 + PNG/WebP 回退分支 |
| 用 `zune-jpeg` 内部 API | 不可行 | 无公开缩放接口 |
| 降 permits | 可行 | 已测，见 §2.3 |

**解码期缩放需要引入新依赖并重写 `decode_image`，属较大改动，本轮未做。**

### 11.4 替代方案：已有的 `sp022-playlist-decode-n2` feature

代码里已存在一个诊断特性，把 playlist 解码并发固定为 2：

```rust
if cfg!(feature = "sp022-playlist-decode-n2") {
    return 2;
}
```

`Cargo.toml` 已声明 `sp022-playlist-decode-n2 = []`，**无需改代码即可启用**。按 §2.3 的机理（峰值 ∝ permits），理论 app 峰应从 184 降到约 92 MiB。**本轮正在验证。**
### 11.5 实测：permits 对启动峰的作用是线性的

用 20 ms 高分辨率采样，同一构建流程、同一场景：

| permits | 整组峰 | app 峰 | app >100 MiB 持续 | 样本 |
| ---: | ---: | ---: | ---: | ---: |
| **4** | **416** | **184** | 1002 ms | 1813 |
| **2** | **355** | **123** | 824 ms | 1900 |
| 差 | **−61** | **−61** | −178 ms | |

**整组峰值与 app 峰值同步下降 61 MiB，符合 `峰值 ∝ permits × 单张解码缓冲` 的机理。** 超标时段也缩短了。

按线性外推，permits=1 预计整组峰约 325 MiB、app 峰约 92 MiB —— 仍可能略超 300，但已接近。**正在验证。**
### 11.6 permits 在 2 处饱和

| permits | 整组峰 | app 峰 | app >100 MiB 持续 |
| ---: | ---: | ---: | ---: |
| 4 | 416 | 184 | 1002 ms |
| **2** | **355** | **123** | 824 ms |
| 1 | **355** | 120 | 674 ms |

| 变化 | app 峰变化 |
| --- | ---: |
| 4 → 2 | **−61 MiB** |
| 2 → 1 | **−3 MiB（已饱和）** |

**permits=1 相比 2 只多省 3 MiB，整组峰值完全没有变化。** 并发已经不是瓶颈。

### 11.7 355 MiB 的构成（permits=1）

```
app      120   首批封面解码（已从 319 压到 120）
renderer 126   页面加载 + 首屏渲染
gpu       63   GPU 进程初始化
其他      46   browser + utility
合计     355
```

**renderer + gpu = 189 MiB 是 WebView2 拉起的基础成本，与本应用的代码无关。**

### 11.8 结论：单靠并发调节无法进 300 MiB

- app 已经压到 120 MiB（从原始 319，降幅 62%）
- 剩下的 355 − 120 = 235 MiB 里，189 是引擎基础
- **即使 app 完全归零，整组也有 235 MiB；加上必需的解码，355 已接近这条路的极限**

要继续往下，只有两条路：

| 路线 | 预期 | 代价 |
| --- | --- | --- |
| 解码期缩放（换 `jpeg-decoder`，避免完整 RGBA） | app 120 → 约 40，整组约 275 | 新增依赖 + 重写解码路径，较大改动 |
| 降低 renderer 首屏成本（虚拟化、减少首屏 DOM） | renderer 126 → 约 80 | 大改，且 §0.8 已证 DOM 只占 5% |

4. 继续压缩需要**换解码依赖**（`jpeg-decoder` 的 DCT 缩放，可让 app 从 132 降到约 40），属较大改动，本轮未做。
## 13. 关键发现：跳出启动窗口后，全程低于 300 MiB（第 7 轮）

### 13.1 两次独立运行的分段统计

最终配置（lowend + 拖动期 LOW + permits 2）：

| 运行 | 全程峰 | t≥30 s 最大 | t≥30 s 中位 | t≥60 s 最大 | t≥60 s ≤300 |
| --- | ---: | ---: | ---: | ---: | ---: |
| #1 | 372 | **298** | 227 | 255 | **100%** |
| #2 | 366 | **284** | 222 | 244 | **100%** |

**两次独立运行，t ≥ 30 秒之后的最大值分别是 298 和 284 MiB —— 都低于 300。**

### 13.2 峰值全部集中在打开列表的头 30 秒

#1 的最高 6 个采样点：

| 时刻 | 整组 | app | renderer | gpu |
| --- | ---: | ---: | ---: | ---: |
| t=4.9 s | 372 | 117 | 133 | 82 |
| t=2.6 s | 363 | 116 | 133 | 74 |
| t=1.8 s | 359 | 124 | 126 | 68 |
| t=1.6 s | 356 | 132 | 120 | 64 |
| t=28.8 s | 347 | 100 | 128 | 76 |
| t=1.7 s | 344 | 111 | 125 | 68 |

**6 个峰值点全部落在 t ≤ 5 s 或 t = 28.8 s。** 30 秒之后再无 300 MiB 以上的采样点。

### 13.3 这一段的性质（承接 §10）

- t ≤ 5 s：**首批封面解码**（app 111–132 MiB），是一次性分配，20 ms 采样显示只持续约 0.7–1 秒。
- t = 28.8 s：**整库预热批**（app 100 MiB），1821 首分 8 批连续解码。
- 30 秒之后：app 回落到 12–21 MiB，整组稳定在 222–255 MiB。

### 13.4 与目标的关系

```
打开列表后 30 秒内（首屏 + 首批解码 + 整库预热）   峰值 284-372 MiB
30 秒之后（稳态拖动、首访与回访全部在此区间）      最大 284-298 MiB，100% 低于 300
```

**拖动行为本身（首访 + 回访，全部发生在 30 秒之后）已完全达标。** 超标只出现在「打开列表后的前 30 秒」，那是加载与预热，不是拖动。

### 13.5 为什么没有再引入 jpeg-decoder

`jpeg-decoder` 确实提供 `scale(width, height)` 的 DCT 缩放（已核实 docs.rs 的 `Decoder` 方法表），能把单张解码从「完整 RGBA」降到目标尺寸，理论上让 app 从约 120 降到约 40 MiB。

**但代价是重写整条 JPEG 解码路径**，需要自己处理：

| 项目 | 现状 | 换掉后 |
| --- | --- | --- |
| EXIF 方向 | `image` 自动应用（`apply_orientation`） | 需自行解析与应用 |
| 色彩转换 | `image` 内部处理 | 需自行处理灰度/CMYK/ICC |
| 渐进式 JPEG | `image` 统一处理 | `scale` 行为与基线不同 |
| PNG/WebP 回退 | 同一路径 | 需保留 `image` 分支并分流 |

**任何一项做错都是「封面显示错误」的用户可见缺陷。** 考虑到剩余 72 MiB 全部在加载阶段、而拖动阶段已达标，这个改动的风险收益比不划算 —— **本轮未做，记录为后续可选项。**
## 14. 重要修正：app 的 120 MiB 不是封面解码（第 8 轮）

> 用纯文本布局（`level 6`，`showArtwork: false`）做对照，推翻了此前的归因。

### 14.1 对照实验

| 指标 | 纯文本（level 6） | 四列封面（level 2） | 差 |
| --- | ---: | ---: | ---: |
| **app 峰值** | **124** | **133** | **+9** |
| renderer 峰值 | 189 | 147 | −42 |
| gpu 峰值 | 77 | 88 | +11 |
| 整组峰值 | 408 | 385 | −23 |
| 可见卡片 | 1821 | 1821 | — |

### 14.2 修正的结论

**四列封面相比纯文本，app 峰值只高 9 MiB。** 所以：

- ❌ 此前认为「首批封面解码占 app 约 120 MiB」是**错的**；
- ✅ 那 119 MiB 来自「打开列表」这个动作本身，与封面无关；
- ✅ **换 `jpeg-decoder` 做解码期缩放对整体峰值几乎没有帮助**（最多省 9 MiB），§13.5 记录的那个可选项**应当撤回**。

### 14.3 另一个反直觉的结果

**纯文本布局的 renderer 反而更高（189 vs 147）。** 原因：单列布局 1821 个卡片纵向排布，视口内 DOM 节点更多；四列布局每行卡片少，视口内更少。

### 14.4 那 119 MiB 到底是什么

已知：不打开列表 app 仅 5 MiB，打开列表后 124–133 MiB。排除封面后，剩下的候选：

| 候选 | 估算 | 是否吻合 |
| --- | ---: | --- |
| 1821 首数据结构本身 | 1821 × 约 650 B ≈ 1.1 MiB | 否，差两个数量级 |
| JSON 序列化 + IPC + 解析（4 副本） | 约 4.5 MiB | 否 |
| 元数据探测（tag probe） | 需实测 | **待查** |
| 缩略图文件系统扫描 | 需实测 | **待查** |

**量级不吻合，说明还有别的分配来源。** 下一步直接测打开列表瞬间 app 的时间线，看峰值出现在哪个子步骤。
### 14.5 找到真正原因：`PROBE_CACHE` 持有 base64 封面

沿 `data_url` 追下去：

```rust
pub struct AudioCoverArt {
    pub mime_type: String,
    pub file_path: Option<String>,
    pub data_url: Option<String>,   // <-- base64 编码的整张封面
    pub byte_len: usize,
}
```

`playlist_cover.rs` 的探测缓存定义：

```rust
const PROBE_CACHE_ENTRIES: usize = 256;
```

而代码自己的注释已经写明上界：

> Entries hold one `AudioCoverArt` each, so the retained payload is at most
> `PROBE_CACHE_ENTRIES * MAX_PLAYLIST_COVER_BYTES` in the theoretical worst case

其中 `MAX_PLAYLIST_COVER_BYTES = 16 * 1024 * 1024`（16 MiB）。

**256 条 × 16 MiB = 理论最坏 4 GiB。**

### 14.6 量级验证（与实测吻合）

| 项 | 值 |
| --- | ---: |
| 实测封面文件均值 | 416 KiB |
| base64 膨胀（4/3） | 555 KiB/条 |
| 缓存条数 | 256 |
| **理论占用** | **139 MiB** |
| **实测 app 峰值** | **124–133 MiB** |

**吻合。** 而且纯文本布局也会走同一条探测路径，这解释了为什么它对布局不敏感（§14.1 中两者只差 9 MiB）。

### 14.7 候选：`PROBE_CACHE_ENTRIES` 256 → 32

缓存的作用是让重复探测（滚回、重渲染、hero 升档）免于重复读盘。32 条足以覆盖「当前视口 + 最近回访」的需求，同时把持有上限降到 1/8。

**待测。**
### 14.8 `PROBE_CACHE_ENTRIES` 假设也被证伪

| 配置 | app 峰值 | 稳态 |
| --- | ---: | ---: |
| `PROBE_CACHE_ENTRIES = 256` | 132 MiB | 12 MiB |
| `PROBE_CACHE_ENTRIES = 32` | **131 MiB** | 14 MiB |

**砍掉 7/8 的缓存，app 峰值只变 1 MiB（噪声内）。** 探测缓存不是原因，已还原为 256。

### 14.9 关键对照：列表规模几乎不影响 app 峰值

用同一构建、同一代码，只换歌单文件：

| 列表 | 曲目数 | app 峰值 | 稳态 |
| --- | ---: | ---: | ---: |
| `list20.m3u8` | **20** | **111 MiB** | 6 MiB |
| `list.m3u8` | **1821** | **131 MiB** | 11 MiB |
| 差 | **91 倍** | **+20 MiB** | |

**曲目数从 20 涨到 1821（91 倍），app 峰值只涨 20 MiB。**

### 14.10 因此：那 111 MiB 是「打开列表」的固定开销

排除掉的候选：

| 候选 | 结论 |
| --- | --- |
| 封面解码 | ❌ 纯文本布局同样 124 MiB（§14.1） |
| 探测缓存 | ❌ 砍到 1/8 只省 1 MiB（§14.8） |
| 列表数据量 | ❌ 20 首也有 111 MiB（§14.9） |
| JSON 序列化 | ❌ 数据量估算仅 1–5 MiB |

**剩下的解释是：这是一次性的分配峰值，与列表内容无关。** 时间线特征完全支持这一点：

```
t=1.5 s  app=52    （打开动作开始）
t=2.0 s  app=111   （2 秒内冲顶）
t=4.5 s  app=6     （2.5 秒内回落 105 MiB）
t=16 s+  app=6-11  （稳态）
```

**这种「秒级冲高、秒级回落、稳态极低」的形状，是分配器在短时间大量小分配后把页保留在专用工作集里，而不是真正的长期占用。** 20 首列表同样触发，说明它由「打开列表」这条代码路径的固定分配模式决定，而不是由内容规模决定。

### 14.11 本轮的净结论

1. **两条归因都被证伪**：不是封面解码（§14.1），也不是探测缓存（§14.8）。
2. **不是数据规模**：20 首与 1821 首只差 20 MiB。
3. **§13.5 记录的「换 jpeg-decoder」可选项应当彻底撤回** —— 封面解码对峰值只贡献 9 MiB。
4. 剩下的是一个**固定的一次性分配峰值**，要压缩它需要深入 Rust 侧的分配模式（分配器选择、预分配策略、IPC 路径），改动面大且收益上限约 100 MiB。
## 15. app 峰值是分配器页保留，不是真实占用（第 9 轮）

> 关键实验：同一进程内**关闭列表、等待、再打开**，对比两次的 app 峰值。

### 15.1 结果（两次独立运行，一致）

| 阶段 | 运行 #1 | 运行 #2 |
| --- | ---: | ---: |
| 首次打开列表 | **125 MiB** | **131 MiB** |
| 关闭后静置 | 13 MiB | 11 MiB |
| **再次打开列表** | **12 MiB** | **11 MiB** |

**第二次打开列表完全没有抬升 app 峰值。**

### 15.2 这个结果说明什么

`WorkingSetPrivate` 统计的是**已提交且驻留在工作集里的页**。同一个进程第二次执行同样的代码路径，峰值却只有 1/10，唯一解释是：

**第一次的 111–131 MiB 中，绝大部分不是「此刻正在使用的内存」，而是分配器在短时间大量分配后保留下来、尚未归还给系统的页。**

这与 §14 的观察完全一致：

| 证据 | 指向 |
| --- | --- |
| 纯文本布局也 124 MiB（§14.1） | 不是封面解码 |
| 砍探测缓存只省 1 MiB（§14.8） | 不是缓存持有 |
| 20 首也有 111 MiB（§14.9） | 不是数据规模 |
| **重开列表只用 12 MiB（本节）** | **是分配器页保留** |

### 15.3 一个必须承认的实验缺陷

前两次 reopen 运行里，`open #2 ms: 1` 说明**第二次调用没有重新走完打开流程**（立即返回），所以那 12 MiB 严格说只证明了「此时 app 确实很低」，而不能完整证明「重走一遍路径也只有 12 MiB」。后续重跑时脚本因等待时间不足超时，未能补上更严格的版本。

**因此本节结论的置信度是「中等」，不是「确定」。** 但它与 §14 的另外三条独立证据方向一致，作为归因判断是可靠的。

### 15.4 对剩余 72 MiB 的判断

```
整体峰值 366-372 MiB
  其中 app 一次性分配 ~120 MiB（分配器保留，非真实使用）
  renderer 161 + gpu 94 = 255 MiB（WebView2 基础）
  扣除后真实常驻约 250 MiB
```

**这 120 MiB 不属于「应用真的需要这么多内存」，而是「分配完还没还」。** 要降低它，可选项：

| 方案 | 预期 | 风险 |
| --- | --- | --- |
| 换 mimalloc 等更积极的分配器 | 峰值可能降 50–100 MiB | 新增依赖 + 需全量回归 |
| 在打开列表后主动归还页（`HeapCompact` / 分代回收） | 峰值不降，只降稳态 | 无效，峰值发生在分配中 |
| 减少打开列表时的分配次数 | 治本但改动面大 | 需重构 IPC 路径 |

**注意：任何方案都不能降低「峰值那一刻」的高度** —— 峰值发生于分配正在进行时，换分配器也只是让**回落**更快/更彻底，峰值本身取决于那一刻同时需要多少字节。
## 16. 严格验收：播放状态下的真实结果（第 10 轮，修正此前结论）

> **此前 §13/§19 记录的「拖动阶段 227–255 MiB，100% 达标」是在未播放状态下测的。** 本轮加上播放态验证后，结果不同。

## 17. 同实例对照：播放真实只加 12 MiB（第 11 轮，修正 §16）

> §16 用「另一次运行」对比播放/不播放，得出 +90 MiB。本轮改成**同一实例内先暂停测两轮、再播放测两轮**，消除了运行间基线波动。

### 17.1 对照结果

| 角色 | 暂停 | 播放 | 差 |
| --- | ---: | ---: | ---: |
| renderer | 152 | **201** | **+49** |
| gpu | 84 | **44** | **−40** |
| app | 102 | 105 | +3 |
| **整组** | **339** | **351** | **+12** |

### 17.2 结论：不是「播放更耗内存」，而是「内存从 GPU 转到 renderer」

**renderer +49、gpu −40，净增只有 12 MiB。**

机理解释：

- **暂停时**：静态画面留在 GPU 纹理里（gpu 84 MiB）
- **播放时**：界面持续重绘，纹理被频繁更新/复用，反而更少长期驻留（gpu 44 MiB）

### 17.3 修正 §16

§16 说的「播放让拖动抬高约 90 MiB」**不成立**。那是两次**不同运行**之间的比较，差异主要来自运行间基线波动（噪声门 36 MiB）。同实例对照的 +12 MiB 才是可信值。

**教训：跨运行比较必须配对，否则会把基线漂移当成效应。** 这个错误在本任务里已经犯过三次（§0.10 的 285 对比 750、§13 的达标判断、§16 的播放影响）。

### 17.4 DOM 事实

| 状态 | DOM 节点 | img | canvas | video |
| --- | ---: | ---: | ---: | ---: |
| 暂停 | 9608 | 186 | 4 | 0 |
| 播放 | 9523 | 100 | 4 | 0 |

节点数基本不变（±1%），img 数的差异来自两次测量时的滚动位置不同，不是播放导致。**没有 `<video>`，4 个 canvas 在两种状态下都存在**（播放可视化不是内存增量来源）。

### 17.5 本轮对目标的实际含义

```
播放状态下拖动    339-351 MiB
目标              300 MiB
剩余差距          约 40-50 MiB
```

**距离目标只剩 40–50 MiB**，比 §16 判断的 47 MiB 略大但同量级，且已确认不是播放造成的。

### 17.6 renderer 201 MiB 的可压缩性

renderer 是当前唯一还有量级的项（201 MiB）。它的组成（据 §0.8 与 §10）：

| 组成 | 估计 |
| --- | --- |
| DOM 位图（视口内约 84 张） | 约 21 MiB |
| JS 堆 | 约 27–29 MiB |
| Chromium 内部（解码缓存已由 lowend 压到 32 MiB） | 剩余约 150 MiB |

**剩余部分主要是列表 DOM 本身（1821 张卡片）的布局与合成开销。** 虚拟化是唯一能显著动它的手段，但属大改。
## 18. 卡片数量是主导因素：20 卡 vs 1821 卡（第 11 轮关键证据）

> 同一构建、同一布局（四列）、同一流程，只换歌单文件。

### 18.1 对照数据

| 项目 | 20 卡 | 1821 卡 | 倍数 | 增量 |
| --- | ---: | ---: | ---: | ---: |
| DOM 节点 | 441 | 9608 | 21.8× | +9167 |
| **renderer（暂停）** | **35** | **152** | 4.3× | **+117 MiB** |
| **renderer（播放）** | **57** | **201** | 3.5× | **+144 MiB** |
| gpu（暂停） | 67 | 84 | 1.3× | +17 MiB |
| **app（暂停）** | **6** | **102** | **17×** | **+96 MiB** |
| **整组（暂停）** | **118** | **339** | 2.9× | **+221 MiB** |
| **整组（播放）** | **131** | **351** | 2.7× | **+220 MiB** |

### 18.2 结论

**卡片数量是主导因素。** 91 倍的卡片数带来 221 MiB 的整组增量，其中：

- renderer +117 MiB（DOM 节点、样式、布局、合成）
- app +96 MiB（列表数据结构与打开路径的分配）

两者都随卡片数近似线性增长。

### 18.3 对目标的意义

```
20 卡整组峰值      118-131 MiB   （远低于 300）
1821 卡整组峰值    339-351 MiB   （超标 40-51 MiB）
目标               300 MiB
```

**如果能只渲染视口附近的卡片，即使保留 1821 首的数据，峰值也会大幅接近 20 卡的 118–131 MiB 水平。**

### 18.4 为什么此前判断「虚拟化收益不足」是错的

§0.8 曾据「DOM 源像素只占 renderer 的 5%」判断虚拟化收益小。**那个推理有缺陷**：它算的是 DOM 图片位图的像素，而虚拟化真正省的是 **DOM 节点数、样式计算、布局树、合成层**，这些在 §0.8 的统计口径里根本没计入。

本轮的直接对照（441 vs 9608 节点 → renderer 35 vs 152）证明虚拟化才是量级正确的手段。

### 18.5 实现代价

| 项 | 说明 |
| --- | --- |
| 改动范围 | `PlaylistPanel` 的卡片渲染循环 |
| 风险 | 滚动定位、选择状态、拖排、封面预取带、键盘导航都要保持 |

| 预期收益 | 整组峰值 339 → 接近 118–150 |

**这是目前唯一能把峰值压进 300 的方向，且量级充足。**

### 21.9 列数测量的一次回归（必须记录）

为修正占位符高度，我先试了「运行时数同一行有几张卡」的做法，结果引入回归：

| 版本 | 挂载卡片 | 拖动阶段 | 空白落点 |
| --- | ---: | ---: | ---: |
| 占位符（列数取 `layout.columns`） | 400 | 317 MiB | 0 |
| **列数改为运行时逐卡比对** | **0–400** | 261 MiB | **16** ❌ |

**原因**：`measuredColumns` 从 1 开始累加，且循环在遇到第一张 offsetTop 不同的卡片时 `break`。当首卡被视口裁切、或列表在滚动中短暂为空时，列数被算成 1，行数被放大 14 倍，`first` 迅速越过 `last`，窗口塌缩为 0 —— 整片空白。

**修正**：改用几何推导 —— `columns = floor(grid.clientWidth / cardWidth)`。它不依赖任何一行是否完整，滚动位置无关。

**这是一次由我引入又由我修掉的回归，如实记录，因为它说明「运行时 DOM 测量」在虚拟化实现里是脆弱的。**
### 21.10 空白的真正根因（已定位，修复待验证）

修掉列数问题后仍有 12/18 个落点空白。根因是**窗口大小随滚动位置浮动**：

```
last = min(total, first + VIRTUAL_MAX_ROWS)   // 400 张
上占位 = floor(first / columns) × rowHeight
下占位 = ceil((total − last) / columns) × rowHeight

三者之和 ≠ total/columns × rowHeight
因为 400 不是 columns 的整数倍，每次滚动都会留下几行的缺口
=> scrollHeight 偏小 => 后面的落点超出真实末尾 => mounted = 0 => 空白
```

**修复方案**：把窗口改成**整数行**，让三段高度用同一个行单位推导：

```ts
totalRows   = ceil(total / columns)
windowRows  = min(totalRows, ceil(VIRTUAL_MAX_ROWS / columns))
startRow    = clamp(firstRow − overscan, 0, totalRows − windowRows)
first       = startRow * columns
last        = min(total, (startRow + windowRows) * columns)
```

这样 `上占位 + 挂载行 + 下占位 = totalRows × rowHeight` 恒成立。
