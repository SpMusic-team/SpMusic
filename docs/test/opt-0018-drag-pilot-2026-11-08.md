# 真实滚动条拖动测试：3 对试跑验证报告

> **目的**：在进入正式对照前，确认这套拖动测量能复现"拖动滚动条后大片封面空白、随后陆续补齐"的体验，且两臂走相同路线。
> **本轮未修改产品代码、未调整调度与并发。**

## 1. 测量方式

| 项 | 做法 |
| --- | --- |
| 拖动方式 | **CDP 真实指针事件**：`mousePressed` → 14 次 `mouseMoved`（每次间隔 16 ms）→ `mouseReleased`，作用在**真实滚动条**上（轨道宽 10 px，x=1115） |
| 为什么不用 `scrollTop` 赋值 | 直接赋值会跳过拖动期间的加载窗口，遗漏"拖动过程中已完成"的封面 |
| 计时起点 | **松手时刻**（`mouseReleased` 之后立即在页面内读取 `performance.now()`） |
| 采样起点 | **拖动开始之前**（`mousePressed` 前），因此拖动期间完成的加载会被算作"松手时已显示"，而不是松手后的成本 |
| 固定目标 | **松手瞬间冻结**视口内全部条目；此后不因"图片是否出现"而增删 |
| 超时 | 20 秒，不延长；未达成即记为超时并保留 |
| 位置 | `scrollTop` 从 174 拖到 **12088**（目标比例 0.55） |
| 停留 | 两臂相同：准备后 2500 ms 再操作；回访额外预热后再回顶部 |

## 3. 体验复现确认

**与描述的现象一致**：

- **松手时视口内 5–6 张封面全部空白**（每屏 2 列 × 3 行 = 6 张）。
- 首张封面约在 **185–298 ms** 后出现。
- 全部补齐约在 **311–448 ms**。
- 回访位置比首次到达快（首张 185–202 ms vs 244–298 ms；全部 313–376 ms vs 374–448 ms），符合磁盘缓存已命中的预期。

**截图核对**：`pair1-first-baseline/after-settle.png` 与 `pair1-first-candidate/after-settle.png` 两臂视角完全相同——相同滚动位置、相同 6 张卡片、封面全部正常显示。说明路线与终点可复现。

## 4. 本轮暴露的一个真实问题（必须在正式测试前说明）

**空白面积×时间这一项在试跑中数值不稳定**（首次 110–135；回访 78–112），因为：

- 视口只有 6 张卡，单张面积大，积分对**首帧 dt 的取值**很敏感；
- 试跑 n=3，逐帧采样受渲染抖动影响，尚不足以给出稳定区间。

**正式测试需注意**：该项只作辅助参考，主判定仍以「首张缺失封面出现时间」与「全部补齐时间」为准。报告中会明确写出这一点，不用空白面积单独下结论。

## 6. 正式测试将采用的规则（预登记）

- **规模**：20 对，每对含 `first` 与 `revisit` 两个场景。
- **顺序**：按对奇偶交替 A→B / B→A，由脚本记录实际顺序。
- **固定条件**：目标比例 0.55、拖动 14×16 ms、准备后停留 2500 ms、超时 20 s 不延长。
- **主指标**：松手后「首张缺失封面出现时间」与「全部补齐时间」。
- **辅助指标**：松手时空白数量、空白面积×时间、长帧数（>50 ms）、错误图数、超时数。
- **判定门槛**：配对差值中位数 ≥20 ms 且 ≥10%，bootstrap 95% CI 下界 > 0 判为改善；反向且 CI 上界 < 0 判为退化；否则「无可证明改善」。
- **失败保留**：超时、错误图、空白未补齐一律保留原记录，不计入平均，单独列出。
- **不混合**：与场景 A（准备后打开列表）、场景 B（首次打开来源）的结果各自独立。
