## 0. 上一版错在哪里（必须先说清）

| 上一版结论 | 实测更正 | 错因 |
| --- | --- | --- |
| 「松手后 **190 ms 内没有请求**，首批延迟 190 ms」 | **首个请求只要 1–37 ms**（三次：37 / 1 / 18） | 上一版的批次判定把两次不同运行的数据混在一起读了；且结束条件错误，导致采样窗口提前闭合 |
| 「所有请求都是 `priority: 2`，没有优先级区分」 | **已有区分**：`useLibraryArtwork.ts:302-303` 是 `previews→0 / detailVisiblePaths→1 / 其它→2` | 只看了 512 hero 分支（`:351` 确实硬编码 2），误推广到全部 |
| 「瓶颈是请求排队（调度器层）」 | **调度器层不是瓶颈**；节拍来自窗口层的 `CONCURRENCY = 2` | 未核对 owner 层的在途上限 |
| 「188 ms 是 `--app-motion-standard: 240ms`」 | 是 **`--app-motion-prototype-press: 200ms`**（`playlist-panel.css:437`） | 看错了变量：240ms 属于 `playlist-hero-image`（`:77`） |

**方法论教训**：上一版用一个宽松的"视口内无 pending 即完成"作为结束条件，而视口外目标根本不在采样范围内，导致在大部分目标仍空白时就收尾。本版改为**松手瞬间冻结目标集合并以该集合全部就绪（连续两帧）为终点**。

## 4. 请求节拍（这是真正的位置）


**稳定特征：绝大多数桶只有 1–2 个请求，节拍持续到 550–600 ms。**

这个"每批约 2 个"正好对应：

| 层 | 上限 | 位置 |
| --- | --- | --- |
| 调度器（全局） | `MAX_CONCURRENT = 4` | `playlistCoverScheduler.ts:83` |
| **窗口 owner（本列表）** | **`CONCURRENCY = 2`** | `useLibraryArtwork.ts:94` |

**瓶颈在窗口 owner 的 2 个在途槽位**，而不是调度器的 4，也不是派发空窗。

## 5. 第二个阻塞：load → 可见的 200 ms

上一版已测出：`load` 完成到 `opacity ≥ 0.99` 之间有稳定的 ~188 ms。根因是：

```css
/* src/features/player/styles/player/playlist-panel.css:436-438 */
.playlist-card-cover-image[data-loaded="true"][data-reveal="new"] {
  animation: playlist-card-cover-reveal var(--app-motion-prototype-press, 200ms) ...;
}
```

**这是产品视觉设计，按约束排除，不作为优化目标，也不计入任何收益主张。**

## 6. 为什么"提高当前视口优先级"这个策略无效

综合以上：

1. **优先级已经在区分**（`previews→0 / detailVisiblePaths→1 / 其它→2`），待优化面接近零；
2. **190 ms 的派发空窗不存在**（实际 1–37 ms），策略的前提不成立；
3. **真正的约束是 owner 的 2 个槽位**，而调整 priority 改变不了 `24 缺失 ÷ 2 并发 × 单批延迟` 这个除法；
4. 即使生效，priority 只能重排**已入队**的作业；在当前节拍下队列里始终只有少数项，重排杠杆很小。

**这个策略的风险/收益不对称**：收益受 2 槽串行化限制而趋近于零，风险却真实落在远处预取上（把预取饿死 → 后续滚动又缺失，正是约束里禁止的"靠牺牲别处制造提升"）。

## 7. 结论与建议

**不建议实现"优先级调整"策略。** 依据是上面四条，尤其"前提不成立"（无派发空窗）与"待优化面接近零"（已区分优先级）。

真正决定首次到达的是两个数：**owner 在途 2** 与 **200 ms 渐入**。而后者被约束排除，前者属于"调整并发"，同样超出本次授权范围（"不改 MAX_CONCURRENT、不改全局并发"）。

因此本次实验**没有在授权范围内可交付的加速策略**。按第 5 条要求，收益不成立时应如实撤回，不实现、不合入。

### 若要继续，需要另行授权的两个方向（本报告只记录，不实施）

| 方向 | 预期 | 与约束的关系 |
| --- | --- | --- |
| 提高 owner `CONCURRENCY`（2→3/4） | 直接影响"每批 2 个"的除法，是**数量级**收益的唯一来源 | **与"不改并发"冲突，需单独授权** |
| 把 predecode（WebView 解码）移出槽位持有期 | 槽位只覆盖 IPC 往返，不覆盖解码与发布，等价于提升吞吐 | 同样触及并发语义，需授权 |

第二项尤其值得注意：`useLibraryArtwork.ts:287` 在 `await ready` **之前**就 `runtime.active += 1`，直到 `:453` 的 `finally` 才释放，**整个异步 IIFE（含 predecode 与发布）都占着槽位**。这是 2 槽串行化的放大因素。
