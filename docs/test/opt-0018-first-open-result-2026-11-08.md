### 判定

按预登记门槛（配对中位数 ≥20 ms 且 ≥10%，CI 下界 > 0）：

- **未达到改善门槛** → 不是改善。
- **但 CI 上界为 −2.0 ms，不含 0，且 14/20 对是候选更慢** → 这是一个**方向一致的轻微退化**，不是噪声。
- 幅度 17.5 ms / 1.67%，远小于任何用户可感知的量级，但方向上不是零。

**结论：候选版在「首次打开来源」场景下略慢，属轻微退化。**

### 分阶段（中位数，相对 t0）

| 阶段（中位数，相对 t0） | 基线 A | 候选 B | 差值 |
| --- | --- | --- | --- |
| 激活 → 列表控件被点击（`listClickedMs`） | 14.5 ms | 14.5 ms | 0 |
| → 面板可见（`panelVisibleMs`） | 87 ms | 86 ms | −1 |
| → 网格 / 首卡挂载（`gridVisibleMs`） | 270 ms | 284 ms | **+14** |
| → **首张图达到可见**（`firstReadyMs`） | **551 ms** | **581 ms** | **+30** |
| 首个 img load（解码完成，`firstImgLoadMs`） | 113.5 ms | 111 ms | −2.5 |

**观察**：首个 img load 两臂几乎相同（113.5 vs 111 ms），但**首张可见**差了 30 ms（551 vs 581）。差距出现在 **load → 可见** 这一段，而不是请求或解码。

> **这一段现有工具无法拆分**（是否含 CSS 过渡、合成、还是 store 提交时机），不做推测。

## 3. 为什么场景 B 得不出改善

- 场景 B 的耗时绝大部分发生在**首次扫描、元数据探测、首次缩略图生成**上，这些由两臂**共用的后端与启动路径**决定。
- 路径通道改变的是**缩略图下发方式**（JPEG 路径 vs 裸像素）。但在首次加载中，缩略图**本来就要先被生成**，无论之后怎么下发。
- 分阶段数据显示：两臂的 `firstImgLoadMs` 几乎一致（113.5 / 111 ms），差异集中在 load→visible 的 30 ms。这不足以抵消首次加载的固定成本。
- 因此**首次加载场景下两臂差异很小，且方向对候选版不利**。这与场景 A 的「无可证明改善」并不矛盾——两个场景测的不是同一件事。
