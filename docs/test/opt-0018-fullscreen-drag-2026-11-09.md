> 本轮修复的两个工具缺陷（非产品问题）：
> 1. **回访补齐计时错误**：原先从拖动开始扫就绪，导致"拖动期间就绪"与"松手时未就绪"并存、出现负值。现改为**从松手时刻起、对同一批冻结 id 重新计时**。
> 2. **落点不稳定**：滚动条比例曾用拖动标定，结果在各次运行间从 1.2 抖到 2.6，造成落点偏差数百像素。现改为**由面板几何直接推算**，并加入**闭环真实拖动修正**。
> 另修复了 `launch.json` 的 `EBUSY` 竞态与进程残留（残留实例会拖慢后续运行）。

> 首张封面出现时间两臂差异均未跨越显著门槛（CI 都贴近 0 或跨 0），说明**第一张出来的速度差不多，差距集中在"后面那些"**。

**判定：退化。** 19/20 对候选更慢。

### 分位数据说明了什么

**三列档中 p50 也是负的（−106.5 ms），p90 −131 ms，全部补齐 −129.5 ms**——三个分位方向一致且幅度相近，说明**候选是从一开始就整体更慢**，不是只差最后一张。

四列档 p50 中位为 0 是因为多数配对在松手瞬间已有 ≥50% 就绪，该分位过早饱和，不具区分力；**p90 与全部补齐均为 −250 ms 左右且 CI 严格为负**。

## 4. 松手时空白（关键混杂因素，必须单列）

| 密度 | 基线空白比例 | 候选空白比例 |
| --- | --- | --- |
| 四列 | **0.301**（中位 24/78） | **0.397**（中位 31/78） |
| 三列 | **0.512** | **0.605** |

**20 对中，候选版每一次松手时的空白都更多**（四列多数多 5–10 张），无一例外。

这不是细节：**候选版在滚动过程中保留/复用已加载封面的能力更差**，导致松手瞬间有更多图需要重新加载。这与它在补齐时间上更慢是**同一个现象的两个侧面**，不能把两者当成独立结论。

因此本报告**不把"补齐更慢"单独归因于加载链路本身**——起点不同（候选要补的更多）也是事实的一部分。若按"每张卡平均补齐时间"折算，差距会缩小，但那需要先把因果分离，本轮数据不足以给出该折算。

## 5. 回访（预热后）

预热规则：**必须先确认目标位置封面真正补齐**（页面内逐帧读取可见状态直到全部就绪），再回顶部执行测量拖动。

| 密度 | 基线 A | 候选 B |
| --- | --- | --- |
| 四列 | 有空白（比例 0.038），补齐中位 **425.5 ms** | **全部命中缓存，0 空白，补齐全 0** |
| 三列 | 有空白（比例 0.186），补齐中位 **476 ms** | **全部命中缓存，0 空白，补齐全 0** |

**这一格不能读作"候选更快"。** 原因是**两臂起点根本不同**：候选在回访时 20/20 次全命中，基线仍有空白。

正确的表述是：**候选版回访时的缩略图缓存保留率更高**（几乎全部命中），因此回访没有可测的补齐。

这也和 §4 相互印证：候选在滚动中保留得更少 → 首次到达要补更多 → 但回访缓存命中更好。两个方向相反的观察同时存在，说明**缓存生命周期行为不同**，而非单纯的"更快/更慢"。

## 7. 结论

| 场景 | 结论 |
| --- | --- |
| 四列档首次到达（78 张） | **退化**：全部补齐 −256.5 ms（−24.0%），CI [−318.5, −184]，0/20 对候选更慢 |
| 三列档首次到达（43 张） | **退化**：全部补齐 −129.5 ms（−13.7%），CI [−166, −67]，19/20 对候选更慢 |
| 回访（两档） | 候选缓存保留率更高（全命中），**但起点不同，不作提速结论** |

**全屏 + 小卡片档位下，候选版的滚动补齐明显更慢，且松手时空白更多。两档密度结论一致，四列档幅度更大。**

## 8. 未覆盖 / 限制

- 单机、单曲库（120 首）、fresh 缓存启动。
- **小窗口旧批次（`dragformal`）单独保留，未与本批合并**，因其视口、cohort 与落点均不同。
- 回访场景两臂起点不同，无法直接比较补齐时间。
- `load → 可见`、`请求 → load`、后端内部各段仍无法拆分（需埋点）。
- 未覆盖 >1000 张独立封面、慢盘、高 DPI/缩放（本轮恒为 DPR 1）。
- CPU 峰值 85%，绝对数值受影响；两臂交替执行降低但不消除影响。
