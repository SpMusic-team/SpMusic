# 作业级全链路诊断：请求发出 / 后端返回 / 预解码（基线 3847bcc）

> 本轮只加**诊断埋点**，产品逻辑与默认行为不变。埋点全部在构建期开关之后。
> 目标：把"请求发出 → 后端返回 → 预解码完成"三段分开计时，确认主要耗时在哪一段。

## 0. 结论先行

| 段 | 中位耗时 | 占首次到达的比例 |
| --- | --- | --- |
| **入队 → 占槽**（前端排队） | **272–444 ms** | **最大单项** |
| **占槽 → 请求发出** | 0 ms | — |
| **请求发出 → 后端返回** | **59–60 ms** | 第二项 |
| **返回 → 预解码完成** | **0 ms** | 可忽略 |

**主要耗时在"返回路径之前"**，因此按你的规则转向测 Rust。

### Rust 内部拆分（决定性数据）

| 阶段 | 中位 | 最大 |
| --- | --- | --- |
| `indexUs`（读索引） | **0** | 0 |
| `cacheLookupUs`（查已发布缩略图） | **0** | 0 |
| **`probeUs`（读源文件提取封面）** | **8.3 ms** | 11.9 ms |
| **`scaleEncodeUs`（Lanczos3 缩放 + JPEG 编码）** | **33–36 ms** | **147.6 ms** |
| **`publishUs`（写缓存 + 更新索引）** | **7.3 ms** | 9.3 ms |
| `slotWaitUs`（等后端许可） | 0.001 ms | — |
| **合计** | **约 49 ms** | |

前端测得 59–60 ms，Rust 内部约 49 ms，**差额 7.6 ms** 为 IPC + 序列化。

**`scaleEncode` 是后端最大单项，占后端总时间的约 70%。**

## 1. 埋点设计

### 作业级 ID

同一条目会反复入队，`trackId` 无法区分不同次尝试。因此每次准入分配独立 `jobId`：

```
<trackId 末 6 位>#<generation>-<序号>      例：eb0eb1#1-464
```

- 只在带埋点的构建里生成（`coverTraceEnabled()` 为假时不产生该字段）；
- 前端所有阶段事件都带 `jobId`，可按作业对齐；
- 一个条目若有多个作业，取**最后一个真正发出请求的作业**作为"产出该图的那次"。

### 三段时刻

| 阶段 | 含义 |
| --- | --- |
| `request` | 原生 invoke **真正发出**（不是入队） |
| `response` | 后端返回路径或数据 |
| `predecode` | 图片预解码完成，可以上屏 |

### Rust 侧

`PlaylistThumbnailPath` 增加可选字段 `traceSegmentsUs`，仅在 `--features cover-trace` 构建下填充；默认构建 `None`，`skip_serializing_if` 使其完全不出现在 payload 里。

## 2. 三次诊断（全屏四列 110px，落点约可滚范围 98%）

| 运行 | 空白比例 | 补齐全部 | 入队→占槽 | 请求→返回 | 返回→预解码 | probe | scaleEncode | publish |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| jt1 | 0.333 | 872 ms | 272 ms | 59 ms | 0 | 8 ms | 36 ms | 7 ms |
| jt2 | 0.385 | 1002 ms | 333 ms | 60 ms | 0 | 8 ms | 33 ms | 7 ms |
| jt3 | 0.423 | 1097 ms | 444 ms | 60 ms | 0 | 8 ms | 33 ms | 8 ms |

三次一致。`response → predecode` **恒为 0 ms**，说明预解码不是瓶颈。

## 4. 判定与下一步

按你设定的规则：

> 如果主要耗在返回路径之前，再测 Rust 的读盘、缩放和写缓存。

**判定：主要耗在返回路径之前**（入队排队 272–444 ms 是最大单项，请求→返回 59–60 ms 是第二项，返回→预解码 0 ms）。因此已转向 Rust，结果见 §0 表格。

**Rust 侧结论**：

| 项 | 耗时 | 是否可优化 |
| --- | --- | --- |
| `index` / `cacheLookup` | 0 | 无需优化 |
| **`scaleEncode`（Lanczos3 + JPEG）** | **33–36 ms 中位 / 147.6 ms 峰值** | **唯一大头** |
| `probe`（读源文件提取封面） | 8.3 ms | 磁盘成本，有限 |
| `publish`（写缓存） | 7.3 ms | 磁盘成本，有限 |
| `slotWait` | 0.001 ms | 不是瓶颈 |

### 一项改进建议

**改 `scaleEncode`，而不是继续调前端调度。**

依据：

1. 后端约 49 ms 里 **33–36 ms 是缩放+编码**（约 70%），且峰值到 147.6 ms；
2. 前端侧已无空间：入队/占槽以外的阶段全是 0，占槽后立即发请求；
3. 入队排队 272–444 ms 是 2 槽 × 每次 ~59 ms 的算术结果，已在上轮证明加并发无效。

**具体可选做法**（都需先验证再实施）：

- 对**首屏/视口内**目标改用更快的缩放核（例如 bilinear 替代 Lanczos3），代价是质量略降，需要产品确认可接受；
- 或降低 `maxEdge`（256 → 192）减少缩放与编码工作量，需确认视觉可接受；
- 或对 512 与 256 之外的中间尺寸做缓存复用，避免同源多次缩放。

> **注意**：这些都触及**图像质量或产物规格**，属于产品决策，不能由性能单方面决定。按你的规则，"不靠视觉手段制造提升"同样适用于降低编码质量——所以应当先测出质量与耗时的权衡曲线，再决定是否采用。

### 本轮修掉的两个埋点缺陷（否则会得出错误结论）

1. **缓存命中路径不回报分段**：命中 `read_playlist_thumbnail_path_cache` 时直接返回，`trace_segments_us` 为 `None`。已在该分支补上（如实报告 index+lookup，其余阶段标 0）。
2. **`parseAudioThumbnailPath` 丢弃诊断字段**：命令包装层只挑固定字段返回，导致 Rust 分段根本没到前端。已改为透传。
