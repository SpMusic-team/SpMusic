## 1. 埋点设计

### 前端：三段独立计时 + 作业 ID

| 阶段 | 含义 |
| --- | --- |
| `request` | 原生 invoke 真正发出（不是入队） |
| `response` | 后端返回路径 |
| `predecode` | 预解码完成，图片可上屏 |

每次准入分配 `jobId`（`<trackId末6位>#<gen>-<序号>`），同一条目反复入队可按作业对齐。**若某作业缺少某一段，该段留空（`null`），不做插值或猜测。**

### Rust：只拆已有的准备阶段

`CoverTraceSegments` 拆成：

```
indexUs → cacheLookupUs → probeUs
        → prepareCacheLookupUs / prepareCacheHit   ← 命中判定
        → sourceDecodeUs → scaleUs → jpegEncodeUs   ← 生成阶段
        → publishUs → slotWaitUs
```

关键实现细节：`decode_image` 内部同时做源图解码与 Lanczos3 缩放，而它的返回元组被多处依赖，不能改签名。因此用**线程局部变量**把这两段传出来——worker 线程写入、同线程立即读取，不存在跨请求污染。该机制整个包在 `#[cfg(feature = "cover-trace")]` 下。

## 4. 判定：下一步该做什么

按你设定的规则：

> 如果确实发现重复生成，优先试复用已有结果；如果主要成本来自每张图都必须做的缩放或编码，再单独比较耗时与画质。

**判定结果**：

| 检查 | 结果 | 结论 |
| --- | --- | --- |
| 是否存在重复生成 | **30 个目标中 0 个被重复生成（三次一致）** | 「复用已有结果」无空间 |
| 主要成本是否来自缩放/编码 | **缩放 25–27 ms（占后端约 45%）、编码 2 ms** | **是缩放**，编码很小 |

**因此进入"单独比较耗时与画质"这一步，且只针对缩放。**

### 具体可比较的选项

| 选项 | 预期 | 代价 |
| --- | --- | --- |
| Lanczos3 → `Triangle`/`CatmullRom` | 缩放耗时可能显著下降 | 缩略图锐度略降 |
| 保留 Lanczos3 但降 `maxEdge` 256→192 | 工作量按面积平方下降 | 110 px 显示尺寸下几乎无损，但 192 对某些布局不足 |
| 两阶段缩放改为单阶段（去掉 `thumbnail_exact` 预降采样） | 省一次遍历 | 需要实测，可能反而更慢或质量下降 |

**其中第二条最值得先测**：当前显示尺寸是 110 px，而生成的是 256 px，**有 2.3 倍的过采样**。这一条既不改变滤镜，也不明显影响画质。

### 但必须由产品拍板

这三条都改变**画质或产物规格**。你之前约束过「不能靠隐藏渐入效果制造提升」——降低图像质量在性质上相同。因此我没有直接改，只给出可测的选项，建议先测**质量-耗时曲线**再决定。

## 6. 上一轮的一处错误归因（必须更正）

上一轮报告把后端的 35.8 ms 写成「**Lanczos3 缩放 + JPEG 编码**」，并据此说"编码也是成本"。

**这是错的。** 本轮把两段拆开后：

- 缩放 **25–27 ms**（真正的成本）
- JPEG 编码 **2 ms**（几乎可忽略）

原因：上一轮的 `scale_encode_us` 计时区间包住了 `decode_playlist_image`，而该函数内部同时做解码和缩放——**所以上一轮的"缩放+编码"里其实混着解码和缩放，编码被高估了**。

更正后不影响"该优化缩放"的结论方向，但**具体该动哪一步变了**：不是编码，是缩放。
