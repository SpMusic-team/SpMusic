# 全链路诊断：首次到达的每一段耗时（基线 3847bcc，带埋点构建）

> 本文件只做诊断，**产品逻辑未改**（埋点为构建期开关，普通构建完全不含）。
> 目标：在动手改之前，确认首次到达到底卡在哪一段。

## 0. 结论先行

| 发现 | 数值 | 判读 |
| --- | --- | --- |
| **`enqueue → occupy`（排队等槽位）** | **中位 706 / 684 / 909 ms** | **绝对瓶颈** |
| `occupy → response`（占槽后等后端） | 中位 64 ms | 第二项，但**槽位全花在这** |
| `response → decoded → publish → release` | 全部 **0–1 ms** | 可忽略 |
| `viewport → target → enqueue` | 全部 **0–1 ms** | 可忽略 |

**结论：不是"没及时入队"，也不是"解码/发布占着槽位"，而是「入队后排队等槽位」+「每次占槽要等 64 ms 后端」。**

## 1. 埋点设计

在测试构建里记录同一条目的 8 个阶段：

```
viewport → target → enqueue → occupy → response → decoded → publish → release
```

每个事件附带当时的**队列长度**与 **owner 实际占用数**，因此能把等待归因为"没活可干"还是"队列满、槽位忙"。

实现方式：

| 项 | 做法 |
| --- | --- |
| 开关 | `VITE_COVER_TRACE=1`，构建期内联；普通构建被编译成 `return false`，分支被摇掉 |
| 模块 | `src/features/player/services/coverTrace.ts`（新增，独立文件） |
| 读取 | `window.__coverTrace()` / `window.__coverTraceReset()`，仅在带埋点构建存在 |
| 有界 | 事件上限 40000，超限记 `dropped` 而不是无限增长 |
| 侵入 | 只在 `useAudioPlayer.ts` 的 6 个点加调用，全部包在 `coverTraceEnabled()` 里 |

### 关于 release 构建的一点如实说明

普通构建（不设 `VITE_COVER_TRACE`）里，`coverTraceEnabled()` 被内联为 **`return false`**，因此**每个埋点调用都在第一行立即返回，运行期零副作用、零开销**。

但**代码体积没有完全消除**（`__coverTrace` 等符号仍在产物中）。我已尝试收紧条件表达式，bundler 仍未摇掉——原因是这些函数被 `main.tsx` 顶层调用，形成了可见的副作用链。为消除它需要额外改构建配置，**收益不值得**，故保留并在此记录。

验证方式：release 产物中 `function Fn(){return!1}`，且所有调用点以 `if(!Fn())return` 开头。

## 4. 松手时仍空白的目标，逐个等在哪一步

| 松手时状态 | 数量 |

**读法**：这 10 个目标**在松手前 274 ms 就已经入队**，队列里积压 15 个作业，但**占用数始终是 2**。它们按顺序一批批被放行，每批要等前一批的 64 ms 后端返回。

`enqueue→occupy` 的等待 = 前面排着的作业数 × 64 ms ÷ 2 槽。37 个作业、2 槽、每个 64 ms ≈ 1184 ms，与实测 `enqueue→occupy` 中位 706 ms 量级一致。

## 6. 一项改进建议

### 建议：降低「占槽后等后端」的 64 ms，而不是再加并发

依据：

1. **加并发已验证无效**（并发 2 vs 4 无差异，peak in-flight 恒为 2）——因为每个槽位每次要占用 64 ms，2 槽已饱和；
2. **槽位没有解码/发布浪费**（余量 0 ms），所以"缩短槽位持有时间"唯一可动的就是**等后端这 64 ms**；
3. 但这 64 ms 是**后端真实耗时**（含 asset 请求 + 可能的解码），不是排队噪声。

因此建议方向是：**确认这 64 ms 里后端在做什么**——如果它大部分是缩略图解码/Lanczos 缩放，那这是 CPU 固有成本，前端无论怎么调度都不会变快；如果其中含可跳过的重复工作（例如同一源被重复解码），那才是可优化点。

> **注意**：这与"再提高并发"是相反方向。前面已证明提高并发无效，因此下一步应该先测**后端这 64 ms 的构成**，而不是继续调前端调度参数。

### 明确不建议的方向（基于实测）

| 方向 | 为什么不建议 |
| --- | --- |
| 提前加载 / 更早提交需求 | `viewport→target→enqueue` 全部 0 ms，已经是最早 |
| 提高并发 | 已验证 2 vs 4 无差异，且槽位已饱和 |
| 缩短解码/发布占槽 | 实测占槽余量 0 ms，无可缩短空间 |

## 7. 下一步（待确认）

在改任何产品代码之前，建议先把**后端 64 ms 的构成**测出来（解码 vs 缩放 vs 磁盘），否则前端调度方向的改动都无法预期收益。
