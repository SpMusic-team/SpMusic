# OPT-0018 阶段拆分与瓶颈分析（候选 3847bcc）

> 前置：[P1 修复验证报告](opt-0018-p1-fix-verification-2026-11-08.md)（两个 P1 已修、20 对 A/B 判定「无可证明改善」）。
> 本文只做**阶段拆分与观察**：**未修改产品代码、未调整并发、未扩大语料**。

## 摘要

- **首屏 8 张从点击到全部可见：1587 ms**；其中 868 ms 时 8 张图已全部 load 完成，**剩下 719 ms 现有数据无法拆分**。
- 首屏期间共发出 **29 次 cover 类请求**，发送跨度 **1008 ms**，后端单次中位 **69 ms**、最慢 209 ms。
- **asset 协议读取仅 2–10 ms**，可排除磁盘与协议层为瓶颈。
- **1052 ms 才发出的请求与首屏可见无关**（8 张图 868 ms 已 load 完），说明**预取请求与首屏请求共享同一条队列**——这是结构性问题。
- 滚动未就绪 37 张中，**33 张没有 `<img>` 元素被挂载**。
- **证据最充分的瓶颈：请求排队 + 后端执行这一段**（不是磁盘、不是 asset 协议、不是 DOM 挂载）。但**"排队"与"后端慢"这两者现有数据分不开**，见 §5。

## 1. 测量方法

| 项 | 做法 |
| --- | --- |
| 被测产物 | `D:\spbuild\...\app.exe`，SHA-256 `69F82944…B9D400`（源码 `3847bcc`） |
| 动作 | 点击「打开音频」→ 列表挂载 → 首屏 8 张可见 |
| 时钟 | 页内 `performance.now()`；CDP `Network` 事件用**受控 IPC 调用**标定到同一时钟 |
| 时钟不确定度 | **±19.8 ms**（实测标定残差，非假设值） |
| 可见判定 | `complete && naturalWidth>0 && opacity>=0.99` |
| 采样 | 页内事件监听 + CDP `requestWillBeSent`/`responseReceived` |

### 标定过程中发现并修正的三个工具错误（不是产品问题）

1. **CDP `timestamp` 不是 epoch**：初版按 epoch 毫秒处理，得到 `1794143265702` 这种偏移和巨额负数时间。实测该值是**任意原点的单调秒**（约 96,145,739 s）。
2. **`Network.loadingFinished` 在本构建不可用**：实测同一请求的 `finished` 时间戳**早于** `response` 时间戳（如 `response@96246059.9`, `finished@96246058.4`）。因此**所有基于 finished 的传输/总耗时一概不作数**，本报告只使用 `sent → response`。
3. **页面会在启动期重载**，早期安装的监听会丢失。改为在打开列表后、滚动前重新安装。

## 2. 阶段耗时表（首屏 8 张，n = 1 次代表运行）

| 阶段 | 观测值 | 数据来源 | 可信度 |
| --- | --- | --- | --- |
| 用户输入 → 首个封面请求发出 | **44 ms** | 页内 t0 与 CDP sent 标定后相减 | 受 ±19.8 ms 时钟不确定度影响 |
| 首个封面请求 → 首个响应 | **127 ms** | CDP `response − sent` | 高（同一时钟内相减，不受标定误差影响） |
| 首屏期间 cover 类请求总数 | **29 次** | CDP | 高 |
| cover 请求发送跨度（44 → 1052 ms） | **1008 ms** | CDP | 高 |
| 单次后端响应耗时（n=29） | **中位 69 ms**，min 1 / max **209 ms** | CDP | 高 |
| asset 协议读取（磁盘 → WebView，n=9） | **2–10 ms** | CDP | 高 |
| 首张图片 load（解码完成） | **397 ms** | 页内事件 | 高 |
| 第 8 张图片 load | **868 ms** | 页内事件 | 高 |
| 最后一张图片 load → 8 张全部可见 | **约 719 ms** | 页内事件 | 高 |
| **总计：点击 → 8 张可见** | **1587 ms** | 页内 | 高 |

### 代表性时间线（相对点击 t0）

```
   44 ms  第一个 cover 请求发出
   72 ms  第二个（与上一个并发）
  127 ms  第一个响应返回（后端 127 ms）
  198 ms  又一个 cover 请求
  397 ms  第 1 张图片 load（解码完成）
  468 ms  第 2 张 load
  515 ms  第 3 张 load
  634 ms  第 4 张 load
  669 ms  第 5 张 load
  747 ms  第 6 张 load
  810 ms  第 7 张 load
  868 ms  第 8 张 load
 1052 ms  最后一个 cover 请求才发出
 1587 ms  8 张全部达到可见（opacity>=0.99）
```

**关键观察**：

1. **请求确实有并发，但同时最多约 2–3 个在飞**，与前端 `MAX_CONCURRENT=4` / 窗口并发 2 一致。
2. 首屏 8 张图在 **868 ms** 时已全部 load 完成，但**可见状态拖到 1587 ms**——中间 719 ms 无法用现有数据拆分。
3. **29 次 cover 请求的发送跨度达 1008 ms**，且最后一个请求直到 1052 ms 才发出，此时 8 张图早已 load 完。说明**首屏可视之外还有大量请求在排队**（预取/超扫描），它们与首屏请求共享同一条队列。
4. asset 读取 2–10 ms，**不是瓶颈**。后端单次中位 69 ms、最慢 209 ms，是主要成本。

## 3. 滚动未就绪样本核查（抽查 10 个，全量 37 个）

在 14 次快速滚动、每次 4 帧采样后，统计所有"曾进入视口但从未在视口内可见"的卡片：

| 分类 | 数量 | 含义 |
| --- | --- | --- |
| `no-img-element` | **33** | 采样期间**从未有 `<img>` 元素挂载**到这张卡上 |
| `decoded-after-exit` | **3** | 图片在卡片离开视口**之后**才 load 完成 |
| `loaded-but-not-visible` | **1** | 图片在视口内 load 完成，但可见代理（opacity≥0.99）未满足 |

### 证据边界（必须说明）

- 用户要求的四分类（未请求 / 请求中 / 已返回未解码 / 已解码未显示）**只能可靠实现三档**：
  - `no-img-element`、`decoded-after-exit`、`loaded-but-not-visible`。
- **无法区分"未请求"与"请求中"**：DOM 不暴露 per-card 请求 ID，无法把某个卡片关联到具体的 IPC/asset 请求。要做到需要产品侧增加映射。
- `no-img-element` **不能**读成"没有请求"——封面可能已在 store 里被请求过，只是元素未挂载。本报告不这样解读。
- 抽查的 10 个样本与全量 37 个的分类逻辑完全一致，不是只挑有利样本。

## 4. 无法观测的阶段（明确标注，不猜原因）

| 阶段 | 为什么无法观测 |
| --- | --- |
| 调度器排队等待（invoke 发出前） | 前端没有在调度器入队/出队处埋点，只能看到请求已发出的时刻 |
| Rust 解码 vs 缩略图生成 vs JPEG 编码 | 后端无分段埋点，`audio_load_*_path` 只返回最终结果 |
| shared-writer 队列等待与原子发布等待 | 同上，且 writer 是单线程后台任务 |
| asset 请求内的磁盘读取时间 | 只能看到 asset URL 的 sent→response（2–10 ms），无法拆分其中读盘与协议开销 |
| 图片解码 vs 实际绘制 | `img load` 在解码后触发，但**不保证已合成到屏幕**；settled 用的 opacity 是 CSS 动画完成信号 |
| 传输完成（loadingFinished） | 本构建时间戳异常（早于 response），**不可用** |

## 5. 证据最充分的瓶颈

### 瓶颈：首屏期间共 29 次 cover 请求挤在同一条队列上，后端每次 69 ms（中位）

**支持证据**（同一次运行、同一时钟域）：

1. **29 次 cover 类请求**，发送时刻从 44 ms 拉长到 **1052 ms**（跨度 1008 ms）。
2. 但**首屏 8 张图在 868 ms 就全部 load 完成**。也就是说 **1052 ms 才发出的那些请求，与首屏可见无关**——它们是预取/超扫描请求，却和首屏请求共享同一条 `MAX_CONCURRENT=4` / 窗口并发 2 的队列。
3. 后端单次响应：中位 **69 ms**、最慢 **209 ms**（n=29，含全部请求）。若只看首屏前几个：127 / 99 / 69 / 159 / 126 / 209 ms。
4. **asset 读取仅 2–10 ms**，可排除磁盘与协议层。
5. 首屏 8 张 load 完（868 ms）到全部可见（1587 ms）还有 **719 ms**，这段现有数据无法拆分。

### 但因果链仍不完整（必须说明）

- 我**不能**证明 1008 ms 的发送跨度是"卡在调度器队列"还是"后端 69 ms×N 回压"。两者产生同样现象。
- 也**不能**证明 719 ms 的 load→visible 差距来自 CSS 动画、opacity 过渡，还是渲染合成。
- 现有工具**看不到调度器入队/出队时刻**，也**看不到后端内部分段**。

因此本报告主张的是：**瓶颈位于"请求排队 + 后端执行"这一整段，而非 asset 协议、磁盘或 DOM 挂载**。这是数据能支撑的最强结论。另外可以确定的是：**首屏之外的预取请求与首屏请求共享队列**，这是一个结构性问题，与后端快慢无关。

## 6. 改进建议（一条，不实施）

**给前端调度器与后端各加一组最小埋点，先把"排队等待"与"后端执行"分开，再决定优化方向。**

具体是三个时间点：

1. `scheduleTrackThumbnail` / `schedulePlaylistCoverPixels` **入队时**记 `performance.now()` 与该作业 key；
2. 作业**实际出队（invoke 发出前）**记一次；
3. Rust 侧在 `audio_load_*_path` / `*_pixels` 的**入口与出口**各记一次（`tracing` 已有基础设施）。

有了这三组数，才能回答"488 ms 里多少是队列等待、多少是后端执行"。**在此之前不建议动并发**——如果瓶颈其实是后端 CPU，加并发只会让每次响应更慢；如果是队列，加并发才有效。这两者现在的数据分不开。
