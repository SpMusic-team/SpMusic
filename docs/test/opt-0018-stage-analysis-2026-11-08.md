## 1. 统一口径

### 场景命名（本报告与后续文档统一使用）

| 场景名 | 定义 | 本文对应数字 |
| --- | --- | --- |
| **A.「新应用缓存启动、准备后打开列表」** | 全新应用缓存与 profile 启动，但**未计时的准备阶段已激活来源、生成目标缩略图并写入缓存**；随后才计时打开列表 | 正式 A/B 的 290/297 ms；本文三次诊断 284–310 ms |
| **B.「首次打开来源」** | 全新应用缓存与 profile，**在第一次激活来源之前**开始记录；包含扫描、元数据、首次缩略图生成的全部等待 | 旧探针的 1061 ms（已修正绝对值错误） |

> **关键更正**：场景 A **不能称为「冷封面加载」**。动作发生前缓存里已有目标缩略图，"冷"只体现在进程与 profile 是新的。此前把 1061 ms 叫"冷启动"、把 287 ms 叫"热磁盘缓存"都不准确，现按上表统一。

- **所有时间一律相对被测动作的 `t0`**；`t0` 在页面内、点击前同一执行上下文读取。**不报绝对 `performance.now()` 值。**
- **就绪时间在页面内逐帧采样**得出，不用外部轮询结束时间代替。
- 场景 A 的缓存准备与动作口径**与正式 A/B 一致**：打开来源 → 确保面板关闭 → 未计时 `settle 2000 ms` → 点击列表控件 → 只计其后的时间。
- 可见判定沿用 A/B 已验证定义：`complete && naturalWidth > 0 && opacity >= 0.99`，固定 8 张 cohort。

| 运行 | 点击 → 8 张全可见 | 点击后 cover 请求 | 其中 asset | 其中 IPC | asset 单次耗时 |
| --- | --- | --- | --- | --- | --- |

| run2 | **284 ms** | 6 | 6 | 0 | 18–20 ms |

- 三次高度一致（284–310 ms），与正式 A/B 的 290 / 297 ms 同级。

## 3. 为什么这次约 287 ms，而之前约 1061 ms

**两者不是同一个场景，不能直接比较。**

| | 之前的 1061 ms | 本次 284–310 ms |
| --- | --- | --- |
| 应用状态 | 场景 B：全新缓存+profile，动作前**未**激活来源 | 场景 A：已启动、来源已激活、面板已准备 |
| 被测动作 | 点「打开音频」（触发启动后全链路） | 点「播放列表」（打开面板） |
| 动作前缓存 | **空**（尚无任何缩略图） | **已填充**（准备阶段的 81 个请求已写好磁盘缓存） |
| 动作后的请求 | 29 个 cover 请求，跨度 1008 ms | 6 个 asset 请求，全部并行 |
| 是否含首次扫描/元数据 | **是** | 否 |
| 后端参与 | 有（29 次 IPC，中位 69 ms） | **无**（0 次 IPC，纯 asset 读） |

**结论**：1061 ms 属**场景 B（首次打开来源）**，包含扫描、元数据与首次填充缓存；287 ms 属**场景 A（新应用缓存启动、准备后打开列表）**，动作前目标缩略图已在缓存中。**正式 A/B 测的也是后者**，所以 A/B 的 290/297 ms 与本次 284–310 ms 可比；**1061 ms 不与任何 A/B 数字可比**。

### 一个必须承认的口径事实

本次三次运行虽然缓存根在启动时是空的，但**在未计时的准备阶段（约 2000 ms settle）里已经写满了 cohort 的缩略图**。因此这 6 次 asset 请求**全部命中磁盘缓存**。

所以：**本次与正式 A/B 测的都是场景 A** —— 新应用缓存启动、准备后打开列表，动作前目标缩略图已在缓存。两者同口径因而可比；**但都不能称为「冷封面加载」**。

### 由此得到的一个明确事实（非猜测）

**打开面板这个动作本身几乎不产生后端工作**（0 次 IPC）。它的耗时由 6 次并发 asset 读取（约 21 ms）加图片解码/呈现构成。所以「打开耗时」这个 A/B 指标的瓶颈**不在后端 IPC**——这在本次数据里是可观测的确定结论，而不是推测。

## 5. 瓶颈：仍无法区分排队与后端执行

- 本次**打开面板**场景里，后端 IPC 为 0，因此**该场景不存在"后端执行"变量**——瓶颈只可能在 asset 读取、解码、呈现三者之间。
- 而**场景 B「首次打开来源」（1061 ms）**中，29 次 IPC、单次中位 69 ms，与 1008 ms 的发送跨度同时存在。**现有数据无法判断这 1008 ms 里多少是调度队列等待、多少是后端执行。**
- 因此「排队是瓶颈」这个说法**在场景 B 下仍未被证实**，本次**撤回**。

## 6. 仍缺失的观测点（最小埋点方案，先不改调度与并发）

要区分排队与后端执行，只需三个时间点：

| # | 位置 | 记录内容 |
| --- | --- | --- |
| 1 | `scheduleTrackThumbnail` / `schedulePlaylistCoverPixels` **入队**处 | `performance.now()` + 作业 key |
| 2 | 同一作业**出队、invoke 发出前** | `performance.now()` + 同一 key |
| 3 | Rust 侧 `audio_load_*_path` / `*_pixels` **入口与出口** | `tracing` 已有基础设施，加两个 span 即可 |

有了 1+2 就得到「队列等待」，有了 3 就得到「后端执行」。在此之前，**不建议调整 `MAX_CONCURRENT` 或窗口并发**——若瓶颈是后端 CPU，加并发会让单次更慢；若瓶颈是队列，加并发才有效，而现在两者不可分。
