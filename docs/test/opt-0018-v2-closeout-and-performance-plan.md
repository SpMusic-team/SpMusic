# OPT-0018 v2 收尾验收与封面加载性能实验方案

## 1. 交接目标与完成条件

本次先补正确性闭环与可信测量，再判断下一项优化。本文是待执行方案，不把现有报告或辅助模块测试通过当作最终验收。

配套实现边界见 [架构收尾方案](../architecture/opt-0018-v2-closeout-and-optimization.md)。Frontend / Rust 实现者提供证据，Test Agent 独立复跑关键用例并作通过、不通过或证据不足判定。任何阶段仍有永久 loading、错误封面或无界工作，暂停性能实验并退回实现者。

完成须同时交付：DOM失败补救与真实hook回归；修正的测量工具；同条件原始数据；有界CPU/内存观测；逐项验收结论。没有明显时延收益可以如实交付，但不得写“封面加载速度优化已验证”。

## 3. 先修测量口径

### 3.1 动作前起钟

旧 `ab-run.mjs` 在打开动作后sleep150 ms，等待grid出现后才记t0；scroll先停留默认900 ms才起钟。这些结果可保留为历史局部指标，不改名为从用户动作开始的端到端耗时。

新版每次动作按以下顺序执行：

1. 确认测量前置状态、清空本轮计数，安装MutationObserver、图片load/error、滚动、长任务与帧采样监听；安装监听不得触发封面预热。
2. 在同一个浏览器执行上下文中记录单调时钟t0，紧接着发出click或首次scroll输入，并写入动作标记。不得等网格、IPC或任意延时后重置t0。
3. 持续采集到预先规定的截止条件；grid尚不存在、元数据未就绪的时间包含在总时延中，另存其分段时间。
4. 每次动作结束关闭监听、清理定时器；超时和未就绪项作为失败/删失样本保留，不能只留下成功样本。

建议打开、返回列表、单次滚动、连续滚动各自独立记录，不把不同用户动作的结果混成一个settle。动作发生在原生对话框前还是选择完成后必须固定；可排除用户选文件的思考时间，但两臂起点必须一致。

### 3.2 合法目标集合与可见代理

测试语料预先标记哪些条目有封面、无封面或损坏。根据固定视口、布局和列表顺序定义目标cohort的稳定条目ID，不能通过“本轮已经有img的卡片”反推目标。

元数据晚到时延可以计入总时延；目标集合从已知fixture/预先保存的ID映射取得，映射在本轮期间不变。发布过程中DOM卸载、身份变更或虚拟化替换必须记录，不将“节点消失”计为封面已完成。

对每个目标分别记录：首次进入可见区域、URL发布、DOM load/error、`complete && naturalWidth > 0`、有效可见尺寸、实际样式opacity及身份匹配。图像就绪与无图占位就绪分开统计。

首次可见与动画完成分开定义；opacity阈值在pilot后预先登记，正式实验保持一致。不得把刚有微弱透明像素等同封面已完整显示，也不能因两臂动画不同而临时换阈值。

有图集合的首图时间、首屏全部有图完成时间；无图集合的合法占位完成时间；坏图/真实错误的终态时间分别报告。无图占位不能让“全部封面完成”提前成功，缺图也不能从分母消失。

连续至少两个动画帧满足条件并保存关键帧截图，作为可见性的代理。DOM属性、requestAnimationFrame或截图代理均不能声称直接测到了GPU合成/屏幕present时点；报告用“可见代理就绪”，并明确精度边界。

### 3.3 滚动进行中的空白暴露

固定同一滚动脚本、速度、方向、停顿与输入方式，至少包含缓慢、快速连续、反向、离开后回访。t0在首次输入前；最后一次输入另记tStop，不在目标位置预等900 ms后才开始采集。

逐帧或固定频率采样每个可见目标的可见面积与封面就绪状态，记录：

- 有图卡片空白曝光累计时间，以及按可见面积加权的空白面积×时间。
- 每卡从首次暴露到就绪的延迟、最长连续空白、停止滚动到当前目标补齐时间。
- 滚动期间帧间隔分布、>50 ms长任务、出错与loading残留数量。

目标在未就绪前离屏，记录已发生的空白曝光和离屏删失状态；不能算作成功。停止时固定最后视口cohort，再等待补齐到有界deadline。压力脚本的最终全就绪可以证明终态正确，不能单独证明滚动跟手。

## 4. 分段观测与真实工作量

| 观测 | 记录方式 | 禁止的推断 |
| --- | --- | --- |
| 前端时序 | 动作、metadata门控、入队、dispatch、响应、decode、store提交、通知、DOM代理 | 把收到路径的3 ms当封面显示时间 |
| 后端时序 | admission等待、来源探测/索引、缓存命中、读取、解码缩放、JPEG编码、writer排队/发布等待 | 前后端绝对时间直接相减 |
| 路径结果 | 请求/尝试ID、lane、cacheHit、missing、stale/abort、command/decode/timeout失败、fallback、熔断 | 0个SPXR文件证明0次回落 |
| IPC与文件字节 | 实测序列化响应大小/二进制长度及asset读取字节；分别说明统计边界 | 将路径字符数等同IPC全部开销或沿用固定100 B |
| 主线程与后端CPU | 同窗口采样CPU时间或trace；JS BMP调用次数/累计耗时另报 | 没有长任务便等于CPU下降，或把JS转码称为一次图片解码 |
| 内存 | 主进程、renderer及相关进程分别采样，注明working set/private bytes等口径 | JPEG文件大小等于WebView解码内存 |

两端分别使用单调时钟计算自身持续时间，通过requestId关联因果；跨进程绝对时间没有校准不得直接作差。诊断日志有界、可关闭，避免日志本身改变I/O实验；同样开关用于两臂。

去重后的原生请求计数和每个消费者的尝试计数分别记录；共享请求不重复计原生失败，多DOM错误不能让同一发布反复扣熔断计数。最终URL来自asset只能证明该图片最终使用路径，不能证明过程中从未失败。

CPU正式比较在相同测试窗口累计CPU时间；trace定位可以另跑，避免只给一臂开高开销分析。未采到CPU数据就写“减少特定JS操作”，不写“总CPU收益已量化”。

内存实验至少10分钟：同一滚动/切页循环、相同预热策略，每秒或固定间隔采样。保存起始稳定值、峰值、每分钟区间及末段趋势；结束后等待固定空闲窗口再采样。缓存趋稳允许平台常驻上升，但持续无界增长、作业/监听/临时Image数量不收敛须退回调查。

## 5. 正确性收尾矩阵

采用架构方案规定的完整identity、artworkRevision和publishGeneration，测试必须调用真实hook/store入口；仅测试helper传对谓词不足以保护实际调用方。

| 场景 | 操作/故障注入 | 通过条件 |
| --- | --- | --- |
| 正常当前请求 | 分别走三个hook与256/512来源 | 已解码对象进入原发布出口，store/订阅/DOM身份一致 |
| 取消与旧代次 | 命令前、响应后、预解码中、发布前分别取消/切页/重扫 | 不发布旧图、不负缓存、不回落、不计真实失败，作业结算 |
| 预解码错误 | 404、坏JPEG、无像素load、预解码超时及晚到完成 | 同候选恰好一次像素回落，晚到结果不污染状态 |
| 发布后DOM错误 | 预解码成功后、真实img读取前删除/损坏受管文件或受控注入onError | 当前发布触发一次强制pixels作业，绕过path；成功后恢复显示 |
| 旧DOM错误 | 先发布新generation，再送旧URL/旧identity错误 | 忽略，不驱逐新资源、不回落、不扣熔断 |
| 共享多img | 同一次发布的多个img并发error；不同owner共用asset URL | 同一发布补救去重，不误取消其他owner，计数符合定义 |
| 双通道失败 | DOM错误后pixels也失败 | 有界终止、保留已有可用图或明确占位；不循环排队、不永久loading |
| 离开后回访 | 双失败后离屏/切页再回来或显式retry | 按定义清除一次补救限制并允许新尝试，不由每次render自动无限重试 |
| 候选与无图 | 首候选无图第二有图；首候选失败后pixels成功；全无图；部分真失败 | 正确continue/停止，只有全确认无图才负缓存，真失败可按策略重试 |
| 缓存与发布 | 同键并发、预算满、淘汰、坏索引、写盘失败/超时、Windows特殊路径 | 原子发布、统一预算、错误分类不伪装无图、权限不扩大 |
| 许可与预热 | 唯一解码许可下让writer等待；前台到来与后台并行 | 等待发布时许可已归还，前台不被磁盘等待独占；产物与启用通道一致 |
| 功能回归 | 专辑/全部歌曲/文件夹/歌单/搜索，大封面/背景/切歌转场 | 图像正确，无闪白/残影/挂起；大图像素契约及旧缓存命中不变 |

注入分三类标注：单元替身、浏览器生命周期注入、真实WebView2/受管缓存I/O。不得把mock失败当作真实慢盘验证，也不得为注入修改用户音乐或真实缓存。

受控慢I/O在测试隔离writer或测试专用文件系统边界延迟/限速，保持生产admission与状态语义；记录注入位置和时间。另在真实慢存储验证代表性子集；未做真实验证时明确外推限制。

## 6. 对照设计与实验纪律

所有实验共享同机器电源模式、WebView2版本、release构建方式、窗口、DPR、布局、语料顺序和日志开关。记录后台负载，避免边构建边计时。用Tauri构建流程生成可用custom-protocol产物，不直接把裸cargo release当可比应用。

语料至少两组：现有120首作为可复现小样本；至少1000个独立封面/专辑的长列表，包含多首共享图、无图和合法坏图fixture的已标注子集。不能复制同一封面制造“1000项”来代表真实缓存压力；记录独立图hash数量、尺寸和文件格式分布。

每组分别测：无缩略图冷生成；已有各自格式缩略图但新进程；同会话热重开。profile使用预先制备的同等副本，注明是仅重启进程还是另用profile副本，不清除入口曲库信息后改变操作起点。OS页缓存不可控就注明，不称完全冷启动。两臂使用隔离且等价的cache/profile快照，预热同时关闭或同时完成；不以不同音乐目录代替等价状态。

先补正确性并冻结新基线，再对架构方案的每个候选优化单独开实验。一次只改一个变量；不要将metadata门控、命中快路径、候选遍历、并发/预热一起改后归因。相邻优化确有交互时，在单项实验之后增加组合版验证。

实验编号与架构方案一致：E1元数据关键路径；E2同epoch预热去重；E3有界会话路径引用提示缓存；E4可选全组确认无图结果的有限复用。每项先用分段观测证明目标成本可观，再实施；E1不能通过隐藏未就绪内容缩小cohort，E2核对实际预热/读取次数，E3核对减少的IPC与失效正确性，E4核对全组重复探测次数及无图失效规则。已有JPEG/来源索引不得重复建设。

| 实验 | 首要证据与通过条件 |
| --- | --- |
| E1 | 相同cohort首图/首屏代理时延超过预登记改善门槛，排序分组/descriptor身份正确，未靠省略目标或错误占位过关 |
| E2 | 同epoch同键预热实际执行次数下降，无跨epoch错误复用，前台排队和冷生成无超限退化 |
| E3 | 重访或跨owner重复IPC实测下降；revision/epoch/edge/格式失效与DOM强制pixels补救全通过，内存有界 |
| E4 | 全组重复探测调用下降；仅所有有效候选均确认missing时写入，异常/取消不写；任一候选文件、兄弟图或目录封面变化均使结果失效；无法可靠捕获变化则不实施；选图顺序及失败重试语义不变 |

每场景至少10对，预先随机化或交替顺序；波动较大扩到预先登记的20对或更多。对内使用相同语料/cache状态，记录每对差值和比例，不能把所有样本当互不相关的独立试验。

在看正式结果前登记：主要指标、实用改善门槛（如毫秒与百分比同时约束）、允许退化上限、正确性/内存硬门槛、样本数和停止规则。门槛依据当前基线波动和体验需求确定，不在结果出来后改门槛以通过。

报告每臂p50、p95、均值、标准差、逐对差值、胜负及效应区间；10或20个样本的p95接近极端顺序统计量，只作探索性描述，不能据此承诺尾时延。需要可信尾部结论时增加样本量并报告不确定性。

不得看到有利结果就提前停止，或因异常不利而静默剔除。机器休眠/脚本崩溃等技术无效样本按事先规则标记并保留，补跑须记录原因；产品超时/缺图属于有效失败，不能当环境噪声删除。

停止条件：出现正确性退化、持续内存增长、无界排队立即暂停；性能到预定样本数仍落在噪声内，结论为“未证明改善”，再决定换场景或放弃，不自动扩大并发或叠加新优化。

## 8. 交付与验收模板

验收表逐项填写：

| 项 | 结论 | 证据/缺口 |
| --- | --- | --- |
| DOM失败补救与异步正确性 | 通过 / 不通过 / 证据不足 | 真实hook及WebView2用例ID |
| 缓存/许可/权限/大图回归 | 同上 | 自动化与真实环境边界 |
