# 测试报告：播放列表性能基线可行性与解码代理测量

## 摘要

已对本机曲库做匿名、只读素材盘点，并用嵌入封面做重复解码代理测量。同步写入版的 Rust Release 交错 A/B 证实冷路径退化，因此改为有界后台写入实验。Test Agent 在 2026-10-01 独立重跑后台版固定 83 张、5 对交错 Release A/B：首次结果冷响应逐对增加 3–147 ms；Rust/Tauri Agent 修正后台写入结果分类后再跑，差异为 −120 至 +209 ms，两次均未复现同步写盘版稳定的约 5–6% 退化。两次写入排空后的热轮均 83/83 命中。协调 Agent 在真实 Release WebView 的五处固定视口共测 208 张有效图，各处 4 秒内补齐，p95 为 2.15–3.38 秒；另采集 1,816 卡片温态滚动轨迹。**阶段 0 尚未完成**：缺少同场景修复前 WebView 对照、严格可见至图片加载分布、实际流水线分段成本、内存稳定平台及 10,000 首素材，不能宣称用户可见体验已改善。

## 代理测量方法

从固定前 100 首中取 83 个 FLAC。每一轮按同一顺序从原音频文件读取内嵌 `PICTURE` 数据，使用 Python Pillow 打开图片、应用 EXIF 方向、以 Lanczos 缩入 256×256、转换为 RGBA 字节；串行执行 5 轮。每张记录读取/提取、解码/缩放/转换和总耗时，以 `time.perf_counter()` 计时；下表为轮次汇总。第 1 轮是**进程内首次**，不是已证实的 OS 文件缓存冷态；后 4 轮是同进程重复访问。没有清理系统缓存或 SpMusic 应用缓存。

这只是素材复杂度与重复解码成本的代理：Pillow 不等于 Rust `image` crate，读的是音频标签而非 SpMusic 的封面缓存文件，也不含元数据队列、Rust 锁、Tauri IPC、RGBA 序列化、前端 BMP 转换、`<img>` 解码或布局。图片原始字节中位数 251,110、p95 1,056,050；源图最大边中位数 1,440、p95 3,000 像素。

### 冷路径闸门与正确性证据评估

任务卡阶段 0A 要求冷请求不能出现明显退化，但未设数值阈值。前版同一进程的 5 轮范围为 4,044.619–4,146.067 ms（极差 101.448 ms）；后版 5 次新缓存目录的首轮范围为 4,287.268–4,359.804 ms。后版最短首轮仍比前版最长一轮慢约 141 ms，后版相对前版首轮慢约 240–312 ms；Test Agent 独立后版首轮慢约 316 ms。**同步写入版不能判定冷路径闸门通过，且有超出前版轮次波动的退化信号。**前版缺 5 次独立进程冷启动，OS 缓存与运行顺序也未配对，故不能将差异全部归因于缩略图写入或定性为最终用户可见退化。当时建议的同进程交错对照已先后在同步版和后台版执行，结果见后文；后台版依旧应保持探索状态。同步版每次写入前后扫描缩略图目录，是当时优先归因线索。

当时独立测试已覆盖命中后响应一致、源内容变化失效、损坏条目回源、残留临时文件清理、文件数预算与过大单条目拒绝；尚未覆盖按字节淘汰和新加的并发同键测试。2026-10-01 后台版 20 项 Release 测试已覆盖这两项，但仍没有多进程竞争、接近 2,048 文件上限的长期磁盘/内存平台。原图缓存仍无上限，不得把衍生缓存上限当成整个封面缓存上限。

### 写入失败语义复核（修复前）

修复前，`thumbnail_writer_loop` 调用返回 `()` 的 `write_thumbnail_cache`，后者在目录不可用、容量检查失败、创建/写入/同步/重命名失败时直接返回或丢弃 I/O 错误。worker 随后无条件移除 `pending`，并把 `completed` 加一。因而旧版 `completed` 仅表示**处理完队列项**，不能用作“已成功落盘”计数；当时日志只记录入队跳过。这个缺口已由 Rust/Tauri Agent 修正，见下节。

## 验证结论

**同步写入版因稳定冷退化未通过；后台写入版的 Rust Release 热命中和写入结果分类修复经 Test Agent 独立测试通过，但冷响应仍有波动，SP-022 阶段 0 仍为证据不足。** 修复后 23 项 Release 封面测试通过，固定 83 张的 5 对交错对照未观察到结果分类引入稳定新增退化；真实进程中断、多进程竞争和系统级写盘失败仍未覆盖。协调 Agent 的真实 Release WebView 温态、固定视口与直接 IPC 代理探针分别提供滚动帧、抽样图片就绪和局部分段成本，但没有同场景修复前 WebView 对照或实际列表流水线的严格端到端分段，无法证明磁盘缩略图缓存改善了用户可见体验，也无法验收“滑动几乎看不出加载”。后台缓存应保持探索状态；主线程几何、列表队列与图片加载的贯通证据需由 Frontend 与 Rust/Tauri Owner 补齐，再由 Test Agent 独立复核。

**阶段 0B 结论：索引的稳定状态 ID 顺序和近屏几何读取减少通过本次独立抽测；整帧性能收益、全部交互正确性与封面端到端改善仍为证据不足。** 同构建强制全量的五对实验有三对显示较快帧分布、两对接近，但跨构建顺序数据的 p50 与超 16.7 ms 帧数反向，不能宣称正式优化验收通过。新构建固定视口抽样均在 4 秒补齐，但不能以不同分母及缓存状态与旧版比较。建议 PM Agent 暂保留可回退实验状态，补齐同条件构建交错、实际回调分项和稳定资源平台后再作保留或回退决定。

**实际列表分段补测**显示五处 184/184 张有效图最终完成，可见卡的单视口关联样本中请求开始前有约 1–2 秒错峰等待，单视口 pixel POST 耗时 p95 约 195 ms，而 BMP URL 创建到图片 `load` 的五处 p95 为约 24–34 ms。该批补测本身没有队列入队/出队、Rust 内部阶段和严格首次可见时刻；后续阶段 0C 补上了热态固定视口的前端队列记录，仍不能将全部等待单独归因于后端解码，也不把 SP-022 阶段 0 标记完成。

**阶段 0C 结论：最终 Release 热态五处视口的 5 对开关测量中，可见作业分段关联完整、匿名且图片最终完成；视觉队列等待比例中位数五轮均超过 50%，但没有可见作业排在旧预取待执行作业后面，未达到批准调度 A/B 的双闸门。** 快滚诊断五轮均触顶并丢失大量事件，错误/取消与长时资源平台未验证，故不能据此宣布诊断覆盖全部滚动或 SP-022 通过。PM 已决定撤除临时诊断代码，原始测量与报告保留；后续如需无丢失观测快滚或 Rust 内部阶段，应另定范围。

**阶段 0D 结论：同构建五轮热磁盘样本中，hydrate 与 pixel POST 的匿名 Rust 摘要双向唯一时间关联各轮均超过 97%，所有有效封面在开启和关闭两种状态下最终完成；没有任何单个 Rust 内部阶段满足 4/5 轮中位占比超过 50% 的后端实验闸门。** pixel `POST−Rust handler` 残差中位占比五轮为 64.04%–65.43%，明显大于本轮观测开关 p50 差，足以提请 Architecture Agent 审查下一项只读分段方案，但不能直接归因为前端 JS 或特定 IPC 环节。hydrate POST p50 在五对中开启态均略长，无法把诊断视为零扰动；失败/取消、长时资源收敛和冷态未验证。PM 已裁定撤除临时 Rust 诊断；Test Agent 独立核对撤除后的源码及 Rust lib 检查通过，当前旧 Release 进程的运行时替换仍未验证。SP-022 仍未完成性能验收。

**阶段 0E 结论：直接串行探针 300/300 双向唯一关联、返回与 CDP 数据字节一致，三档每档五轮的 `requestWillBeSent→loadingFinished` 占 JS 调用比例中位数均超过 50%。** 但 `responseReceived` 的 CDP 时间戳 300/300 次晚于 `loadingFinished`，完整事件顺序验收失败，且磁盘命中、进程哈希/显示环境与采样扰动无法从原始记录独立闭环。此数值结果只支持 Architecture Agent 复审观测语义，不能确认某个 IPC、传输、解析或 Rust wrapper 瓶颈；真实列表可见封面与滚动性能仍未验收。

**阶段 0F 结论：新版同构建五对正式样本的有效封面均 184/184 就绪，同卡 DOM 实例与图片 load 各轮 184/184 唯一关联。** `scrollBefore` 保守分母下，视觉 job 等待占槽的逐卡比例 p50 仍为 84.45%–86.01%，五轮均超过 50%；快返 416 episode 中 345 个按右删失计入，排队失效与占槽 stale 均未跨视口提交。开关没有 4/5 稳定同向退化，但第 3 对差异明显；两次错误注入尝试未形成可解释的单次失败证据，且仅用环境变量无法证明应用目录隔离；缓存共享命中和长期资源未覆盖。临时诊断已撤除，Test Agent 独立的生产前端构建、目标 ESLint、Rust Release lib check 与静态清理检查通过；无探针的新 Release 运行时五处视口有效图分别 40/40、40/40、40/40、32/32、32/32 最终就绪。动态错误回退和长期资源仍未验证。因此仅将视觉队列列为架构复审候选，**不批准直接调度/并发优化，也不宣布 SP-022 已达到流畅验收**。

**阶段 0G 结论：无探针 Release 十轮固定视口共 1,840/1,840 张有效封面最终就绪，CDP 模拟 DPR 2 两次五视口均为 184/184。** 顶部稳定 DOM 与挂载 blob `<img>` 十轮一致；Renderer 进程私有内存在最终冷却后接近首点，GPU 子进程仍高 80.6 MiB，尚无相同稳定状态的长期收敛证据。管理 Object URL、在途像素/作业、Rust 磁盘缓存占用未采集，DPR 2 进程样本也未覆盖稳定峰值。因此 Stage 0G 资源/高 DPR 完整闸门及动态错误回退仍未通过，**不能批准视觉槽 2↔3 的单变量 A/B，SP-022 继续保持未完成**。
